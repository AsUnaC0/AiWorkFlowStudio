# 03 - UI Control 界面操作桥接

> 阅读本文后，你应该能回答：前端的 UI Control 模块长什么样？页面怎么注册自己的操作？
> 网页版怎么长轮询后端拿指令？执行结果怎么回传？桌宠发的「去 Skill 页」到底是怎么被浏览器执行的？

相关代码路径：

```
fronted/src/modules/ui-control/           ← UI Control 本体（12 个文件）
fronted/src/api/uiControl.ts              ← 桥接层 HTTP API（register / poll / result / heartbeat）
backend/src/platform-tools/ui-action-bridge.service.ts  ← 后端桥（长轮询、队列、wait/resolve）
backend/src/platform-tools/ui-control.tools.ts          ← 5 个 UI 平台工具定义
```

后端桥的原理见 [后端 11-平台助理 §八·一](../后端代码逻辑/11-平台助理.md)。

---

## 一、一句话理解

**UI Control = 前端语义化操作注册中心 + 长轮询指令接收器。**

- 注册中心让每个页面告诉 AI「我是谁、我能做什么、怎么做」—— 不暴露 DOM 选择器，
  模型只能看到 `navigate` / `open_dialog` / `click_action` 这种语义化名字。
- 长轮询接收器只服务于「桌宠发起」的指令（网页版自己聊天走 SSE 事件那条路）。

两条入口、同一条执行链：

```
桌宠发起 → 后端 post 到浏览器会话队列 → 长轮询 poll() 取走 → executeUIAction() → reportUIActionResult()
网页版发起 → SSE ui_action 事件 → executeUIAction() → 回传同样走 result
```

## 二、目录结构

```
fronted/src/modules/ui-control/
├── index.ts                 # 对外总出口 + installUIControl(router) 安装函数
├── types.ts                 # 共享类型（UIActionDescriptor / UIActionResult / UIContextPayload …）
├── runtime.ts               # Vue Router 引用（延迟注入，避免循环引用）
├── registry.ts              # UIActionRegistry：操作元信息 + 页面上下文 + 执行函数 三份数据
├── context.ts               # getCurrentUIContext()：随聊天请求上报的页面快照
├── session.ts               # getBrowserSessionId()：sessionStorage 生成标签页唯一 ID
├── page-catalog.ts          # PAGE_CATALOG / DIALOG_ACTIONS / ROUTE_PAGE_MAP（静态目录）
├── page-registration.ts     # registerPageContext / unregisterPageContext（页面生命周期接线）
├── executor.ts              # executeUIAction() + 串行队列 + navigateTo / runHandler
├── browser-bridge.ts        # startUICommandBridge()：长轮询主循环 + 心跳 + 幂等
└── actions/
    ├── navigation.actions.ts  # navigate（一个）
    └── common.actions.ts      # open_dialog / click_action / fill_form（三个）
```

**为什么把 `executor.ts` 独立出来**：它是纯函数，不依赖 DOM/Vue Router 的副作用。
这样 SSE 层（chat/index.vue）和长轮询层（browser-bridge）都能走同一条执行链，
保证「无论指令来自 SSE 还是 poll，路由守卫校验、错误码、真实状态回传都一致」。

## 三、Registry — 三份数据，两条边界

`UIActionRegistry` 维护三份数据，**两条边界**保证安全：

| 数据 | 存什么 | 生命周期 |
|---|---|---|
| `descriptors` | 所有语义化操作的元信息（name / label / category / risk） | 应用启动时**静态注册**，运行时不变 |
| `pageContexts` | 每个页面的挂载上下文（pageId / title / route / 可用 actions） | 页面 onMounted 注册，onUnmounted 撤销 |
| `pageHandlers` | 每个页面的**实际执行函数** | 同上，动态注册 |

**关键边界 1：`resolveHandler()` 只查当前激活页面**。

用户离开 Skill 页后，再调 `open_create_skill_dialog` 会返回 null，执行器会先跳转回去。
不会出现「我在 Dashboard 页，却把 Skill 弹窗开出来」的错乱。

**关键边界 2：`pageHandlers` 由页面动态注册，不是静态写在 actions 文件里**。

打开弹窗依赖组件内部的 `ref`（如 `createDialogVisible.value = true`），
这些执行函数必须在页面挂载后才能拿到。让页面把 `openCreateDialog` 注册进来，
不需要重构弹窗状态，也不让 AI 找 DOM 元素。

## 四、Executor — 四种核心操作的执行链

### 4.1 navigate（页面跳转）

```ts
async function navigateTo(pageId): Promise<UIActionResult> {
  // 1. PAGE_CATALOG 里查不到 pageId → 返回 errorCode: UNKNOWN_PAGE
  // 2. router.push(page.route)
  // 3. 重新读 router.currentRoute.path —— **只看 push() 没抛异常不算成功**
  //    路由守卫可能把用户重定向到登录页，必须比对实际 path
  // 4. 实际 path !== 期望 → 返回 success: false, errorCode: ROUTE_MISMATCH
}
```

**为什么要重新读路由**：早期版本只检查 `push()` 有没有抛异常。
实测发现 auth 守卫会把未登录用户的 `router.push('/skills')` 重定向到 `/login` ——
模型以为 Skill 页已经打开，实际停在登录页。现在 `actualPath !== expectedRoute` 一律算失败。

### 4.2 open_dialog（打开弹窗）

```ts
async function openDialog(dialog): Promise<UIActionResult> {
  // 1. DIALOG_ACTIONS 查 dialog → 得到 { action, pageId, label }
  // 2. 当前不在 pageId 页 → 先 navigateTo(pageId)，再 waitForHandler(action, 2500ms)
  //    waitForHandler 每 50ms poll 一次 registry，最多 2.5s（页面挂载 + handler 注册需要时间）
  // 3. resolveHandler(action) → 拿到页面注册的执行函数
  // 4. runHandler(handler, params) —— 统一兜底异常 + 补真实页面信息
  // 5. 打开后校验还在 pageId —— 又被路由守卫切走算失败
}
```

`DIALOG_ACTIONS` 静态列出 6 种弹窗：

| dialog id | 归属页面 | 执行函数名 |
|---|---|---|
| create_skill | skills | open_create_skill_dialog |
| create_mcp_server | mcp | open_create_mcp_dialog |
| create_agent | agents | open_create_agent_dialog |
| create_knowledge_base | knowledge | open_create_knowledge_dialog |
| create_workspace / create_workflow | workspace | open_create_workspace_dialog / open_create_workflow_dialog |

### 4.3 click_action（执行页面操作）

类似 open_dialog，但可以**自动找归属页**：

```ts
// 当前页没有这个 action → 遍历 registry.listPageContexts()
// → 找到第一个 hasActionOnPage(pageId, action) → navigate → waitForHandler → runHandler
```

适用场景：用户说「帮我打开那个面板」，模型先调 `ui_get_page_context` 看当前页有哪些 action，
挑一个调。

### 4.4 fill_form（填写表单）

**只填不提交** —— 执行函数也是页面自己注册的，通常就是把 `fields` 合并进表单组件的 ref。
这个操作的风险等级是 MEDIUM（不 LOW），因为「帮我把名字和描述填好」虽然不改业务数据，
但确实是一种用户可见的主动行为。

### 4.5 get_page_context（查询当前页面）

不走 executor，直接读 registry：

```ts
return registry.getActivePageContext() + registry.listDescriptors()
// → 拼出人类可读的页面快照：页面名 + 路由 + 可执行操作清单
```

## 五、Browser Bridge — 长轮询主循环

> 这一层**只处理桌宠发来的指令**。网页版自己聊天时，后端直接通过 SSE 推 `ui_action` 事件，
> 不走 poll 队列 —— 避免同一指令被执行两次。

### 5.1 三条链路

```
启动（应用 mounted 时调用一次）
  startUICommandBridge() → 注册会话 + 启动 loop()

主循环（loop()）
  ① 登录态检查（没登录 1.5s 轮询一次）
  ② pollUICommands(timeout=20s, sessionId, currentUIContext)
     → 每次轮询都带上当前页面上下文，桌宠那边的模型才能知道用户在哪
  ③ 对每条 command：
     → executeUIAction(command.name, params)
     → reportUIActionResult({ commandId, success, message, currentRoute, … })

停止（登出 / 应用销毁）
  stopUICommandBridge() → stopped = true，loop() 退出
```

### 5.2 失败退避

| 失败类型 | 退避 | 原因 |
|---|---|---|
| 401 token 失效 | **30s** | 别每 3s 撞一次后端，也给用户自己的 401 弹窗留时间 |
| 断网 / 后端没起 | 3s | 正常退避 |
| 指令已处理 | 跳过 | 幂等：`processedCommands` Set 记最近 500 个 commandId |

### 5.3 多标签页：选哪个会话

后端按「**最近真的看过**」的标签页投递 —— 前端上报心跳让这个信号准确：

```ts
bindActivityHeartbeat() {
  document.addEventListener("visibilitychange", () => {
    if (document.visibilityState === "visible") ping();  // 标签页切回可见
  });
  window.addEventListener("focus", ping);                // 窗口聚焦
}
```

只靠轮询时间戳不够 —— 三个后台 tab 每 20s 也在轮询，时间戳一样新。
心跳让后端知道「现在哪个 tab 真正在用户眼前」。

## 六、Session ID — 标签页唯一，刷新保留

```ts
export function getBrowserSessionId(): string {
  if (cached) return cached;
  const existing = sessionStorage.getItem("wb_ui_session_id");
  if (existing) { cached = existing; return existing; }
  const id = randomId();
  sessionStorage.setItem("wb_ui_session_id", id);
  return id;
}
```

| 特性 | 选择 | 原因 |
|---|---|---|
| 存储 | **sessionStorage** 不是 localStorage | 同源 tab 不共享；刷新保留；新 tab 新 ID |
| 隐私模式 | 退化到内存变量 | try/catch 全兜底 |
| 生成 | `crypto.randomUUID()`，老环境退 `时间戳+随机` | 跨浏览器兼容 |
| 复制 tab | 部分浏览器连 sessionStorage 一起复制 | 可接受的边界：两个 tab 共用会话，后端会选最近活动的那个 |

## 七、各页面的接线方式

```vue
<!-- views/skills/index.vue -->
<script setup lang="ts">
import {
  registerPageContext, unregisterPageContext,
} from "@/modules/ui-control/page-registration";

const dialogVisible = ref(false);
const openCreateDialog = () => { dialogVisible.value = true; return { success: true }; };

onMounted(() => {
  registerPageContext(
    { pageId: "skills", title: "Skill 管理", route: "/skills", description: "管理 Skill" },
    { open_create_skill_dialog: openCreateDialog },
  );
});
onUnmounted(() => unregisterPageContext("skills"));
</script>
```

页面自己**不 import UIActionRegistry** —— 只调 `registerPageContext` / `unregisterPageContext`，
这样不用知道「registry 里有什么、怎么匹配」。模块之间完全解耦。

## 八、安装入口 — main.ts

```ts
// fronted/src/main.ts
import { installUIControl, startUICommandBridge } from "@/modules/ui-control";
import { createRouter } from "@/router";

const router = createRouter();
app.use(router);

// 1. 注入 Router（延迟避免循环引用）+ 注册内置 navigate/open_dialog 等元信息
installUIControl(router);
// 2. 启动长轮询（登录态变化时会自动重新注册会话）
startUICommandBridge();
```

`installUIControl` 做两件事：
1. `setUIRouter(router)` — 让 `executor.ts` 能 `getUIRouter()` 拿到实例
2. 注册内置的 4 个 `UIActionDescriptor`（navigate / open_dialog / click_action / fill_form）+ 路由变化同步当前激活页面

## 九、常见坑

| 坑 | 原因 | 表现 | 修 |
|---|---|---|---|
| 指令执行两次 | SSE 和 poll 同时发了同一条 | 弹窗开了两个 | `uiControl=true`（网页聊天）时 `dispatch()` 返回 false，不投递队列 |
| 模型收到 ROUTE_MISMATCH | 路由守卫把跳转重定向到登录页 | 模型以为页面没打开 | executor 里 `actualPath !== expectedRoute` 直接判失败 |
| handler 未注册 | 页面还没挂完 / onMounted 里的 ref 还没 ready | `PAGE_NOT_READY` | executor 会 `waitForHandler(action, 2500ms)` 轮询最多 2.5s |
| 跨页 action 找不到 | registry 里只有当前页的 handler | `ACTION_NOT_REGISTERED` | executor 会自动 `findOwnerPage` → navigate → waitForHandler |
| 心跳不触发 | `visibilitychange` 在某些浏览器不可靠 | 后台 tab 被当成活跃 tab | 加了 `window.focus` 事件兜底 |
| sessionStorage 被隐私模式禁用 | safari 无痕 | 每次 poll 都失败 | catch 后退化为内存变量，tab 刷新后换号（可接受） |

## 十、后端接口（前端消费方）

| 方法 | 路径 | 前端调用时机 |
|---|---|---|
| POST | `/platform/ui-command/register` | 登录后第一次 poll 前；token 变化时重新注册 |
| POST | `/platform/ui-command/heartbeat` | 标签页切可见 / 窗口聚焦 |
| POST | `/platform/ui-command/poll` | 主循环：20s 超时，有指令立刻返回 |
| POST | `/platform/ui-result` | 执行完任何 UI 操作后回传真实结果 |
| GET | `/platform/ui-command/sessions` | 暂未消费（给后端调试 / 未来"选目标 tab"界面） |
| POST | `/platform/ui-command/cancel` | 暂未消费（由 `PlatformToolsService.cancelTask()` 在后端内部调） |

前端 API 封装见 `fronted/src/api/uiControl.ts`。
