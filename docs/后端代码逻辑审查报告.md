## 总评

文档整体**框架、调用链路、设计意图基本正确**，作为"小白入门材料"是合格的：模块划分、ReAct 循环、RAG 流水线、版本管理、Provider 双层设计的讲解都站得住。

## 一、严重错误（与代码不符，会直接误导）

### ❌ 1. StorageService 接口与实现不符（01 第五节 / 08 第三节）

| 文档写的                                                                     | 代码实际                                                                                                         |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `save(buffer, originalName, dir?): Promise<string>`                      | `upload(buffer, originalName, subDir='documents'): Promise<{key: string; size: number}>`                     |
| "NestJS DI 模块里根据 env 条件注入 `LocalStorageService` 或 `QiniuStorageService`" | **只有一个 `StorageService` 类**，内部用 `this.type` 分支（`storage.module.ts` 里 `providers: [StorageService]`），不存在两个实现类 |

其他遗漏：

- 漏了 `getDownloadUrl(key, expireSeconds)` —— local 返回 `null`，qiniu 拼 domain
- 环境变量漏了 `LOCAL_UPLOAD_DIR`、`QINIU_REGION`（默认 z0）、`QINIU_DOMAIN`（七牛下载必须有）
- 七牛下载不是"一次下载"，而是**多候选 URL 轮询**：签名 http → 签名 https → 公开 http → 公开 https，逐个 try
- local 模式的 key 是**绝对路径**（`uploads/documents/<uuid>.ext`），qiniu 是 `documents/<date>/<uuid>.ext`

### ❌ 2. WorkspaceMember 根本没有 role 字段（08 第四节）

文档写的：

```typescript
model WorkspaceMember {
  userId String; workspaceId String;
  role   String   // "OWNER" | "MEMBER"
}
```

`schema.prisma` 实际只有 `id / workspaceId / userId / createdAt`，**没有 role 列**。role 是 `WorkspacesService.listMembers()` 在内存里算出来的：

```typescript
role: m.user.id === workspace.ownerId ? 'OWNER' : 'MEMBER',
```

同时遗漏了核心业务规则：

- `inviteMember()`：被邀请人必须是 **ACCEPTED 好友**（依赖 FriendshipService）、不能邀请自己、不能重复加入（ConflictException）
- `removeMember()`：只有 Owner 能移除、不能移除自己
- `create()` 会自动把 owner 也写进 members 表

### ❌ 3. 加密密钥的环境变量名写错（01 第六节 / 07 第三节）

文档写「密钥从 `.env` 的 `ENCRYPTION_KEY` 读取」——**代码里没有这个变量**。

`encryption.service.ts` 实际的优先级：

```
LLM_CONFIG_ENCRYPTION_KEY → JWT_SECRET → 'dev-only-insecure-key-change-me'
```

并用 `createHash('sha256')` 摘要成固定 32 字节。缺配置时会打 warn 日志。

其他应补充：

- 算法是 **AES-256-GCM**（不是笼统的 "AES"），密文格式 `base64(iv):base64(authTag):base64(ciphertext)`，用 `:` 分隔
- `maskApiKey` 真实格式是 **前 4 位 + `****` + 后 4 位**（`sk-a****1234`），不是文档写的 `sk-****abcd`；长度 ≤ 8 直接返回 `****`

### ❌ 4. WorkflowTool / KnowledgeTool 的 ToolDefinition 参数描述错误（04 第四、五节）

**WorkflowTool** —— 文档写 `parameters: { properties: {}, required: [] }`，实际：

```typescript
properties: {
  input: { type: 'string', description: '传给工作流的输入内容（自然语言 / JSON 字符串都可）' }
},
required: ['input']
```

description 也不是裸的 `workflow.description`，而是拼成：  
`调用工作流「名称」（已发布 vN）。用途：xxx`

**KnowledgeTool** —— 文档写只有 `query`，实际有 3 个参数：

- `query`（必填）
- `knowledgeBaseIds`（数组，**支持前 8 位缩写匹配完整 UUID**）
- `topK`（默认 5）

且 description 里注入了可用知识库清单（`- abcd1234 (名称)：描述`），让 LLM 知道该选哪个库。

遗漏的执行细节：

- WorkflowTool 只跑 `publishedVersion`，未发布/无发布版本直接抛错
- 输出兜底：`typeof result.previousOutput === 'string' ? ... : JSON.stringify(result.previousOutput ?? result.data)`
- `extractInput()` 兼容 `{input}` / `{raw:{input}}` / `{raw}` / 任意字段整体 JSON 化
- KnowledgeTool 无命中返回「知识库中未检索到与「x」相关的内容。」

### ❌ 5. ChunkService 描述错误（06 第四节）

文档写的：

```typescript
createMany(...) {
  data: chunks.map(text => ({ documentId, knowledgeBaseId, content: text, metadata: {} })),
  skipDuplicates: true,
}
```

实际（`chunk.service.ts`）：

- 写入字段是 `documentId / content / chunkIndex`，**没有 metadata、没有 skipDuplicates**
- 外面包了 `$transaction`，同步 `knowledgeBase.chunkCount: { increment: created.count }`

文档写「默认 chunk 大小和 overlap **可配置**」——**实际硬编码**：

```typescript
new RecursiveCharacterTextSplitter({ chunkSize: 100, chunkOverlap: 50 })
```

（LangChain 的 RecursiveCharacterTextSplitter，不可配置，且 100 字符偏小，值得单独提示）

### ❌ 6. "只有 COMPLETED 的文档才会被 RAG 检索到" 未落地（06 第三节）

文档这句话在代码里**没有对应实现**。`vectorSearch` / `keywordSearch` 的 WHERE 条件只有：

```sql
WHERE d."knowledgeBaseId" = ANY($n::text[])
  AND dc."embedding" IS NOT NULL
```

**没有 `d.status = 'COMPLETED'` 过滤**。PROCESSING 中已写入 embedding 的 chunk 会被检索出来。这是一个真实的文档↔实现偏差（也是潜在 bug）。

### ❌ 7. MCP 模块多处不符（08 第一节）

| 项           | 文档                              | 实际                                                                                       |
| ----------- | ------------------------------- | ---------------------------------------------------------------------------------------- |
| transport   | `"sse" \| "http"`               | 默认 `STREAMABLE_HTTP`；**`SSE` 在 `callTool()` 里直接抛错**"SSE 传输方式暂不支持工具调用"                    |
| credentials | "加密存储"                          | **明文 JSON 入库**（`buildCredentials()` 直接存 `{apiKey, bearerToken}`，schema 注释也标了"生产环境应加密存储"） |
| authType    | `"bearer" \| "api_key" \| null` | `NONE \| API_KEY \| BEARER_TOKEN`                                                        |
| status      | `CONNECTED \| DISCONNECTED`     | 还有 `ERROR`                                                                               |

遗漏的重要逻辑：

- `callTool()` 是**三步 JSON-RPC**：`initialize`（protocolVersion `2024-11-05`）→ `notifications/initialized` → `tools/call`，每步都是独立 HTTP POST
- 响应解析按 `content-type` 分流：`text/event-stream` 就逐行找 `data: ` 再 JSON.parse，否则直接 json()
- 鉴权头：`API_KEY` → `X-API-Key`，`BEARER_TOKEN` → `Authorization: Bearer`
- `result.isError` 会转成异常抛出
- `testConnection()` 走 `tools/list`，成功后把工具列表缓存进 `availableTools`，失败置 `ERROR` + 清空 tools
- `update()` 时若改了 `serverUrl` 或 `authType`，会重置 `status=DISCONNECTED`、`availableTools=null`

### ❌ 8. Skill 注入时机写错，且掩盖了一个真实缺口（08 第二节）

文档标题写「LLMNodeExecutor.createParams() → **AgentService 启动时**」。

**AgentService 完全没有注入 Skill 或 MCP。** `agent.service.ts` 的构造函数只有：

```typescript
constructor(prisma, aiService, toolRegistry, llmConfigService) {}
```

`Agent.skillIds` / `Agent.mcpServerIds` 这两个字段**存进去了、但运行时没有任何代码读取**——目前是死配置。文档把它写成"Agent 会用"，属于反向误导。

其他：

- `Skill.instructions` 在 schema 里是 **`String?`（可选）**，文档写 `instructions String`（必填）
- 遗漏字段：`inputSchema`、`outputFormat`(默认 Markdown)、`workflowId`、`mcpServerId`、`mcpToolName`
- 注入时只取有 instructions 的 Skill（`filter(s => s.instructions)`），拼成 `## Skill: 名称\n指令` 后追加到 System Prompt

## 二、描述不完整 / 半对（会让人理解偏差）

### ⚠️ 9. ReAct 循环（04 第二节）

文档漏掉的关键行为（按重要性排序）：

1. **最终答案会被生成两次**——当 `toolCalls.length === 0` 时，代码先 `yield {type:'message', content: result.content}`（非流式拿到的完整答案），**然后立刻再调 `streamChat()` 重新生成一遍**并逐 token yield。前端会看到内容"推完整段 → 清空重播"。这是最容易踩坑的行为，文档完全没写。
2. 无工具分支会先 yield `{type:'thinking', message:'思考中...'}`，文档代码块里没有。
3. 工具执行**异常不中断循环**：被 catch 成 `工具执行错误：${message}` 字符串，照样作为 tool 消息喂回 LLM。
4. 超 `maxToolIterations` 时，除了 yield error，还会落库一条 assistant 消息 `⚠️ Agent 达到最大工具调用次数限制`。
5. `executeTool` 的 context 还带 `knowledgeBaseIds`（KnowledgeTool 用它过滤范围），文档只写 `{agentId, userId}`。
6. `ChatMessage.trail` 字段会记录 thinking/tool_call/tool_result 完整轨迹；文档只提 roles。
7. 文档自己写「role 有 4 种」却只列了 3 种（`user/assistant/tool`），实际 schema 注释是 `user/assistant/system/tool`。
8. 每次落库都会 `chatSession.update({ updatedAt: new Date() })`，让会话在列表里置顶。
9. 更新/创建 Agent 时，`llmModelId` 会连带把 `Agent.model` 同步成真实模型标识（`resolveModelName()`）；传空字符串表示清除绑定。

---

### ⚠️ 10. 工作流引擎（05）

- 缺 start 节点 → 抛 `Workflow 缺少 Start Node`；`pickNextEdge` 返回 null → 抛 `无法选择后继边`；找不到目标节点 → 抛 `找不到目标 Node`
- `pickNextEdge()` 有**历史数据兜底**：`sourceHandle === branch` 匹配不到时，再试 `${branch}` 和 `source-${branch}`
- **版本状态机守卫未写**：ARCHIVED 不能直接发布、只有 PUBLISHED 能归档、只有 ARCHIVED 能恢复
- `publish()` 的 version = 该 workflow 现有**最大 version + 1**（不能只用 publishedVersion.version + 1，否则首次 publish 会和 create 的 v1 撞 unique constraint）——这个坑文档没记
- 文档说 runStream 会 yield `error` 事件，实际 `WorkflowStreamEvent` 类型里有 `error` 但 **runStream 从不 yield**，异常是直接 throw，由 Controller catch 后手写 error 事件
- 变量系统：`{{output}}` 也是 previousOutput 的别名，文档只写了 `{{previous}}`
- **HTTP 节点 4xx/5xx 不报错**：`validateStatus: () => true`，错误响应当正常结果返回（只有 DNS/超时/连接拒绝才 throw）；body 是 json 字符串时会先尝试 `JSON.parse`
- RAG 节点：query 为空返回 `''`；knowledgeBaseIds 为空时**透传 query 给下游**而不是报错
- LLM 节点 RAG：既无 `{{rag_context}}` 又无 systemPrompt 时，用第三套默认模板

### ⚠️ 11. AI Provider（03）

- Ollama 流式的结束信号**不是 `done: true` 字段**——代码只读 `message.content`，靠 reader 的 `done` 结束循环。表格里那行会误导
- `createProvider()`：`openai` 缺 baseUrl 时用 `DEFAULT_BASE_URL.openai`；`openai-compatible` 缺 baseUrl **直接 throw**；还有 `default: throw`
- Ollama 的 `embedding()` 是 **for 循环一条一条发请求**，`EmbeddingService` 的 `BATCH_SIZE=100` 只是外层分批，Ollama 内部仍是 N 次 HTTP
- 两个 Provider 的 embedding 入参不同：Ollama 用 `{model, prompt}`，OpenAI 用 `{model, input}`
- `toolCall.id` 缺失时用 `call_${i}_${Date.now()}` 兜底；`arguments` 统一用 `stringifyToolArguments()` 归一化为 JSON 字符串

### ⚠️ 12. LLM 配置管理（07）

- 漏了 `create()` 的强制校验：非 ollama 必须提供 apiKey
- 漏了 `resolveBaseUrl()`：openai/deepseek 有默认值、openai-compatible 必须给、ollama 留 null（运行时取 localhost:11434）
- 漏了 `resolveChatProvider()`、`getModelName()`、`listModels(capability)`、`setDefaultModel()`、`updateModel()` 五个方法
- `capabilities` 实际默认 `["CHAT","STREAM"]`，注释里是 `TOOLS`（文档写的 `TOOL_CALL` 对不上）
- **"自动设置 capabilities"不准确**：`fetchModels()` upsert 时写死 `['CHAT','STREAM']`，不会识别 EMBEDDING——云端 embedding 模型必须用户手工改 capabilities 才能用
- `update()` 时 `apiKey` 传空字符串表示不改（文档反过来说"只有 !== undefined 才覆盖"，还额外排除了空串）

### ⚠️ 13. Dashboard（08 第五节）

| 文档                                 | 实际                                                                                                                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 概览返回 4 个计数                         | 返回 workflows(total/published/runCount/runCompleted/runFailed/runQueued/runRunning/successRate/avgDurationMs) + knowledgeBases + agents + skills + mcpServers + `tokenUsage`（**恒为 0**） |
| 节点耗时排行"Top 10 最慢的 WorkflowNodeRun" | 按 **nodeType 聚合的平均耗时**，近 30 天，取 Top `limit`（默认 10）                                                                                                                                    |
| 最近运行"最近 20 条"                      | 默认 `limit = 10`，且同时返回最近 10 条文档                                                                                                                                                        |
| 队列监控"BullMQ Queue 深度、活跃 Job"       | **没调 BullMQ API**，是按 `WorkflowRun.status` 计数（QUEUED/RUNNING/COMPLETED/FAILED），`delayed` 恒为 0                                                                                          |

### ⚠️ 14. 架构与 Auth（01 / 02）

- 01 的表清单漏了 `Friendship` 和 `WorkspaceKnowledgeBase` 两张表
- 02「错误处理优先级」与实际不符。实际是：
  - `HttpException` 且 response 是对象 → `error = obj.error ?? exception.message`，`message = obj.message 数组用「；」join ?? exception.message`
  - **非 HttpException → message 被脱敏成「服务器内部错误，请稍后重试或联系管理员」**（不是 "Internal Server Error"），完整堆栈只进服务端日志
  - **所有 401 的 message 会被强制改写成「邮箱或密码不正确」**——这是过滤器层做的二次保护，而不只是 AuthService 里的处理，文档没说清
