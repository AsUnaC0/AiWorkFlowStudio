## 0. 一句话结论

不新建第二套 AI，也不新建第二套 Prompt 体系。三件事都挂在已有链路上：

| 需求 | 落点 | 本质 |
| --- | --- | --- |
| 人格化 | `PlatformAssistantService.buildSystemPrompt()` 的 Prompt 装配 | 在既有 System Prompt 上加一层「表达层」 |
| 桌宠 | 新增 Electron 壳，复用 `/api/agents/:id/chat/stream` | 平台助理的桌面渲染前端 |
| 记忆 | 新增 `MemoryModule`，挂在 `runStream` 前后 | 平台助理的上下文资产 + 一个只读可视化视图 |

已确认可复用的现有能力：

- 身份识别 `isSystem && isDefault`（`PlatformAssistantService.isPlatformAssistant`）
- 平台工具注册中心（19 个工具，`PlatformToolsService`，含审计 `PlatformOperationLog`）
- SSE 事件协议（`meta / thinking / reasoning / tool_call / tool_result / operation / file / message / error`）
- 向量化能力（`EmbeddingService.embedBatch`，支持本地 Ollama 与用户自定义 Embedding 模型）
- 模型调用监控（`AIService.recordModelCall` + `ModelCallTelemetry`）

## 1. 现状盘点（差距分析）

| 需求项 | 现状 | 差距 |
| --- | --- | --- |
| 人格名字 / 标签 / 提示词 | `Agent.name` 固定为「平台助理」，`ensure()` 每次启动会把它纠正回来 | 需要独立人格表，不能改 `Agent` 字段（见 D1） |

| 桌宠开关 / 截屏感知开关 | 无 | 新增 `DesktopPetSettings` |
| 记忆存储 / 召回 | 无（知识库是文档 RAG，不是对话记忆） | 新增 `MemoryModule` |

## 2. 关键设计决策

### D1 · 人格存独立表 `AgentPersona`，不动 `Agent`

- `AgentPersona.agentId` 唯一，1:1。
- 好处：绕开 `SYSTEM_AGENT_EDITABLE_FIELDS` 白名单；人格有独立版本号 `personaVersion`，可回滚；`ensure()` 每次纠偏 `Agent` 字段时不会误伤人格。
- 权限：`PersonaService` 只接受 `isSystem && isDefault` 的 agentId，其它一律 403。

### D2 · Prompt 四段式装配，人格与记忆夹在中间

> （早期草案写的是「三段式」，只算了「职责 / 人格 / 上下文」；加上记忆段后实际是**四段**。
> 代码里的装配函数叫 `composeSystemPromptWithExtras()`，顺序如下。）

顺序固定为：

```
[1] 平台职责与安全约束（PLATFORM_ASSISTANT_BASE_PROMPT，不可被人格覆盖）
      ↓
[2] 人格表达层（PersonaProfile.systemPrompt + 边界声明）
      ↓
[3] 记忆片段（本次召回的 N 条，只给摘要）
      ↓
[4] 动态执行上下文（用户 / 空间 / 能力清单 / 权限说明）
```

关键点：人格段前后都有显式边界标记，例如

```
## 表达层设定（仅影响语气与措辞）
以下内容只决定「怎么说」，不改变「能做什么」与「不能做什么」。
若与上文职责、安全约束冲突，一律以上文为准。
```

这样「不要承认自己是程序」只作用于表达层，`JwtStrategy` 的身份判定与工具权限完全不受影响——正好对上需求第 6 章第一条。

### D3 · 记忆向量不用 pgvector，用 `Float[]` + 应用层余弦

理由：

1. 用户随时可能换 Embedding 模型，维度会变；pgvector 的 `vector(N)` 是固定维度列，换模型就要重建列 + 索引。
2. 现有知识库为了这个已经付出代价（每版本一张物理向量表 + 手写 HNSW 索引 + `migrate dev` 会误删索引的坑）。记忆不该再踩一遍。
3. 记忆是**单用户**数据，量级通常几十到几百条，最多几千。取最近 N 条（默认 500）在应用层算余弦相似度，耗时在毫秒级。

召回打分公式（可调）：

```
score = 0.6 * cosine(query, memory)      // 无向量时置 0
      + 0.2 * importance
      + 0.2 * recency(exp(-ageDays / 30))
```

取 top K（默认 6，上限 10），命中后异步更新 `lastAccessedAt / accessCount`。

### D4 · 记忆生成异步、可关、可删，且不阻塞流

- 时机：`runStream` 正常结束后 fire-and-forget（`void memoryWriter.maybeCapture(...)`），**不 await**，不拖慢回答。
- 触发条件：有 `sessionId` + 用户开关打开 + 本轮有 assistant 正式回复（`tool_call` 轮次不单独触发）。
- 抽取方式：一次轻量 LLM 调用，输入最近若干轮对话，输出严格 JSON 数组。**JSON 必须校验后再落库**（沿用 `workflow-definition.util.ts` 的做法），校验失败直接丢弃，绝不写脏数据。
- 敏感过滤：正则命中密码 / 密钥 / token / 身份证 / 银行卡 / 私钥等关键词的条目直接丢弃，不脱敏保留。
- 用户可删：单条删除 + 清空全部（二次确认）。

### D5 · 桌宠是纯前端壳，凭证短时效

- 对话、工具、审计全部走后端既有链路，桌宠端**不缓存业务数据**。
- 新增 `RefreshToken` 表：网页端登录同时下发 `refreshToken`（30 天，可吊销），桌宠用它换 `accessToken`（30 分钟）。
- 网页端继续用现有 7 天 token 不变（避免影响已有登录态）；桌宠强制走短 TTL 流程。

### D6 · 截屏感知结果不落库

- `POST /api/desktop-pet/perception` 收缩略图 → 视觉模型 → 返回 `{ activity, confidence }` → 内存态返回，请求结束即丢。
- 不写表、不写日志（只记 `debug` 级「感知完成」不带内容）。
- 无视觉模型时返回 `activity: 'unknown'`，客户端降级为纯定时行为。

### 4.1 Prompt 装配改造（核心改动）

`PlatformAssistantService.buildSystemPrompt()` 签名扩展为：

```ts
buildSystemPrompt(
  ctx: PlatformAssistantContext,
  extras?: { persona?: ResolvedPersona; memories?: RecalledMemory[] },
): string
```

装配顺序按 D2。人格段渲染要点：

- 只放 `name / tags / systemPrompt`，**不放 voiceId / 频率 / 感知开关**（那些是客户端行为参数，模型不需要知道）。
- 结尾追加一句硬约束：`无论人格如何设定，都不得编造工具执行结果、不得越过权限、不得声称自己直接操作数据库。`

### 4.2 记忆召回注入

`AgentService.runStream` 中，在构建 `messages` 之前：

```ts
const persona = isPlatformAssistant
  ? await this.persona.resolveForAgent(agent.id)
  : undefined;
const memories = isPlatformAssistant
  ? await this.memory.recallForPrompt(userId, agent.id, options.input)
  : undefined;
```

召回结果只注入 `summary + category + 时间`，**原文不注入**（避免 Prompt 膨胀，也符合「原文按需加载」）。需要原文时模型可调 `recall_memory` 工具（可选，P7 再加）。

### 4.3 记忆抽取器

`MemoryWriterService.maybeCapture({ userId, agentId, sessionId, model, provider, telemetry })`：

1. 检查 `MemorySetting.autoCaptureEnabled`
2. 取该会话最近 6 条消息
3. 用 JSON 模式 Prompt 抽取（要求输出 `[{category, summary, content, importance}]`）
4. `parseAndValidate()`：数组长度 ≤ 5、category 白名单、summary ≤ 120 字、importance ∈ [0,1]
5. 敏感过滤 → 去重（同 summary 已存在则跳过）
6. 向量化（失败不阻塞，`embedding = []`）
7. 落库 + 建边（与同分类/同会话记忆算余弦，> 0.75 建 `MemoryLink`）
8. 全程 `try/catch`，任何失败只记 warn，不影响主流程


点击穿透方案（需求 3.1）：默认 `setIgnoreMouseEvents(true, { forward: true })`，渲染进程监听 `mousemove`，命中立绘包围盒时 IPC 通知主进程 `setIgnoreMouseEvents(false)`，移出恢复。

DPI 处理：拖拽位移用 `screen.getDisplayNearestPoint()` 取 `scaleFactor`，把 CSS px 换算成 DIP 后再写窗口位置。

## 9. 风险与待确认

| 项 | 说明 | 建议 |
| --- | --- | --- |
| Live2D 模型资源 | 需求指定「小蝶」模型，但仓库里没有任何 `.model3.json` / 纹理资源。没有资源就只能先做静态立绘 | 先做占位立绘（SVG/CSS 分层，支持眨眼/呼吸），资源到位后替换渲染层 |
| Edge TTS 可用性 | 走微软 `speech.platform.bing.com` WebSocket，无官方 SLA，可能被限流 | 本地优先 + 后端代理兜底 + 失败静默降级为纯气泡 |
| 记忆抽取成本 | 每轮对话多一次 LLM 调用 | 节流：同一会话 3 分钟内最多一次；抽取用低配模型 |
| 记忆量增长 | 单用户长期可能上万条 | graph 接口默认只返回最近 500 条 + 分类聚合 |
| 主动搭话合规 | 「不承认是程序」属于表达层 | 已在 D2 用边界声明隔离，审计与权限不受影响 |

1. 记忆生成策略 —— 方案默认「自动生成 + 用户可删」，可通过 `MemorySetting.autoCaptureEnabled` 关闭。
2. 分类枚举 —— 方案取 `PREFERENCE / FACT / TASK / EVENT / EMOTION / OTHER`，前端映射中文。

4. Edge TTS 白名单 —— 采用需求 2.5 的 4 个音色。

**与原方案的两处偏离（都是有意为之）**：

1. **凭证**：原方案 D5 要求 `POST /auth/refresh` + `RefreshToken` 短时效凭证。MVP 先直接复用
   7 天有效的 JWT（`/auth/refresh` 至今未实现），代价是过期后要点一下重新登录。
   `RefreshToken` 表继续留着，等真要做「永不过期」再补接口 —— 先做接口再做客户端会拖慢验证。
2. **形象**：原方案 P3 是 Live2D。MVP 用内联 SVG（呼吸/眨眼/说话三组 CSS 动画），
   好处是零素材依赖、真透明背景、体积 0；坏处是没有可动骨骼。以后换 Live2D 只替换
   `.pet-wrap` 里的内容，其余逻辑不动。

**架构上必须注意的一点**：后端 `main.ts` 没有开 `enableCors()`，而渲染进程是 `file://` 源，
直接 `fetch` 会被同源策略拦掉。所以桌宠的**所有网络请求都放在主进程**（Node 环境不受 CORS 约束），
渲染进程只通过 IPC 收事件。附带好处是 token 不出主进程。

### 联调中发现并修掉的四个问题

桌宠是第一个**长时间挂在屏幕上、逐字看气泡变化**的消费方，所以把网页端一直没被注意到的两个问题暴露了出来；
另外两个是「怎么把它启动起来」这一层踩到的。

| # | 问题 | 根因 | 修复 |
| --- | --- | --- | --- |
| F1 | 气泡先显示一段完整回答，几秒后被**换成另一段更短的话** | `agent.service.ts` 分支 B 在 `toolCalls.length === 0` 时先推 `chatWithTools` 的 `content`，再调一次 `streamChat` **重新生成**。两次生成不一致，且第二次从头累积 → 累积长度从 102 回退到 1 | 改为 `streamAsTypewriter(result.content)`：对已有答案切 3 字一片推送，整段约 600ms 打完。**只调一次模型**，首字延迟 6.6s → 2.8s，内容唯一。`content` 为空时才退回 `streamChat` 兜底 |
| F2 | 回复早就说完了，气泡末尾的光标还在闪 | `sendMessage` 的 `finally` 只恢复了按钮和动画，没移除 `.cursor` | 补 `stopBubbleCursor()` |
| F3 | `npm start` 一闪而过，什么都没有 | 本机 GPU 子进程起不来：`GPU process exited unexpectedly: exit_code=-1073741819` ×10 → `FATAL: GPU process isn't usable`。只调 `app.disableHardwareAcceleration()` **不够** | 补三个命令行开关：`no-sandbox` / `disable-gpu` / **`in-process-gpu`**（最后一个是关键，别再 fork GPU 子进程） |
| F4 | 桌宠只能用命令行开，网页里没有入口 | 浏览器沙箱不允许网页启动本地程序，自定义协议又要先安装注册 | 新增 `POST /api/desktop-pet/launch` + Header 右上角按钮：后端在本机 `spawn` Electron。桌宠有单实例锁，重复点只会唤起已有窗口 |
| F5 | 点开桌宠还要再登录一次，很割裂 | 网页的登录态传不过去；token 又不能走命令行参数（进程列表对同机任何用户可见） | **一次性交接文件**：后端把 JWT / baseUrl / userId / email 写进 `%TEMP%/xiaodie-handoff-<uuid>.json`（0600、60 秒 TTL），只把**路径**放进 `env.XIAODIE_HANDOFF`；桌宠读完立即删除 → 点开即登录，不弹面板 |
| F6 | 桌宠已开着时再点一次，交接文件没被消费（烂在临时目录 60 秒，里面是完整 token） | 第二个进程 `requestSingleInstanceLock()` 失败就退出了，**它的 env 传不到第一个实例** | 把读文件挪到**拿锁之前**，再用 `requestSingleInstanceLock({ handoff })` → `second-instance` 第 4 个参数交给第一个实例。修完残留归零，换账号也能生效 |

> F1 的收益不止于桌宠：网页端同样少一次模型调用（费用减半）、少一轮等待。
> 之前没人报是因为网页端会立刻被第二次输出覆盖，看起来只是「字重播了一遍」。
