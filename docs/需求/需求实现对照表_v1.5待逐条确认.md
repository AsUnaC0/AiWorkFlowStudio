## I. 技术债与一致性问题（不是需求，但会影响需求怎么写）

这几条是我读代码时发现的**现状与文档不符**之处，建议在新文档里明确裁决，否则后续会反复踩坑。

| 编号 | 问题 | 现状 | 建议裁决 |
|---|---|---|---|
| I1 | **运行版本语义不一致** | BullMQ 处理器读 `currentVersion.definition`（草稿），Agent 工具读 `publishedVersion.definition`（已发布）。发布后继续编辑草稿 → 手动运行跑的是草稿 | 明确三套「运行入口 → 版本来源」：调试运行=草稿、Agent 调用=已发布、市场安装=指定版本快照 |
| I2 | **保存时不做定义校验** | 校验工具只被平台助理调用，普通编辑器保存可以存进非法定义 | 在 `WorkflowsService.update` 里强制调用 `validateWorkflowDefinition()` |
| I3 | **两套 SSRF 实现** | 工作流 HTTP 节点不校验 DNS、跟随重定向；MCP 全校验 | 统一到一套 guard |
| I4 | **SSE 调试链路不落 NodeRun** | 正式链路（BullMQ）与流式链路（SSE）行为不一致 | 统一为「BullMQ 执行 + SSE 推送事件」，或明确 SSE 仅用于调试 |
| I5 | MCP OAuth 缺失 | 仅 NONE / API_KEY / BEARER_TOKEN | 市场里的主流 MCP 多为 OAuth，建议列入 P1 |

### J2. AI 能力市场（Capability Hub）

已确认：一个统一市场入口，四类能力，依赖图 + 一键配置向导。

| 编号 | 模型 | 作用 |
|---|---|---|
| J2-1 | `CapabilityListing` | 名称、描述、类型、作者、分类、封面、发布状态 |
| J2-2 | `CapabilityVersion` | 版本号、兼容要求、资源快照、变更说明 |
| J2-3 | `CapabilityDependency` | 依赖能力、版本约束、是否必需 |
| J2-4 | `CapabilityInstallation` | 谁装了什么版本、装到哪、当前状态 |
| J2-5 | `CapabilityReview` | 评分、评论、举报 |
| J2-6 | `CapabilityCategory` | 分类与标签 |
| J2-7 | `CapabilityTestResult` | 发布前验证与兼容性测试 |

四类资源继续用各自业务模型（`Workflow` / `Agent` / `Skill` / `McpServer`），市场层通过「资源类型 + 资源 ID」关联，**不合并成一张大表**。

**关键原则**：市场发布版本 ≠ 用户安装实例。用户安装后可自由修改，市场发布新版时用户可看 diff 选择升级并保留自己的配置。

| 编号 | 能力 | 优先级 |
|---|---|---|
| J2-8 | 搜索 / 分类 / 标签 | P0 |
