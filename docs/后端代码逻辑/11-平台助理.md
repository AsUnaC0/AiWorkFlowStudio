# 11 - 平台助理（Platform Assistant）

> 面向小白开发者的代码讲解：默认聊天 Agent 是怎么从「普通聊天机器人」升级成
> 「理解当前用户 + 了解平台资源 + 可执行平台操作的统一入口」的。

相关代码路径：

```
backend/src/assistant/                      ← 平台助理本体（身份 / Prompt / 上下文 / 编排）
backend/src/platform-tools/                 ← 平台内置工具（注册中心 + 6 组工具 + 审计）
backend/src/agent/agent.service.ts          ← runStream：复用既有 ReAct 引擎跑平台助理
fronted/src/views/chat/index.vue            ← 聊天页：操作卡片 / 工作空间切换 / 操作记录
```

---

## 一、一句话理解

平台助理 = **系统默认 Agent（`isSystem && isDefault`）** + **专属 System Prompt** + **一整套平台内置工具**。

它没有另起一套大模型调用引擎，而是复用 `AgentService.runStream()` 的
流式对话 + Function Calling 能力，只是把「Prompt」和「工具」换掉了。

```
用户消息
   ↓
AgentController POST /agents/:agentId/chat/stream
   ↓
AgentService.runStream()
   ├─ 判断 isPlatformAssistant(agent) ?
   │     ├─ 是 → PlatformAssistantService.buildContext(userId, workspaceId)
   │     │        ├─ 生成动态 System Prompt（身份规则 + 服务端注入的上下文）
   │     │        └─ 注入 19 个平台工具定义
   │     └─ 否 → 老逻辑（Agent.systemPrompt + 绑定资源工具）
   ↓
ReAct 循环（chatWithTools → tool_calls → 执行 → 喂回）
   ├─ 平台工具 → PlatformAssistantService.executeTool()（权限校验 + 审计 + 异常兜底）
   ├─ MCP 工具 → McpToolService.callTool()
   └─ 资源工具 → ToolRegistry.executeTool()
   ↓
SSE：meta / thinking / tool_call / tool_result / operation / file / message / error
```

## 二、三条不可动摇的架构约束

这三点是这次改造的核心，任何新增平台工具都必须遵守：

### 1. `userId` 只能来自后端已验证的 JWT

`PlatformToolContext.userId` 由 `PlatformAssistantService.buildToolContext()` 填充，
值来自 `JwtStrategy.validate()` 查库后的 `user.id`。

**工具的入参 Schema 里没有任何 userId 字段** —— 模型在结构上就无法声明「我是谁」。

### 2. 不绕过业务 Service，不直接改库

每个工具都调用既有的业务 Service 或 Prisma 查询，而不是自己写一套平行的资源管理：

| 工具 | 复用的服务 |
|---|---|
| `create_workflow_draft` / `publish_workflow` / `run_workflow` | `WorkflowsService`（自带工作空间成员校验 + 版本管理） |
| `create_knowledge_base` | `KnowledgeService` |
| `attach_document_to_knowledge_base` | `DocumentService` + `StorageService` + BullMQ `document-processing` |
| `get_*` / `list_*` | Prisma 查询（只读，带权限过滤） |

> 唯一的例外是 `create_agent`：它直接用 Prisma 而不是 `AgentService.create`，
> 目的是避免 `AgentModule → AssistantModule → PlatformToolsModule → AgentModule`
> 的循环依赖。因此它的默认值（type / status / 运行参数）需要与 `AgentService.create` 手工保持同步。

### 3. 模型生成的 JSON 不许直接落库

`create_workflow_draft` 内部**强制再跑一次** `validateWorkflowDefinition()`：

- 节点类型必须来自 `NodeExecutorRegistry` 注册的 8 种（`start / input / llm / prompt / rag / http / condition / output`）
- 必填配置必须齐全（`rag→knowledgeBaseIds`、`http→url`、`condition→conditions`、`prompt→prompt`）
- 连线引用的节点必须存在；必须恰好一个 `start`；从 start 出发不得成环
- 引用的知识库 / 模型必须属于当前用户

校验不通过 → **返回错误原文，不写库**，让模型自己修正后重试。

## 三、平台助理是怎么「被识别」的

```ts
isPlatformAssistant(agent) {
  return agent?.isSystem === true && agent?.isDefault === true;
}
```

**判据是「系统默认 Agent」这个事实，不是名字。** 名字可以被改，标识不能。

初始化在 `PlatformAssistantService.ensure()`（幂等）：

1. 已有 `isSystem && isDefault` 的 Agent → 需要时原地升级（改名 / 换 Prompt / 提高迭代上限）
2. 没有，但存在历史遗留的 `meibus` / `AWS` 系统助手 → **原地升级**（保留 id，会话历史不丢）
3. 都没有 → 新建

> 这就是为什么升级后聊天页里那个默认助手直接变成了「平台助理」，
> 而它下面的历史会话一条都没丢。

## 四、动态上下文：注入什么、不注入什么

`PlatformAssistantContext`（见 `platform-assistant.context.ts`）分两部分：

**只注入元信息**（`buildContextSection()`）：

- 我是谁（username / email / userId）
- 当前工作空间（id + name）以及可访问的全部工作空间（id + name + role）
- 我能用哪些平台能力（19 个工具的中文名 + 风险等级）
- 权限说明（越权请求必须拒绝）

**绝不注入业务数据明细**：

工作流列表、知识库文档内容、运行记录…… 一律**按需通过工具查询**。
原因很简单：把用户全量数据拼进每次 Prompt，既浪费 token，也会让模型
「看到什么就想聊什么」，还容易泄露不该给模型的数据。

### workspaceId 的三道关

1. 前端可以传（用户在下拉框里选）
2. `buildContext()` 会**重新校验成员关系**，不是成员就当没传（并打 warn 日志）
3. 只有一个工作空间时自动采用，避免每次都要问用户

工具内部还会再查一次（例如 `create_workflow_draft` 的 `resolveWorkspaceId()`），
**任何一层都不信任上一层的结论**。

### 五·一、两个创建工具的红线：不接收密钥

`create_mcp_server` / `create_skill` 是**唯一会写库**的 skill-mcp 工具，两者都遵守同一条约束：
**MCP 的 apiKey / bearerToken 绝不经过聊天**。

原因是两处落库都会存原始入参：

| 落库点 | 内容 | 后果 |
|---|---|---|
| `ChatMessage.content` | 用户原话（含他贴的密钥） | 明文进会话历史，且会被当作上下文回灌给模型 |
| `PlatformOperationLog.params` | 工具入参 `args` | 明文进审计表，事后无法追溯清理 |

所以 `create_mcp_server` 的 Schema 里**根本没有** `apiKey` / `bearerToken` 两个字段；
模型若硬塞进来，工具直接返回 FAILED 并拒绝执行（不是静默丢弃 —— 静默丢弃会让模型以为配好了）。
另外 `platform-operation-log.service.ts` 的 `sanitizeParams()` 用**子串正则**脱敏
（`api[-_]?key|token|secret|passw|credential|authorization|cookie`），
覆盖 `bearerToken` / `accessToken` / `x-api-key` 等变体 —— 早期版本用 key 全等匹配，
`bearerToken` 是漏的。

#### create_mcp_server 的三条分支

```
1. authType=NONE
   McpService.createPendingCredentials() → McpService.testConnection()
     ├─ 成功 → status=CONNECTED，availableTools 落库，返回前 12 个工具名
     └─ 失败 → status=ERROR + lastError，文本里给排查方向（URL 路径 / 服务未启动 / 其实要认证）
2. authType=API_KEY / BEARER_TOKEN
   只建配置，**不测试连接**（没凭据必然 401，测了只会产生误导性错误）
   → 返回「还差一步：去 /mcp 填密钥」，此时 status=DISCONNECTED，Agent 调不到它
3. 同 serverUrl 已存在
   直接返回已有记录，不重复创建（防止模型重试刷出一堆重复配置）
```

为什么单独开 `McpService.createPendingCredentials()` 而不复用 `create()`：
`create()` 里的 `assertCredentialsProvided()` 会强制要求 API_KEY / BEARER_TOKEN 带凭据，
平台助理这条路天然拿不到凭据。新方法跳过凭据校验，但 **URL 形态校验（SSRF）与 `create()` 完全一致**，
且未配置凭据的 Server 在运行时拿不到任何认证头，不存在"绕过认证"。

#### create_skill 的类型校验

`SkillService.create()` 本身不做归属校验（它信任调用方），所以工具层必须自己查：

| 类型 | 必填 | 额外校验 |
|---|---|---|
| `PROMPT` | `instructions` | — |
| `WORKFLOW` | `workflowId` | 工作流必须属于用户可访问空间；未发布只给 ⚠️ 警告不阻断 |
| `TOOL` | `mcpServerId` + `mcpToolName` | Server 必须 `ownerId = 当前用户`；工具名不在缓存里只警告（缓存可能过期） |

> 工具返回文本里会主动说明「Skill 目前只在工作流 LLM 节点生效，Agent 运行时尚未接入」，
> 避免用户以为绑到 Agent 上就能用。

### 风险等级怎么用

风险等级目前有三个消费方：

1. **审计落库**（`PlatformOperationLog.riskLevel`）
2. **前端操作卡片**的徽标（只读 / 中风险 / 高风险）
3. **注入 Prompt 的能力清单** —— 让模型自己知道哪些操作要先跟用户确认

> 它不是技术限制，而是产品授权策略。
> 真正兜底权限的永远是工具内部的 Service 校验，不是这个标签。

## 六、一次真实调用长什么样

以「帮我创建一个 PDF 摘要工作流」为例：

```
1. LLM 决定调 list_workspaces            → 拿到当前工作空间（1 个，自动采用）
2. LLM 生成 nodes / edges
3. LLM 调 validate_workflow              → 自检（可选但推荐）
4. LLM 调 create_workflow_draft
      ├─ resolveWorkspaceId()  校验空间归属
      ├─ validateWorkflowDefinition() 再校验一次（不通过就返回错误，不写库）
      ├─ normalizeWorkflowDefinition() 统一成画布格式（type: 'custom' + data.nodeType）
      ├─ WorkflowsService.create() 落库（v1 草稿）
      └─ 返回 id + 编辑器链接 /workspace/<id>
5. LLM 回复用户：名称 / 执行路径 / 节点数 / 编辑器链接
6. ⛔ 不自动发布 —— publish_workflow 是 HIGH 风险，必须等用户明确同意
```

每一步都会推一个 `operation` SSE 事件给前端，渲染成操作卡片。

### 「文件转知识库」的完整链路

```
用户上传 PDF → ChatAttachment（status: READY，已解析）
   ↓ 平台助理调 attach_document_to_knowledge_base(attachmentId, knowledgeBaseId)
1. DocumentService.assertKbOwner()          校验知识库归属
2. ChatFilesService.findOne()               校验附件归属 + 必须 READY
3. 扩展名白名单（pdf/docx/txt/md/markdown）   xlsx/图片不在知识库支持范围内
4. ChatFilesService.getStorageKey() → StorageService.readBuffer()
   → StorageService.upload(buffer, name, `documents/${kbId}`)
   （附件存储 key 归会话所有，不能直接复用，必须复制一份）
5. DocumentService.create()                 建 Document 记录
6. documentQueue.add('process-document')    入队异步处理
7. 返回「已排队」+ 提示「入队成功 ≠ 向量化完成」
```

**为什么反复强调「入队成功 ≠ 向量化完成」**：
BullMQ 只是把任务塞进队列，解析 / 分块 / Embedding / 写 pgvector 都在后台。
所以工具返回值明确区分「已排队」与「已完成」，并提供
`get_document_processing_status` 让用户随时查真实进度。

## 七、操作审计（PlatformOperationLog）

### 为什么不用 `ChatMessage.trail`

`trail` 是**会话上下文**：它会作为历史消息喂回模型，属于对话数据。
审计需要的是**独立账本**：按用户 / 资源 / 工具 / 时间维度检索，不参与对话。

所以单独建了 `PlatformOperationLog` 表：

| 字段 | 说明 |
|---|---|
| `userId` / `workspaceId` / `sessionId` / `agentId` | 谁、在哪个会话、由哪个 Agent 触发 |
| `tool` / `action` / `riskLevel` | 用了什么工具、什么语义动作、什么风险等级 |
| `targetType` / `targetId` / `targetName` | 作用在哪个资源 |
| `status` / `summary` / `link` | 结果、人类可读摘要、可跳转入口 |
| `params` / `errorMessage` / `durationMs` | 入参（已脱敏）、错误、耗时 |

> 迁移文件：`prisma/migrations/20261014160000_add_platform_operation_log/migration.sql`（**手写 SQL**，
> 不要用 `prisma migrate dev`，原因见第十节第 7 条）。

### 两条硬规则

1. **写入失败不影响主流程**：`PlatformOperationLogService.record()` 全程 try/catch，
   审计写不进去也必须把工具结果正常返回给模型。
2. **入参必须脱敏 + 截断**：`sanitizeParams()` 会把 `apikey / token / password /
   secret / credential / authorization` 等键替换成 `***`，并对超长 JSON 截断到 4000 字符。

### 查询接口

```
GET /api/platform/assistant          → 平台助理信息 + 能力清单 + 可访问工作空间
GET /api/platform/operations         → 当前用户的操作记录（支持 sessionId/targetType/status/tool/limit 过滤）
GET /api/platform/operations/stats   → 按状态分组的操作统计
```

> 全部按 `userId = 当前登录用户` 过滤，**不提供查别人操作记录的能力**。

## 九、如何新增一个平台工具

1. 在 `backend/src/platform-tools/tools/` 对应分组的类里，往 `readonly tools` 数组加一项：

```ts
{
  name: 'my_new_tool',
  meta: {
    label: '中文名（前端卡片展示）',
    action: 'CREATE',            // QUERY / CREATE / UPDATE / DELETE / EXECUTE
    riskLevel: 'MEDIUM',         // LOW / MEDIUM / HIGH
    targetType: 'workflow',
  },
  definition: {
    type: 'function',
    function: {
      name: 'my_new_tool',
      description: '给模型看的能力说明（写清楚什么时候用）',
      parameters: { type: 'object', properties: { /* ... */ }, required: [] },
    },
  },
  execute: (args, ctx) => this.myNewTool(args, ctx),
}
```

2. 实现 `execute`，返回 `PlatformToolOutcome`：

```ts
{
  text: '喂回 LLM 的文本',
  status: 'SUCCESS',            // 可选，默认 SUCCESS
  targetType / targetId / targetName,
  summary: '人类可读摘要',
  link: '/workspace/xxx',       // 前端「打开资源」按钮
}
```

3. **必须做的三件事**：
   - 用 `ctx.userId` 而不是任何入参里的用户标识
   - 校验目标资源的归属（走对应 Service 的 assert 方法，或 Prisma where 里带上权限条件）
   - 用 `asString / asStringArray / asInt / asOptionalString` 解析入参
     （模型经常把数字传成字符串、把数组传成 JSON 字符串）

4. 审计、异常兜底、耗时统计、operation 事件都由 `PlatformToolsService.execute()` 统一处理，
   **不需要在工具里重复写**。

## 十、最容易踩的坑

1. **不要给平台助理绑定 `workflowIds` / `knowledgeBaseIds`**
   —— 它拿的是「一整套平台工具」，而不是「某几个绑定资源」。
   两套工具在 `runStream` 里是分别注入的，互不影响。

2. **平台助理不绑定固定模型**
   一份 Agent 记录服务所有用户，所以 `llmModelId` 为 null。
   运行时走 `LlmConfigService.resolveUserDefaultChatModel(userId)`
   —— 按**每个用户各自的默认对话模型**解析，找不到才回退全局 Ollama。

3. **`Agent.type` 仍是 `'CUSTOM'`**
   识别平台助理靠 `isSystem && isDefault`，不要新增 `type` 枚举值
   —— 否则前端已有的模板映射 / 表单分支全都要跟着改，收益为零。

4. **`run_workflow` 只接受已发布的工作流**
   草稿状态会被拒绝并返回明确提示。

5. **`attach_document_to_knowledge_base` 只支持 5 种扩展名**
   `pdf / docx / txt / md / markdown` —— 与 `documents.controller.ts` 的白名单一致。
   聊天附件支持 xlsx / csv / 图片，但**知识库不支持**，会返回明确错误。

6. **`create_agent` 的默认值要和 `AgentService.create` 手工同步**
   原因见第二节第 2 点（循环依赖）。

7. **迁移是手写 SQL**
   因为 `prisma migrate dev` 会把 pgvector 的 IVFFlat 索引当多余对象删掉
   （见 `schema.prisma` 里 `DocumentChunk.embedding` 的注释）。
   新增表时：手写 `prisma/migrations/<timestamp>_xxx/migration.sql` →
   `npx prisma migrate deploy` → `npx prisma generate`。
