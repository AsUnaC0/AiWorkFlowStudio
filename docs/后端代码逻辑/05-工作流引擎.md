## 一、整体架构

```
WorkflowsController
    │  CRUD + publish/archive/restore + enqueueRun（带 JwtAuthGuard）
    ▼
WorkflowsService
    │  版本管理（currentVersion / publishedVersion）
    │  BullMQ 入队 → workflow-execution Queue
    ▼
WorkflowProcessor (BullMQ Worker)
    │  加载 currentVersion.definition → 传给 WorkflowEngine.run()
    ▼
WorkflowEngine
    │  按拓扑顺序遍历 nodes → NodeExecutorRegistry.get(type) → 执行
    │  循环: 当前节点.execute() → 选下一条边 → 下一个节点
    │  构造时注入 RunMonitorService（logRunStart / logNodeStart / logNodeComplete / logNodeFailed / logRunComplete）
    │  context 注入 telemetry（workspaceId / workflowId / runId，NodeRun 创建后回写 nodeRunId）
    ▼
NodeExecutorRegistry
    │  Map<nodeType, NodeExecutor>
    │  8 种 Executor 实现
    ▼
具体 Executor（Start / Input / LLM / RAG / HTTP / Prompt / Condition / Output）
```

> ⚠️ 同文件里还有第二个 Controller：**`WorkflowController`（`@Controller('workflow')`）**，
> 提供 `POST /workflow/run` 和 `POST /workflow/run/stream` 两个**开发调试用**的直跑接口
> （接收前端传的 definition 对象，不经过 BullMQ、不落 WorkflowRun）。
> 它**没有加 JwtAuthGuard**——任何人只要能连上后端就能跑，仅限开发环境用。

## 二、WorkflowEngine — 执行核心

**文件路径**：`backend/src/workflows/engine/workflow.engine.ts`

### 节点归一化

从 VueFlow 画布来的 definition 有个坑：所有节点的 `node.type` 都是 `"custom"`，真正的类型在 `node.data.nodeType` 里。BullMQ 路径从 DB 加载也是只有 `node.data`，而 SSE 路径前端已经把 `data.nodeType` 提升到 `node.type`。

`normalizeWorkflow()` 统一两种来源：
```typescript
{
  nodes: workflow.nodes.map(node => ({
    ...node,
    type: node.type !== 'custom' ? node.type : (node.data?.nodeType ?? node.type),
    config: node.config ?? { ...node.data },   // 执行器从 node.config 读配置
  })),
  edges: workflow.edges,
}
```

### run() 主循环

```typescript
async run(workflow, input, options) {
  const normalized = this.normalizeWorkflow(workflow);
  const context = { input, data: {}, previousOutput: input };

  // 1. 从 start 节点开始
  let currentNode = normalized.nodes.find(n => n.type === 'start');
  if (!currentNode) throw new Error('Workflow 缺少 Start Node');   // ← 必须有 start

  // 2. 遍历（防循环）
  const visited = new Set();
  while (currentNode) {
    if (visited.has(currentNode.id)) throw new Error(`Workflow 存在循环: ${currentNode.id}`);
    visited.add(currentNode.id);

    // 3. 执行当前节点（内部会创建/更新 WorkflowNodeRun，失败置 FAILED 后 rethrow）
    const result = await this.executeNode(currentNode, context, runId);

    // 4. 存储结果
    context.data[currentNode.id] = result.branch
      ? { result: result.output, branch: result.branch, metadata: result.metadata }
      : result.output;
    context.previousOutput = result.output;

    // 5. 选下一条边
    const outgoing = normalized.edges.filter(e => e.source === currentNode.id);
    if (outgoing.length === 0) break;                     // 没后继 → 正常结束
    const targetEdge = this.pickNextEdge(outgoing, result);

    if (!targetEdge) {                                    // ← 选不出来才报错
      throw new Error(
        `Node ${currentNode.id} 无法选择后继边（outgoing=${outgoing.length}, branch=${result.branch ?? 'none'}）`
      );
    }

    // 6. 找下一个节点
    const nextNode = normalized.nodes.find(n => n.id === targetEdge.target);
    if (!nextNode) throw new Error(`找不到目标 Node: ${targetEdge.target}`);

    currentNode = nextNode;
  }

  return context;
}
```

**三种会抛错的情况**：缺 Start Node / 检测到循环 / 选不出后继边或找不到目标节点。抛错后由 `WorkflowProcessor` 捕获，把 WorkflowRun 置 `FAILED` 并写 `errorMessage`。

### 遥测注入与监控打点

Engine 在 `run()` / `runStream()` 里会做两件贯穿全程的事：

1. **telemetry 注入**：`context.telemetry = { workspaceId, workflowId, runId }`（来自 options）——
   每个节点创建 `WorkflowNodeRun` 后，把 `nodeRunId` **回写**进 `context.telemetry.nodeRunId`。
   这样 LLM / RAG 节点写 `ModelCallLog` 时能带上完整归属（谁在哪个工作流哪次运行哪个节点调的模型）。
2. **RunMonitorService 打点**：`logRunStart` / `logNodeStart` / `logNodeComplete` / `logNodeFailed` / `logRunComplete`
   —— 每次运行和每个节点都有结构化日志，方便排查「卡在哪个节点」。

### 选边逻辑 pickNextEdge()

```typescript
private pickNextEdge(outgoingEdges, result) {
  // Condition/Switch 节点 → result.branch 存在 → 用 sourceHandle === branch 匹配
  if (result.branch) {
    const matched = outgoingEdges.find(e => e.sourceHandle === result.branch);
    if (matched) return matched;

    // 防御：部分历史数据可能用 '-true' / '-false' / 'source-true' 这类后缀
    const fallback = outgoingEdges.find(
      e => e.sourceHandle === `${result.branch}` || e.sourceHandle === `source-${result.branch}`
    );
    return fallback ?? null;      // ← 返回 null，由调用方抛「无法选择后继边」
  }

  // 普通节点：恰好 1 条边 → 直接用
  if (outgoingEdges.length === 1) return outgoingEdges[0];

  // 多条：找不带 sourceHandle（或空串）的那条，且必须唯一
  const noHandle = outgoingEdges.find(e => !e.sourceHandle || e.sourceHandle === '');
  if (noHandle && outgoingEdges.filter(e => !e.sourceHandle).length === 1) return noHandle;

  // 还不确定 → 直接抛错（普通节点不能有多个带 sourceHandle 的后继）
  throw new Error('普通节点不能有多个带 sourceHandle 的后继边；请确认是否应该使用 Condition 节点');
}
```

> 注意两条分支的失败方式不同：`result.branch` 分支是**返回 null**（调用方抛「无法选择后继边」），普通节点分支是**直接 throw**。

### runStream() — 流式版本

和 `run()` 逻辑一样，区别是：
- 边执行边 yield 事件：`node:start` / `token` / `node:complete` / `complete`
- LLMNodeExecutor 会走 `executeStream()` 逐 token yield（**其他节点仍是普通 `execute()`**）
- 每个节点创建/更新 WorkflowNodeRun 记录（RUNNING → SUCCESS/FAILED），失败后 **rethrow**

> ⚠️ `WorkflowStreamEvent` 类型里虽然定义了 `error`，但 **runStream 从不 yield 它**——节点异常是 `throw` 出去的，由 Controller 的 catch 手写 `send({ type: 'error', ... })`。
> 另外 `runStream()` 结束时 yield 的是 `{ type:'complete', data: context.data }`（只含 data，不含 input / previousOutput）。

## 四、各 Executor 详解

### StartNodeExecutor — 起点节点

最简单，直接透传 input：
```typescript
async execute(context) { return { output: context.input }; }
```

### InputNodeExecutor — 输入节点

和 Start 一样。在工作流里可以有多个，用来把之前的输出"命名"后供下游引用。

### OutputNodeExecutor — 输出节点

返回 `context.previousOutput ?? context.input`。通常放在工作流末端，标记"这里是最终结果"。

### PromptNodeExecutor — 提示词模板

```typescript
async execute(context, node) {
  const template = node.config?.prompt ?? '';

  // 变量解析
  const resolved = this.variableService.resolve(template, context);

  if (hasVariables) {
    // 模板里有 {{变量}} → 完全由解析结果决定
    return { output: resolved };
  } else {
    // 没有变量 → 保留历史行为：模板内容 + 上一个节点输出
    return { output: resolved ? `${resolved}\n${previousOutput}` : previousOutput };
  }
}
```

### LLMNodeExecutor — 大模型节点（最复杂）

**createParams() 流程**：

1. 解析 System Prompt 和 User Prompt（都支持 `{{变量}}`）
2. **注入 Skill**：`config.skillIds` 有值 → 查 Skill 表拿到 `instructions` → 追加到 System Prompt 末尾
3. **RAG 简单模式**：`config.enableRag && knowledgeBaseIds` → 调 KnowledgeRetrievalService.search() → 把检索结果注入 System Prompt（三级分支，见下）
4. **MCP 工具**：`config.mcpServerIds` 有值 → `mcpService.findByIds()` 取 Server 配置（凭据在这里解密）→
   `mcpToolService.buildBindings(servers)` 得到 `{ tools, bindings }`
   —— **优先复用 `availableTools` 缓存，没有缓存才实时发现**；工具重名时保留先注册的那个并打 warn
5. **选择 Provider**：`config.llmModelId` 有值 → 动态构造云端 Provider；否则用全局 Ollama

**execute() 分支**（非流式，BullMQ 路径走这里）：
```typescript
const { messages, options, tools, mcpBindings, provider } = await this.createParams(context, node);

if (tools && tools.length > 0) {
  return await this.executeWithTools(provider, messages, options, tools, mcpBindings, telemetry);
} else {
  const result = await provider.chat(messages, options);   // 无工具 → 普通对话
  return { output: result.content };
}
```

> `mcpBindings` 是 `Map<toolName, McpToolBinding>`，不是早期的 `mcpServerMap`。
> 工具调用统一走 `mcpToolService.callTool(binding, args)` —— 会话由连接层复用（TTL 10 分钟），
> 会话失效会自动重连重试一次。协议细节见 [08](./08-MCP-Skill-Storage-其他模块.md) 第一节。

**RAG 注入的三级分支**（`llm.executor.ts`）：
1. System Prompt 里有 `{{rag_context}}` 占位符 → 先把检索结果塞进 `context.data.rag_context`，再走 VariableService 解析整个模板（占位符位置精确替换）
2. 没占位符但有 System Prompt → 自动追加「知识库参考」段：`${systemPrompt}\n\n知识库参考：\n${ragContext}`
3. **既没占位符也没 System Prompt → 用默认模板**：
   `请基于以下知识库内容回答用户问题。如果检索内容中没有相关信息，请坦诚说明。\n\n${ragContext}`

**executeWithTools() — MCP Function Calling 循环**：
最多 **5 轮**（`MAX_ROUNDS = 5`），每轮：
1. `chatWithTools()` → 拿到 `result.content` 和 `result.toolCalls`
2. `content` 有值且无 toolCalls → 直接返回（结束）
3. 有 toolCalls → 把 assistant 的 tool_calls 消息 push 进上下文 → 逐个执行
4. 执行失败（找不到 Server / 调用异常）→ **不中断**，push 一条 `工具 "xxx" 未找到对应的 MCP Server` 或 `工具执行失败: xxx` 的 tool 消息，让 LLM 自己调整
5. 继续下一轮

超过 5 轮仍未结束 → 返回 `{ output: '（工具调用轮次已达上限）' }`。
另外，LLM 返回**既无 content 也无 toolCalls**（部分兼容服务的空响应）→ 返回 `{ output: '' }`（`llm.executor.ts:247`），不当成错误。

> ⚠️ **已知缺口：流式路径不支持 MCP 工具**（缺口 G2）。
> `executeStream()` 虽然也调了 `createParams()`（会返回 `tools` 和 `mcpBindings`），但它**只解构了 `messages` / `options` / `provider`**，
> 直接 `provider.streamChat()`，完全忽略了 `tools`。
> 所以在画布上"调试运行"（SSE 流式）的 LLM 节点**调不到 MCP 工具**，只有 BullMQ 异步路径（`execute()`）才会走 `executeWithTools()`。同理，流式路径也不支持 Skill 之外的工具注入。

### RAGNodeExecutor — 知识库检索节点

```typescript
async execute(context, node) {
  const config = node.config;

  // query 来源：优先 queryTemplate（支持 {{变量}}），否则 previousOutput
  const query = config.queryTemplate
    ? this.variableService.resolve(config.queryTemplate, context)
    : context.previousOutput;

  // ⭐ 两种提前返回
  if (!query) return { output: '' };                    // query 为空 → 跳过检索
  if (kbIds.length === 0) return { output: query };     // 没选知识库 → 把 query 透传给下游，让 LLM 还能回答

  // 统一走 KnowledgeRetrievalService.search()
  const results = await this.knowledgeRetrievalService.search({
    knowledgeBaseIds: kbIds,
    query,
    topK,
    scoreThreshold,     // config.threshold ?? 0.2（相似度语义，越大越严格）
    mode,               // config.searchMode ?? 'hybrid'
    embeddingModel: config.embeddingModel,
  });

  // 输出格式
  if (config.outputFormat === 'json') {
    return { output: { query, hits: results.map(r => ({ chunkId, documentId, content, score, metadata, fileName })) } };
  }

  // 默认纯文本
  const contextBlock = results.length > 0
    ? results.map((r, i) => `[${i + 1}]${r.fileName ? ` 来源：${r.fileName}` : ''}\n${r.content}`).join('\n\n')
    : '（未检索到相关内容）';
  return { output: `【问题】\n${query}\n\n【知识库参考】\n${contextBlock}` };
}
```

### HttpNodeExecutor — HTTP 请求节点

6 步流水线：
```
validateConfig() → resolveAll() → ssrfCheckService.validate() → buildAxiosConfig() → axios() → normalizeResponse()
```

**validateConfig()**：检查 URL 必填、method 合法（GET/POST/PUT/PATCH/DELETE）、timeout 范围 1000-120000ms（默认 30000）。

**resolveAll()**：所有配置字段都经过 VariableService 解析，支持 `{{http_1.body.userId}}` 这种引用。
注意区别：`url` / `headers` / `query` 用 **`resolveAsString()`**（强制转字符串，对象会 JSON 化）；`body` 用 **`resolve()`**（保持原始类型）。headers/query 解析后会跳过 key 为空的项。

**SSRF 防护**：请求 URL 必须经过 `SsrfCheckService.validate()`，防止恶意请求内网地址（详见 [08](./08-MCP-Skill-Storage-其他模块.md)）。

**⚠️ 4xx / 5xx 不抛错**：axios 配了 `validateStatus: () => true`，所以 HTTP 400/500 会作为**正常响应**返回（status 字段照实填），不会中断工作流。只有网络层错误（DNS 失败、超时、连接拒绝）才 `throw new Error('HTTP 请求失败: ...')`。

另外 body 处理：只有 POST/PUT/PATCH 才带 body；`bodyType: 'json'` 且 body 是字符串时会先尝试 `JSON.parse`（失败就当普通字符串发）；没设 Content-Type 时自动补 `application/json`。

**输出标准化**：
```typescript
interface HttpNodeOutput {
  status: number;       // HTTP 状态码
  headers: Record<string, string>;
  body: unknown;         // 自动 JSON 解析后的响应体
}
```

下游可以用 `{{http_1.status}}`、`{{http_1.body.userId}}` 来引用。

### ConditionNodeExecutor — 条件分支节点

**支持的运算符**（10 种）：

| 运算符 | 含义 | 示例 |
|---|---|---|
| eq / neq | 等于 / 不等于 | `{{http_1.status}} eq 200` |
| gt / gte / lt / lte | 数值比较 | `{{input.age}} gte 18` |
| contains / not_contains | 字符串/数组包含 | `{{previous}} contains 成功` |
| is_empty / is_not_empty | 空判断 | `{{http_1.body.data}} is_empty` |

**执行流程**：
```
1. 校验 config.conditions 非空
2. 逐条：variableService.resolve(left) 和 resolve(right) 都解析（右侧也支持 {{变量}}）→ evaluate(left, operator, right)
3. 按 logicalOperator（AND/OR）合并
4. 返回 branch = matched ? 'true' : 'false'
5. metadata 里附带每条条件的调试信息
```

Engine 的 `pickNextEdge()` 用 `result.branch` 匹配 outgoing edges 的 `sourceHandle` → 决定走 true 分支还是 false 分支。

## 五、VariableService — 变量模板系统

**文件路径**：`backend/src/workflows/engine/variable.service.ts`

### 支持的变量格式

| 格式 | 含义 |
|---|---|
| `{{input}}` | 工作流初始输入 |
| `{{previous}}` / `{{output}}` | 上一个节点的输出（**两个名字等价**，都会解析到 `context.previousOutput`） |
| `{{nodeId}}` | 指定节点的输出（整个值） |
| `{{nodeId.output.field}}` | 指定节点输出的某个字段（支持任意层级嵌套） |
| `{{nodeId.body.userId}}` | HTTP 节点 body 里的 userId |
| `{{nodeId.status}}` | HTTP 节点的状态码 |
| `{{rag_context}}` | LLM 节点 RAG 模式注入的占位符（运行时塞进 `context.data`，由 LLM executor 处理，不是 VariableService 的内置变量） |

> `resolve()` 是递归的：传数组会逐项解析，传对象会逐字段解析，number/boolean 原样返回。所以模板不只限于字符串。

### resolve() — 类型保持

关键设计：**单个变量引用保持原始类型**，多变量模板才字符串拼接。
```typescript
// 整个模板就是 {{http_1.status}} → 返回 number（200）
// 模板是 "状态 {{http_1.status}}" → 返回 string（"状态 200"）
// 模板是 "{{input.name}}" 而 input.name 是对象 → 返回对象本身
```

## 六、版本管理

**WorkflowsService 核心规则**：

| 操作 | 做什么 | 前置校验（状态机守卫） |
|---|---|---|
| create() | 在事务里创建 Workflow + 第一个 WorkflowVersion(v1) → `currentVersionId` 指向它 | 必须是 workspace 的 owner 或 member |
| update() | `dto.definition !== undefined` 时创建新 WorkflowVersion(`max(version)+1`) → `currentVersionId` 指向新版本（旧版本保留）；同时可选改 name/description | 同上 |
| publish() | 快照 `currentVersion.definition` → 创建新 WorkflowVersion → `publishedVersionId` **和** `currentVersionId` 都指向它 → `status = PUBLISHED` | **ARCHIVED 不能直接发布**（先 restore）；必须有 `currentVersionId` |
| archive() | `status = ARCHIVED`，保留 `publishedVersionId` / `currentVersionId` 供追溯 | **只有 PUBLISHED 才能归档** |
| restore() | `ARCHIVED → DRAFT`，不动 `publishedVersionId`（要重新上线再调 publish） | **只有 ARCHIVED 才能恢复** |
| remove() | **永久删除**：事务里先摘除所有 Agent 的 `workflowIds` 绑定（数组字段无外键，需手动清理），再删 Workflow 本体（versions / runs / nodeRuns 由外键级联删） | 成员校验（`workspace.members.some({ userId })`），不存在抛 404 |

> `update()` 有个容易忽略的细节：**只有传了 `definition` 才建新版本**——纯改名/改描述
> （`dto.definition === undefined`）不会产生新 WorkflowVersion。

**publish 的 version 怎么算**（这里有个坑）：

```typescript
// ❌ 不能写成 (publishedVersion?.version ?? 0) + 1
//    因为 create 时已经建了 v1，首次 publish 会算出 version=1，撞 @@unique([workflowId, version])
const latestVersion = await prisma.workflowVersion.findFirst({
  where: { workflowId: id },
  orderBy: { version: 'desc' },
  select: { version: true },
});
const nextPublishVersion = (latestVersion?.version ?? 0) + 1;   // ✅ 取该 workflow 现有最大 version +1
```

**为什么要 publishedVersionId？**
Agent 调用工作流时应该调 `publishedVersion`（稳定），而用户在画布上编辑的是 `currentVersion`（草稿）。两者解耦 → 草稿怎么改都不影响 Agent。

> 注意 `publish()` 会把 `currentVersionId` **也**指向新的发布版本，让用户继续编辑时基于刚发布的版本。
> 另外 `WorkflowProcessor`（BullMQ 异步执行）读的是 **`currentVersion`** 而不是 publishedVersion——只有 Agent 的 `WorkflowTool` 走 publishedVersion。

## 七、BullMQ 异步执行

### 入队（WorkflowsService.enqueueRun）

```typescript
async enqueueRun(userId, workflowId, input) {
  // 1. 权限校验
  // 2. 创建 WorkflowRun 记录（status=QUEUED）
  // 3. 入队 workflow-execution Queue
  await this.workflowQueue.add('execute-workflow', {
    runId, workflowId, input
  }, { attempts: 1, removeOnComplete: 100, removeOnFail: 500 });
}
```

### Worker 执行（WorkflowProcessor）

```typescript
async process(job) {
  const { runId, workflowId, input } = job.data;

  // 1. 加载 Workflow + currentVersion.definition
  // 2. 更新 WorkflowRun → RUNNING + startedAt
  // 3. workflowEngine.run(definition, input, { runId, workflowId })
  //    ↑ 会自动持久化 WorkflowNodeRun（每个节点的执行记录）
  // 4. 成功 → COMPLETED + output；失败 → FAILED + errorMessage
}
```

### WorkflowNodeRun — 节点级执行记录

每次 runStream/run 都会为每个执行的节点创建一条：
```typescript
{
  runId, nodeId, nodeType, label,
  status: 'RUNNING' | 'SUCCESS' | 'FAILED',
  input, output, branch, metadata,
  durationMs, errorMessage, errorCode,   // ← errorCode 是失败时归类的错误码（toErrorCode()）
  startedAt, endedAt,
}
```

前端可以通过 `listNodeRuns(runId)` 拿到完整的节点级执行历史，用来可视化展示工作流运行过程。
