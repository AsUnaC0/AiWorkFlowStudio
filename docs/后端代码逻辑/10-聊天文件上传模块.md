# 10 - 聊天文件上传模块（Chat Files）

> 让用户在**聊天页直接上传文件**（PDF / Word / Excel / CSV / TXT / MD / 图片），文件内容作为上下文随消息交给 AI 一起对话。
> 这是 `backend/src/chat-files/**` 的完整逻辑讲解，与 **09 文件生成模块**是一对互补能力：
> - **09 是「AI 产出文件」**（generate_file 工具，落 `GeneratedFile`）；
> - **10 是「用户喂文件」**（聊天附件，落 `ChatAttachment`）。

---

### 与知识库 / 文件生成模块的关系

| 维度 | 聊天附件（本模块） | 知识库文档（06） | 生成文件（09） |
|---|---|---|---|
| 落库模型 | `ChatAttachment` | `Document` + `Chunk` | `GeneratedFile` |
| 是否向量化 | ❌ 不向量化 | ✅ pgvector | ❌ |
| 是否进知识库检索 | ❌ 不参与 RAG | ✅ 参与 | ❌ |
| 生命周期 | 跟随会话 / 消息 | 跟随知识库 | 跟随会话 / 消息 |
| 用途 | 单次对话的「随问随读」 | 长期知识沉淀 | AI 产出可下载文件 |

> ⚠️ **这是本模块最重要的设计原则**：聊天附件是「普通聊天附件」，和知识库**完全解耦**——不上传知识库、不做嵌入、不向量化。用户只是把文件内容「贴进这一轮对话」，AI 读完即止，不影响知识库检索。

## 二、数据模型

```prisma
model ChatAttachment {
  id           String   @id @default(uuid())
  userId       String            // 权限校验依据
  sessionId    String?           // 所属会话（上传时可能还没建会话）
  messageId    String?           // 随哪条用户消息发给模型（发送后回填）

  originalName String
  mimeType     String
  extension    String
  size         Int      @default(0)
  storageKey   String   @unique   // 对象存储 Key（本地模式为绝对路径）

  kind         String   @default("TEXT")   // PDF / DOCUMENT / SPREADSHEET / TEXT / IMAGE
  status       String   @default("UPLOADED") // UPLOADED / PROCESSING / READY / FAILED

  extractedText String?   // 解析出的纯文本（超长会截断）
  charCount    Int      @default(0)
  summary      String?   // 结构化摘要（如 Excel 的工作表 / 列统计）
  parseError   String?   // status = FAILED 时可直接展示给用户
  meta         Json?     // 页数 / 工作表数 / 图片尺寸等附加元数据

  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  session      ChatSession? @relation(fields: [sessionId], references: [id], onDelete: SetNull)
  message      ChatMessage? @relation(fields: [messageId], references: [id], onDelete: SetNull)
}
```

> ⚠️ **表里不存二进制、也不存 `previewType`**：二进制在对象存储（七牛云）里（只存 `storageKey`）；`previewType` 是运行时按扩展名现算的（见 `file-parser.service.previewTypeOf()`），**前端历史消息拿不到该字段时要按扩展名兜底**（前端 `previewTypeFromExt()`）。

`ChatSession` 与 `ChatMessage` 各自新增了一对多关系：`attachments ChatAttachment[]`（引用关系，删除会话/消息时置空 `sessionId` / `messageId`，附件记录保留）。`getWithMessages()` 已 include `attachments`，所以**历史回看能直接看到用户当时发的文件**。

迁移文件：`prisma/migrations/20261012130000_add_chat_attachment/migration.sql`（手写，待 `prisma migrate deploy` 应用）。

## 三、上传策略与解析器分派

**文件路径**：`backend/src/chat-files/file-parser.service.ts`

### 上传策略（前端轮询 `GET /policy` 做前置校验）

```typescript
const CHAT_FILE_MAX_SIZE       = 50 * 1024 * 1024;  // 单文件 50MB
const CHAT_FILE_MAX_PER_MESSAGE = 10;                // 单条消息最多 10 个附件
const ALLOWED_EXTENSIONS = [                         // 小写、不含点
  'pdf','docx','xlsx','xlsm','csv','tsv','txt','md','markdown','json','log',
  'yaml','yml','xml','html','htm','sql','png','jpg','jpeg','webp','gif','bmp',
];
```

- `classify(extension)` → `kind`（`PDF` / `DOCUMENT` / `SPREADSHEET` / `IMAGE` / `TEXT`）
- `previewTypeOf(extension)` → 预览组件类型（`pdf` / `document` / `spreadsheet` / `csv` / `image` / `markdown` / `text`）
- `assertSupported(fileName)` → 不支持直接抛 400（带可展示提示文案）

### 解析器抽象

`parsers/parser.types.ts` 定义统一接口：

```typescript
interface AttachmentParser {
  parse(input: ParseInput): Promise<ParseResult>;
}
interface ParseResult {
  text?: string;       // 注入模型的纯文本
  summary?: string;    // 结构化摘要（如 Excel 统计）
  meta?: Record<string, unknown>;
}
interface ChatAttachmentLike {   // 注入上下文时给 file-context 用的精简视图
  id; originalName; extension; kind; mimeType; storageKey;
  extractedText?; summary?;
}
```

`file-parser.service.parse()` 按 `kind` / `extension` 分派到具体解析器。各解析器要点：

| 解析器 | 库 / 方式 | 要点 |
|---|---|---|
| `text.parser` | 读 UTF-8 | TXT/MD/JSON/LOG/YAML/XML/HTML/SQL 等，纯文本直读；超 **400k** 字符截断防单记录过大 |
| `pdf.parser` | `pdf-parse` | 提取正文；若提取字符数 < 20 判定为**扫描版 PDF**，提示「需要 OCR」 |
| `docx.parser` | `mammoth` | `extractRawText` 取纯文本 |
| `excel.parser` | `ExcelJS` | 多工作表（最多 **10**），每表最多 **300** 行；**数值列自动算合计/均值/最小/最大**，summary 里带统计，让 AI 先读统计再看抽样 |
| `csv.parser` | 手写解析 | 支持引号内换行 / TSV；最多 **500** 行、**60** 列（超了截断并提示）；同样产出列统计 summary |
| `image.parser` | `Buffer.toString('base64')` | 转 base64 交给**视觉模型**；> **8MB** 跳过（避免请求体过大） |

> **方案 A（第一版采用）**：直接提取文本 → 按预算截断后注入模型上下文。Excel 优先「程序读表 + 基础统计」再让 AI 分析，而不是把整个 sheet 丢给模型。图片走视觉输入，模型不支持视觉时降级为文字提示。

## 四、上传 → 存储 → 异步解析链路

**入口**：`POST /api/chat/files/upload`（`multipart/form-data`，字段 `file`；可选 `sessionId`）

```
ChatFilesService.upload(userId, file, sessionId?)
  │
  ├─① assertSupported(file.originalname)       类型/大小前置校验
  ├─② 若带了 sessionId：校验该会话属于当前用户（ForbiddenException 否则）
  ├─③ StorageService.upload(buffer, name, 'chat-attachments')  → { key, size }
  ├─④ prisma.chatAttachment.create({ status: 'UPLOADED', kind, … })
  └─⑤ scheduleProcessing(attachment.id)        ↓ 异步解析
```

### 解析调度（关键：Redis 不可用时降级）

```typescript
scheduleProcessing(attachmentId) {
  const useQueue = process.env.CHAT_FILE_USE_QUEUE !== 'false';
  if (useQueue) {
    try {
      await withTimeout(this.queue.add('parse-attachment', { attachmentId }, {…}), 1500);
      update status = 'PROCESSING';
      return;
    } catch { /* Redis 连不上 → 走下面降级 */ }
  }
  // 降级：进程内后台执行，不 await（不阻塞上传响应）
  void this.process(attachmentId).catch(() => {});
}
```

- 优先走 **BullMQ**（Redis 可用）；`CHAT_FILE_USE_QUEUE='false'` 可强制关闭队列。
- Redis 不可用时**自动降级为进程内解析**，保证「Redis 没起来，聊天附件照样能用」。
- `process()`：读对象存储 buffer → `parser.parse()` → 更新 `status/extractedText/summary/charCount`；失败写 `parseError` + `status='FAILED'`。

> ⚠️ **BullMQ Worker 初始化本身需要 Redis**。降级路径只覆盖「调度解析」这一环；如果 Redis 彻底起不来，Worker 模块初始化可能报错——运行环境需自行保证 Redis 可用（降级是兜底，不是免死金牌）。

## 五、把附件塞进 AI 上下文（file-context）

**文件路径**：`backend/src/chat-files/file-context.service.ts`

`build({ question, attachments, model, userId })` 产出 `{ text, images }`：

1. **文本附件**：按 `DEFAULT_CONTEXT_MAX_CHARS = 24000` 预算截断后拼接进 `text`（超长文档只取前 N 字符，避免单次上下文爆炸）。
2. **图片附件**：若模型支持视觉（`supportsVision()` 命中 `VISION_MODEL_HINTS` 或环境变量 `CHAT_FILE_VISION_MODELS`），读 base64 注入 `images`；**不支持视觉则降级**为一段「用户上传了图片但当前模型无法看图」的提示。
3. 最终 `text` 形如：`用户问题：…\n\n---- 附件内容 ----\n[1] xxx.pdf:\n<文本>\n[2] data.png: (图片已作为图像输入)`。

- `supportsVision()`：命中白名单（`gpt-4o` / `qwen-vl` / `llava` 等）或 `CHAT_FILE_VISION_MODELS` 显式指定。
- `buildHistoryBlock()`：历史轮次里**已绑定消息的附件**，用更小预算（**6000** 字符）重新注入，保证多轮追问也能基于之前上传的文件。

> **视觉通道打通位置**：`ai/ai-provider.interface.ts` 的 `ChatMessage` 新增 `images?: ChatImage[]`（`{ mimeType, base64 }`）；`openai-compatible.provider.ts` 把 user+images 转成多模态 `content` parts（`image_url` data URL），`ollama.provider.ts` 挂 `images = base64[]`。两个 Provider 都已支持。
>
> ⚠️ 上面说的是**输入侧**的多模态（把图片塞进请求）。**输出侧**如果模型把 `content` 返回成多模态内容块数组
> （如图像生成结果 `[{ url: "https://…" }]`），Provider 会用 `normalizeContentToString()` 归一化成**纯文本 URL**，
> 避免 `Expected String, provided Object` 落库报错 —— 详见 [03 第九节](./03-AI%20Provider大模型接入层.md)。

## 六、与 Agent 聊天的集成

**文件路径**：`backend/src/agent/agent.service.ts`（`runStream`）

`agent.controller.ts` 的 `run` / `runStream` body 新增 `attachmentIds?: string[]`，透传给 `runStream`。

发送流程：

```
runStream(userId, { input, sessionId, attachmentIds })
  │
  ├─① 解析运行时 Provider（用户自定义模型优先 → 回退 Ollama）
  ├─② 若有 attachmentIds：
  │     const attachments = await chatFiles.resolveForChat(userId, attachmentIds, sessionId)
  │     const ctx = await fileContext.build({ question: input, attachments, model, userId })
  │     currentUserContent = ctx.text
  │     if (ctx.images.length) currentUserImages = ctx.images
  ├─③ 组装 messages = system + history(augmentHistoryWithAttachments) + user(带 images)
  ├─④ 持久化用户消息（content = 原始 input）
  ├─⑤ if (attachmentIds?.length) chatFiles.attachToMessage(userId, ids, messageId, sessionId)
  └─ 解析失败 → yield error 事件并 return（用户消息已落库，不丢）
```

### `resolveForChat()` —— 严格权限校验（防越权）

- 必须是**当前用户**的附件（`ChatAttachment.userId === 当前用户`），存在不属于自己的 id 直接 `ForbiddenException`。
- 会话归属一致：附件必须属于当前会话或未绑定会话。
- `waitUntilReady()`：发送时若还在解析，最多等 **30 秒**；超时仍非 `READY` 则拒绝（避免把半截内容喂给模型）。
- 失败附件直接抛 `BadRequestException`（列出文件名 + 错误）。

`augmentHistoryWithAttachments(history, userId, sessionId)`：把历史用户消息里附带的附件上下文（通过 `getAttachmentsByMessages` 按 messageId 分组）重新注入，使后续追问也能继续引用之前上传的文件。

## 七、HTTP 接口

**文件路径**：`backend/src/chat-files/chat-files.controller.ts`（全部 `JwtAuthGuard` + 严格校验 `attachment.userId === 当前用户`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/chat/files/policy` | 上传策略（允许类型 / 大小 / 数量），前端前置校验用 |
| GET | `/api/chat/files/status?ids=a,b` | 批量查解析状态（前端轮询，避免 N 次请求） |
| GET | `/api/chat/files` | 我的附件列表（可按 `sessionId` 过滤） |
| POST | `/api/chat/files/upload` | 上传附件（multipart，字段 `file`） |
| GET | `/api/chat/files/:id` | 附件元数据 + 状态 |
| POST | `/api/chat/files/:id/reprocess` | 重新解析失败的附件 |
| DELETE | `/api/chat/files/:id` | 删除记录 + 对象存储对象 |
| GET | `/api/chat/files/:id/preview` | 预览数据（`html` / `sheets` / `text` / `rawUrl`），`rawUrl` 指向本模块 `/raw` |
| GET | `/api/chat/files/:id/raw` | 原始文件流（`inline`，前端转 blob 预览） |
| GET | `/api/chat/files/:id/download` | 原始文件流（`attachment` 下载） |

> 七牛云是**私有空间**，不能把对象 Key 拼成 URL 给浏览器。所有读取都走后端代理并带 `Authorization`（参考 09 第七节同样的 RFC 5987 文件名编码）。

**聊天侧真正触发 AI 读附件的入口**仍是 `POST /api/agents/:agentId/chat/stream`，只是 body 多了 `attachmentIds` 字段（见 04 第四节）。`runAgentStream` 前端封装已把 `attachmentIds` 透传进 SSE body。

## 八、最容易踩的 8 个坑

1. **聊天附件 ≠ 知识库文档**：不上传知识库、不向量化、不参与 RAG。想「长期记忆」请走 06 的知识库上传，别把聊天附件当知识库用。
2. **`resolveForChat` 会等 30 秒**：发送时附件还在解析会阻塞等待；前端应在发送前轮询 `status` 到 `READY` 再发，否则会被拒绝。
3. **越权防护**：不能把别人的 `attachmentId` 传进来——`resolveForChat` 校验 `userId` + `sessionId`，混入他人 id 直接 403/400。
4. **图片有视觉门槛**：当前模型不支持视觉时，图片不会进模型，只会留一段降级文字提示；要让 AI「看」图，需接支持视觉的模型（或配 `CHAT_FILE_VISION_MODELS`）。
5. **Redis 不可用只是「调度降级」**：解析会退化为进程内执行，但 BullMQ Worker 初始化本身要 Redis；运行环境仍需保证 Redis 可用。
6. **上下文有 24000 字符预算**：超长文件会被截断注入，AI 看不到全文——上传大文档时建议配合摘要/提问，或期待后续 RAG 化。
7. **`previewType` 不持久化**：历史消息的附件没有该字段，前端必须用 `previewTypeFromExt(extension)` 兜底，否则预览会用错组件（如 pdf 被当 text）。
8. **私有空间不能拼 URL**：预览/下载必须走 `/raw` / `/download` 代理并带 JWT，直接给 `storageKey` 给前端是无效的。
