# AI WorkFlow Studio 学习指南
## 第 3 篇：认证与权限 —— 后端怎么判断「这条请求是不是你自己发的」

> **本篇核心问题**：前端每次请求都发一堆数据，后端凭什么相信操作人是你？
> 答案是一条链：**JWT 通行证 → Guard 保安 → @CurrentUser 取出身份 → Service 查库校验权限。**
>
> 按 **前端发了什么 → 后端怎么收 → 后端怎么处理** 的顺序讲。

---

## 1. 用「游乐园」建立模型

把后端想成一个游乐园：

```
你 = 前端浏览器
你的身份 = JWT 通行证（一张带防伪签章的卡）
保安 = JwtAuthGuard（每个收费项目门口都有）
存包柜 = 数据库
票根 = 用户 ID（从通行证里读出来的，永远不信你自己写在纸上的号码）
```

| 概念 | 游乐园类比 | 实际含义 |
|------|-----------|---------|
| **注册** | 买年卡 | 存你的账号，密码做成「指纹」 |
| **bcrypt 哈希** | 存指纹不存指纹图样 | 数据库里只有 `$2b$10$...`，反向算不出密码 |
| **登录** | 验指纹 | 密码对上 → 发一张 JWT 卡 |
| **JWT** | 通行证 | 三段式、带签名、7 天过期 |
| **Guard（守卫）** | 保安 | 没卡 / 卡过期 / 签名不对 → 401 |
| **@CurrentUser()** | 验卡后把你记下来 | 后端拿到你的真实 ID，**不信前端传的** |
| **Service 权限校验** | 看票根决定你能进哪个区 | 401（你是谁？） vs 403（你能干嘛？） |

## 3. 注册接口：`POST /api/auth/register`

### 3.1 前端发了什么

`fronted/src/views/login/index.vue`：

```typescript
const response = await register({
  username: form.username,    // 表单输入
  email: form.email,
  password: form.password,
});
```

`fronted/src/api/auth.ts`：

```typescript
export const register = (data: RegisterRequest): Promise<AuthResponse> => {
  return request.post("/auth/register", data);
};
```

**实际发出去的 HTTP 请求：**

```http
POST /api/auth/register HTTP/1.1
Content-Type: application/json

{
  "username": "alice",
  "email": "alice@example.com",
  "password": "secret123"
}
```

> 注意：**没有 `Authorization` 头**。这是公开接口，前端此时还没 token。
> `utils/request.ts` 的请求拦截器会检查 `if (userStore.token)`，没 token 就跳过。

### 3.2 后端 Controller 收到什么

`auth.controller.ts`：

```typescript
@Controller('auth')                    // → 路径前缀 /api/auth
export class AuthController {
  constructor(private readonly authService: AuthService) {}

  @Post('register')
  register(@Body() dto: RegisterDto): Promise<AuthResult> {
    //              ↑ 关键：声明了 DTO 类，ValidationPipe 会自动校验
    return this.authService.register(dto);
  }
}
```

- `@Controller('auth')` + `setGlobalPrefix('api')` → 完整路径 `POST /api/auth/register`
- `@Body() dto: RegisterDto` → **这一行触发了自动校验**

### 3.3 ValidationPipe 怎么校验

`RegisterDto` 的规则：

```typescript
export class RegisterDto {
  @IsString()
  @IsNotEmpty()
  username: string;

  @IsEmail()
  @IsNotEmpty()
  email: string;

  @IsString()
  @IsNotEmpty()
  @MinLength(6)
  password: string;
}
```

**校验流程：**

```
前端发来的 body（原始）
  { username: "alice", email: "alice@example.com", password: "secret123" }
      ↓
① 逐个字段检查装饰器规则
   username: 是 string ✓ 非空 ✓
   email:    是 string ✓ 像邮箱 ✓
   password: 是 string ✓ 非空 ✓ 长度 6 ≤ 6 ✓
      ↓
② 检查 DTO 里没声明的字段（whitelist: true）
   如果前端传了 { ..., "role": "admin" } → 删掉 role
      ↓
③ 转成 RegisterDto 的实例（transform: true）
   dto instanceof RegisterDto === true
      ↓
全部通过 → 调 authService.register(dto)
```

**不通过就立刻返回 400，请求根本到不了 Service。**

`ValidationPipe` 内部抛出的 `message` 是**数组**，但经过全局异常过滤器（§4.4）后，
对外返回的 `message` 会被用「；」拼成**一个字符串**，并补上 `path` / `timestamp`：

```json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "email must be an email；password must be longer than or equal to 6 characters",
  "path": "/api/auth/register",
  "timestamp": "2026-10-09T08:58:00.000Z"
}
```

### 3.4 Service 做了什么（4 步）

`auth.service.ts`：

```typescript
async register(dto: RegisterDto): Promise<AuthResult> {
  // ① 查邮箱有没有被注册过
  const existingEmail = await this.prisma.user.findUnique({ where: { email: dto.email } });
  if (existingEmail) throw new ConflictException('该邮箱已被注册');   // 409

  // ② 查用户名有没有被占用
  const existingUsername = await this.prisma.user.findUnique({ where: { username: dto.username } });
  if (existingUsername) throw new ConflictException('该用户名已被占用'); // 409

  // ③ ★ 密码哈希 —— 明文在这一行之后就消失了
  const passwordHash = await bcrypt.hash(dto.password, 10);

  // ④ 插入用户
  const user = await this.prisma.user.create({
    data: { username: dto.username, email: dto.email, passwordHash },
  });

  // ⑤ 签发 JWT
  return this.buildAuthResult(user);
}
```

### 3.5 ★ 为什么密码要哈希？

```
用户输入 "123456"
    ↓  bcrypt.hash("123456", 10)
数据库里存 "$2b$10$WPdBPpJ0sbdbNEb76rM3F.VPQZ69Wr..."   ← 一长串乱码
```

**为什么不能用 MD5/SHA256 直接哈希？**

因为它们**太快**。现代显卡每秒能算几十亿次 MD5，一份 10 亿条的彩虹表几秒就撞完了。

**bcrypt 的三个特性：**

| 特性 | 做了什么 | 防什么 |
|------|---------|--------|
| **不可逆** | 数学上无法从哈希反推密码 | 数据库泄露也拿不到密码 |
| **自带盐（salt）** | 每个哈希前 22 字符就是随机盐 | 防止彩虹表：两个相同密码的哈希不同 |
| **故意慢（cost=10）** | 每次算要几十毫秒 | 暴力破解成本被放大几千倍 |

`bcrypt.hash(明文, 10)` 的 `10` 是 **salt rounds**（计算成本）。
每加 1，计算量翻倍，耗时也翻倍。10 是「用户体感可接受」和「安全」的平衡点。
一般建议 10~12。

> **验证时**用 `bcrypt.compare(明文, 存的哈希)`：
> 它会用哈希里记录的盐重新算一遍，再比对。

### 3.5.1 ★ 本项目有「两套」敏感数据保护，别搞混

认证这一层看起来只有密码，其实后端有**两类**敏感数据，保护手段**完全不同**：

| 敏感数据 | 存哪张表 | 字段 | 保护方式 | 能不能还原明文 |
|---------|---------|------|---------|--------------|
| **用户密码** | `User` | `passwordHash` | **单向哈希**（bcrypt，cost=10） | ❌ 永远不能 |
| **用户自带的 API Key** | `LlmProviderConfig` | `encryptedApiKey` | **对称加密**（AES-256-GCM） | ✅ 能，调模型时必须还原 |

**为什么 API Key 不能像密码那样哈希？**

因为密码只需要「验证是不是同一个」，而 API Key 是**要拿去用**的——
后端调 DeepSeek/OpenAI 时，必须把 `sk-xxxx` 原样放进 `Authorization` 请求头。
如果哈希了，就再也还原不出明文，也就没法调模型了。
所以它必须是**可逆的对称加密**，而不是哈希。

> 一句话记忆：**密码只需「对答案」→ 哈希；API Key 需要「拿出来用」→ 加密。**

**AES-256-GCM 怎么存？** 看 `common/crypto/encryption.service.ts`：

```typescript
// 密文格式：base64(iv) : base64(authTag) : base64(ciphertext)
// 例：  "aB3x...==" + ":" + "9Kp...==" + ":" + "Zx1...=="
encrypt(plaintext: string): string {
  const iv = randomBytes(12);                                   // ① 每次加密随机 12 字节 IV
  const cipher = createCipheriv('aes-256-gcm', this.key, iv);
  const encrypted = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
  const authTag = cipher.getAuthTag();                          // ② GCM 的「防篡改标签」
  return [iv.toString('base64'), authTag.toString('base64'), encrypted.toString('base64')].join(':');
}
```

三个关键点：

- **IV 每次都随机**（`randomBytes(12)`）→ 同一把 Key 加密两次，密文也不同，防「相同明文=相同密文」的比对攻击。
- **`authTag`（认证标签）** 是 GCM 相比老式 CBC 的核心优势：解密时若密文被篡改过一个字节，`decipher.final()` 会**直接抛错**，而不是解出一段垃圾。
- **密钥从哪来？** 优先级 `LLM_CONFIG_ENCRYPTION_KEY` → `JWT_SECRET` → 开发兜底常量，最后统一 `sha256(source)` 压成 32 字节（AES-256 要求）：
  ```typescript
  const source = process.env.LLM_CONFIG_ENCRYPTION_KEY || process.env.JWT_SECRET || 'dev-only-insecure-key-change-me';
  this.key = createHash('sha256').update(source).digest();
  ```
  没配 `LLM_CONFIG_ENCRYPTION_KEY` 时会在启动日志里 `warn`。**生产环境必须单独配一个 32 字节随机串**，不要蹭 `JWT_SECRET`。

**返回给前端时还要再脱敏一次**：即使密文存在库里，接口也**从不返回密文**，只返回 `maskApiKey()` 生成的预览：

```typescript
maskApiKey('sk-abcdefghijklmnopqrstuvwxyz1234')  // → "sk-a****1234"
maskApiKey('abcdef')                             // → "****"   （≤8 位直接全遮）
maskApiKey(null)                                 // → null
```

所以前端「模型供应商」页面看到的永远是 `sk-a****1234` 这种样子，明文只在**服务端内存里**短暂存在。
（这一整套机制的完整用法在第 10 篇《大模型接入与模型管理》里展开。）

### 3.6 后端返回什么

```typescript
private async buildAuthResult(user: User): Promise<AuthResult> {
  const payload: JwtPayload = {
    sub: user.id,            // ★ Subject，JWT 规范里表示「主体是谁」
    email: user.email,
    username: user.username,
  };
  return {
    user: this.toPublicUser(user),                        // 脱敏
    accessToken: await this.jwtService.signAsync(payload),  // 签名
  };
}

private toPublicUser(user: User): PublicUser {
  const { passwordHash: _passwordHash, ...result } = user;   // ★ 解构丢弃
  return result;
}
```

**实际返回的 JSON：**

```json
{
  "user": {
    "id": "9f8a1b2c-3d4e-5f60-7182-93a4b5c6d7e8",
    "username": "alice",
    "email": "alice@example.com",
    "avatar": null,
    "status": "OFFLINE",
    "createdAt": "2026-09-30T08:15:00.000Z",
    "updatedAt": "2026-09-30T08:15:00.000Z"
  },
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiI5ZjhhMWIyYy4zZDRlLTVmNjAtNzE4Mi05M2E0YjVjNmQ3ZTgiLCJlbWFpbCI6ImFsaWNlQGV4YW1wbGUuY29tIiwidXNlcm5hbWUiOiJhbGljZSIsImlhdCI6MTc2NDQ5MTQwMCwiZXhwIjoxNzY5NTQxNDQwMH0.4K3m2..."
}
```

**两个关键点：**

1. **`toPublicUser` 为什么要丢掉 `passwordHash`？**
   就算哈希不可逆，也能离线暴力破解。**不给攻击者任何可乘之机**。
   注释里的 `_passwordHash` 带下划线是告诉 TypeScript「这变量故意不用，别报错」。

2. **JWT 的三段结构**（看懂它你就懂 JWT 了）：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9   .  eyJzdWIiOiI5...f6d7e8...   .  4K3m2...8xQ
└──────────┬──────────┘                  └──────────┬──────────┘            └─────┬─────┘
         头 Header                        载荷 Payload                      签名 Signature
       {"alg":"HS256",                   {"sub":"9f8a...","email":        用 JWT_SECRET
        "typ":"JWT"}                      "username":"alice",              对前两段
                                         "iat":1764491400,                 算出的 HMAC
                                         "exp":1769541400}                 指纹
```

| 段 | 内容 | 能不能解密看？ |
|----|------|-------------|
| 头 | 算法说明（HS256） | Base64，**直接可解** |
| 载荷 | 用户 ID、邮箱、用户名、签发时间、过期时间 | Base64，**直接可解，没有加密** |
| 签名 | 私章指纹 | 无法伪造 |

> **⚠️ 重要**：JWT 的载荷是**明文**（只是 Base64 编码，不是加密）！
> 任何人都能解开看你的邮箱和用户 ID。
> JWT 保证的是**「不是我签的我不认」**，不是**「内容别人看不到」**。
> 所以**绝不要往 JWT 里放密码、身份证号等敏感信息**。

签名机制：`HMAC-SHA256(头.载荷, JWT_SECRET)`。
后端验签时用同一个 `JWT_SECRET` 重算一遍，对得上就说明没被篡改。
**别人不知道 `JWT_SECRET`，所以伪造不出来。**

## 4. 登录接口：`POST /api/auth/login`

### 4.1 前端发了什么

```typescript
const response = await login({
  email: form.email,
  password: form.password,
});
// 注意：没有 username！登录只用邮箱 + 密码
```

```http
POST /api/auth/login HTTP/1.1
Content-Type: application/json

{ "email": "alice@example.com", "password": "secret123" }
```

### 4.2 后端处理

`LoginDto` 只有两个字段（对比注册少了 `username`）：

```typescript
export class LoginDto {
  @IsEmail()
  @IsNotEmpty()
  email: string;

  @IsString()
  @IsNotEmpty()
  password: string;
}
```

`AuthService.login`：

```typescript
async login(dto: LoginDto): Promise<AuthResult> {
  // ① 按邮箱查用户
  const user = await this.prisma.user.findUnique({ where: { email: dto.email } });
  if (!user) throw new UnauthorizedException('邮箱或密码不正确');     // 401

  // ② 比对密码（bcrypt.compare 会用哈希里记录的盐重算）
  const valid = await bcrypt.compare(dto.password, user.passwordHash);
  if (!valid) throw new UnauthorizedException('邮箱或密码不正确');   // 401

  // ③ 签发 JWT
  return this.buildAuthResult(user);
}
```

**注意 ①② 两次的错误消息完全一样：`'邮箱或密码不正确'`。**

这是**刻意的安全设计**。如果分两种报错：

```
"邮箱不存在"        → 攻击者能拿邮箱列表探测哪些账号注册过
"密码错误"          → 攻击者知道邮箱肯定存在，就专心爆破密码
统一报错            → 攻击者无法区分，只能两种都试，成本翻倍
```

> 同样的道理，注册接口的报错就**分开了**（`该邮箱已被注册` / `该用户名已被占用`），
> 因为注册时用户本来就该知道自己的邮箱有没有注册过。
>
> 另外还有一层兜底：全局异常过滤器（见下一节）会把**所有 401 的 message 强制改写成
> `'邮箱或密码不正确'`**，即使 Service 里抛的是别的文案，前端也拿不到内部细节。

### 4.3 前端拿到 token 后做了什么

`views/login/index.vue`：

```typescript
const response = isRegister.value
  ? await register({ username: form.username, email: form.email, password: form.password })
  : await login({ email: form.email, password: form.password });

userStore.setToken(response.accessToken);   // → 内存 ref + localStorage
userStore.setUserInfo(response.user);       // → 内存 ref（不持久化！）

const redirect = (route.query.redirect as string) || "/chat";
await router.push(redirect);
```

`stores/user.ts` 的「双写」：

```typescript
const token = ref<string>(localStorage.getItem("token") || "");   // ① 启动时从 localStorage 恢复

const setToken = (newToken: string) => {
  token.value = newToken;                          // ② 写内存（响应式，界面立刻更新）
  localStorage.setItem("token", newToken);         // ③ 写 localStorage（刷新不丢）
};
```

| 存哪 | 作用 | 缺点 |
|------|------|------|
| `ref` 内存 | 组件能**响应式**读到，登录后界面立刻变 | 刷新页面就没了 |
| `localStorage` | 刷新页面后 JS 内存清空，但浏览器本地还存着 | 不安全（任何脚本都能读） |

**⚠️ 一个已知缺陷**：`userInfo` **只存内存不持久化**。
所以刷新页面后 token 还在（还是「登录」状态），
但顶栏头像会退回显示「用户」，因为 `userInfo` 是 `null`。
`api/auth.ts` 里有个 `getCurrentUser()` 调 `GET /api/auth/me` 就是为了补这个洞，
但**目前没有任何地方调用它**。这是个很好的练手项目。

### 4.4 ★ 全局统一错误格式：`AllExceptionsFilter`

前面看到的 `ConflictException('该邮箱已被注册')`、`UnauthorizedException('邮箱或密码不正确')`
都是**在 Service 里抛异常**。但抛出去的异常最终变成什么 JSON，是由一个**全局异常过滤器**
决定的：`backend/src/common/filters/all-exceptions.filter.ts`。

它在 `main.ts` 里注册（`app.useGlobalFilters(new AllExceptionsFilter())`），
所以**整个后端所有错误**都走它，格式统一成：

```json
{
  "statusCode": 409,
  "error": "Conflict",
  "message": "该邮箱已被注册",
  "path": "/api/auth/register",
  "timestamp": "2026-10-09T08:58:00.000Z"
}
```

它做了三件事：

| # | 做什么 | 代码位置 |
|---|--------|---------|
| ① | **统一格式**：不管什么异常，都补上 `path` 和 `timestamp` | `response.status(...).json({...})` |
| ② | **处理校验错误**：ValidationPipe 抛的 `message` 是数组，这里用 `；` 拼成一句 | `Array.isArray(obj.message) ? ...` |
| ③ | **401 脱敏**：所有 401 的 message 一律改写成「邮箱或密码不正确」 | `if (statusCode === UNAUTHORIZED) message = '邮箱或密码不正确'` |

> **为什么前端不用逐个接口写错误提示？** 因为错误响应里的 `message` 已经是统一的中文，
> 前端 `utils/request.ts` 的响应拦截器直接把它弹出来即可（见第 5 篇第 4 节）。

## 5. ★ 之后每一次请求：Guard 怎么拦、怎么验

### 5.1 Guard（保安）：`jwt-auth.guard.ts` 全文

```typescript
import { Injectable } from '@nestjs/common';
import { AuthGuard } from '@nestjs/passport';

@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {}
```

**只有 3 行。** 全部逻辑在 Passport 里。写上 `@UseGuards(JwtAuthGuard)`
就是告诉框架「这个接口要验通行证，验不过直接 401」。

### 5.2 Strategy（验卡规则）：`jwt.strategy.ts`

```typescript
@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  //                          ★ 注入了 PrismaService —— 这是"要查库"的信号
  constructor(private readonly prisma: PrismaService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),  // ① 从哪读卡
      ignoreExpiration: false,                                   // ② 过期就拒
      secretOrKey: process.env.JWT_SECRET,                       // ③ 用哪个私章验
    });
  }

  async validate(payload: JwtPayload): Promise<JwtUser> {        // ④ 验签通过后做什么
    // ★ 防御：确保 token 里的 user.id 在数据库中真实存在
    const user = await this.prisma.user.findUnique({
      where: { id: payload.sub },
      select: { id: true, email: true, username: true },
    });
    if (!user) {
      throw new UnauthorizedException('用户不存在，请重新登录');
    }
    return { id: user.id, email: user.email, username: user.username };
  }
}
```

| 行 | 干什么 |
|----|--------|
| ① | 从请求头 `Authorization: Bearer eyJ...` 里把 token 抠出来（`Bearer ` 后面那串） |
| ② | 检查 `exp`（过期时间）字段，过了就拒 |
| ③ | 用 `.env` 里的 `JWT_SECRET` 重算签名，对不上就拒 |
| ④ | ★ 验签成功后，`validate()` 的返回值会被 **NestJS 自动挂到 `request.user`** |

### 5.3 ★ 一个安全细节：`validate()` 查不查数据库？

> **⚠️ 本节此前写的是「不查」，与代码不符，现已更正。**

**查。** 而且**每个带 JWT 的请求都会查一次**。

代码证据在 `backend/src/auth/strategies/jwt.strategy.ts:20-40`：
构造函数注入了 `PrismaService`，`validate()` 里执行 `findUnique({ where: { id: payload.sub } })`，
查不到直接抛 `UnauthorizedException('用户不存在，请重新登录')`。
返回给 `request.user` 的是**数据库查出来的那一条**，不是 token 载荷里的内容。

**这带来什么实际后果？**

| 场景 | 纯无状态（不查库） | 本项目（查库） |
|------|------------------|---------------|
| 用户被删除 | 旧 token 到过期前仍能用 | ✅ 下一个请求立刻 401「用户不存在，请重新登录」 |
| 数据库被 reset（清库重来） | token 看着合法，但外键操作全部失败（500） | ✅ 直接 401，报错清晰 |
| 用户改了邮箱/用户名 | `request.user` 还是签发时的旧值，数据不一致 | ✅ 每次拿到最新值 |
| 性能 | 验签即可，零查询 | ⚠️ **每个受保护接口多一次 DB 查询** |

代码里那句注释写得很清楚：

```
// 防御：确保 token 中的 user.id 在数据库中真实存在
// 防止 DB reset 后旧 token 继续通过鉴权但外键操作失败
```

> **这不是「无状态 vs 有状态」的取舍，而是本项目主动做的一次trade-off**：
> 用「每次请求一次主键查询」的代价，换掉「删号/清库后 token 仍能通行」这个更麻烦的隐患。
> 主键查询本身极快（有索引），对中型项目这个代价完全可以接受。

另外 `GET /api/auth/me` 会**再**查一次库，而且查的是全字段（不带 `select`）：

```typescript
async getMe(user: JwtUser): Promise<PublicUser> {
  const dbUser = await this.prisma.user.findUnique({ where: { id: user.id } });
  if (!dbUser) throw new UnauthorizedException('User not found');   // 这里其实走不到了
  return this.toPublicUser(dbUser);                                  // 解构剥掉 passwordHash
}
```

> 注意：因为 `validate()` 已经查过一次，这里的 `if (!dbUser)` 实际上**永远不会触发** —— 用户不存在早在守卫阶段就被拦了。
> 真正起作用的脱敏是 `toPublicUser()`（解构丢弃 `passwordHash`）。

### 5.4 `@CurrentUser()`：从 request.user 里取值

```typescript
export const CurrentUser = createParamDecorator(
  (data: string | undefined, ctx: ExecutionContext) => {
    const request = ctx.switchToHttp().getRequest();
    const user = request.user;                    // ← Strategy.validate() 挂上去的
    return data ? user?.[data] : user;            // @CurrentUser('id') 或 @CurrentUser()
  },
);
```

**用法（本项目全部用不带参数的版本）：**

```typescript
@Get(':id')
findOne(
  @CurrentUser() user: JwtUser,                              // ← 拿到 { id, email, username }
  @Param('id', ParseUUIDPipe) id: string,
) {
  return this.workspacesService.findOne(user.id, id);        // ← 只把 id 传给 Service
}
```

### 5.5 ★ 最重要的一条安全原则

> **后端永远用「JWT 里的 id」当操作人，绝不信前端传来的任何 userId。**

因为前端传来的 `userId` 是攻击者可以随便改的。
`@CurrentUser()` 里的 id 是用 `JWT_SECRET` 签过名的，攻击者改不了。

**所以本项目所有 Service 方法的第一个参数都是 `userId: string`，
而且一定来自 `@CurrentUser()`。** 你可以打开任何一个 controller 检查，没有例外。

### 5.6 完整走一遍：`GET /api/workspaces`

```
浏览器：GET /api/workspaces
        Headers: { Authorization: "Bearer eyJhbGciOi..." }

  ↓
JwtAuthGuard 拦截
  ↓
JwtStrategy.validate(payload)
  ├─ 从 Authorization 头抠出 token        ✓ 找到了
  ├─ 检查 exp（7 天后过期）                 ✓ 没过期
  ├─ HMAC(payload, JWT_SECRET) 验签        ✓ 签名对
  ├─ ★ prisma.user.findUnique({ id: payload.sub })   ✓ 用户还在（不在就 401）
  └─ 返回 { id: "9f8a...", email, username }（★ 来自数据库，不是来自 token）
  ↓
NestJS 把它挂到 request.user
  ↓
WorkspacesController.findAll(@CurrentUser() user)
  ↓
WorkspacesService.findAll(user.id)          ← user.id 来自 JWT
  ↓
prisma.workspace.findMany({
  where: { OR: [ { ownerId: user.id },                    // 我是老板？
                   { members: { some: { userId: user.id } } } ] }  // 或是成员？
  orderBy: { createdAt: 'desc' },
  select: workspaceSelection,
})
  ↓
返回 JSON 数组，浏览器渲染成卡片
```

**每一步的结果：**

| 失败情况 | HTTP 状态码 | 响应体 | 前端表现 |
|---------|------------|--------|---------|
| 没带 token | **401** | `{"message":"Unauthorized","statusCode":401}` | 拦截器弹「登录过期」，清 token，跳 `/login` |
| token 格式错 | **401** | 同上 | 同上 |
| token 签名错（被篡改） | **401** | 同上 | 同上 |
| token 过期 | **401** | 同上 | 同上 |
| token 有效但该接口参数不合法 | **400** | `{"message":[...], "error":"Bad Request"}` | 页面显示错误文字，**不跳登录** |
| token 有效但权限不够 | **403** | `{"message":"...","statusCode":403,"error":"Forbidden"}` | 页面显示错误，**不跳登录** |

> **401 vs 403 一定要分清**：
> - **401 Unauthorized** = 「你是谁？」（认证 Authentication 失败）
> - **403 Forbidden** = 「我知道你是谁，但你不配」（授权 Authorization 失败）

## 6. 权限模型：owner 还是 member？

认证解决「你是谁」，授权解决「你能干嘛」。

### 6.1 本项目的三级权限模型

| 资源 | 规则 | 代码在哪 |
|------|------|---------|
| **Workspace** 读 | owner **或** member | `OR: [{ ownerId }, { members: { some } }]` |
| **Workspace** 改/删 | **仅 owner** | `assertOwner()` |
| **Workflow** 读/写 | 该空间的 **member**（含 owner） | `assertWorkspaceMember()` / `where: { workspace: { members: { some } } }` |
| **KnowledgeBase** | **仅 owner**（独立资源，不挂 workspace） | `assertOwner()` / `assertOwnerExists()` |
| **Document** | 所属知识库的 **owner** | `assertKbOwner()` / `assertDocumentOwner()` |
| **`/workflow/run*`** | ⚠️ **任何人** | 根本没加 Guard |

### 6.2 三个权限校验函数的实现

**① `WorkspacesService.assertOwner`（仅老板）**

```typescript
private async assertOwner(userId: string, id: string) {
  const workspace = await this.prisma.workspace.findUnique({
    where: { id },
    select: { ownerId: true },
  });
  if (!workspace) throw new NotFoundException('Workspace not found');       // 404
  if (workspace.ownerId !== userId) throw new ForbiddenException('Only the workspace owner can modify it');  // 403
}
```

**② `WorkflowsService.assertWorkspaceMember`（老板或成员）**

```typescript
private async assertWorkspaceMember(userId: string, workspaceId: string) {
  const workspace = await this.prisma.workspace.findFirst({
    where: {
      id: workspaceId,
      OR: [
        { ownerId: userId },                            // 条件 A：我是老板
        { members: { some: { userId } } },              // 条件 B：成员表里有我
      ],
    },
    select: { id: true },
  });
  if (!workspace) throw new ForbiddenException('You do not have access to this workspace');   // 403
}
```

**③ `KnowledgeService.assertOwnerExists`（知识库仅 owner）**

```typescript
private async assertOwnerExists(userId: string, id: string) {
  const kb = await this.prisma.knowledgeBase.findUnique({
    where: { id },
    select: { ownerId: true },
  });
  if (!kb) throw new NotFoundException('Knowledge base not found');    // 404
  if (kb.ownerId !== userId) throw new ForbiddenException('You do not own this knowledge base');  // 403
}
```

**★ 值得学的两个设计：**

**① 「不存在」返回 404，「不是你的」返回 403**

```
assertOwner 的判断顺序：
  1. 空间都不存在      → 404
  2. 存在但 ownerId ≠ 我 → 403
```

**为什么不直接 403？** 因为 404 会泄露信息：
如果不存在返回 403、不是你的返回 403，你就知道「这个 ID 确实存在于数据库」。
返回 404 等于说「我什么都不知道」。

**② 权限判断放在 Service，不放 Controller**

```typescript
// Controller 只负责：取参数 → 调 Service
@Post('workspaces/:workspaceId/workflows')
create(
  @CurrentUser() user: JwtUser,
  @Param('workspaceId', ParseUUIDPipe) workspaceId: string,
  @Body() dto: CreateWorkflowDto,
) {
  return this.workflowsService.create(user.id, workspaceId, dto);
  //                                 ↑ 权限校验藏在 Service 内部
}
```

好处：任何人调这个 Service，权限自动生效，**不可能忘记加**。
如果放 Controller，早晚会有人新加一个接口忘贴。

## 7. ★ 前端 token 的三种传递方式（本项目实际有 3 种）

这是很多教程不讲的细节，但本项目**三处代码三种写法**：

| # | 位置 | 怎么带 token | 走不走 axios 拦截器 |
|---|------|------------|------------------|
| 1 | `api/*.ts` 里所有常规请求 | **自动带** | ✅ 走（`utils/request.ts`） |
| 2 | `api/workflow.ts` 的 `runWorkflowStream` | **手写 header** | ❌ 不用（原生 `fetch`） |
| 3 | `api/knowledge.ts` 的 `uploadDocument` | **手写 header** | ❌ 不用（原生 `fetch`） |

**① 常规请求（走拦截器）**

```typescript
// utils/request.ts
request.interceptors.request.use((config) => {
  const userStore = useUserStore();
  if (userStore.token) {
    config.headers.Authorization = `Bearer ${userStore.token}`;   // ← 每次请求自动加
  }
  return config;
});
```

所以 `api/auth.ts` 写起来很短：

```typescript
export const getWorkspaces = () => request.get("/workspaces");   // 没提 token，但自动带了
```

**② SSE 流式请求（手写）**

```typescript
// api/workflow.ts
const response = await fetch("/api/workflow/run/stream", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    ...(userStore.token ? { Authorization: `Bearer ${userStore.token}` } : {}),   // ← 手写
  },
  body: JSON.stringify(data),
});
```

**为什么必须手写？** 因为 axios 拦截器只在 axios 请求里生效。
这里用的是浏览器原生 `fetch`，拦截器管不到。（axios 不支持流式读取，第 5 篇细讲。）

**③ 文件上传（手写）**

```typescript
// api/knowledge.ts
const response = await fetch(`/api/knowledge-bases/${kbId}/documents`, {
  method: "POST",
  headers: userStore.token ? { Authorization: `Bearer ${userStore.token}` } : {},
  body: formData,     // ⚠️ 不能设 Content-Type！浏览器的 boundary 边界要自动生成
});
```

> **为什么上传不设 `Content-Type`？**
> `FormData` 上传时，浏览器会自己生成一个带随机边界的 `Content-Type: multipart/form-data; boundary=----xxx`。
> 如果你手动设成 `application/json`，boundary 就丢了，后端根本解析不出哪个是文件。
> **这是新手最常见的上传 bug。**

## 9. 本篇小结（速查表）

| 问题 | 答案 |
|------|------|
| **前端注册发什么？** | `{ username, email, password }` |
| **后端怎么收？** | `@Body() dto: RegisterDto` → `ValidationPipe` 按装饰器逐条校验 |
| **后端怎么处理？** | 查重（409）→ `bcrypt.hash(密码, 10)` → insert → 签 JWT |
| **返回什么？** | `{ user: { id, username, email, avatar, status, createdAt, updatedAt }, accessToken }`（**哈希被剥掉了**） |
| **为什么不存明文密码？** | 库泄露就全完了。bcrypt 不可逆 + 带盐 + 故意慢 |
| **API Key 为什么不用 bcrypt？** | 密码只需「对答案」，API Key 要「拿出来调模型」→ 必须**可逆**，所以用对称加密 AES-256-GCM |
| **API Key 怎么存？** | `encryptedApiKey` = `base64(iv):base64(authTag):base64(密文)`；IV 每次随机，authTag 防篡改 |
| **加密密钥从哪来？** | `LLM_CONFIG_ENCRYPTION_KEY` → `JWT_SECRET` → 开发兜底，再 `sha256` 压成 32 字节。**生产要单独配** |
| **前端能看到 API Key 明文吗？** | 看不到。接口只返回 `maskApiKey()` 的预览，如 `sk-a****1234` |
| **JWT 三段是什么？** | 头（算法）+ 载荷（用户信息，**明文可解**）+ 签名（HMAC 防伪） |
| **每次请求怎么带 token？** | 请求头 `Authorization: Bearer <token>` |
| **Guard 干了什么？** | 抠 token → 验签名 → 查过期 → 通过则把用户挂到 `request.user` |
| **`validate()` 查库吗？** | ★ **查**，每次都查（`findUnique` 主键）。好处是删号/清库后旧 token 立即失效；代价是每请求多一次 DB 查询 |
| **`@CurrentUser()` 是什么？** | 从 `request.user` 取当前用户。**这是唯一可信的身份来源** |
| **错误响应统一在哪？** | 全局异常过滤器 `AllExceptionsFilter`（`main.ts` 注册）：统一 `{ statusCode, error, message, path, timestamp }`，401 一律脱敏成「邮箱或密码不正确」 |
| **401 vs 403？** | 401 = 你是谁（认证失败）；403 = 你不能（权限不足） |
| **权限模型？** | Workspace 读=owner或member，改删=仅owner；Workflow=member；知识库=仅owner |
| **⚠️ 最大漏洞？** | `/api/workflow/run` 和 `/run/stream` **完全没鉴权**，任何人能烧你的 Ollama 算力 |
