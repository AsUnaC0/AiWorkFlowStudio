# AI WorkFlow Studio 学习指南
## 第 10 篇：大模型接入与模型管理 —— 从「写死 Ollama」到「用户自带模型」

> 本篇是**后续新增的专题**（编号接在附录 09 之后）。它讲的是最近一次大改造：
> 项目从「只能用本地 Ollama」升级成「用户可以在页面上自己添加任意大模型（OpenAI / DeepSeek / 任意 OpenAI 兼容网关），API Key 加密存储」。
>
> 读完你会明白：
> ① 为什么要做「模型管理」；② 两张新表存了什么；③ API Key 是怎么加密的；
> ④ 一个「Provider 工厂」如何把 4 种厂商统一成一套接口；⑤ **15 个**接口怎么用；⑥ ★ 模型能力体系与「验证模型」实测维度；
> ⑥ Agent / 工作流 / 知识库是怎么「按用户所选模型」动态调用的。

## 1. 心智模型：为什么要「模型管理」？

### 1.1 改造前：模型名写死在代码/配置里

在改造之前，项目里调用大模型的路径只有一条：

```
LLM 节点 / Agent / 知识库向量化
        ↓
   AIService（门面）
        ↓
   AI_PROVIDER 令牌（写死绑定 OllamaProvider）
        ↓
   http://localhost:11434/api/chat     ← 永远只连本地 Ollama
```

这带来三个问题：

| 问题 | 表现 |
|------|------|
| **只能用本地模型** | 想用 DeepSeek / GPT 得改代码、重新部署 |
| **密钥没地方放** | 就算加了云端厂商，API Key 存哪？明文存数据库太危险 |
| **模型名散落各处** | `qwen2.5:7b` 这个字符串出现在 Agent、LLM 节点、知识库……改一处漏一处 |

### 1.2 改造后：多了一层「模型注册表」

现在多了一整层「模型管理」：

```
用户在 /providers 页面添加「我的 DeepSeek」
        ↓
  LlmProviderConfig 表（存厂商 + 地址 + 加密后的 Key）
        ↓
  LlmModel 表（存该厂商下可用的模型，如 deepseek-chat）
        ↓
  Agent / LLM 节点 / 知识库  只记一个 llmModelId
        ↓
  运行时：LlmConfigService.resolveModelRuntime(llmModelId)
        ↓
  解密 Key → Provider 工厂造出对应的 AiProvider → 发请求
```

**一句话记住**：`llmModelId` 是「指向某个用户自建模型的指针」。
有它 → 用用户自己的模型；没有它 → 回退到老的本地 Ollama 行为（**完全向后兼容**）。

### 1.3 「回退」是这套设计的灵魂

项目里到处都能看到这个模式：

```typescript
// agent.service.ts / llm.executor.ts / embedding.service.ts 都是这个套路
let backend: AiProvider = this.aiService.getProvider();   // ① 默认：全局 Ollama
let model = agent.model;
if (agent.llmModelId) {                                   // ② 有自建模型就用它
  const runtime = await this.llmConfigService.resolveModelRuntime(agent.llmModelId);
  backend = runtime.provider;
  model = runtime.modelId;
}
```

> **为什么这样设计？** 因为「用户没配任何模型」是常态（尤其刚 clone 项目的人）。
> 没有 `llmModelId` 时绝对不能报错，必须能像以前一样用本地 Ollama 跑通。

## 2. 数据库：两张新表

文件：`backend/prisma/schema.prisma`。全库从 **17 张表**增加到 **19 张**。

### 2.1 LlmProviderConfig（模型提供商连接配置）

```prisma
model LlmProviderConfig {
  id              String   @id @default(uuid())
  ownerId         String                       // ★ 用户私有，和 Skill/MCP 一样

  name            String                       // 用户自定义名称，如「我的 DeepSeek」
  provider        String                       // ollama | openai | deepseek | openai-compatible
  baseUrl         String?                      // API 根地址（可空，云端有默认值）

  encryptedApiKey String?                      // ★★ 加密后的 API Key（AES-256-GCM），绝不明文

  status          String   @default("UNKNOWN") // UNKNOWN / CONNECTED / ERROR / DISABLED
  lastError       String?                      // 最近一次连接测试的错误（不记录密钥）

  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt

  owner           User       @relation("LlmConfigOwner", fields: [ownerId], references: [id])
  models          LlmModel[]

  @@index([ownerId])
}
```

| 字段 | 为什么这么设计 |
|------|--------------|
| `ownerId` | 和 `Skill` / `McpServer` 同一套「owner 私有」模型：每个用户管自己的 Key |
| `provider` | 决定运行时用哪个 Provider 实现（工厂靠它 switch） |
| `baseUrl` | 允许自定义（走代理 / 自建网关）；为空时云端厂商取默认地址 |
| **`encryptedApiKey`** | ★ 关键：**永远不存明文**。字段名带 `encrypted` 就是提醒你它已加密 |
| `status` | 连接测试的结果。`DISABLED` 表示用户主动停用 |
| `lastError` | 记错误方便排障，但**只记 HTTP 状态/报错文本，绝不记密钥** |

### 2.2 LlmModel（提供商下的可选模型）

```prisma
model LlmModel {
  id           String   @id @default(uuid())
  configId     String                          // 属于哪个配置

  provider     String                          // 冗余存一份，查询不用连表

  modelId      String                          // ★ 真实模型 ID，如 deepseek-chat / gpt-4o-mini / qwen2.5:7b
  displayName  String?                         // 前端展示名（可空，为空用 modelId）

  capabilities String[] @default(["CHAT", "STREAM"])  // ★ 8 值：见下方表格（多选，非互斥）

  // ↓↓↓ 「模型能力体系」升级新增的 6 个字段
  inputModalities     String[] @default(["text"])  // 输入模态：text / image / audio
  outputModalities    String[] @default(["text"])  // 输出模态：text / image / audio
  embeddingDimensions Int?                         // 向量输出维度，由「验证模型」实测写入
  maxInputTokens      Int?                         // 上下文窗口上限（可选）
  isVerified          Boolean  @default(false)     // 是否跑过真实调用验证
  verifiedAt          DateTime?                    // 上次验证通过时间

  isDefault    Boolean  @default(false)        // 是否为用户默认模型（同一 owner 仅一个）
  enabled      Boolean  @default(true)         // 是否出现在模型选择器里

  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  config       LlmProviderConfig @relation(fields: [configId], references: [id], onDelete: Cascade)

  @@unique([configId, modelId])                 // 同一配置下模型不重复
  @@index([configId])
}
```

| 字段 | 说明 |
|------|------|
| `modelId` | **真实模型标识**，直接透传给厂商 API 的 `model` 字段 |
| `capabilities` | ★ **能力标签**（多选），选择器靠它过滤：对话（`CHAT`）/ 向量（`EMBEDDING`）… 共 **8 值**，见下表 |
| **`inputModalities` / `outputModalities`** | ★ 输入 / 输出模态：`text` / `image` / `audio`，独立于 capabilities |
| **`embeddingDimensions`** | ★ 向量输出维度，**默认 null**；由 `POST models/:id/verify` 真实调用实测后写入 |
| **`maxInputTokens`** | ★ 上下文窗口上限，可选 |
| **`isVerified` / `verifiedAt`** | ★ 是否跑过验证 / 上次验证通过时间 |
| `isDefault` | 「默认模型」，同一个用户只能有一个（`setDefaultModel` 用事务保证） |
| `enabled` | 关掉后不再出现在选择器里，但记录还在 |
| `onDelete: Cascade` | 删配置 → 其下模型一起删 |

**★ `capabilities` 的 8 个取值（`MODEL_CAPABILITIES`，多选非互斥）：**

| 值 | 含义 | 谁在消费 |
|---|---|---|
| `CHAT` | 单轮 / 多轮对话（`complete`） | 聊天、LLM 节点、`resolveUserDefaultChatModel()` |
| `STREAM` | 流式输出（`streamChat`） | 打字机效果 |
| `TOOLS` | 函数调用（`chatWithTools`） | Agent 工具调用、MCP |
| `EMBEDDING` | 文本向量化（`embedding`） | ★ 知识库向量化；`listModels('EMBEDDING')` 选择器 |
| `VISION` | 图像理解 | 多模态对话 |
| `REASONING` | 推理 / 慢思考 | 需要 CoT 的场景 |
| `RERANK` | 重排序 | 检索结果 rerank |
| `IMAGE_GENERATION` | 文生图 | 图片生成 |

> **⚠️ 为什么能力要用数组而不是枚举？** 因为一个模型可能同时具备多种能力
> （比如某个兼容网关既支持对话又支持流式还支持工具调用，还可以是 `['CHAT','STREAM','TOOLS','VISION','REASONING']`）。
> 数组让「一个模型打多个标签」变得自然，查询时用 `capabilities: { has: 'CHAT' }`。
>
> **⚠️ 模态为什么独立于能力？** 「能看图」（VISION）说的是能力，「输入接受 image」说的是接口形态，
> 两者不是一回事。分开建模后，前端可以分别提示「这个模型支持上传图片」和「这个模型是推理模型」。

### 2.3 两个「关联字段」（改的是老表）

除了两张新表，还通过迁移 `20261010140712_add_model_refs` 给两张老表各加了一列：

| 表 | 新列 | 含义 | 为空时 |
|----|------|------|--------|
| `Agent` | `llmModelId` | Agent 使用哪个自建模型 | 回退 `Agent.model`（本地 Ollama 模型名） |
| `KnowledgeBase` | `embeddingLlmModelId` | 知识库用哪个自建向量模型 | 回退 `embeddingModel`（本地 `nomic-embed-text`） |

```sql
-- migration: 20261010140712_add_model_refs
ALTER TABLE "Agent" ADD COLUMN "llmModelId" TEXT;
ALTER TABLE "KnowledgeBase" ADD COLUMN "embeddingLlmModelId" TEXT;
```

> ⚠️ 注意这两列**都没有外键约束**（不是 `@relation`）。它们是「软引用」——
> 指向 `LlmModel.id`，但删掉模型不会级联清空它们。运行时如果按 `llmModelId` 查不到模型，
> `resolveModelRuntime` 会抛错，调用方需要自己回退（当前 Agent 创建时会校验，运行时会走 `findUniqueOrThrow`）。

## 3. ★ API Key 加密：`EncryptionService`

文件：`backend/src/common/crypto/encryption.service.ts`

用户填的 API Key 是**敏感信息**，绝不能明文入库。项目用 **AES-256-GCM**（Node 内置 `crypto`，无需第三方库）做对称加密。

### 3.1 密钥从哪来？

```typescript
constructor() {
  const source =
    process.env.LLM_CONFIG_ENCRYPTION_KEY ||   // ① 首选：专门的加密密钥
    process.env.JWT_SECRET ||                  // ② 次选：JWT 密钥
    'dev-only-insecure-key-change-me';         // ③ 兜底：开发用常量（会打 warn）

  // SHA-256 摘要 → 固定 32 字节，满足 AES-256 密钥长度
  this.key = createHash('sha256').update(source).digest();
}
```

| 优先级 | 来源 | 适用 |
|--------|------|------|
| ① | `LLM_CONFIG_ENCRYPTION_KEY` | **生产环境必须配**（见第 1 篇 §3） |
| ② | `JWT_SECRET` | 没配上面那个时的临时回退 |
| ③ | 开发兜底常量 | 本地随便跑跑（启动时会打 warning） |

> **为什么要 `sha256` 一下？** AES-256 要求密钥正好 32 字节。
> 不管源字符串多长，`sha256` 都产出固定 32 字节，省去「补齐/截断」的麻烦。

### 3.2 加密 / 解密

```typescript
encrypt(plaintext: string): string {
  const iv = randomBytes(12);                              // ① 随机 12 字节 IV
  const cipher = createCipheriv('aes-256-gcm', this.key, iv);
  const encrypted = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
  const authTag = cipher.getAuthTag();                     // ② GCM 的认证标签
  return [
    iv.toString('base64'),
    authTag.toString('base64'),
    encrypted.toString('base64'),
  ].join(':');                                             // ③ 密文格式：iv:tag:data
}
```

**密文格式**：`base64(iv):base64(authTag):base64(ciphertext)`，用 `:` 分隔三段。

| 段 | 作用 |
|----|------|
| `iv` | 初始化向量。**每次加密都随机**，同一个 Key 加密两次结果不同（防「相同明文→相同密文」） |
| `authTag` | GCM 的认证标签。解密时校验，**密文被篡改会解密失败**（这是选 GCM 而不是 CBC 的原因） |
| `ciphertext` | 真正加密后的内容 |

`decrypt` 就是反过来：拆三段 → `createDecipheriv` → `setAuthTag` → 还原明文。密文格式不对会抛 `密文格式不正确`。

### 3.3 脱敏返回：`maskApiKey`

接口**永远不返回明文 Key**，而是返回脱敏预览：

```typescript
maskApiKey('sk-abcdefghijklmnopqrstuvwxyz1234')  // → 'sk-a****1234'
maskApiKey('abcdef')                              // → '****'（≤8 位直接全遮）
maskApiKey(null)                                  // → null
```

`LlmConfigService.toConfigView()` 在返回前做了两件事：
1. 把 `encryptedApiKey` 从对象里**剔除**（解构 `const { encryptedApiKey, ...rest } = config`）
2. 补两个字段给前端：`apiKeyMasked`（脱敏串）+ `hasApiKey`（是否已配置）

所以前端拿到的配置长这样：

```json
{
  "id": "...", "name": "我的 DeepSeek", "provider": "deepseek",
  "baseUrl": "https://api.deepseek.com/v1",
  "status": "CONNECTED",
  "apiKeyMasked": "sk-a****1234",
  "hasApiKey": true,
  "models": [ ... ]
}
```

> **一个安全细节**：`toConfigView` 里虽然先 `decrypt` 再 `mask`（为了拿到前 4 位/后 4 位），
> 但明文只在内存里存在一瞬间，**不会出现在任何响应里**。而且 `maskApiKey` 只留首尾 4 位，
> 中间用 `****` 盖住，即使日志泄露也拿不到完整 Key。

## 4. ★ Provider 工厂：一套接口，四种厂商

### 4.1 统一的「插座」：`AiProvider` 接口

文件：`backend/src/ai/ai-provider.interface.ts`

所有 Provider 都实现同一个接口，上层只认接口不认实现：

```typescript
export interface AiProvider {
  readonly name: string;                                    // 用于日志
  complete(prompt, options): Promise<ChatResult>;           // 单轮
  chat(messages, options): Promise<ChatResult>;             // 多轮
  streamChat(messages, options): AsyncGenerator<string>;    // 流式（逐 token）
  embedding(texts, options): Promise<EmbeddingResult>;      // 向量化
  chatWithTools(messages, options, tools): Promise<ToolChatResult>;  // 工具调用
  listModels?(): Promise<string[]>;                         // 列模型（可选）
}
```

> **注意 `listModels?` 带问号**：不是所有 Provider 都必须实现它。
> 调用方（连接测试）要写 `await provider.listModels?.() ?? []` 做兜底。

### 4.2 工厂函数：`createProvider`

文件：`backend/src/ai/providers/provider.factory.ts`

```typescript
export function createProvider(input: {
  provider: LlmProviderType;
  baseUrl?: string | null;
  apiKey?: string | null;
}): AiProvider {
  const { provider, baseUrl, apiKey } = input;
  switch (provider) {
    case 'ollama':
      return new OllamaProvider(baseUrl || undefined);
    case 'deepseek':
      return new DeepSeekProvider(baseUrl || undefined, apiKey || undefined);
    case 'openai':
      return new OpenAICompatibleProvider(baseUrl || DEFAULT_BASE_URL.openai, apiKey || undefined, 'openai');
    case 'openai-compatible':
      if (!baseUrl) throw new Error('openai-compatible 类型必须提供 baseUrl');
      return new OpenAICompatibleProvider(baseUrl, apiKey || undefined);
    default:
      throw new Error(`不支持的提供商类型: ${provider}`);
  }
}
```

| provider | 用哪个类 | 默认 baseUrl |
|----------|---------|-------------|
| `ollama` | `OllamaProvider` | `http://localhost:11434`（运行时取） |
| `openai` | `OpenAICompatibleProvider` | `https://api.openai.com/v1` |
| `deepseek` | `DeepSeekProvider`（继承前者） | `https://api.deepseek.com/v1` |
| `openai-compatible` | `OpenAICompatibleProvider` | **必填**（无默认） |

> **为什么工厂函数不依赖 NestJS 的依赖注入？** 因为 Provider 是「纯类」，
> `LlmConfigService` 需要**在运行时按数据库里的配置临时 new 一个**（每个用户、每个模型都可能不同），
> 没法靠启动时固定的 DI 容器。所以写成普通工厂函数最灵活。

### 4.3 四个 Provider 的关系图

```
                    ┌──────────────────────┐
                    │   AiProvider（接口）  │
                    └──────────┬───────────┘
             ┌─────────────────┼─────────────────────┐
             ▼                 ▼                     ▼
   ┌──────────────────┐  ┌───────────────────────────────┐
   │  OllamaProvider  │  │ OpenAICompatibleProvider       │
   │  NDJSON 流式      │  │ SSE 流式 / OpenAI 协议         │
   │  /api/chat       │  └───────────────┬───────────────┘
   │  /api/tags       │                  │ extends
   └──────────────────┘                  ▼
                              ┌──────────────────────┐
                              │  DeepSeekProvider     │
                              │  只改了默认 baseUrl    │
                              └──────────────────────┘
```

**`DeepSeekProvider` 的全部代码只有 12 行**——它继承 `OpenAICompatibleProvider`，只覆盖默认地址：

```typescript
export class DeepSeekProvider extends OpenAICompatibleProvider {
  constructor(baseUrl?: string, apiKey?: string) {
    super(baseUrl || 'https://api.deepseek.com/v1', apiKey, 'deepseek');
  }
}
```

> **这就是「接口 + 继承」的威力**：DeepSeek 的 API 和 OpenAI 完全兼容，
> 所以不需要重写任何逻辑，**换个默认地址、改个名字就够了**。

### 4.4 `OpenAICompatibleProvider` 的三个关键实现

**① baseUrl 归一化**（防用户填错）：

```typescript
private static normalizeBaseUrl(input: string): string {
  let url = (input ?? '').trim().replace(/\/+$/, '');   // 去首尾空格 + 去末尾 /
  const knownSuffixes = ['/chat/completions', '/embeddings', '/models'];
  for (const suffix of knownSuffixes) {
    if (url.toLowerCase().endsWith(suffix)) {
      url = url.slice(0, url.length - suffix.length).replace(/\/+$/, '');  // 剥掉叶子接口
      break;
    }
  }
  return url;
}
```

> **为什么需要这个？** 用户经常把「完整聊天接口 URL」（如 `.../v1/chat/completions`）
> 误当成 baseUrl 填进来。如果不处理，后端再拼一次 `/chat/completions` 就变成
> `.../chat/completions/chat/completions` → 404。
> 归一化会自动剥掉 `/chat/completions`、`/embeddings`、`/models` 这些「叶子后缀」，
> 保留到 `/v1`、`/v4` 这样的版本根。**前端表单的提示语也在反复强调「填到版本号为止」**。

**② 流式解析（SSE，和 Ollama 的 NDJSON 不一样）**：

```typescript
// OpenAI：每行形如  data: {"choices":[{"delta":{"content":"你"}}]}
for (const line of lines) {
  const trimmed = line.trim();
  if (!trimmed.startsWith('data:')) continue;
  const payload = trimmed.slice(5).trim();
  if (payload === '[DONE]') return;                    // ★ 结束标志
  const json = JSON.parse(payload);
  const delta = json.choices?.[0]?.delta?.content;
  if (delta) yield delta;
}
```

> ⚠️ **Ollama 和 OpenAI 的行解析逻辑不能共用**：Ollama 用 NDJSON（一行一个完整 JSON），
> OpenAI 用 SSE（`data: ` 前缀 + `[DONE]` 结束）。这就是为什么 `OllamaProvider` 要单独实现。

**③ 工具调用（Function Calling）**：`chatWithTools` 把 `tools` 透传给 `/chat/completions`，
并把返回的 `tool_calls[].function.arguments` **归一化成 JSON 字符串**（有些兼容服务会返回对象）。

### 4.5 一个「参数形态」的坑：`tool-args.util.ts`

不同厂商对 `tool_calls.function.arguments` 的形态不一致：

| 厂商 | arguments 是 |
|------|-------------|
| 标准 OpenAI | **JSON 字符串** `'{"a":1}'` |
| 部分兼容服务 | **对象** `{ a: 1 }` |
| Ollama | 要求传**对象**，但内部统一按 OpenAI 存字符串 |

项目用一个工具函数统一处理：

```typescript
stringifyToolArguments(args)  // 对象 → JSON 字符串（存库/发给 OpenAI 时用）
parseToolArguments(args)      // 字符串 → 对象（发给 Ollama 时用）
```

> 这个「来回转换」在 `ollama.provider.ts` 的 `toOllamaMessages()` 里有专门注释：

### 5.1.1 ★ 验证模型 `POST /llm-configs/models/:id/verify`

```typescript
async verifyModel(userId: string, modelId: string) {
  const { provider } = await this.resolveModelRuntime(modelId);

  if (model.capabilities.includes('EMBEDDING')) {
    const res = await provider.embedding(['维度校验'], { model: model.modelId });
    const dim = res.embeddings?.[0]?.length ?? 0;      // ← 真实跑一次，不靠名字猜
    if (!dim) throw new Error('未返回任何向量，无法确定输出维度');
    await prisma.llmModel.update({ where: { id: modelId },
      data: { embeddingDimensions: dim, isVerified: true, verifiedAt: new Date() } });
    return { ok: true, dimensions: dim, latencyMs, checked: ['embedding'] };
  }

  await provider.complete('ping', { model: model.modelId, maxTokens: 16 });
  await prisma.llmModel.update({ where: { id: modelId },
    data: { isVerified: true, verifiedAt: new Date() } });
  return { ok: true, dimensions: null, latencyMs, checked: ['chat'] };

  // catch → isVerified = false，返回 { ok: false, error }
}
```

| 返回字段 | 含义 |
|---|---|
| `ok` | 是否通过 |
| `dimensions` | EMBEDDING 模型的**实测**维度（768 / 1024 / 1536 …）；非 EMBEDDING 为 `null` |
| `latencyMs` | 耗时 |
| `checked` | `['embedding']` 或 `['chat']` |
| `error` | 失败原因（仅失败时） |

> **⚠️ 向量模型必须先验证**：`embeddingDimensions` 默认 `null`，
> 知识库创建向量版本时会直接 400「该模型尚未实测输出维度，请先到「模型管理」点「验证模型」」。
> 维度不能靠模型名猜 —— `nomic-embed-text` 768、`bge-m3` 1024、`text-embedding-3-small` 1536。

> ⚠️ **路由顺序的坑**：`GET /llm-configs/models` 必须写在 `GET /llm-configs/:id` **前面**，
> 否则 Nest 会把 `models` 当成一个 `:id` 参数去匹配（然后 `ParseUUIDPipe` 报 400）。
> 看控制器源码你会发现 `listModels` 确实排在 `findOne` 之前。

### 5.2 新增配置 `POST /llm-configs`

| 项 | 内容 |
|----|------|
| 请求体 | ```json { "name": "我的 DeepSeek", "provider": "deepseek", "apiKey": "sk-xxx", "baseUrl": "https://api.deepseek.com/v1", "modelId": "deepseek-chat", "displayName": "DeepSeek 对话", "capabilities": ["CHAT","STREAM"] } ``` |
| 后端校验 | `name` 必填 `MaxLength(100)`；`provider` 必须是 4 种之一；`baseUrl` `MaxLength(500)`；`capabilities` 每项必须是 **8 值之一**（`CHAT`/`STREAM`/`TOOLS`/`EMBEDDING`/`VISION`/`REASONING`/`RERANK`/`IMAGE_GENERATION`） |
| ★ 额外校验 | **`provider !== 'ollama'` 且没传 `apiKey` → 400「云端模型提供商必须提供 API Key」** |
| 处理 | ① 解析 baseUrl（云端厂商为空则取默认值；`openai-compatible` 为空 → 400）② `encrypt(apiKey)` 存密文 ③ 建配置 ④ 若传了 `modelId`，顺带建第一条 `LlmModel` |
| 响应 201 | 配置对象（含 `apiKeyMasked` / `hasApiKey` / `models[]`） |

**`resolveBaseUrl` 的规则**（`llm-config.service.ts:425`）：

```typescript
private resolveBaseUrl(provider, baseUrl?) {
  if (baseUrl) return baseUrl;                          // 传了就用自己的
  if (provider === 'openai') return DEFAULT_BASE_URL.openai;    // https://api.openai.com/v1
  if (provider === 'deepseek') return DEFAULT_BASE_URL.deepseek;// https://api.deepseek.com/v1
  if (provider === 'openai-compatible') throw new BadRequestException('openai-compatible 必须提供 baseUrl');
  return null;                                          // ollama：运行时取默认本地地址
}
```

## 6. ★ 运行时解析：Agent / 工作流 / 知识库怎么用自建模型

### 6.1 核心方法 `resolveModelRuntime`

```typescript
async resolveModelRuntime(modelId: string): Promise<{
  provider: AiProvider;
  modelId: string;
  providerType: LlmProviderType;
}> {
  const model = await this.prisma.llmModel.findUniqueOrThrow({
    where: { id: modelId },
    select: { id: true, modelId: true, config: { select: { provider: true, baseUrl: true, encryptedApiKey: true } } },
  });
  const plainKey = model.config.encryptedApiKey ? this.encryption.decrypt(model.config.encryptedApiKey) : null;
  const provider = createProvider({
    provider: model.config.provider as LlmProviderType,
    baseUrl: model.config.baseUrl ?? null,
    apiKey: plainKey,
  });
  return { provider, modelId: model.modelId, providerType: model.config.provider };
}
```

**它一次做了四件事**：① 按 `LlmModel.id` 查模型 + 父配置 → ② 解密 API Key →
③ 用工厂造 Provider → ④ 返回「可直接调用的 provider + 真实模型名」。

> **为什么要返回 `modelId`（真实模型名）？** 因为发请求时要传给厂商 API 的 `model` 字段是
> `deepseek-chat` 这种**真实标识**，而不是我们数据库里的 UUID。

### 6.3 ★ Agent 的 `model` 列会被「同步成真实模型名」

这是个容易忽略的细节。`Agent` 表里有两个跟模型有关的列：

| 列 | 存什么 | 例子 |
|----|--------|------|
| `llmModelId` | 指向 `LlmModel.id`（UUID） | `"a1b2c3..."` |
| `model` | **真实模型名**（会被同步） | `"deepseek-chat"` |

创建/更新 Agent 时，只要传了 `llmModelId`，`model` 列就会被**自动同步为真实模型名**：

```typescript
private async resolveModelName(llmModelId: string | null, fallback?: string) {
  if (llmModelId) {
    const name = await this.llmConfigService.getModelName(llmModelId);   // 查 LlmModel.modelId
    if (name) return name;
  }
  return fallback?.trim() || DEFAULT_LOCAL_MODEL;   // 回退本地 qwen2.5:7b
}
```

> **为什么要冗余存 `model`？** 为了「即使模型配置被删了，Agent 记录里也还留着一个可读的模型名」，
> 也方便列表页直接展示。前端 `agentModelLabel()` 的逻辑就是：优先按 `llmModelId` 找显示名，
> 找不到再回退 `agent.model`。

### 6.4 前端「模型显示」的权威来源：SSE `meta` 事件

Chat 页顶部有个「model chip」。它的取值优先级是：

```
① 后端 SSE meta 事件回报的 model（最权威，就是本次真正用的）
② 按 agent.llmModelId 在本地模型列表里查显示名
③ 回退 agent.model
```

> 这样设计的目的是**避免「改了模型但感觉没生效」**：后端在每次对话开始时
> `logger.log(...)` 并 `yield meta`，把「这次到底用了哪个模型、哪个 provider」明确告诉前端。

```typescript
verifyLlmModel(id)       // POST /llm-configs/models/:id/verify  ★ 实测验证（写回维度）
```

## 8. 完整走一遍：添加一个 DeepSeek 模型并让 Agent 用上

```
① 用户在 /providers 点「添加模型」
   → 填：名称=我的 DeepSeek，provider=deepseek，apiKey=sk-xxx，modelId=deepseek-chat
   → 点「测试连接」→ POST /api/llm-configs/test
     后端临时造 DeepSeekProvider → GET https://api.deepseek.com/v1/models
     成功 → 返回 { ok: true, models: ["deepseek-chat","deepseek-reasoner",...] }

② 点「保存」→ POST /api/llm-configs
   后端：encrypt("sk-xxx") → 存密文；建 LlmProviderConfig + 第一条 LlmModel
   返回：{ id, name, provider, apiKeyMasked: "sk-x****xxx", hasApiKey: true, models: [...] }

③ 用户点「获取模型」→ GET /api/llm-configs/:id/models/remote
   ★ 只拉不落：返回 { models: [...], existing: [...] }，前端弹窗（t-dialog + t-table）展示，
     existing 里的打上「已添加」标签；用户勾选想要的 → POST /api/llm-configs/:id/models
     后端 upsert 进 LlmModel 表，配置 status → CONNECTED
     （手动填了 modelId 时只添加填的那一个，不会全量落库）

④ 用户去 /agents 创建一个 Agent，模型下拉选「DeepSeek 对话（DeepSeek）」
   → POST /api/agents { name, type, llmModelId: "<LlmModel.id>" }
   后端：resolveModelName(llmModelId) → 把 Agent.model 同步成 "deepseek-chat"

⑤ 用户在 /chat 发消息 → POST /api/agents/:agentId/chat/stream
   后端 agent.service.runStream：
     agent.llmModelId 有值 → resolveModelRuntime → 解密 Key → 造 DeepSeekProvider
     → 发 POST https://api.deepseek.com/v1/chat/completions (stream:true)
     → 逐 token 通过 SSE 推回前端
   同时 yield meta 事件：{ type:'meta', model:'deepseek-chat', provider:'deepseek' }
   前端 model chip 显示「deepseek-chat · DeepSeek（云端 API）」
```

## 9. ⚠️ 已知坑与注意点

| # | 坑 | 说明 |
|---|-----|------|
| 1 | **删模型不会清掉引用它的 Agent/知识库** | `llmModelId` 是软引用，没有外键。删掉 `LlmModel` 后，指向它的 Agent 在运行时 `findUniqueOrThrow` 会报错。**删模型前最好确认没人引用** |
| 2 | **`LLM_CONFIG_ENCRYPTION_KEY` 变了 → 旧 Key 解不开** | 加密密钥是「全局一把」。**改了密钥，之前存的 `encryptedApiKey` 全部失效**（`decrypt` 抛错）。生产环境务必固定住这个值 |
| 3 | **`GET /llm-configs/models` 的路由顺序** | 必须写在 `GET /llm-configs/:id` 之前，否则 `models` 被当 `:id` 匹配报 400 |
| 4 | **拉来的模型默认只有 `CHAT`/`STREAM` 能力** | 如果某模型要当向量模型用，得在「编辑模型」里手动勾上 `EMBEDDING`，否则知识库选择器看不到它 |
| 5 | **`openai-compatible` 必须填 baseUrl** | 没有默认值，不填直接 400 |
| 6 | **baseUrl 填成完整接口 URL** | 会被 `normalizeBaseUrl` 自动剥掉叶子后缀，但**填错了版本段仍会失败**（如把 `/v1` 漏了） |
| 7 | **连接测试「成功」≠ 模型可用** | `listModels` 成功只说明「地址 + Key 对得上」。真跑对话时若模型名写错，仍会报错 |
| 8 | **`status` 只是「最近一次测试结果」** | 不会自动刷新。改了 Key 要重新点「测试连接」 |
| 9 | **能力标签大小写敏感** | 必须是全大写（8 值之一），小写会被 DTO 校验拦下 |
| 10 | **两个 `DEFAULT_BASE_URL` 别搞混** | 后端 `provider.factory.ts` 和后端 `llm-config.service.ts` 各有一份，值一致；前端 `providers/index.vue` 里还有一份 `defaultBaseUrl`。改默认地址要三处一起改 |
| 11 | **★ 向量模型不「验证」就用不了** | `embeddingDimensions` 默认 `null`，知识库创建向量版本时会 400。先勾 `EMBEDDING` → 点「验证」→ 实测维度写入后才可用 |
| 12 | **★ 维度不能靠名字猜** | `nomic-embed-text` 768、`bge-m3` 1024、`text-embedding-3-small` 1536。必须让后端真实跑一次 embedding 测出来 |
| 13 | **★ 勾了 `EMBEDDING` ≠ 知识库立刻换模型** | 还要去知识库详情页「创建目标版本 → 重新向量化 → 激活」。直接改知识库的 `embeddingModel` 字段是无效的（第 7 篇 §4.10） |
| 14 | **★ 「获取模型」不会再自动塞满库** | 现在只拉不落，要勾选/手填才添加。误加的可以用每行「删除」按钮删单个模型 |

## 10. 本篇小结

| 概念 | 一句话记住 |
|------|-----------|
| **`LlmProviderConfig`** | 存「厂商 + 地址 + 加密后的 Key」，用户私有 |
| **`LlmModel`** | 存「真实模型名 + 能力标签（8 值多选）+ 输入/输出模态 + 实测向量维度」，选择器靠它过滤 |
| **`llmModelId`** | Agent / LLM 节点 / 知识库指向自建模型的「指针」；为空回退本地 Ollama |
| **★ 能力体系** | `capabilities` 8 值**多选非互斥**：CHAT / STREAM / TOOLS / EMBEDDING / VISION / REASONING / RERANK / IMAGE_GENERATION；模态 `text/image/audio` 独立建模 |
| **★ 验证模型** | `POST models/:id/verify`：EMBEDDING 真实跑一次 embedding 写回维度，其它跑 `complete('ping')`；结果记 `isVerified` / `verifiedAt` |
| **`encryptedApiKey`** | AES-256-GCM 加密，**永不明文**；密钥来自 `LLM_CONFIG_ENCRYPTION_KEY` |
| **密文格式** | `base64(iv):base64(authTag):base64(ciphertext)` |
| **`maskApiKey`** | 返回 `sk-a****1234` 脱敏串，接口不泄明文 |
| **Provider 工厂** | `createProvider()` 按 provider 造出 4 种 Provider 之一（纯函数，不用 DI） |
| **DeepSeek = OpenAI 兼容** | 只继承 + 换默认 baseUrl，12 行代码 |
| **`normalizeBaseUrl`** | 自动剥掉 `/chat/completions` 等叶子后缀，防用户填错 |
| **`resolveModelRuntime`** | 按 `LlmModel.id` → 解密 Key → 造 Provider → 返回「可直接调的 provider + 真实模型名」 |
| **回退是灵魂** | 没有 `llmModelId` 就用全局 Ollama，保证向后兼容 |
| **15 个接口** | `/llm-configs` 下 CRUD + 测试 + 模型管理（含 verify / 只拉不落 / 按需添加 / 删单个）；选择器统一走 `GET /llm-configs/models?capability=` |
| **★ 知识库换向量模型** | 不是改 `embeddingLlmModelId`，而是「建版本 → 重新向量化 → 激活」（第 7 篇 §4.10） |
| **`Agent.model` 会被同步** | 传了 `llmModelId` 就把 `model` 列刷成真实模型名，方便展示与回退 |
| **SSE `meta` 事件** | 后端每次对话回报「本次实际用的 model + provider」，前端 chip 以此为准 |
