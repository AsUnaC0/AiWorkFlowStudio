## 1. NestJS 四大概念：先把心智模型建起来

把 NestJS 想象成一家**餐厅的后厨系统**：

| NestJS 概念 | 餐厅类比 | 干什么 | 接收前端数据吗？ |
|------------|---------|--------|----------------|
| **Module（模块）** | 一个部门 | 把相关功能聚在一起，声明「我需要哪些依赖」 | 否 |
| **Controller（控制器）** | 前台服务员 | **接收 HTTP 请求**、把 `@Body()` 交给 Service、把结果返回 | **是，就在这里** |
| **Service（服务）** | 后厨厨师 | 真正的业务逻辑：查库、算、拼装响应 | 否 |
| **依赖注入 (DI)** | 自动配菜系统 | 你只声明「需要什么」，框架自动创建并传进来 | — |

### 1.1 一次请求的完整旅程

```
浏览器发 HTTP 请求
      ↓
[中间件层] Vite 代理转发（开发时）→ 到达 localhost:3000
      ↓
[Guard] JwtAuthGuard 拦截 —— 没 token 就 401 直接返回
      ↓
[Pipe]  ValidationPipe 用 DTO 装饰器校验 body —— 不合格就 400
      ↓
[Controller] @Param / @Body / @CurrentUser 把数据取出来
      ↓   调用
[Service]  业务逻辑、查 Prisma、拼装结果
      ↓   返回
[Controller] 返回对象 → NestJS 自动 JSON 序列化
      ↓
浏览器收到 JSON
```

**本教程后面所有内容，都按这 5 步来描述。**

### 1.2 依赖注入：写一行就有人送上门

```typescript
// backend/src/workspaces/workspaces.service.ts
@Injectable()                                    // ← 声明「我可以被注入」
export class WorkspacesService {
  constructor(private readonly prisma: PrismaService) {}   // ← 声明「我需要 PrismaService」
}
```

- `@Injectable()` 装饰器：这个类可以交给框架管理。
- 构造函数参数写 `PrismaService`：框架在启动时就创建一个 `PrismaService` 实例，**自动塞进来**。
- 你不需要写 `new PrismaService()`，也不需要管它什么时候创建、什么时候销毁。

**好处**：单元测试时可以把 `prisma` 换成个假的（mock），不用真的连数据库。

## 2. `main.ts`：程序入口只有 17 行，但每一行都重要

文件：`backend/src/main.ts`（完整内容）

```typescript
import 'dotenv/config';                            // ①
import { ValidationPipe } from '@nestjs/common';     // ②
import { NestFactory } from '@nestjs/core';          // ③
import { AppModule } from './app.module';            // ④

async function bootstrap() {
  const app = await NestFactory.create(AppModule);  // ⑤
  app.setGlobalPrefix('api');                       // ⑥
  app.useGlobalPipes(                                // ⑦
    new ValidationPipe({
      whitelist: true,
      transform: true,
    }),
  );
  await app.listen(process.env.PORT ?? 3000);        // ⑧
}
bootstrap();                                        // ⑨
```

| 行 | 代码 | 大白话 | **对「前后端传数据」的影响** |
|----|------|--------|------------------------------|
| ① | `import 'dotenv/config'` | 把 `.env` 里的值读进 `process.env` | 数据库密码、JWT 私章从这来 |
| ⑤ | `NestFactory.create(AppModule)` | 启动整个应用（读 `app.module.ts` 装配所有模块） | |
| ⑥ | `app.setGlobalPrefix('api')` | 所有路由前面加 `/api` | **所以前端请求 `POST /api/auth/login`，Controller 里写的是 `@Controller('auth')`** |
| ⑦ | `useGlobalPipes(ValidationPipe)` | 全局挂一个「参数校验器」 | ★ **只对有 DTO 参数的方法生效**，见下 |
| ⑧ | `app.listen(PORT ?? 3000)` | 监听 3000 端口 | |

### 2.1 ⚠️ 三个「没写但你该知道」的事

| 没写的 | 意味着什么 | 影响 |
|--------|-----------|------|
| 没有 `app.enableCors()` | **后端不开跨域** | 前端必须走 Vite 代理（`/api` → 3000）。直连 `localhost:3000` 会被浏览器拦 |
| 没有 `app.enableShutdownHooks()` | 优雅关闭没开 | 进程被 kill 时数据库连接不会优雅断开 |
| `ValidationPipe` 没设 `forbidNonWhitelisted` | 多余字段是**静默丢弃**而不是报错 | 前端传了 DTO 里没有的字段 → 不会 400，会被丢掉 |

### 2.2 ★ 关键：`ValidationPipe` 到底校验什么？（这是本篇最实用的部分）

`whitelist: true` + `transform: true` 的行为，取决于**方法的参数有没有写 DTO 类**：

| Controller 方法写法 | pipe 会不会校验 | 后果 |
|---------------------|----------------|------|
| `@Body() dto: RegisterDto` | **会** | 按 `RegisterDto` 的装饰器逐条校验；DTO 里没声明的字段被**丢弃** |
| `@Body() body: any` | **完全不会** | 传什么都不校验，传错了引擎会抛 `TypeError` → 变成 **500** |
| `@Body() body: { model: string; messages: ChatMessage[] }` | **不会** | 这是手写 TypeScript 类型，运行时不存在，全靠手写 `if` 检查 |

**本项目属于第三种情况的两个地方**（`workflows.controller.ts`）：

```typescript
// src/workflows/workflows.controller.ts
@Post('run')
async run(@Body() body: any) {           // ← any！零校验
  return this.engine.run(body.workflow, body.input);
}

@Post('run/stream')
async runStream(@Body() body: any, @Res() response: Response) {
  //                              ↑ 同样零校验
  for await (const event of this.engine.runStream(body.workflow, body.input)) { ... }
}
```

以及 `ai.controller.ts`：

```typescript
@Post('chat')
async chat(@Body() body: { model: string; messages: ChatMessage[]; ... }) {
  if (!body.model) throw new HttpException('model 不能为空', 400);      // 手写
  if (!body.messages?.length) throw new HttpException('messages 不能为空', 400);  // 手写
  ...
}
```

> **记住这条**：**「传 `body: any` 的接口 = 后端不校验，你传任何东西后端都收」**。
> 这是本项目最需要你警惕的设计，因为 `/api/workflow/run` 就是这种接口。

### 2.3 DTO 长什么样？——「规定前端能传什么」

`backend/src/auth/dto/register.dto.ts`：

```typescript
import { IsEmail, IsNotEmpty, IsString, MinLength } from 'class-validator';

export class RegisterDto {
  @IsString()
  @IsNotEmpty()
  username: string;

  @IsEmail()
  @IsNotEmpty()
  email: string;

  @IsString()
  @IsNotEmpty()
  @MinLength(6)
  password: string;
}
```

**每个装饰器就是一条规则：**

| 装饰器 | 规则 | 不满足时 |
|--------|------|---------|
| `@IsString()` | 必须是字符串 | 400 |
| `@IsNotEmpty()` | 不能是空串 | 400 |
| `@IsEmail()` | 必须像邮箱 | 400 |
| `@MinLength(6)` | 至少 6 个字符 | 400 |
| `@MaxLength(100)` | 最多 100 个字符 | 400 |
| `@IsObject()` | 必须是对象 `{}` | 400 |
| `@IsInt()` / `@Min(1)` / `@Max(8192)` | 必须是 1~8192 的整数 | 400 |
| `@IsOptional()` | 这个字段可以不传 | — |

`register.dto.ts` 里**没有**的字段（比如 `admin: true`、`role: "root"`）：

- 因为 `whitelist: true`，**会被静默删除**；
- 传了也不会报错（因为没设 `forbidNonWhitelisted`）。

**这就是「声明式校验」**：用装饰器写规则，框架执行，不用手写一堆 `if`。

### 2.4 一个 400 响应的真实样子

如果前端发：

```json
{ "username": "a", "email": "不是邮箱", "password": "123" }
```

后端返回 **400**：

```json
{
  "statusCode": 400,
  "message": [
    "email must be an email",
    "password must be longer than or equal to 6 characters"
  ],
  "error": "Bad Request"
}
```

> `message` 是**数组**。前端 `views/login/index.vue` 专门处理了这个：
> ```typescript
> const message = error.response?.data?.message;
> errorMessage.value = Array.isArray(message) ? message.join("；") : message || "请求失败";
> ```
> 数组用 `；` 拼成一句话显示给用户。

## 3. `app.module.ts`：根模块把所有积木拼起来

```typescript
@Module({
  imports: [
    PrismaModule,      // 数据库
    AiModule,          // AI（全局）
    AuthModule,        // 认证
    KnowledgeModule,   // 知识库 + RAG
    WorkspacesModule,  // 工作空间
    WorkflowsModule,   // 工作流 + 引擎（核心）
  ],
})
export class AppModule {}
```

只有 6 个模块（**没有** `users/`、`queue/`、`reports/`、`files/`、`documents/` 这些目录了，旧文档已过时）。

### 3.1 两个「全局模块」省掉一堆 import

| 模块 | 有 `@Global()` 吗 | 导出了什么 | 效果 |
|------|----------------|-----------|------|
| `PrismaModule` | **有** | `PrismaService` | 任何模块直接 `constructor(private prisma: PrismaService)` 就能用，**不用 import** |
| `AiModule` | **有** | `AIService` | 同上 |
| `AuthModule` | 没有 | 无 | 但 `JwtModule` 注册时写了 `global: true`，所以 `JwtService` 全局可用 |
| `KnowledgeModule` | 没有 | 5 个 Service | **别的模块要用它的 Service，必须显式 `imports: [KnowledgeModule]`** |
| `WorkspacesModule` | 没有 | 无 | |
| `WorkflowsModule` | 没有 | 无 | |

**一个容易懵的点**：`WorkflowsModule` 里明明要用到 `EmbeddingService` 和 `VectorStoreService`（在 KnowledgeModule 里），
看它的 `imports`：

```typescript
@Module({
  imports: [PrismaModule, AuthModule, AiModule, KnowledgeModule],  // ← 显式 import 了
  ...
})
```

**因为这两个 Service 不是全局的，所以必须显式 import。** 这就是「模块化」的价值：你想让 RAG 能力只服务于工作流，就通过 import 明确表达这个依赖关系，而不是全网都可见。

### 3.2 `WorkflowsModule` 装配清单（很重要，第 4 篇要用）

```typescript
@Module({
  imports: [PrismaModule, AuthModule, AiModule, KnowledgeModule],
  controllers: [WorkflowsController, WorkflowController],   // ← 两个 Controller！
  providers: [
    WorkflowsService,        // 业务层
```

## 4. `PrismaService`：数据库连接

文件：`backend/src/prisma/prisma.service.ts`

```typescript
import { Injectable, OnModuleDestroy, OnModuleInit } from '@nestjs/common';
import { PrismaPg } from '@prisma/adapter-pg';
import { PrismaClient } from '@prisma/client';

@Injectable()
export class PrismaService
  extends PrismaClient                      // ← 继承，所有增删改查方法都是现成的
  implements OnModuleInit, OnModuleDestroy  // ← 生命周期钩子
{
  constructor() {
    super({
      adapter: new PrismaPg({             // ← Prisma 7 用「驱动适配器」连 PG
        connectionString: process.env.DATABASE_URL,   // ← 从 .env 读
      }),
    });
  }

  async onModuleInit()    { await this.$connect(); }       // 模块初始化时连库
  async onModuleDestroy() { await this.$disconnect(); }    // 销毁时断库
}
```

**三个理解点：**

1. **`extends PrismaClient`** —— 这就是 ORM。9 张表自动对应成 9 个"对象管理器"：
   ```
   prisma.user              → User 表
   prisma.workspace         → Workspace 表
   prisma.workflow          → Workflow 表
   prisma.workflowVersion   → WorkflowVersion 表
   prisma.knowledgeBase     → KnowledgeBase 表
   prisma.workspaceKnowledgeBase
   prisma.document
   prisma.documentChunk
   ```
   字段名写错会**编译期就报错**。

2. **`PrismaPg` 适配器** —— Prisma 7 改了架构，不再内置数据库驱动，要单独装 `@prisma/adapter-pg`。

3. **`onModuleInit`** —— NestJS 启动时自动调它。所以「数据库连不上」会在启动时报错，而不是等到第一个请求。

### 5.2 User（用户）

```prisma
model User {
  id           String   @id @default(uuid())
  username     String   @unique
  email        String   @unique
  passwordHash String                        // ← 只有哈希，绝不存明文
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
  workspaces   Workspace[] @relation("WorkspaceOwner")
  memberships  WorkspaceMember[]
  knowledgeBases KnowledgeBase[] @relation("KnowledgeBaseOwner")
}
```

| 写法 | 含义 | 好处 |
|------|------|------|
| `@id @default(uuid())` | 主键，自动生成 UUID | 不用自增 ID，多服务器也不会撞车 |
| `@unique` | 数据库层面保证唯一 | 重复插入直接报错（数据库兜底，不靠应用层判断） |
| `@updatedAt` | 每次 update 自动填当前时间 | 不用手写 `updatedAt: new Date()` |
| `@relation("WorkspaceOwner")` | 给关系起名字 | User↔Workspace 之间**有两条关系**（owner 和 member），必须命名区分 |

**`passwordHash` 是理解「数据流」的关键**：前端传的 `password` 是明文，
`AuthService` 立刻 `bcrypt.hash()` 变成 `$2b$10$...` 一长串，**只有哈希入库**。
第 3 篇细讲。

### 5.3 Workspace + WorkspaceMember（工作空间和成员）

```prisma
model Workspace {
  id        String   @id @default(uuid())
  name      String
  ownerId   String
  owner     User     @relation("WorkspaceOwner", fields: [ownerId], references: [id])
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  members         WorkspaceMember[]
  workflows       Workflow[]
  knowledgeBases  WorkspaceKnowledgeBase[]
}

model WorkspaceMember {
  id          String @id @default(uuid())
  workspaceId String
  userId      String
  workspace   Workspace @relation(fields: [workspaceId], references: [id], onDelete: Cascade)
  user        User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  createdAt   DateTime  @default(now())
  @@unique([workspaceId, userId])
}
```

**`ownerId` 是什么？** 外键（FK），存的是某个 `User.id`。
`@relation(fields: [ownerId], references: [id])` 告诉 Prisma：「`ownerId` 这一列的值，去 `User` 表的 `id` 列里找」。

有了这个声明，查的时候能直接拿到对象：

```typescript
prisma.workspace.findFirst({ include: { owner: true } })   // 自动 JOIN 出 owner 完整信息
```

**为什么要有 WorkspaceMember 表？**

- 一个用户可以在多个空间当成员
- 一个空间可以有多个用户

这就是**多对多**关系。关系型数据库没法直接表达多对多，于是拆一张中间表，一行代表「某某在某某空间里」。

| 写法 | 含义 |
|------|------|
| `onDelete: Cascade` | **连坐删除**。空间被删，成员记录自动一起删，不会留脏数据 |
| `@@unique([workspaceId, userId])` | 复合唯一。同一个人不能在同一个空间重复加入 |

**⚠️ 一个重要设计细节**：`WorkspacesService.create` 创建空间时，
会**同时给创建者自己插一条 WorkspaceMember 记录**：

```typescript
create(userId: string, dto: CreateWorkspaceDto) {
  return this.prisma.workspace.create({
    data: {
      name: dto.name,
      ownerId: userId,
      members: { create: { userId } },    // ← 创建者自动也是成员
    },
    select: workspaceSelection,
  });
}
```

这样 `findAll` 里 `OR: [{ ownerId }, { members: { some: ... } }]` 两个条件对 owner 都成立。
**副作用**：owner 天然拥有 member 权限，不需要额外处理。

### 5.4 Workflow + WorkflowVersion（★ 核心设计）

```prisma
model Workflow {
  id              String           @id @default(uuid())
  workspaceId     String
  name            String
  description     String?                                // 可空
  status          String           @default("DRAFT")     // ⚠️ 是 String 不是 enum
  currentVersionId String?                               // 「当前用哪一版」的指针
  workspace       Workspace        @relation(fields: [workspaceId], references: [id], onDelete: Cascade)
  versions        WorkflowVersion[] @relation("WorkflowVersions")
  currentVersion  WorkflowVersion? @relation("WorkflowCurrentVersion", fields: [currentVersionId], references: [id], onDelete: SetNull)
  createdAt       DateTime         @default(now())
  updatedAt       DateTime         @updatedAt
  @@index([workspaceId])
  @@unique([currentVersionId])                            // ★ 见下
}

model WorkflowVersion {
  id             String    @id @default(uuid())
  workflowId     String
  version        Int                                          // 1, 2, 3...
  definition     Json                                        // ★★ 整张工作流图存在这
  createdAt      DateTime  @default(now())
  workflow       Workflow  @relation(fields: [workflowId], references: [id], onDelete: Cascade)
  currentWorkflow Workflow? @relation("WorkflowCurrentVersion")
  @@unique([workflowId, version])
  @@index([workflowId])
}
```

**这是本项目最重要的数据库设计，值得慢慢读：**

| 设计 | 为什么 |
|------|--------|
| `definition Json` | 整张工作流图（nodes + edges）存成一列 JSON。**加了新节点类型不用改表结构** |
| `version Int` | 版本号。每次保存 +1 |
| **不覆盖，只追加** | 保存 = 插一条新 WorkflowVersion。旧版本永远在，可以回溯 |
| `currentVersionId` | 一个「指针」，指向「当前该用哪一版」 |
| `@@unique([currentVersionId])` | **这一行让「指针」只能指向一版**。没这行，一个版本可能被两个工作流同时当"当前" |
| `@@unique([workflowId, version])` | 同一工作流里版本号不重复。**这是并发保存时唯一的保护**（不加会报 Prisma P2002） |
| `status String` | ⚠️ 不是 `enum`，是字符串。合法值（`DRAFT`）靠代码约定，数据库不约束 |

**画个图就懂了**：

```
Workflow（工作流的"壳"：名字、所属空间、当前版本指针）
  currentVersionId ──────► WorkflowVersion #3  { nodes:[...], edges:[...] }  ← 前端打开看到的就是这版
  versions ─────────────► WorkflowVersion #1  { nodes:[...], edges:[...] }  ← 存档
                           WorkflowVersion #2  { nodes:[...], edges:[...] }  ← 存档
```

> **所以「保存工作流」这个动作，在数据库层面是：**
> 1. `INSERT` 一条 WorkflowVersion（`version = 最大值 + 1`）
> 2. `UPDATE` Workflow 的 `currentVersionId` 指向它
> 3. 两步在**一个事务**里

第 4 篇第 2 节会逐行走这段代码。

### 5.5 KnowledgeBase + WorkspaceKnowledgeBase（知识库）

```prisma
model KnowledgeBase {
  id                 String   @id @default(uuid())
  ownerId            String                              // ★ 独立 owner 模型，不挂 workspace
  name               String
  description        String?
  embeddingModel     String                              // ★ 必须是 Ollama 里真实存在的模型
  embeddingDimension Int                                 // ★ 必须是模型真实输出的长度
  documentCount      Int      @default(0)                // 冗余计数，列表页不用 COUNT
  chunkCount         Int      @default(0)
  createdAt          DateTime @default(now())
  updatedAt          DateTime @updatedAt
  owner              User     @relation("KnowledgeBaseOwner", fields: [ownerId], references: [id])
  documents          Document[]
  workspaces         WorkspaceKnowledgeBase[]
  @@index([ownerId])
}
```

**`embeddingModel` 和 `embeddingDimension` 为什么必须存在知识库上？**

因为**向量必须同维度才能比距离**。你在建知识库时填的这两个值，
决定了上传文档时用哪个模型、写成几维。检索时也用同样的模型算查询向量。

> **典型翻车场景**：建库时填 `nomic-embed-text` / `768`，
> 但用 `mxbai-embed-large`（1024 维）去检索 → `pgvector` 报
> `expected 768 dimensions, not 1024`。第 7 篇会详细讲。

**`documentCount` / `chunkCount` 是「冗余计数」**：
不实时 `COUNT(*)`，而是每次增删时手动 `increment`/`decrement`。
好处是列表页查询快，代价是要维护一致性（本项目删除时是**重算**的，最保险）。

### 5.6 Document + DocumentChunk（★ RAG 的地基）

```prisma
model Document {
  id             String   @id @default(uuid())
  knowledgeBaseId String
  fileName       String
  fileType       String                              // "PDF" | "DOCX" | "TXT" | "MARKDOWN"
  fileSize       Int                                 // ★ Int 最大约 2GB，够用
  storagePath    String                              // 磁盘相对路径
  mimeType       String?
  status         String   @default("UPLOADED")       // UPLOADED/PROCESSING/COMPLETED/FAILED
  errorMessage   String?                             // FAILED 时记原因
  pageCount      Int?                                // ⚠️ 声明了但从未被赋值
  createdAt      DateTime @default(now())
  updatedAt      DateTime @updatedAt
  knowledgeBase  KnowledgeBase @relation(..., onDelete: Cascade)
  chunks         DocumentChunk[]
  @@index([knowledgeBaseId])
  @@index([status])
}

model DocumentChunk {
  id          String   @id @default(uuid())
  documentId  String
  content     String                            // ★ 切出来的文本块
  chunkIndex  Int                               // ★ 第几块（0,1,2...）
  tokenCount  Int?                              // ⚠️ 声明了但从未被赋值
  // ⚠️ embedding 由 pgvector 扩展单独手写 migration 添加（Prisma 无此类型）
  //   embedding vector(768)    ← 手写 migration 加的，schema 里看不到
  metadata    Json?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
  document    Document @relation(..., onDelete: Cascade)
  @@index([documentId])
  @@index([chunkIndex])
}
```

**为什么文档要「切块」？**

1. 大模型有上下文长度限制，不能把整本书塞进去
2. 检索要**精确**：你问「报销标准是多少」，命中的是相关那一段，不是整份文档
3. 检索结果塞进 Prompt 时更省 token

切块的参数在 `chunk.service.ts`：

```typescript
private readonly splitter = new RecursiveCharacterTextSplitter({
  chunkSize: 1000,        // 每块约 1000 字符
  chunkOverlap: 200,      // 相邻块重叠 200 字符 ← 防止一句话被切断
});
```

> `chunkOverlap` 的作用：假设第 1 块结尾是「……差旅费标准为」，第 2 块开头是「市内 30 元/天」。
> 重叠 200 字符能让第 2 块也包含前文的上下文，检索到第 2 块时不会看到半句话。

**★ 关于 `embedding` 列**（再强调一次，这是最容易踩坑的地方）：

- `schema.prisma` 里**没有** `embedding` 字段
- 它由手写 migration 添加：`ALTER TABLE "DocumentChunk" ADD COLUMN "embedding" vector(768)`
- 后果：**Prisma 完全不认识这一列**。`prisma.documentChunk.findMany()` 查不到它，`create` 也不能写它
- 所以所有向量的读写必须走**裸 SQL**（`VectorStoreService` 用 `$queryRaw` / `$executeRawUnsafe`）
- 而且**每次手动 join Document 表才能知道 chunk 属于哪个知识库**（`KnowledgeBaseId` 只在 Document 上）

第 7 篇会把这些裸 SQL 逐条讲。

### 5.7 关于「表名/列名大小写」的坑

`schema.prisma` 里写的：

```prisma
model DocumentChunk {
  documentId  String
  ...
}
```

Prisma 生成的数据库表名是 **`"DocumentChunk"`**（PascalCase，带双引号），
列名是 **`"documentId"`**（camelCase，带双引号）。

**PostgreSQL 的双引号标识符是区分大小写的**，所以写裸 SQL 时必须用**完全一致**的大小写：

```sql
-- ✅ 对
SELECT dc."id", dc."documentId" FROM "DocumentChunk" dc

-- ❌ 错（会报 relation "document_chunk" does not exist）
SELECT dc.id FROM document_chunk dc
```

而且 Prisma 的 `String` 映射到 PostgreSQL 的 **`TEXT`**，不是原生 `uuid`。
所以裸 SQL 里要写 `::text[]` 而不是 `::uuid[]`：

```sql
WHERE d."knowledgeBaseId" = ANY(${knowledgeBaseIds}::text[])   -- ✅
```

## 6. 三个 Prisma 核心概念（够用就行）

### 6.1 `select`：只查需要的字段

项目里到处都有 `select`，比如 `workspaces.service.ts`：

```typescript
const workspaceSelection = {
  id: true,
  name: true,
  ownerId: true,
  createdAt: true,
  updatedAt: true,
  _count: { select: { members: true, workflows: true } },   // ★ Prisma 的魔法
} as const;
```

**`_count` 是 Prisma 特有的语法**，不用写 `COUNT(*)` 子查询，直接给你计数结果。

前端拿到的响应长这样：

```json
{
  "id": "uuid",
  "name": "我的空间",
  "ownerId": "uuid",
  "createdAt": "2026-01-01T00:00:00.000Z",
  "updatedAt": "2026-01-01T00:00:00.000Z",
  "_count": { "members": 1, "workflows": 3 }
}
```

**注意**：这就是前端 `types/workspace-api.ts` 里 `WorkspaceApiItem` 的形状。
`useWorkspace.ts` 里的 `mapWorkspace` 再把它转成页面用的形状：

```typescript
const mapWorkspace = (w: WorkspaceApiItem): WorkspaceItem => ({
  id: w.id,
  name: w.name,
  workflowCount: w._count?.workflows ?? 0,   // ?? 是「空值兜底」运算符
  knowledgeCount: 0,                          // ⚠️ 硬编码 0，后端还没这个字段
  memberCount: w._count?.members ?? 0,
});
```

> `??` 的意思是「左边是 null 或 undefined 就用右边」。
> `??` 和 `||` 的区别：`0 ?? 5` 是 `0`，但 `0 || 5` 是 `5`。计数为 0 时必须用 `??`。

**为什么 `select` 很重要？** `Workflow.currentVersion` 里的 `definition` 可能几十 KB，
不用 `select` 的话每次列工作流都会把所有版本的定义全查出来，性能极差。

### 6.2 `$transaction`：要么全成，要么全不成

`workflows.service.ts` 的 `create`：

```typescript
async create(userId: string, workspaceId: string, dto: CreateWorkflowDto) {
  await this.assertWorkspaceMember(userId, workspaceId);      // ① 权限校验（不在事务里）

  return this.prisma.$transaction(async (transaction) => {  // ② 开事务
    const workflow = await transaction.workflow.create({    // ③ 插工作流 + 插 v1
      data: {
        workspaceId,
        name: dto.name,
        description: dto.description,
        versions: { create: { version: 1, definition: dto.definition } },  // 嵌套创建
      },
      select: { id: true, versions: { select: { id: true } } },
    });

    return transaction.workflow.update({                      // ④ 回写 currentVersionId
      where: { id: workflow.id },
      data: { currentVersionId: workflow.versions[0].id },
      select: workflowSelection,
    });
  });
}
```

**两个理解点：**

**① `versions: { create: {...} }`（嵌套创建）**

一次 `create` 连着把 `Workflow` 和它的第一个 `WorkflowVersion` 都建出来。
Prisma 自动处理外键顺序 —— 先插 Workflow 拿到 id，再插 WorkflowVersion。
这依赖 schema 里声明的 `versions WorkflowVersion[]` 关系。

**② 为什么要事务？**

「创建工作流」和「设置当前版本指针」是**两个独立的 SQL 语句**。
如果第 4 步失败了，第 3 步已经插进去了，数据库就变成：

```
Workflow 存在，但 currentVersionId = null
```

前端打开这个工作流会拿到 `currentVersion: null`，画布一片空白，
而且**这个坏数据永远修不好**（因为 `update` 会再插一版，`create` 不会重跑）。

`$transaction` 保证：中间任何一步失败，两步一起回滚，数据库干净。

> **为什么权限校验（①）放在事务外？**
> 因为它是纯查询，不改数据。放事务里会白白占着数据库连接。

### 6.3 `$queryRawUnsafe`：写裸 SQL（只为 pgvector）

`vector-store.service.ts` 里的向量检索：

```typescript
const rows = await this.prisma.$queryRaw<VectorHit[]>`
  SELECT
    dc."id"        AS "chunkId",
    dc."documentId",
    d."knowledgeBaseId",
    dc.content,
    dc."embedding" <=> ${vectorString}::vector AS distance
  FROM "DocumentChunk" dc
  JOIN "Document" d ON d."id" = dc."documentId"
  WHERE d."knowledgeBaseId" = ANY(${knowledgeBaseIds}::text[])
    AND dc."embedding" IS NOT NULL
    AND dc."embedding" <=> ${vectorString}::vector <= ${threshold}
  ORDER BY dc."embedding" <=> ${vectorString}::vector ASC
  LIMIT ${topK}
`;
```

**逐行读懂**（这是全项目最复杂的 SQL）：

| 部分 | 意思 |
|------|------|
| `$queryRaw\`...\`` | **带变量占位符**的标签模板。`${vectorString}` 由 Prisma 转义成参数，**不会 SQL 注入** |
| `dc."embedding" <=> ${vectorString}::vector` | **`<=>` 是 pgvector 的余弦距离运算符。值越小越相似** |
| `AS distance` | 给这列起别名，方便 TypeScript 读 |
| `JOIN "Document" d` | ★ 必须 join！因为 `KnowledgeBaseId` 在 `Document` 表上，`DocumentChunk` 上没有 |
| `ANY(${knowledgeBaseIds}::text[])` | 「知识库 ID 在这个数组里」= 一次查多个知识库（多选） |
| `AND ... <= ${threshold}` | 距离超过阈值（太不像）就丢弃 |
| `ORDER BY ... ASC` | 距离升序 = 最像的排最前 |
| `LIMIT ${topK}` | 只取 K 条 |

对比一下 `$queryRawUnsafe` 的用法（批量写向量）：

```typescript
const sql = `
  UPDATE "DocumentChunk" AS dc
  SET "embedding" = v.vec::vector
  FROM unnest($1::text[], $2::text[]) AS v(id, vec)
  WHERE dc."id" = v.id
`;
await this.prisma.$executeRawUnsafe(sql, ids, vectors);
```

**为什么用 `Unsafe` 版本？** 因为 `unnest($1::text[], $2::text[])` 这种「数组参数展开」
Prisma 的标签模板语法表达不了，只能拼成 SQL 字符串再用 `?` 传参。
`$1` / `$2` 是 PostgreSQL 的原生占位符。**参数仍然是安全的**（值不拼进字符串）。

> `unnest` 的意思：把两个数组「摊平」成两列，交叉配对。
> `ids = [a,b,c]` + `vectors = [v1,v2,v3]` → 变成 3 行 `(a,v1) (b,v2) (c,v3)`。
> 这样**一条 SQL 就能更新 100 个 chunk**，比循环 100 次 `UPDATE` 快一个数量级。

## 7. 本篇小结

| 概念 | 一句话记住 |
|------|-----------|
| **Controller** | 唯一接收前端数据的地方（`@Body` / `@Param` / `@CurrentUser`） |
| **Service** | 业务逻辑 + 查库，不碰 HTTP 细节 |
| **`@Injectable` + 构造函数** | 声明依赖，框架自动注入 |
| **`setGlobalPrefix('api')`** | 所有路由带 `/api` 前缀 |
| **DTO + `ValidationPipe`** | 声明式校验；**`body: any` 的接口零校验** |
| **`whitelist: true`** | DTO 没声明的字段被静默丢弃 |
| **`@Global()`** | 模块的 Service 全局可用，不用 import |
| **`extends PrismaClient`** | 表变成对象，字段名写错编译期报错 |
| **`select`** | 只查需要的字段；`_count` 白送计数 |
| **`$transaction`** | 多步写库要么全成要么全不成 |
| **9 张表** | User / Workspace / WorkspaceMember / Workflow / WorkflowVersion / KnowledgeBase / WorkspaceKnowledgeBase / Document / DocumentChunk |
| **`definition Json`** | 工作流图存一列 JSON，加新节点不用改表 |
| **版本只追加不覆盖** | 每次保存 +1 版，`currentVersionId` 指向当前版 |
| **`embedding vector(768)`** | 手写 migration 加的，Prisma 不认，必须裸 SQL |
