# AI WorkFlow Studio 学习指南
## 第 8 篇：前后端数据对照总表（全部 58 个接口逐一拆解）

> **本篇是全书收尾**。前 7 篇教会了你走通链路原理，这一篇给一份"字典"：
> 每个接口 → **前端发什么 → 后端怎么校验 → 后端怎么处理 → 返回什么 → 前端类型怎么定义**。
> 以后写新页面、修 bug、加接口，都回来翻这一篇。
>
> 全后端实际 **58** 个接口，覆盖 10 个 Controller：Auth、AI、Workspaces（含成员）、Workflows（含运行/发布）、Knowledge（含文档）、**Agent**、**Friendship**、**Skill**、**MCP**。
>
> **★ 后续新增**：Agent（3）、Friendship（6）、Skill（5）、MCP（6）、工作空间成员（3）、工作流发布/归档（3）、节点运行明细（1）。异步队列接口仍是 `api/workflow.ts` 的 `enqueueRun`/`getRun`/`listRuns`（§4.7~4.9）。

## 0. 公共约定（先读）

| 约定 | 值 |
|------|----|
| Base URL | 前端 `/api` 前缀被 Vite 代理到 `http://localhost:3000`（axios 直接写 `/auth/login`，fetch 需要写 `/api/...`） |
| 响应解包 | axios 拦截器直接返回 `response.data`，所以 `request.get()` 拿到的就是业务 JSON |
| 鉴权 | `Authorization: Bearer <accessToken>`；登录返回的 `accessToken` 存 Pinia + localStorage |
| 未登录访问保护接口 | 401，前端拦截器自动登出并跳 `/login` |
| Token 过期 | JWT 过期，返回 `{ statusCode: 401, message: "Unauthorized" }` |
| 参数错误 | NestJS 全局校验管道返回 `{ statusCode: 400, message: [...y],"error": "Bad Request" }`，`message` 是数组 |
| 内容类型 | JSON 用 `request`（自动 `application/json`）；文件上传必须 FormData + `fetch`（第 5/6 篇讲过的坑） |
| ★ **异步接口约定** | 走队列的接口**立即返回一条记录**（`status=QUEUED`），**不是最终结果**。前端要拿结果得轮询。详见 §0.1 |

### 0.1 ★ 两种响应模式（读下面任何接口前先分清）

| | **同步模式** | **异步模式（队列）** |
|---|---|---|
| 长什么样 | 直接返回你要的结果 | 返回一条**状态记录**，`status` 是 `QUEUED` |
| HTTP 耗时 | = 业务耗时 | **< 100ms** |
| 怎么拿结果 | 不用拿，响应里就是 | **轮询**到 `status` 是终态 |
| 失败表现 | HTTP 4xx/5xx + 错误信息 | HTTP **201 成功**，但记录的 `status` 是 `FAILED` + `errorMessage` |
| 涉及接口 | §4.5、§4.6、其余全部 | **§4.7、§4.8、§4.9、§5.9** |
| 后端机制 | Controller 直接调 Service | `queue.add()` → Redis → `queues/` 下的 Processor |

**记住这一条就够**：看到响应里有 `status: "QUEUED"` 或 `status: "UPLOADED"`，
就说明**还没出结果**，需要轮询。

## 1. Auth 认证（3 个）

### 1.1 注册 `POST /auth/register`

| 项 | 内容 |
|----|------|
| 鉴权 | **公开**（无需 token） |
| 请求体 | ```json { "username": "小明", "email": "ming@example.com", "password": "123456" } ``` |
| 前端类型 | `RegisterRequest { username, email, password }`（types/auth.ts） |
| 后端 DTO | `RegisterDto`：username `IsString+IsNotEmpty`，email `IsEmail+IsNotEmpty`，password `IsString+IsNotEmpty+MinLength(6)` |
| 处理 | ① 查 email 重复 → `409 ConflictException('Email already registered')`；② 查 username 重复 → `409`；③ `bcrypt.hash(password, 10)`；④ 建 User |
| 响应 201 | ```json { "user": { "id": "4f6...", "username": "小明", "email": "ming@example.com", "avatar": null, "status": "OFFLINE", "createdAt": "2026-...", "updatedAt": "2026-..." }, "accessToken": "eyJhbGciOiJIUzI1NiIs..." } ``` |

> **注意两个坑**：① 响应里的 `user` **不会包含 `passwordHash`**——`auth.service.toPublicUser` 解构时把它剔除了（`const { passwordHash, ...result } = user`），所以 JSON 里只有 7 个字段（新增 `avatar`/`status`）。② `AuthResponse.user`（types/auth.ts）要与这 7 个字段对齐：`{ id, username, email, avatar, status, createdAt, updatedAt }`。

### 1.2 登录 `POST /auth/login`

| 项 | 内容 |
|----|------|
| 鉴权 | **公开** |
| 请求体 | ```json { "email": "ming@example.com", "password": "123456" } ``` |
| 前端类型 | `LoginRequest { email, password }` |
| 后端 DTO | `LoginDto`：email `IsEmail`，password `IsString+IsNotEmpty` |
| 处理 | 查 user → 无或 `bcrypt.compare` 失败 → **统一 `401 'Invalid credentials'`**（不区分用户不存在/密码错） |
| 响应 200 | 同注册：`{ user, accessToken }` |

### 1.3 当前用户 `GET /auth/me`

| 项 | 内容 |
|----|------|
| 鉴权 | **Bearer** |
| 前端 | `auth.ts getCurrentUser(): Promise<User>`（⚠️ 整个项目没地方调用它，见第 6 篇缺陷清单） |
| 处理 | 从 JWT `sub` 查 DB，返回 PublicUser |
| 响应 | `{ id, username, email, avatar, status, createdAt, updatedAt }` |

## 2. AI 大模型（2 个）

### 2.1 模型列表 `GET /ai/models`

| 项 | 内容 |
|----|------|
| 鉴权 | **Bearer**（Controller 级 `@UseGuards`） |
| 前端 | `ai.ts getModels(): Promise<ListModelsResponse>` |
| 后端 | 调 Ollama `GET http://localhost:11434/api/tags`，映射为 `{ name, size, modifiedAt }` |
| 未启动 Ollama | **不报错**，返回兜底默认模型列表 + `note` 字段 |
| 响应 | ```json { "provider": "ollama", "models": [ { "name": "qwen2.5:7b", "size": 4863347937, "modifiedAt": "2026-..." }, { "name": "nomic-embed-text", "size": 274000000, "modifiedAt": null } ] } ``` |

> 兜底默认值（Ollama 没起来时）：
> ```json
> { "provider": "ollama",
>   "models": [ {"name":"qwen2.5:7b"}, {"name":"qwen2.5:3b"}, {"name":"deepseek-r1:7b"}, {"name":"nomic-embed-text"} ],
>   "note": "Ollama 未连接，返回默认模型列表" }
> ```
> LLM 节点下拉框、Chat 页模型下拉框都用它。**注意：模型名必须和 Ollama 里 `ollama list` 完全一致**（含 tag），否则跑节点时报错。

### 2.2 聊天 `POST /ai/chat`

| 项 | 内容 |
|----|------|
| 鉴权 | **Bearer** |
| 请求体 | ```json { "model": "qwen2.5:7b", "messages": [ { "role": "system", "content": "你是客服助手" }, { "role": "user", "content": "退款多久到账？" } ], "temperature": 0.7, "maxTokens": 512, "knowledgeBaseIds": ["kb-uuid"] } ``` |
| 前端类型 | `ChatRequest { model, messages, temperature?, maxTokens?, knowledgeBaseIds? }` |
| 后端校验 | `model` 为空 → 400；`messages` 空 → 400（其余零校验） |
| 处理 | 透传 `AIService.chat`；`temperature` 默认 `0.7`。**`knowledgeBaseIds` 被忽略（源码 TODO）** |
| 响应 | ```json { "content": "通常 3~5 个工作日到账…", "model": "qwen2.5:7b", "usage": { "promptTokens": 128, "completionTokens": 96, "totalTokens": 224 } } ``` |
| 前端类型 | `ChatResponse { content, model, usage? }` |

> **非流式**：做不出打字机效果。要流式只能用 `GET /event-stream`（投喂模块，第 5 篇讲过）或工作流 `POST /workflow/run/stream`。

## 3. Workspaces 工作空间（8 个，含成员管理）

## 4. Workflows 工作流（**13** 个）

> **核心机制回顾**（第 4 篇）：保存 = 存 Vue Flow 原样节点（`type:"custom"` + 配置在 `data`）；**运行 = 转业务类型 + 配置搬进 `config`**。两个 DTO 里的 `definition` 都是 `Record<string, unknown>`（宽类型），前端见第 6 篇不同格式差异。
>
> 分两组：§4.1~4.4 是 CRUD，§4.5~4.6 是**同步直接跑**（开发调试），§4.7~4.9 是**★ 异步队列**。

### 4.1 创建工作流 `POST /workspaces/:workspaceId/workflows`

| 项 | 内容 |
|----|------|
| 权限 | workspace member（非成员 → `403 'You do not have access to this workspace'`） |
| 请求体 | ```json { "name": "客服流程", "description": "RAG 客服", "definition": { "nodes": [ { "id": "node1", "type": "custom", "position": {"x":0,"y":0}, "data": { ... } } ], "edges": [] } } ``` |
| 后端 DTO | `CreateWorkflowDto`：name `MaxLength(100)`，description `MaxLength(500)`，definition `IsObject` |
| 处理 | **事务**：① 建 Workflow + 建 **version 1**（`definition` 存 `versions[0]`）；② 用 `versions[0].id` 回填 `currentVersionId` |
| 响应 201 | `Workflow`（含 `currentVersion`） |
| 前端类型 | `Workflow { id, workspaceId, name, description, status, currentVersionId, currentVersion, createdAt, updatedAt }` |

### 4.2 列表 `GET /workspaces/:workspaceId/workflows`

| 项 | 内容 |
|----|------|
| 条件 | workspace member |
| 排序 | `updatedAt DESC` |
| 响应 | `Workflow[]`（**每项带 `currentVersion`**，前端下载用） |

### 4.3 详情 `GET /workflows/:id`

| 项 | 内容 |
|----|------|
| 查询 | `findFirst WHERE id = :id AND workspace.members.some(userId = me)` |
| 响应 | `Workflow` 或 `404 'Workflow not found'` |

### 4.4 更新 `PUT /workflows/:id`

| 项 | 内容 |
|----|------|
| 请求体 | ```json { "name": "新名字", "description": "...", "definition": { "nodes": [], "edges": [] } } ```（name/description 可选；**definition 必须有**） |
| 处理 | 查出最新 `version` → **事务**：建 version N+1，更新 Workflow 的 `currentVersionId` 指向新版本；name/description 只在传了才更新 |
| 响应 | `Workflow`（`currentVersion` 指向最新） |

### 4.5 运行（一次性）`POST /workflow/run`

| 项 | 内容 |
|----|------|
| ⚠️ 鉴权 | **没有 `@UseGuards`**（WorkflowController 类级无 Guard、body 是 `any`）——高风险遗留问题 |
| 请求体 | ```json { "workflow": { "nodes":[ { "id":"start1","type":"start","config":{},"data":{},"position":{"x":0,"y":0} } ], "edges":[] }, "input": "用户的问题或输入" } ``` |
| 前端类型 | `RunWorkflowRequest { workflow: WorkflowDefinition, input: unknown }` |
| 关键 | workflow 里的节点是**业务类型**（`start`/`input`/`llm`/`prompt`/`rag`/`http`/`condition`/`output`）+ 配置在 `config`，**不是保存时的 Vue Flow 格式**。类型写错（比如还是 `custom`）会报 `没有找到 Node Executor: custom` |
| 响应 | ```json { "input": "用户的问题或输入", "data": { "start1": {}, "rag_1": "【问题】…【知识库参考】[1]…", "llm_1": "答案文本" } } ``` |
| 前端类型 | `WorkflowRunResult { input, data }` |

### 4.6 运行（流式）`POST /workflow/run/stream`

| 项 | 内容 |
|----|------|
| 鉴权 | **无 Guard**（同上） |
| 请求 | 同 4.5（运行转格式后的定义） |
| 响应 | SSE。每行 `data: <json>\n\n`，前端按 `\n\n` 分割再取 `data: ` 行（api/workflow.ts 里手动实现） |

SSE 事件（对应前端 `WorkflowStreamEvent`）：

| type | 载荷字段 | 含义 |
|------|---------|------|
| `node:start` | `nodeId,nodeType,label?` | 某节点开跑 |
| `token` | `nodeId, content` | LLM 流式输出片段 |
| `node:complete` | `nodeId,nodeType,output,branch?,metadata?` | 节点完成；**condition 才有 branch 和 metadata** |
| `complete` | `data: Record` | 全部完成 |
| `error` | `message` | 出错 |

### 4.7 ★ 入队运行 `POST /workflows/:id/run`（异步队列）

| 项 | 内容 |
|----|------|
| 权限 | `JwtAuthGuard` + workspace member（非成员 → `404 'Workflow not found'`） |
| 请求体 | ```json { "input": "用户的问题" } ```（`input` **任意类型**：string / object / number；可省略） |
| 后端处理 | ① 权限校验 → ② `workflowRun.create({ status: 'QUEUED', input })` → ③ `queue.add('execute-workflow', { runId, workflowId, input }, { attempts: 1, removeOnComplete: 100, removeOnFail: 500 })` |
| 响应 201 | `WorkflowRun`，**`status` 一定是 `QUEUED`**，`output`/`startedAt`/`completedAt` 都是 `null` |
| ★ 跑哪张图 | **`Workflow.currentVersion.definition`**（数据库里最新保存的那版）。**不读你 POST 过来的图** —— 因为这个接口根本不接收 definition。⚠️ 所以页面上**改完必须先保存再运行** |
| ★ 为什么要这样 | 没法「试跑未保存的画布」。要试跑只能用 §4.5 / §4.6，而这两条在页面上已经没有按钮了 |
| 前端类型 | ✅ `api/workflow.ts` → `enqueueRun(workflowId, input): Promise<WorkflowRun>`，画布「运行」弹窗在用 |

**响应体：**

```json
{
  "id": "b7c3e...",
  "workflowId": "a1b2...",
  "input": "用户的问题",
  "output": null,
  "status": "QUEUED",
  "errorMessage": null,
  "startedAt": null,
  "completedAt": null,
  "createdAt": "2026-09-30T12:00:00.000Z"
}
```

### 4.8 ★ 查单次运行 `GET /workflow-runs/:runId`（前端轮询用）

| 项 | 内容 |
|----|------|
| 查询 | `findUnique({ where: { id: runId } })`，顺便带上 `workflow { id, name, workspace { ownerId, members } }` |
| 权限 | workspace **owner 或 member 都行**，否则 `403 'You do not have access to this workflow run'` |
| 处理 | 返回前把内部的 `members` 剥掉，`workflow` 只留 `{ id, name }` |
| 不存在 | `404 'WorkflowRun not found'` |
| 前端类型 | ✅ `api/workflow.ts` → `getRun(runId): Promise<WorkflowRun>`，画布弹窗每 2s 轮询它 |

**响应体（COMPLETED 时）：**

```json
{
  "id": "b7c3e...",
  "workflowId": "a1b2...",
  "input": "用户的问题",
  "output": { "input": "用户的问题", "data": { "start1": {}, "llm_1": "答案文本" } },
  "status": "COMPLETED",
  "errorMessage": null,
  "startedAt": "2026-09-30T12:00:03.000Z",
  "completedAt": "2026-09-30T12:00:09.000Z",
  "createdAt": "2026-09-30T12:00:00.000Z",
  "workflow": { "id": "a1b2...", "name": "客服流程" }
}
```

**FAILED 时**：`status: "FAILED"`、`output: null`、`errorMessage` 是引擎的报错原文
（和 §4.5 同步跑抛的错**是同一个错**，因为内部调的是同一个 `run()`）。

**status 状态机：**

```
QUEUED ──→ RUNNING ──┬──→ COMPLETED   (写 output + completedAt)
  (接口写)  (Processor) └──→ FAILED     (写 errorMessage + completedAt)
```

> **轮询建议**：2 秒一次，`status` 是 `COMPLETED` 或 `FAILED` 就停。
> 没有长轮询（`?wait=1`）支持，所以别写 100ms 那种高频轮询。

### 4.9 ★ 运行历史 `GET /workflows/:id/runs`

| 项 | 内容 |
|----|------|
| 权限 | workspace member（先 `findFirst` 校验，不存在/非成员 → `404`） |
| 排序 | `createdAt DESC` |
| **条数上限** | **固定 `take: 50`**，没有分页参数 |
| 响应 | `WorkflowRun[]`（**不带** `workflow` 嵌套） |
| 前端类型 | ✅ `api/workflow.ts` → `listRuns(workflowId): Promise<WorkflowRun[]>`，**已封装但没有页面调用** |

> ⚠️ **两个都返回同一个 `WorkflowRun` 形状**，只有 §4.8 多了 `workflow: { id, name }`。
> 前端 `WorkflowRun` 类型把这个字段声明成可选 `workflow?: { id, name }`，正好对上这个差异。

### 4.10 ★ 节点运行明细 `GET /workflow-runs/:runId/nodes`

| 项 | 内容 |
|----|------|
| 权限 | 该 run 所属 workspace 的 owner/member |
| 处理 | 查 `WorkflowNodeRun`（每次运行按节点落库的执行明细：`nodeId`、`nodeType`、`status`、`input`、`output`、`error`、`startedAt`、`completedAt` 等） |
| 响应 | `WorkflowNodeRun[]`，按执行顺序返回 |
| 前端 | ⚠️ 暂未封装到 api 层；排查某次运行为什么失败时可手动调用 |

### 4.11 发布 / 归档 / 恢复（状态机）

工作流多了 3 个状态迁移接口，改的是 `Workflow.status`，**不动 `currentVersion`**：

| 接口 | 作用 | 迁移 |
|------|------|------|
| `POST /workflows/:id/publish` | 发布：把当前版本标记为已发布（写 `publishedVersionId`） | `DRAFT → PUBLISHED` |
| `POST /workflows/:id/archive` | 归档：停用 | `PUBLISHED → ARCHIVED` |
| `POST /workflows/:id/restore` | 恢复：重新启用 | `ARCHIVED → PUBLISHED` |

| 项 | 内容 |
|----|------|
| 权限 | workspace member（owner/member） |
| 关键概念 | `currentVersionId`（最新保存的草稿版）与 `publishedVersionId`（对外生效的稳定版）**分开**。Agent / 运行时读的是已发布版，改画布不影响线上 |
| 前端 | ⚠️ 页面暂未接入发布按钮（当前「运行」读 `currentVersion`） |

workspace member 即可（无需 kb owner）。`deleteMany`，响应空体 204。

### 5.9 ★ 上传文档 `POST /knowledge-bases/:kbId/documents`（multipart，★ 现在是异步的）

| 项 | 内容 |
|----|------|
| 权限 | kb owner |
| 请求 | `multipart/form-data`，**字段名必须 `file`**；`FileInterceptor limits.fileSize = 50MB` |
| 前端实现 | 不走 axios，`fetch("/api/...")` + FormData + 手写 `Authorization`（api/knowledge.ts `uploadDocument`） |
| 允许扩展名 | `.pdf .docx .txt .md .markdown`（其他 → 400 '不支持的文件类型'） |
| ★ 处理 | **只做 5 件事**：① owner 校验 ② 扩展名白名单 ③ 落盘 `uploads/<kbId>/<docId><ext>` ④ 建记录 **`status='UPLOADED'`** ⑤ `queue.add('process-document', { documentId, knowledgeBaseId, storagePath }, { attempts: 3, backoff: { type: 'exponential', delay: 3000 }, removeOnComplete: 100, removeOnFail: 500 })` |
| ★ 响应 201 | **不是 `DocumentItem`！** 是 `{ documentId, jobId, status, message }`，`status` 一定是 `"UPLOADED"` |
| ★ 异步段在哪 | `queues/document-processing/document.processor.ts`：`PROCESSING` → 解析 → 切块 → 批量 embedding → 写 pgvector → `COMPLETED`；任何一步失败 → `FAILED` + `errorMessage` |
| ★ 失败不再 HTTP 报错 | 传 `.docx`（解析器未实现）或维度错，**上传请求照样返回 201**。要去 §5.10 的列表里看 `status`/`errorMessage` |
| ✅ 前端类型已改对 | ★ 本次修：新增 `UploadDocumentResult` 接口，`uploadDocument` 返回类型从 `DocumentItem` 改成它（`status` 字面量类型 `"UPLOADED"`） |

**响应体：**

```json
{
  "documentId": "2a1...",
  "jobId": "3",
  "status": "UPLOADED",
  "message": "文件已上传，正在后台处理"
}
```

**前端类型（`api/knowledge.ts`）：**

```typescript
/** uploadDocument 返回 —— 后端入队后立即返回（异步处理中） */
export interface UploadDocumentResult {
  documentId: string;
  jobId: string;
  status: "UPLOADED";
  message: string;
}
```

**跟进状态**：轮询 §5.10（前端 `detail.vue` 已经这么做了，每 2s，有 `UPLOADED`/`PROCESSING` 就刷）。
想自己轮 §5.11 的 `GET /documents/:id` 也可以（`getDocument()` 已封装，页面还没用）。

### 5.10 文档列表 `GET /knowledge-bases/:kbId/documents`

kb owner；`createdAt DESC`。响应 `DocumentItem[]`。**★ 这是跟进异步处理进度的推荐方式**。

### 5.11 文档详情 `GET /documents/:id`

kb owner（经 `assertDocumentOwner`）。响应 `DocumentItem`。
前端 ✅ 已封装：`api/knowledge.ts` → `getDocument(id): Promise<DocumentItem>`（页面目前仍用列表轮询，没调它）。

### 5.12 删除文档 `DELETE /documents/:id`

| 项 | 内容 |
|----|------|
| 权限 | kb owner |
| 处理 | 删磁盘文件（失败只 warn）→ 删 DB 行 → **重算** documentCount 和 chunkCount |
| 响应 | **204 空体**（前端 `Promise<void>`） |

**DocumentItem 完整字段（前后端一致）：**

```json
{
  "id": "2a1...",
  "knowledgeBaseId": "6f2...",
  "fileName": "员工手册.pdf",
  "fileType": "PDF",
  "fileSize": 123456,
  "storagePath": "D:\\...\\uploads\\6f2...\\2a1....pdf",
  "mimeType": "application/pdf",
  "status": "COMPLETED",
  "errorMessage": null,
  "pageCount": null,
  "createdAt": "2026-...",
  "updatedAt": "2026-..."
}
```

> `status` **四种**：`UPLOADED / PROCESSING / COMPLETED / FAILED`。
> ★ `UPLOADED` → `PROCESSING` → `COMPLETED`/`FAILED` 的切换**发生在后台 Worker 里**（不是同一个 HTTP 请求内），
> 所以上传响应里 `status` 必然是 `UPLOADED`。前端要靠轮询 §5.10 跟进。
> `pageCount`、`tokenCount`（后端有字段）**永远 null**（没人维护，第 7 篇已知缺陷）。

## 8. 常见报错速查（对照表）

| 前端看到 | 实际原因 | 去查哪 |
|---------|---------|--------|
| 401 跳登录页 | 没带 token / JWT 过期 | 第 3 篇 3.x / 第 5 篇拦截器 |
| 400 `message` 是数组 | DTO 校验没通过（某个字段规则违反） | 本节对应 DTO |
| 400 `不支持的文件类型` | 上传了白名单外的扩展名 | §5.9 |
| 409 `Email already registered` | 注册邮箱已存在 | §1.1 |
| 403 `You do not own this knowledge base` | 动了别人的知识库/文档 | §5 |
| 403 `Only the workspace owner can modify it` | 非 owner 改/删工作空间 | §3.4/3.5 |
| 403 `You do not have access to this workspace` | 不是该空间成员 | §3/4/5.6 |
| 403 `You do not have access to this workflow run` | 不是该运行所属空间的 owner/member | §4.8 |
| 404 `xxx not found` | 权限不足也返回 404（故意不泄露） | §3.3 |
| 500 `没有找到 Node Executor: custom` | 运行把「保存格式」当「运行格式」传了 | 第 6 篇 §2 / §4.5 |
| ★ `Workflow xxx 或其当前版本不存在` | 队列运行的工作流**一条版本都没有**（`currentVersion` 为空） | 先 `PUT /api/workflows/:id` 保存一次 |
| ★ 文档卡在 `已上传` 很久 | Worker 没起来 / `@Processor` 名字写错 / Redis 没起 | 第 7 篇 §7 / 第 4 篇 §8.6 |
| ★ 上传返回 201 但文档变 `FAILED` | 解析器报错（docx 未实现）、或 embedding 维度不符 | 查文档的 `errorMessage`（第 7 篇 §7） |
| ★ `expected 768 dimensions, not X` | embeddingModel 或 dimension 与模型不符 | 第 7 篇 §7 |
| ★ 后端启动报 `ECONNREFUSED 6379` | Redis 没起（BullMQ 硬依赖） | 第 1 篇 §2 / §10 |
| Ollama 相关报错 | Ollama 没启动 / 模型没 pull | `ollama list` + `ollama pull <model>` |

## 9. 给编程新手的「怎么看这一篇」

1. **先看公共约定**（§0）——理解 axios 解包、鉴权头、错误结构。
2. **按模块挑一个接口**，先看「前端类型」和「请求体 JSON」，想象数据长什么样。
3. **看「后端 DTO」**——这就是「前端传什么，后端才收什么」。
4. **看「处理」和「响应」**——后端怎么花式加工，最后返回什么。
5. **最后对「前端类型」**——两边字段名一致就通了；不一致的地方文档已用 ⚠️ 标出。

> 规律：后端返回一律是**下划线的 snake 分不清？不——全部 camelCase**！
> 只有**数据库列名**是下划线 `snake_case`（不在 JSON 里出现），JSON 字段全是驼峰。别搞混。
