## 0. 公共约定（先读）

| 约定 | 值 |
|------|----|
| Base URL | 前端 `/api` 前缀被 Vite 代理到 `http://localhost:3000`（axios 直接写 `/auth/login`，fetch 需要写 `/api/...`） |
| 响应解包 | axios 拦截器直接返回 `response.data`，所以 `request.get()` 拿到的就是业务 JSON |
| 鉴权 | `Authorization: Bearer <accessToken>`；登录返回的 `accessToken` 存 Pinia + localStorage |
| 未登录访问保护接口 | 401，前端拦截器自动登出并跳 `/login` |
| Token 过期 | JWT 过期，返回 401；`message` 为「登录已过期，请重新登录」。前端路由守卫会先比对 JWT 的 `exp`，过期直接跳登录页；拦截器再把同一波 401 合并成一条提示 |
| 参数错误 | 全局异常过滤器统一成 `{ statusCode, error, message, path, timestamp }`；`ValidationPipe` 的数组 `message` 会被「；」拼成字符串 |
| 内容类型 | JSON 用 `request`（自动 `application/json`）；文件上传必须 FormData + `fetch`（第 5/6 篇讲过的坑） |
| ★ **异步接口约定** | 走队列的接口**立即返回一条记录**（`status=QUEUED`），**不是最终结果**。前端要拿结果得轮询。详见 §0.1 |

### 0.1 ★ 两种响应模式（读下面任何接口前先分清）

| | **同步模式** | **异步模式（队列）** |
|---|---|---|
| 长什么样 | 直接返回你要的结果 | 返回一条**状态记录**，`status` 是 `QUEUED` |
| HTTP 耗时 | = 业务耗时 | **< 100ms** |

## 1. Auth 认证（3 个）

### 1.1 注册 `POST /auth/register`

| 项 | 内容 |
|----|------|
| 鉴权 | **公开**（无需 token） |
| 请求体 | ```json { "username": "小明", "email": "ming@example.com", "password": "123456" } ``` |
| 前端类型 | `RegisterRequest { username, email, password }`（types/auth.ts） |
| 后端 DTO | `RegisterDto`：username `IsString+IsNotEmpty`，email `IsEmail+IsNotEmpty`，password `IsString+IsNotEmpty+MinLength(6)` |
| 处理 | ① 查 email 重复 → `409 ConflictException('该邮箱已被注册')`；② 查 username 重复 → `409 '该用户名已被占用'`；③ `bcrypt.hash(password, 10)`；④ 建 User |
| 响应 201 | ```json { "user": { "id": "4f6...", "username": "小明", "email": "ming@example.com", "avatar": null, "status": "OFFLINE", "createdAt": "2026-...", "updatedAt": "2026-..." }, "accessToken": "eyJhbGciOiJIUzI1NiIs..." } ``` |

> **注意两个坑**：① 响应里的 `user` **不会包含 `passwordHash`**——`auth.service.toPublicUser` 解构时把它剔除了（`const { passwordHash, ...result } = user`），所以 JSON 里只有 7 个字段（新增 `avatar`/`status`）。② `AuthResponse.user`（types/auth.ts）要与这 7 个字段对齐：`{ id, username, email, avatar, status, createdAt, updatedAt }`。

### 1.2 登录 `POST /auth/login`

| 项 | 内容 |
|----|------|
| 鉴权 | **公开** |
| 请求体 | ```json { "email": "ming@example.com", "password": "123456" } ``` |
| 前端类型 | `LoginRequest { email, password }` |
| 后端 DTO | `LoginDto`：email `IsEmail`，password `IsString+IsNotEmpty` |
| 处理 | 查 user → 无或 `bcrypt.compare` 失败 → **统一 `401 '邮箱或密码不正确'`**（不区分用户不存在/密码错） |
| 响应 200 | 同注册：`{ user, accessToken }` |

### 1.3 当前用户 `GET /auth/me`

| 项 | 内容 |
|----|------|
| 鉴权 | **Bearer** |
| 前端 | `auth.ts getCurrentUser(): Promise<User>`（⚠️ 整个项目没地方调用它，见第 6 篇缺陷清单） |
| 处理 | 从 JWT `sub` 查 DB，返回 PublicUser |
| 响应 | `{ id, username, email, avatar, status, createdAt, updatedAt }` |

## 2. AI 大模型（2 个）

### 2.1 模型列表 `GET /ai/models`

| 项 | 内容 |
|----|------|
| 鉴权 | **Bearer**（Controller 级 `@UseGuards`） |

>   "note": "Ollama 未连接，返回默认模型列表" }

### 2.2 聊天 `POST /ai/chat`

| 项 | 内容 |
|----|------|
| 鉴权 | **Bearer** |
| 请求体 | ```json { "model": "qwen2.5:7b", "messages": [ { "role": "system", "content": "你是客服助手" }, { "role": "user", "content": "退款多久到账？" } ], "temperature": 0.7, "maxTokens": 512, "knowledgeBaseIds": ["kb-uuid"] } ``` |

## 4. Workflows 工作流（**14** 个）

> **核心机制回顾**（第 4 篇）：保存 = 存 Vue Flow 原样节点（`type:"custom"` + 配置在 `data`）；**运行 = 转业务类型 + 配置搬进 `config`**。两个 DTO 里的 `definition` 都是 `Record<string, unknown>`（宽类型），前端见第 6 篇不同格式差异。
>
> 分两组：§4.1~4.4 是 CRUD，§4.5~4.6 是**同步直接跑**（开发调试），§4.7~4.9 是**★ 异步队列**。

### 4.1 创建工作流 `POST /workspaces/:workspaceId/workflows`

| 项 | 内容 |
|----|------|
| 权限 | workspace member（非成员 → `403 'You do not have access to this workspace'`） |
| 请求体 | ```json { "name": "客服流程", "description": "RAG 客服", "definition": { "nodes": [ { "id": "node1", "type": "custom", "position": {"x":0,"y":0}, "data": { ... } } ], "edges": [] } } ``` |
| 后端 DTO | `CreateWorkflowDto`：name `MaxLength(100)`，description `MaxLength(500)`，definition `IsObject` |
| 处理 | **事务**：① 建 Workflow + 建 **version 1**（`definition` 存 `versions[0]`）；② 用 `versions[0].id` 回填 `currentVersionId` |
| 响应 201 | `Workflow`（含 `currentVersion`） |
| 前端类型 | `Workflow { id, workspaceId, name, description, status, currentVersionId, currentVersion, createdAt, updatedAt }` |

### 4.2 列表 `GET /workspaces/:workspaceId/workflows`

| 项 | 内容 |
|----|------|
| 条件 | workspace member |
| 排序 | `updatedAt DESC` |
| 响应 | `Workflow[]`（**每项带 `currentVersion`**，前端下载用） |

### 4.3 详情 `GET /workflows/:id`

### 5.14 ★ 向量版本与重新向量化（6 个，`knowledge-bases/:id/embedding-versions/*`）

> **为什么要有这一组接口**：pgvector 的 HNSW/IVFFlat 索引只能建在**固定维度**的 `vector(N)` 列上。
> 换 Embedding 模型 = 换维度，所以必须「一个版本一张物理表」，不能原地改列。
> 详见 **第 7 篇 §4 / 后端代码逻辑 06 §六**。

| # | 接口 | 作用 | 关键点 |
|---|------|------|--------|
| 1 | `GET /knowledge-bases/:id/embedding-versions` | 列出全部版本（含进度） | 返回 `EmbeddingVersion[]` |
| 2 | `GET /knowledge-bases/:id/embedding-versions/active` | 当前生效版本 | 没有时会**自动按 KB 配置补建 v1 并激活** |
| 3 | `POST /knowledge-bases/:id/embedding-versions` | **创建目标版本** | body `{ llmModelId?, modelId?, dimensions? }`；校验模型有 `EMBEDDING` 能力 + 有实测维度 |
| 4 | `POST .../embedding-versions/:versionId/re-embed` | **启动重新向量化** | body `{ retryFailedOnly?: boolean }`；入队 `knowledge-reembed` |
| 5 | `POST .../embedding-versions/:versionId/activate` | **激活该版本** | 只有 `status = READY` 才允许；原子切换 |
| 6 | `DELETE .../embedding-versions/:versionId` | 删除历史版本 | 不能删 `isActive` 的版本 |

**③ 创建版本 请求体 / 校验：**

```json
{ "llmModelId": "lm-uuid", "modelId": "bge-m3", "dimensions": 1024 }
```

| 校验 | 错误提示 |
|------|---------|
| 传了 `llmModelId` 但模型不存在 | 404 `模型不存在` |
| 模型 `capabilities` 不含 `EMBEDDING` | 400 `所选模型没有 EMBEDDING（向量化）能力` |
| 模型 `embeddingDimensions` 为空 | 400 `该模型尚未实测输出维度，请先到「模型管理」点「验证模型」` |
| 两者都推不出维度 | 400 `无法确定目标模型的输出维度` |

响应 `EmbeddingVersion`（`status: "PENDING"`，`isActive: false`）。建版本时会同步：
建物理表 `EmbeddingVector_<id>`（`vector(dimensions)` + HNSW）→ 把 KB 下所有 chunk 登记为 `PENDING`。

**④ 启动重新向量化 响应（异步）：**

```json
{ "versionId": "v-uuid", "jobId": "12", "status": "PROCESSING" }
```

队列 `knowledge-reembed`（`attempts: 2`，exponential backoff 5000ms），批处理 `BATCH_SIZE = 64`。
**不重新解析原文件**，只复用已有文本块重新生成向量。前端轮询 #1 看 `chunkDone / chunkTotal / chunkFailed`。

**⑤ 激活：** 事务内三件事 —— 旧生效版本 `isActive=false` + `status=ARCHIVED`；目标版本 `isActive=true`；
同步 `KnowledgeBase.embeddingModel / embeddingLlmModelId / embeddingDimension`。非 `READY` → 400。

**EmbeddingVersion 完整字段（前后端一致）：**

```json
{
  "id": "4d75adfe-...",
  "knowledgeBaseId": "f68197e9-...",
  "modelId": "nomic-embed-text",
```

| 接口 | 作用 |
|------|------|

| `GET /mcp-servers/:id` | 详情 |

| `POST /mcp-servers/:id/tools/refresh` | 刷新工具列表（重新握手并覆盖缓存） |
| `GET /mcp-servers/:id/tools` | 实时发现工具列表（**不落库**） |
| `POST /mcp-servers/:id/tools/call` | 调试用：直接调用某个工具 |

`test` / `refresh` 返回 `{ success, status, transport, protocolVersion, serverInfo, instructions, tools, lastConnectedAt, message }`；
**失败不抛异常**，而是 `success:false + message`，前端可直接展示错误详情。

> **transport 有三种，不能只靠下拉框区分**：`STREAMABLE_HTTP`（推荐，2025-06-18 / 2025-03-26）
> 与旧版 `SSE`（2024-11-05）是**两套独立实现**，握手流程、响应解析、会话管理完全不同；
> `STDIO`（本地子进程，2026-10 新增）又是第三套 —— 没有 URL，靠 spawn 进程 + 换行分隔 JSON-RPC，
> 默认关闭（`MCP_STDIO_ENABLED=true` 才开放），命令受 `MCP_STDIO_ALLOWED_COMMANDS` 白名单限制。
> 枚举值是 `STREAMABLE_HTTP`，不是 "http"；`authType` 是 `NONE / API_KEY / BEARER_TOKEN`。
> 凭据自本轮起改为 **AES-256-GCM 加密存储**，接口只返回 `hasCredentials` + 掩码，绝不返回明文；
> stdio 的 `env` 同样加密（`envCipher`），只回显键名。
> 详见 `docs/后端代码逻辑/08` 第一节。
>
> Skill / MCP 已**后端完整 + 前端 API 封装 + 页面**（`api/skill.ts`、`api/mcp.ts`，`views/skills/`、`views/mcp/`）。

> 用户手动填了 modelId 仍被迫拉一堆用不上的模型。现在改成**只拉不落 → 勾选 → 按需添加**。

> **★ `capabilities` 已从 4 值扩到 8 值（多选，非互斥）**：
> `CHAT` / `STREAM` / `TOOLS` / `EMBEDDING` / `VISION` / `REASONING` / `RERANK` / `IMAGE_GENERATION`。
> 另有两个独立字段 `inputModalities` / `outputModalities`（`text | image | audio`）。
> 详见 **第 10 篇 §2.2 / §7.4** 与 `docs/后端代码逻辑/07`。

> **★ 向量模型必须「验证」过才能用于知识库**：
> `embeddingDimensions` 默认 `null`，`createTargetVersion()` 会直接 400。
> 流程是：模型管理页打上 `EMBEDDING` 能力 → 点「验证」→ 实测维度写入 → 知识库详情页才选得到它。

> **⚠️ 路由顺序坑（读代码时注意）**：`@Get('models')` 必须写在 `@Get(':id')` **之前**。

> 这是 NestJS 路由按**声明顺序**匹配导致的，不是 bug 但极易踩。

> **★ 三个地方会「绑定」这些模型**（都是**软引用**，只存 id 无外键）：
> - `Agent.llmModelId` —— Agent 用哪个对话模型

> - `KnowledgeBase.embeddingLlmModelId` —— 知识库用哪个 Embedding 模型

### 6.10 ★ 桌宠启动（**1** 个，`@Controller('desktop-pet')`，本次新增）

| 方法 | 路径 | 前端封装 | 干什么 |
|------|------|---------|--------|
| POST | `/api/desktop-pet/launch` | `api/desktopPet.ts` `launchDesktopPet()` | 在本机拉起桌宠客户端（Electron）；已在跑则唤起它的窗口 |

**前端在哪发**：`layout/components/AppHeader.vue` 右上角的小圆脸按钮（`title="打开桌宠"`）。

**为什么要绕后端**：浏览器沙箱不允许网页启动本地程序，自定义协议又要先安装注册。
所以只能「网页 → 后端 → 后端在本机 spawn Electron」。

**它顺带完成了登录**：接口把当前请求的 JWT 写进一个**一次性交接文件**
（`%TEMP%/xiaodie-handoff-<uuid>.json`，0600、60 秒 TTL），spawn 时只把**文件路径**
放进 `env.XIAODIE_HANDOFF` —— token 不走命令行参数，因为进程命令行对同机任何用户可见。
桌宠启动读到后立即删除并加密存进自己的 config，于是**点开就是登录状态，不弹登录面板**。
文件里还带 `baseUrl`（由请求 Host 推断）和 `userId`（换账号时桌宠据此丢弃旧会话）。

**响应**：

```json
{ "ok": true, "message": "已唤起桌宠；首次启动要等几秒，没看到的话看看是不是被别的窗口挡住了" }
```

**错误**：

| 状态码 | message | 原因 |
|---|---|---|
| 503 | `没找到桌宠客户端目录（desktop/）。这个功能要求后端和桌宠在同一台机器上。` | 后端在服务器上，或项目结构变了 |
| 503 | `桌宠依赖还没装好（desktop/node_modules 里没有 Electron）。先在 desktop 目录执行 npm install，再点一次。` | 没跑过 `npm install` |
| 401 | `登录已过期，请重新登录` | 未登录（接口有 `JwtAuthGuard`，不允许匿名 spawn 进程） |

> 桌宠自己的业务请求（`/auth/login`、`/platform/assistant`、`/agents/:id/chat/stream`）
> 全部复用既有接口，不经过这里 —— 启动是唯一必须由外部代劳的动作。

### 6.11 ★ TTS 语音合成（`src/tts/`，1 个接口，本次新增）

桌宠「边读边出字」的**后端兜底**通道：桌宠优先用本地 TTS，本地失败或没装时回退到这个后端代理把文本合成 mp3。

| 方法 | 路径 | 鉴权 | 前端 API | 说明 |
|------|------|------|----------|------|
| POST | `/api/tts/synthesize` | 需 | `synthesizeTts()` | body `{ text, voice?, rate?, pitch? }` → `{ format:'mp3', audio: base64 }` |

- `voice` 必须是服务端白名单 `VOICE_IDS`（`persona/persona.prompt.ts` 定义，与桌宠音色一致），否则回落默认 `zh-CN-XiaoyiNeural`；
- `rate` 默认 `1.0`（可传 `+50%` 这类相对值），`pitch` 默认 `+0Hz`；
- 用 `msedge-tts` 而不是 `edge-tts`：微软当前要求 Sec-MS-GEC **v2** 令牌（`edge-tts@1.0.x` 只发 v1，直接 403）；`msedge-tts` 已实现 v2 且带时钟偏差校正；
- `TtsService.synthesize()` 先把文本按句切片（≤800 字/段）逐段合成再 `Buffer.concat` 拼接，单段失败仅 `warn` 跳过，不中断整体；
- 音频以 base64 包在 JSON 返回，便于桌宠复用既有 JSON 请求通道（不另开二进制流）；
- 模块**零依赖**：`TtsModule` 只注册 Controller + Service，不碰 Prisma（详见 [后端代码逻辑 08](../后端代码逻辑/08-MCP-Skill-Storage-其他模块.md) 第九节）。

## 9. 给编程新手的「怎么看这一篇」

1. **先看公共约定**（§0）——理解 axios 解包、鉴权头、错误结构。
2. **按模块挑一个接口**，先看「前端类型」和「请求体 JSON」，想象数据长什么样。
3. **看「后端 DTO」**——这就是「前端传什么，后端才收什么」。
4. **看「处理」和「响应」**——后端怎么花式加工，最后返回什么。
5. **最后对「前端类型」**——两边字段名一致就通了；不一致的地方文档已用 ⚠️ 标出。

> 规律：后端返回一律是**下划线的 snake 分不清？不——全部 camelCase**！
> 只有**数据库列名**是下划线 `snake_case`（不在 JSON 里出现），JSON 字段全是驼峰。别搞混。
