## 1. 这个项目是什么？

一句话：

> **AI WorkFlow Studio 是一个「AI 工作流可视化编排平台」。你在网页上拖拽节点，把大模型、提示词、知识库检索、HTTP 请求、条件判断连成一条流水线，然后一键运行。**

### 1.1 用奶茶店打比方

工作流 = 奶茶店的制作流水线：

```
顾客点单（输入）
   ↓
加奶（Prompt 节点：把问题改写成更好的问法）
   ↓
查配方（RAG 节点：去知识库找资料）
   ↓
问厨师（LLM 节点：让大模型写答案）
   ↓
出杯（Output 节点：结果）
```

程序里，「加奶」「查配方」「问厨师」被抽象成一个个**节点（Node）**，节点之间用**连线（Edge）**串联。这条「节点 + 连线」的结构叫**工作流定义（Workflow Definition）**，它就是一份 JSON：

```json
{
  "nodes": [
    { "id": "start-1",   "type": "start",     "data": { "label": "开始" } },
    { "id": "llm-1",     "type": "llm",       "config": { "model": "qwen2.5:7b", "prompt": "你是一个助手" } },
    { "id": "output-1",  "type": "output",    "data": { "label": "输出" } }
  ],
  "edges": [
    { "id": "e1", "source": "start-1",  "target": "llm-1" },
    { "id": "e2", "source": "llm-1",    "target": "output-1" }
  ]
}
```

用户在浏览器上画出这个结构 → 前端把它发给后端 → 后端**引擎（Engine）**照着 JSON 一步步执行 → 最后返回结果。

**本教程最重要的一句话**：上面这份 JSON 就是**前端和后端之间传递的全部核心数据**。第 4、6、8 篇会把它的每个字段掰开讲。

## 2. 整体架构：一个请求怎么走完全程

```
┌──────────────────────────┐         ┌──────────────────────────┐        ┌─────────────────┐
│      前端 fronted         │  HTTP   │       后端 backend        │  SQL   │   PostgreSQL    │
│   Vue3 + Vite + VueFlow  │ ──────> │  NestJS + Prisma + JWT   │ ────> │  + pgvector     │
│   TDesign UI             │  JSON   │  接口层 + 业务层 + 引擎   │        │  10 张表        │
└──────────────────────────┘         └──────────────────────────┘        └─────────────────┘
             │                                    │                                │
             │ 浏览器访问 5173                     │ fetch localhost:11434          │
             v                                    v                                │
      ┌────────────────┐                 ┌──────────────────┐                    │
      │  Vite 开发代理   │                 │  Ollama 本地大模型 │                    │
      │ /api → :3000   │                 │ qwen2.5:7b 等     │                    │
      └────────────────┘                 │ nomic-embed-text │                    │
                                        └──────────────────┘                    │
                                             ▲                                    │
                                             │ enqueue / dequeue                  │
                              ┌──────────────────────────────┐                  │
                              │   Redis :6379（BullMQ 队列）  │ <────────────────┘
                              │   workflow-execution         │   Processor 跑完
                              │   document-processing        │   回写状态到 PG
                              └──────────────────────────────┘
```

> **架构里最关键的一条线**：所有**耗时任务**（跑工作流、解析文档+向量化）都不在 HTTP 请求里做，
> 而是「接口只负责**入队**并立刻返回 → Redis 排队 → 后台 **Processor** 慢慢跑 → 结果回写数据库」。
> 这就是本项目的 **BullMQ 异步队列**，第 2、4、7 篇会逐行拆解。

### 2.1 「运行一次工作流」的完整旅程（先有印象）

```
① 用户在 /workspace/:id 页面点「运行」，输入一句话
② 前端把「画布上的节点和连线」打包成 JSON
   POST /api/workflow/run/stream
   body: { "workflow": { "nodes": [...], "edges": [...] }, "input": "用户那句话" }
        ↓
③ 后端 WorkflowController 收到，手动把 HTTP 响应头改成 text/event-stream
        ↓
④ WorkflowEngine 找到 type === 'start' 的节点，开始 while 循环
        ↓
⑤ 每一步：registry.get(节点类型) → 拿到执行器 → 执行器.execute(context, 节点)
        ↓
⑥ 遇到 llm 节点 → LLMNodeExecutor → AIService → OllamaProvider
   → fetch http://localhost:11434/api/chat (stream: true)
        ↓
⑦ Ollama 一段段吐字 → 每来一段就 yield 一个事件
   → 控制器 response.write("data: {...}\n\n")
        ↓
⑧ 前端 fetch 的 getReader() 读到新的一帧 → 追加到聊天气泡 → 打字机效果
```

**这份教程会把这 8 步每一行代码都讲一遍。**

### 2.2 「耗时任务」怎么被搬到 Redis 上（BullMQ）

上面那条链路是**同步**的：浏览器一直等着，Ollama 慢慢吐字。一旦任务耗时几十秒到几分钟（跑完整工作流、解析大 PDF 再向量化），同步就撑不住了——HTTP 超时、Nginx 502、页面转圈。

所以本项目引入 **BullMQ**（基于 Redis 的 Node 任务队列），把耗时部分拆成两条链路：

```
【同步接口模式（页面要实时反馈的）】

① 前端 POST /api/workflow/run/stream
② 后端边执行边 yield 事件 → SSE 推回浏览器
③ 浏览器立刻看到打字机效果
   ✅ 适合：要「边跑边看」的
   ⚠️ 缺点：不能关页面、请求超时风险仍在


【异步队列模式（耗时久、只需要「最终结果」的）】

① 前端 POST /api/workflow/uploads… /api/workflows/:id/run
② 后端：建一条 WorkflowRun / Document 记录（status = QUEUED / UPLOADED）
        → 把任务丢进 Redis 队列
        → ★ 立刻返回 runId，HTTP 结束（通常 < 100ms）
③ 前端拿着 runId 轮询 GET /api/workflow-runs/:runId（每 2s 一次）
④ Redis 里的 Worker（@Processor 类）取到任务，后台慢慢执行
        状态：QUEUED → RUNNING → COMPLETED / FAILED
⑤ 前端轮询到 COMPLETED，拿 output 渲染
   ✅ 适合：跑工作流、解析文档+向量化
```

**两条队列一览：**

| 队列名 | Processor 类 | 谁入队 | 干什么 | 重试 |
|--------|-------------|--------|--------|------|
| `workflow-execution` | `WorkflowProcessor` | `POST /api/workflows/:id/run` | 读 `currentVersion.definition` → `WorkflowEngine.run()` → 回写 `WorkflowRun` | `attempts: 1`（不重试） |
| `document-processing` | `DocumentProcessor` | `POST /api/knowledge-bases/:kbId/documents` | 解析 → 切块 → 批量 embedding → 写 pgvector → 回写 `Document.status` | `attempts: 3` + 指数退避（3s 起） |

**代码位置**：`backend/src/queues/`
- `queues.module.ts` — 统一挂载两个 Processor
- `workflow-execution/workflow.processor.ts`
- `document-processing/document.processor.ts`

**三句话记住 BullMQ 的角色分工：**

| 角色 | 大白话 | 本项目对应 |
|------|--------|-----------|
| **Queue（队列）** | Redis 里的一个「待办清单」 | `BullModule.registerQueue({ name: 'workflow-execution' })` |
| **Job（任务）** | 清单上的一张纸条（`{ runId, input }`） | `queue.add('execute-workflow', {...})` |
| **Processor / Worker** | 后台干活的工人，循环从清单取纸条 | `@Processor('workflow-execution') class WorkflowProcessor extends WorkerHost` |

**⚠️ 一个必须知道的前提**：**Redis 挂了，后端启动就报错**。`app.module.ts` 里 `BullModule.forRoot` 在引导阶段就要连 Redis。所以 `docker-compose up -d` 必须把 Redis 一起拉起来（见第 1 篇）。

## 4. 8 种节点类型：后端引擎能执行什么

| 类型字符串 | 中文名 | 干什么 | 输出是什么 | 特殊能力 |
|-----------|--------|--------|-----------|---------|
| `start` | 开始 | 入口，把工作流初始输入透传下去 | `input` 原样 | — |
| `input` | 输入 | 中途再读一次初始输入 | `input` 原样 | — |
| `prompt` | 提示词 | 字符串模板拼装 + 变量替换 | 字符串 | 支持 `{{变量}}` |
| `rag` | 知识库检索 | 去 pgvector 找相关资料 | 拼好的文本 或 `{query, hits}` | 支持三种检索模式 |
| `http` | HTTP 请求 | 调外部 API | `{ status, headers, body }` | 带 SSRF 安全检查 |
| `llm` | 大模型 | 调 Ollama 生成文字 | 字符串 | **支持流式逐字返回** |
| `condition` | 条件判断 | 比较变量，决定走哪条路 | `true` / `false` | **唯一能分支的节点** |
| `output` | 输出 | 终点，把结果送出去 | `previousOutput ?? input` | — |

这 8 个字符串是**硬约定**：`WorkflowEngine` 拿节点 JSON 里的 `type` 字段去 `NodeExecutorRegistry` 查表。写错一个字母就会报 `没有找到 Node Executor: xxx`。

### 5.3 基础设施

| 技术 | 干什么 |
|------|--------|
| **Docker Compose** | 一键拉起 PostgreSQL(pgvector) 和 Redis |
| **Redis** | ★ **BullMQ 队列的存储**。两个队列的待办任务都躺在里面。**后端启动的硬依赖**，挂了起不来 |

> **为什么选 BullMQ 而不是「自己 new 一个 Promise 丢后台跑」？**
>
> | 需求 | 裸 Promise | BullMQ |
> |------|-----------|--------|
> | 不阻塞 HTTP 响应 | ✅ | ✅ |

### 6.2 队列装配的三行代码（先有个整体印象）

`app.module.ts`：

```typescript
BullModule.forRoot({                       // ① 全局 Redis 连接
  connection: {
    host: process.env.REDIS_HOST || 'localhost',
    port: Number(process.env.REDIS_PORT || 6379),

```

各业务模块里**声明自己要哪条队列**（`workflows.module.ts` / `knowledge.module.ts`）：

```typescript
BullModule.registerQueue({ name: 'workflow-execution' })   // ② 声明队列
BullModule.registerQueue({ name: 'document-processing' })
```

业务服务里**注入并使用**：

```typescript
constructor(@InjectQueue('workflow-execution') private queue: Queue) {}
await this.queue.add('execute-workflow', { runId, workflowId, input }, { attempts: 1 });
```

工人写在 `queues/` 下，靠 `@Processor('队列名')` 声明自己听哪条队列。

## 7. 必须先懂的术语（小白准备篇）

| 术语 | 大白话解释 |
|------|-----------|
| **API / 接口** | 后端对外开的「窗口」。前端通过 `POST /api/auth/login` 这样的地址调用功能 |
| **HTTP 方法** | GET=拿数据；POST=提交/触发；PUT=修改；DELETE=删除 |
| **JSON** | 前后端传数据的通用格式：`{ "name": "张三" }` |
| **JWT (Token)** | 后端发的一张带防伪签章的「通行证」，前端每次请求带着它，后端验章放行 |
| **SSE** | Server-Sent Events，服务器→客户端的单向实时通道。用来看 AI 打字机效果 |
| **流式 / Streaming** | 不等全部算完，边算边往外吐。本项目 LLM 节点是逐 token 吐的 |
| **ORM** | 把数据库的「表」变成代码里的「对象」。`prisma.user.create(...)` 就是在插一条用户 |
| **依赖注入 (DI)** | 写 `constructor(private x: X)` 框架就自动把 `X` 实例塞给你，不用手动 new |
| **DTO** | 一个类，用来声明「这个接口最多能传哪些字段、每个字段什么规则」。靠装饰器自动校验 |
| **Guard（守卫）** | 请求进来前的「保安」。`@UseGuards(JwtAuthGuard)` = 这个接口要验通行证 |
| **执行器 (Executor)** | 一个节点类型对应一个执行器类，负责「拿到节点配置 → 算出结果」 |
| **注册表 (Registry)** | 一张 `类型字符串 → 执行器` 的对照表，引擎靠它找到该用哪个执行器 |
| **向量 / Embedding** | 把一段文字变成一串数字（如 768 个浮点数），语义相近的文字数字也相近 |
| **RAG** | Retrieval-Augmented Generation。先从知识库「检索」资料，再把资料塞给大模型回答 |
| **topK** | 检索时只取最相关的 K 条。`topK: 5` = 取 5 条 |
| **余弦距离 (`<=>`)** | pgvector 算两个向量有多像的指标，**值越小越相似** |
| **BullMQ** | 基于 Redis 的任务队列库。把耗时活儿丢后台跑，接口立刻返回 |
| **Queue（队列）** | Redis 里的一个「待办清单」。本项目有 `workflow-execution` 和 `document-processing` 两条 |
| **Job（任务）** | 清单上的一张纸条。`queue.add(name, data, options)` 丢进去的 |
| **Processor / Worker** | 后台干活的工人。`@Processor('队列名')` + `extends WorkerHost`，实现 `process(job)` |
| **入队 enqueue** | 把任务丢进队列（`queue.add`）。接口在这步就结束了 |
| **出队 dequeue** | Worker 从队列取任务开始跑 |
| **轮询 polling** | 前端隔几秒查一次状态。本项目 `Document.status` 和 `WorkflowRun.status` 都靠它 |

## 10. 几条贯穿全项目的「坑」（提前知道会省很多时间）

| # | 坑 | 说明 |
|---|-----|------|
| 1 | **保存和运行发的 JSON 不一样** | 保存时节点 `type` 是 `"custom"`、配置在 `data` 里；运行时前端会改写成 `type: "llm"`、配置在 `config` 里。第 6 篇第 6 节详解 |
| 2 | **直接拿数据库里的 definition 去调 `/run` 会报错** | 因为存的是 `type: "custom"`，引擎不认识。第 4 篇第 5 节讲原因 |
| 3 | **运行接口没鉴权** | `POST /api/workflow/run` 和 `/run/stream` 是公开的（走队列的 `/workflows/:id/run` **有**鉴权） |
| 4 | **`run` 接口的 body 类型是 `any`** | 没有任何 DTO 校验，传错结构会变成 500 而不是 400 |
| 5 | **Condition 节点在 `context.data` 里是「三层对象」** | 别的节点存的是 `输出本身`，Condition 存的是 `{ result, branch, metadata }` |
| 6 | **引擎不支持一个节点被走两次** | 有防循环的 `visitedNodeIds` 检查，所以真正的「并行分支汇聚」目前跑不了 |
| 7 | **前端 `userInfo` 不持久化** | 只存了 token 到 localStorage，刷新后用户信息要重新登录才有 |
| 8 | **Redis 没起 → 后端起不来** | ★ `BullModule.forRoot` 在启动引导阶段就要连 Redis，报 `ECONNREFUSED` |
| 9 | **★ 队列重试会重复插入 chunk**（已修） | 以前 `attempts: 3` 重投时 `createMany` 前不删旧 chunk，会重复插入并重复 `increment chunkCount`。现在 `DocumentProcessor` 开头加了幂等保护：`count` 出残留量 → `$transaction` 里 `deleteMany` + `decrement chunkCount` |
| 10 | **★ `uploadDocument` 返回类型和后端对不上**（已修） | 以前声明 `Promise<DocumentItem>`，后端实际返回 `{ documentId, jobId, status, message }`。现在新增 `UploadDocumentResult` 接口，返回类型改对了 |
| 11 | **★ 走队列的 3 个接口前端没封装**（已修） | 以前 `api/workflow.ts` 里没有 `enqueueRun / getRun / listRuns`，页面点「运行」走的还是旧的同步 SSE。现在三个函数 + `WorkflowRun` / `EnqueueRunRequest` 类型都补齐，画布「运行」按钮改成入队 + 2s 轮询 |
| 12 | **★ 上传变成异步后，Document 状态会「卡在」UPLOADED** | 后端只保证 `UPLOADED`，之后靠 `DocumentProcessor` 改。前端 `detail.vue` 已经加了 2s 轮询，所以没问题；但**直接用 curl 测会看到 `UPLOADED` 不动** |
| 13 | **★ 点「运行」跑的是数据库里最新的版本，不是你眼前的画布** | `enqueueRun` 只发 `{ workflowId, input }`，`WorkflowProcessor` 读 `currentVersion.definition`。**改完画布必须先保存再运行**，否则跑的是上一版 |
| 14 | **★ SSE 调试入口没接按钮** | `workflow.vue` 里 `handleRunWorkflowStream()`（SSE 打字机）函数还在，但 `@confirm` 只绑了 `handleRunWorkflow`（异步队列）。所以 `POST /workflow/run/stream` 从页面上**已经点不到**了，只能 curl 测 |
| 15 | **★ 轮询没有超时兜底** | `pollRunResult` 用 `setInterval` 每 2s 查一次，只在 `COMPLETED` / `FAILED` 时 `clearInterval`；请求报错只 `console.error` 然后继续等。Worker 卡死时对话框会一直转，只能手动取消 |
| 16 | **队列模式没有 SSE，拿不到打字机效果** | 队列是「跑完给结果」，要实时反馈只能用 `/workflow/run/stream`。二者不能兼得 |
| 17 | **`Document.status` 失败后不会自动重试到成功** | `attempts: 3` 是队列级重试；三次都挂就是 FAILED，需要用户删了重传 |
