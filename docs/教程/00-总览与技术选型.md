## 1. 这个项目是什么？

一句话：

> **AI WorkFlow Studio 是一个「AI 工作流可视化编排平台」。你在网页上拖拽节点，把大模型、提示词、知识库检索、HTTP 请求、条件判断连成一条流水线，然后一键运行。**

### 1.1 用奶茶店打比方

工作流 = 奶茶店的制作流水线：

```
顾客点单（输入）
   ↓
加奶（Prompt 节点：把问题改写成更好的问法）
   ↓
查配方（RAG 节点：去知识库找资料）
   ↓
问厨师（LLM 节点：让大模型写答案）
   ↓
出杯（Output 节点：结果）
```

程序里，「加奶」「查配方」「问厨师」被抽象成一个个**节点（Node）**，节点之间用**连线（Edge）**串联。这条「节点 + 连线」的结构叫**工作流定义（Workflow Definition）**，它就是一份 JSON：

```json
{
  "nodes": [
    { "id": "start-1",   "type": "start",     "data": { "label": "开始" } },
    { "id": "llm-1",     "type": "llm",       "config": { "model": "qwen2.5:7b", "prompt": "你是一个助手" } },
    { "id": "output-1",  "type": "output",    "data": { "label": "输出" } }
  ],
  "edges": [
    { "id": "e1", "source": "start-1",  "target": "llm-1" },
    { "id": "e2", "source": "llm-1",    "target": "output-1" }
  ]
}
```

用户在浏览器上画出这个结构 → 前端把它发给后端 → 后端**引擎（Engine）**照着 JSON 一步步执行 → 最后返回结果。

**本教程最重要的一句话**：上面这份 JSON 就是**前端和后端之间传递的全部核心数据**。第 4、6、8 篇会把它的每个字段掰开讲。

## 2. 整体架构：一个请求怎么走完全程

```
┌──────────────────────────┐         ┌──────────────────────────┐        ┌─────────────────┐
│      前端 fronted         │  HTTP   │       后端 backend        │  SQL   │   PostgreSQL    │
│   Vue3 + Vite + VueFlow  │ ──────> │  NestJS + Prisma + JWT   │ ────> │  + pgvector     │
│   TDesign UI             │  JSON   │  接口层 + 业务层 + 引擎   │        │  31 张表        │
└──────────────────────────┘         └──────────────────────────┘        └─────────────────┘
             │                                    │                                │
             │ 浏览器访问 5173                     │ fetch localhost:11434          │
             v                                    v                                │
      ┌────────────────┐                 ┌──────────────────┐                    │
      │  Vite 开发代理   │                 │  Ollama 本地大模型 │                    │
      │ /api → :3000   │                 │ qwen2.5:7b 等     │                    │
      └────────────────┘                 │ nomic-embed-text │                    │
                                        └──────────────────┘                    │
                                             ▲                                    │
                                             │ enqueue / dequeue                  │
                              ┌──────────────────────────────┐                  │
                              │   Redis :6379（BullMQ 队列）  │ <────────────────┘
                              │   workflow-execution         │   Processor 跑完
                              │   document-processing        │   回写状态到 PG
                              └──────────────────────────────┘
```

> **架构里最关键的一条线**：所有**耗时任务**（跑工作流、解析文档+向量化）都不在 HTTP 请求里做，
> 而是「接口只负责**入队**并立刻返回 → Redis 排队 → 后台 **Processor** 慢慢跑 → 结果回写数据库」。
> 这就是本项目的 **BullMQ 异步队列**，第 2、4、7 篇会逐行拆解。

### 2.1 「运行一次工作流」的完整旅程（先有印象）

> ⚠️ 阅读提示：现在画布上有**两个运行按钮**——「运行（异步）」走 §2.2 的 BullMQ 队列；「调试运行（SSE）」走下面这条实时链路，适合试跑当前画布、看打字机效果。

```
① 用户在 /workspace/:id 页面点「调试运行（SSE）」，输入一句话
② 前端把「画布上的节点和连线」打包成 JSON
   POST /api/workflow/run/stream
   body: { "workflow": { "nodes": [...], "edges": [...] }, "input": "用户那句话" }
        ↓
③ 后端 WorkflowController 收到，手动把 HTTP 响应头改成 text/event-stream
        ↓
④ WorkflowEngine 找到 type === 'start' 的节点，开始 while 循环
        ↓
⑤ 每一步：registry.get(节点类型) → 拿到执行器 → 执行器.execute(context, 节点)
        ↓
⑥ 遇到 llm 节点 → LLMNodeExecutor → AIService → OllamaProvider
   → fetch http://localhost:11434/api/chat (stream: true)
        ↓
⑦ Ollama 一段段吐字 → 每来一段就 yield 一个事件
   → 控制器 response.write("data: {...}\n\n")
        ↓
⑧ 前端 fetch 的 getReader() 读到新的一帧 → 追加到聊天气泡 → 打字机效果
```

**这份教程会把这 8 步每一行代码都讲一遍。**

### 2.2 「耗时任务」怎么被搬到 Redis 上（BullMQ）

上面那条链路是**同步**的：浏览器一直等着，Ollama 慢慢吐字。一旦任务耗时几十秒到几分钟（跑完整工作流、解析大 PDF 再向量化），同步就撑不住了——HTTP 超时、Nginx 502、页面转圈。

所以本项目引入 **BullMQ**（基于 Redis 的 Node 任务队列），把耗时部分拆成两条链路：

```
【同步接口模式（页面要实时反馈的）】

① 前端 POST /api/workflow/run/stream
② 后端边执行边 yield 事件 → SSE 推回浏览器
③ 浏览器立刻看到打字机效果
   ✅ 适合：要「边跑边看」的
   ⚠️ 缺点：不能关页面、请求超时风险仍在


【异步队列模式（耗时久、只需要「最终结果」的）】

① 前端 POST /api/workflows/:id/run（跑工作流）或 POST /api/knowledge-bases/:kbId/documents（上传文档）
② 后端：建一条 WorkflowRun / Document 记录（status = QUEUED / UPLOADED）
        → 把任务丢进 Redis 队列
        → ★ 立刻返回 runId，HTTP 结束（通常 < 100ms）
③ 前端拿着 runId 轮询 GET /api/workflow-runs/:runId（每 2s 一次）
④ Redis 里的 Worker（@Processor 类）取到任务，后台慢慢执行
        状态：QUEUED → RUNNING → COMPLETED / FAILED
⑤ 前端轮询到 COMPLETED，拿 output 渲染
   ✅ 适合：跑工作流、解析文档+向量化
```

**四条队列一览：**

| 队列名 | Processor 类 | 谁入队 | 干什么 | 重试 |
|--------|-------------|--------|--------|------|
| `workflow-execution` | `WorkflowProcessor` | `POST /api/workflows/:id/run` | 读 `currentVersion.definition` → `WorkflowEngine.run()` → 回写 `WorkflowRun` | `attempts: 1`（不重试） |
| `document-processing` | `DocumentProcessor` | `POST /api/knowledge-bases/:kbId/documents`、★ `POST /api/documents/:id/reprocess` | 解析 → 切块 → 按**生效向量版本**批量 embedding → 写版本物理表 → 回写 `Document.status` | `attempts: 3` + 指数退避（3s 起） |
| **`knowledge-reembed`** ★ | `ReEmbeddingProcessor` | ★ `POST /api/knowledge-bases/:id/embedding-versions/:vid/re-embed` | **换 Embedding 模型后的重新向量化**：复用已有文本块（不重新解析），分批 64 条写新版本物理表 | `attempts: 2` + 指数退避（5s 起） |
| **`chat-file-processing`** ★ | `ChatFileProcessingProcessor` | 聊天附件上传（`POST /api/chat/files/upload`） | 解析附件 → 按扩展名派发 6 个解析器 → 状态置 READY，供 Agent 组装上下文 | `attempts: 2` + 指数退避（2s 起） |

**代码位置**：
- `backend/src/queues/` —— `queues.module.ts` 统一挂载 **三个** Processor（workflow-execution / document-processing / re-embedding）
- ★ `chat-file-processing` 的队列注册与 Processor 都在 `backend/src/chat-files/`（`chat-file-processing.processor.ts`，`chat-files.module.ts` 里 `BullModule.registerQueue`）—— 它不归 queues 目录管

**三句话记住 BullMQ 的角色分工：**

| 角色 | 大白话 | 本项目对应 |
|------|--------|-----------|
| **Queue（队列）** | Redis 里的一个「待办清单」 | `BullModule.registerQueue({ name: 'workflow-execution' })` |
| **Job（任务）** | 清单上的一张纸条（`{ runId, input }`） | `queue.add('execute-workflow', {...})` |
| **Processor / Worker** | 后台干活的工人，循环从清单取纸条 | `@Processor('workflow-execution') class WorkflowProcessor extends WorkerHost` |

**⚠️ 一个必须知道的前提**：**Redis 挂了，后端启动就报错**。`app.module.ts` 里 `BullModule.forRoot` 在引导阶段就要连 Redis。所以 `docker-compose up -d` 必须把 Redis 一起拉起来（见第 1 篇）。

### 3.8 ★ Agent 管理 + 对话 + 会话 `src/agent/`（13 个接口）

> 现在 Agent 是**持久化、可配置的实体**（`Agent` 表）：模型、系统提示词、绑定的工作流/知识库/Skill/MCP 都存在数据库里。

### 3.15 ★ 桌宠启动 `src/desktop-pet/`（1 个接口，本次新增）

浏览器沙箱**不允许网页启动本地程序**，自定义协议（`xiaodie://`）又要先安装注册、开发期常被拦。
所以「网页点一下打开桌宠」只能绕后端：网页 → 这个接口 → 后端在本机 `spawn` Electron。

| 方法 | 路径 | 鉴权 | 前端在哪发 | 干什么 |
|------|------|------|-----------|--------|
| POST | `/api/desktop-pet/launch` | 需 | `api/desktopPet.ts` `launchDesktopPet()`（Header 右上角小圆脸图标） | 在本机拉起桌宠；已在跑则把它叫到最前面 |

三个实现细节：

1. **目录靠探测不靠写死**：从 `process.cwd()` 和 `__dirname` 分别往上找 `desktop/package.json`，
   不管后端是 `npm run start:dev` 还是 `node dist/src/main.js` 启动都能找到（不依赖 tsconfig 的 `rootDir`）。
2. **必须删掉 `ELECTRON_RUN_AS_NODE`**：本机环境预设了这个变量，Electron 会以纯 Node 模式启动并直接崩
   （`Cannot read properties of undefined (reading 'handle')`）。
3. **重复点击是安全的**：桌宠主进程有 `requestSingleInstanceLock()`，第二次启动立刻退出、
   并唤起第一个实例；服务端另有 3 秒防抖，避免连点产生一串短命进程。

**它顺带完成了登录**（所以桌宠点开就是登录状态，不弹登录面板）：

```
POST /desktop-pet/launch（带 JWT）
   → 后端写 %TEMP%/xiaodie-handoff-<uuid>.json（token / baseUrl / userId / email / expiresAt，0600，60 秒 TTL）
   → spawn 时只把【文件路径】放进 env.XIAODIE_HANDOFF
   → 桌宠启动读文件 → 立即删除 → safeStorage 加密存进自己的 config → 后台拉 /platform/assistant
```

> token 为什么不能走命令行参数：**进程的命令行对同机任何用户都可见**，`--token=xxx` 等于公开。
> 另外交接文件必须在**拿单实例锁之前**读 —— 桌宠已开着时第二个进程拿不到锁会立刻退出，
> 它的环境变量传不到第一个实例，靠 `requestSingleInstanceLock({ handoff })` 把数据带过去。

> 这个接口只在**后端与用户同机**时有意义。后端部署在服务器上会找不到 `desktop/` 目录，
> 接口返回 503 并说明原因 —— 不假装成功让人干等。
> 桌宠自己的业务请求（拉助理信息 / SSE 对话）都走既有接口，不经过这里。

### 3.16 ★ TTS 语音合成 `src/tts/`（1 个接口，本次新增）

桌宠「边读边出字」的**后端兜底**：桌宠优先用本地 TTS，本地失败 / 没装时回退到这个后端代理把文本合成 mp3。

| 方法 | 路径 | 鉴权 | 前端 API | 说明 |
|------|------|------|----------|------|
| POST | `/api/tts/synthesize` | 需 | `synthesizeTts()` | 文本 → 返回 `{ format:'mp3', audio: base64 }` |

- `voice` 必须是服务端白名单 `VOICE_IDS`（定义在 `persona/persona.prompt.ts`，与桌宠音色一致），否则回落默认 `zh-CN-XiaoyiNeural`；
- 用 `msedge-tts`（不是 `edge-tts`）：微软现要求 Sec-MS-GEC **v2** 令牌，`edge-tts@1.0.x` 只发 v1 会 403；
- 长文本按句切片（≤800 字/段）逐段合成再拼接，降低首字延迟；单段失败只 warn 跳过不中断；
- 音频以 base64 包在 JSON 里返回，便于桌宠复用既有 JSON 请求通道（不另开二进制流）；
- 模块零依赖：`TtsModule` 只注册 Controller + Service，不碰 Prisma（见 [后端代码逻辑 08](../后端代码逻辑/08-MCP-Skill-Storage-其他模块.md) 第九节）。

## 4. 8 种节点类型：后端引擎能执行什么

| 类型字符串 | 中文名 | 干什么 | 输出是什么 | 特殊能力 |
|-----------|--------|--------|-----------|---------|
| `start` | 开始 | 入口，把工作流初始输入透传下去 | `input` 原样 | — |
| `input` | 输入 | 中途再读一次初始输入 | `input` 原样 | — |
| `prompt` | 提示词 | 字符串模板拼装 + 变量替换 | 字符串 | 支持 `{{变量}}` |
| `rag` | 知识库检索 | 去 pgvector 找相关资料 | 拼好的文本 或 `{query, hits}` | 支持三种检索模式 |
| `http` | HTTP 请求 | 调外部 API | `{ status, headers, body }` | 带 SSRF 安全检查 |
| `llm` | 大模型 | 调大模型生成文字 | 字符串 | **支持流式逐字返回**；可选自建模型（`llmModelId`）、注入 Skill、调用 MCP 工具、简单模式 RAG |
| `condition` | 条件判断 | 比较变量，决定走哪条路 | `true` / `false` | **唯一能分支的节点** |
| `output` | 输出 | 终点，把结果送出去 | `previousOutput ?? input` | — |

这 8 个字符串是**硬约定**：`WorkflowEngine` 拿节点 JSON 里的 `type` 字段去 `NodeExecutorRegistry` 查表。写错一个字母就会报 `没有找到 Node Executor: xxx`。

> ⚠️ **v1.5+ 补充**：引擎开头会先执行 `normalizeWorkflow()` 做「归一化」——保存格式里的 `type: "custom"` 会被自动提升成 `data.nodeType`，`data` 里的配置也会铺平到 `config`。所以「直接拿数据库 definition 跑」不再必然报错；只有归一化后仍不认识这个类型（`data.nodeType` 也缺失或写错）才会报 `没有找到 Node Executor: xxx`。
>
> ⚠️ **LLM 节点 v1.5 新增能力**（第 4、10 篇详解）：`config.llmModelId`（用「模型管理」里的自建模型，为空回退本地 Ollama）、`config.skillIds`（把 Skill 的 instructions 注入 System Prompt）、`config.mcpServerIds`（把 MCP 工具交给 LLM 调用）、`config.enableRag` + `knowledgeBaseIds`（简单模式：节点内直接检索知识库并注入 `{{rag_context}}`）。

### 5.3 基础设施

| 技术 | 干什么 |
|------|--------|
| **Docker Compose** | 一键拉起 PostgreSQL(pgvector) 和 Redis |
| **Redis** | ★ **BullMQ 队列的存储**。四条队列的待办任务都躺在里面。**后端启动的硬依赖**，挂了起不来 |

> | 需求 | 裸 Promise | BullMQ |

> | 不阻塞 HTTP 响应 | ✅ | ✅ |
> | 进程重启后任务不丢 | ❌ 全丢 | ✅ 存在 Redis |
> | 失败自动重试 | ❌ | ✅ `attempts` + 指数退避 |
> | 能看任务状态/进度 | ❌ | ✅ `job.updateProgress(n)` |
> | 能横向扩容多个工人 | ❌ | ✅ 起多个实例自动抢任务 |
> | 能查历史运行记录 | ❌ | ✅ 本项目另外落 `WorkflowRun` 表 |

constructor(@InjectQueue('workflow-execution') private queue: Queue) {}

## 7. 必须先懂的术语（小白准备篇）

| 术语 | 大白话解释 |
|------|-----------|
| **API / 接口** | 后端对外开的「窗口」。前端通过 `POST /api/auth/login` 这样的地址调用功能 |
| **HTTP 方法** | GET=拿数据；POST=提交/触发；PUT=修改；DELETE=删除 |
| **JSON** | 前后端传数据的通用格式：`{ "name": "张三" }` |
| **JWT (Token)** | 后端发的一张带防伪签章的「通行证」，前端每次请求带着它，后端验章放行 |
| **SSE** | Server-Sent Events，服务器→客户端的单向实时通道。用来看 AI 打字机效果 |
| **流式 / Streaming** | 不等全部算完，边算边往外吐。本项目 LLM 节点是逐 token 吐的 |
| **ORM** | 把数据库的「表」变成代码里的「对象」。`prisma.user.create(...)` 就是在插一条用户 |
| **依赖注入 (DI)** | 写 `constructor(private x: X)` 框架就自动把 `X` 实例塞给你，不用手动 new |
| **DTO** | 一个类，用来声明「这个接口最多能传哪些字段、每个字段什么规则」。靠装饰器自动校验 |
| **Guard（守卫）** | 请求进来前的「保安」。`@UseGuards(JwtAuthGuard)` = 这个接口要验通行证 |
| **执行器 (Executor)** | 一个节点类型对应一个执行器类，负责「拿到节点配置 → 算出结果」 |
| **注册表 (Registry)** | 一张 `类型字符串 → 执行器` 的对照表，引擎靠它找到该用哪个执行器 |
| **向量 / Embedding** | 把一段文字变成一串数字（如 768 个浮点数），语义相近的文字数字也相近 |
| **RAG** | Retrieval-Augmented Generation。先从知识库「检索」资料，再把资料塞给大模型回答 |
| **topK** | 检索时只取最相关的 K 条。`topK: 5` = 取 5 条 |
| **余弦距离 (`<=>`)** | pgvector 算两个向量有多像的指标，**值越小越相似** |
| **Provider（提供商）** | 一个能调大模型的服务端。本项目支持 4 种：Ollama / OpenAI / DeepSeek / OpenAI 兼容 |
| **API Key** | 调云端大模型的「付费凭证」。本项目**加密存储**（AES-256-GCM），接口只返回脱敏串 |
| **AES-256-GCM** | 一种对称加密算法：同一把密钥加/解密，GCM 模式自带「防篡改」校验 |
| **脱敏 / Mask** | 把敏感串中间盖掉再返回（如 `sk-a****1234`），防止密钥泄露 |
| **回退（Fallback）** | 首选不可用时自动改备选。本项目「没配自建模型 → 用本地 Ollama」 |
| **`llmModelId`** | 指向用户在「模型管理」里添加的模型的指针；有它用自建模型，为空回退本地 Ollama |
| **BullMQ** | 基于 Redis 的任务队列库。把耗时活儿丢后台跑，接口立刻返回 |
| **Queue（队列）** | Redis 里的一个「待办清单」。本项目有 `workflow-execution`、`document-processing`、`knowledge-reembed`、`chat-file-processing` 四条 |
| **Job（任务）** | 清单上的一张纸条。`queue.add(name, data, options)` 丢进去的 |
| **Processor / Worker** | 后台干活的工人。`@Processor('队列名')` + `extends WorkerHost`，实现 `process(job)` |
| **入队 enqueue** | 把任务丢进队列（`queue.add`）。接口在这步就结束了 |
| **出队 dequeue** | Worker 从队列取任务开始跑 |
| **轮询 polling** | 前端隔几秒查一次状态。本项目 `Document.status` 和 `WorkflowRun.status` 都靠它 |
| **人格（Persona）** | 平台助理「怎么说话」的配置：名字、语气标签、提示词、音色。★ 它只是 System Prompt 里的**一个片段**，不改变助理能调哪些工具 |
| **记忆召回（Recall）** | 对话前先从用户的历史记忆里挑几条相关的塞进 Prompt。本项目打分 = `0.6*相关度 + 0.2*重要度 + 0.2*新鲜度` |
| **记忆沉淀（Capture）** | 对话结束后让模型总结「这轮有什么值得记的」，写成 `Memory` 条目。★ fire-and-forget，失败不影响回复 |

## 10. 几条贯穿全项目的「坑」（提前知道会省很多时间）

| # | 坑 | 说明 |
|---|-----|------|
| 1 | **保存和运行发的 JSON 不一样** | 保存时节点 `type` 是 `"custom"`、配置在 `data` 里；运行时前端会改写成 `type: "llm"`、配置在 `config` 里。⚠️ 现在即使不改写，引擎也会自动归一化（见坑 #2），但前端改写能让行为更一致。第 6 篇第 6 节详解 |
| 2 | **直接拿数据库里的 definition 去调 `/run` 会报错** | 因为存的是 `type: "custom"`，引擎不认识。第 4 篇第 5 节讲原因 |
| 3 | **运行接口没鉴权** | `POST /api/workflow/run` 和 `/run/stream` 是公开的（走队列的 `/workflows/:id/run` **有**鉴权） |
| 4 | **`run` 接口的 body 类型是 `any`** | 没有任何 DTO 校验，传错结构会变成 500 而不是 400 |
| 5 | **Condition 节点在 `context.data` 里是「三层对象」** | 别的节点存的是 `输出本身`，Condition 存的是 `{ result, branch, metadata }` |
| 6 | **引擎不支持一个节点被走两次** | 有防循环的 `visitedNodeIds` 检查，所以真正的「并行分支汇聚」目前跑不了 |
| 7 | **前端 `userInfo` 不持久化** | 只存了 token 到 localStorage，刷新后用户信息要重新登录才有 |
| 8 | **Redis 没起 → 后端起不来** | ★ `BullModule.forRoot` 在启动引导阶段就要连 Redis，报 `ECONNREFUSED` |
| 9 | **★ 队列重试会重复插入 chunk**（已修） | 以前 `attempts: 3` 重投时 `createMany` 前不删旧 chunk，会重复插入并重复 `increment chunkCount`。现在 `DocumentProcessor` 开头加了幂等保护：`count` 出残留量 → `$transaction` 里 `deleteMany` + `decrement chunkCount` |
| 10 | **★ `uploadDocument` 返回类型和后端对不上**（已修） | 以前声明 `Promise<DocumentItem>`，后端实际返回 `{ documentId, jobId, status, message }`。现在新增 `UploadDocumentResult` 接口，返回类型改对了 |
| 11 | **★ 走队列的 3 个接口前端没封装**（已修） | 以前 `api/workflow.ts` 里没有 `enqueueRun / getRun / listRuns`，页面点「运行」走的还是旧的同步 SSE。现在三个函数 + `WorkflowRun` 类型都补齐，画布「运行」按钮改成「先保存 → 入队 → 2s 轮询」 |
| 12 | **★ 上传变成异步后，Document 状态会「卡在」UPLOADED** | 后端只保证 `UPLOADED`，之后靠 `DocumentProcessor` 改。前端 `detail.vue` 已经加了 2s 轮询，所以没问题；但**直接用 curl 测会看到 `UPLOADED` 不动** |
| 13 | **★ 点「运行」前会自动保存当前画布（已修）** | `handleRunWorkflow` 会先调 `saveWorkflow()` 把画布保存成新版本，再 `enqueueRun`，`WorkflowProcessor` 读 `currentVersion.definition`。所以现在「运行」跑的就是你眼前的内容；用 curl 直接调 `enqueueRun` 时仍要自己保证已保存 |
| 14 | **★ SSE 调试入口已有按钮（已修）** | ~~没接按钮~~ → `workflow.vue:920-921` 现在有「调试运行（SSE）」按钮，绑 `handleRunWorkflowStream()`，title 写明「直接在前端传 definition 运行，未保存的画布改动也能试跑」。所以 `POST /workflow/run/stream` 可从页面直接触发 |
| 15 | **★ 轮询已有超时兜底（已修）** | `pollRunResult` 每 2s 查一次（`POLL_INTERVAL_MS`），最多 150 次（`POLL_MAX_COUNT`，约 5 分钟）后自动停止并提示超时；`stopRunPolling` / `onBeforeUnmount` 也会清理定时器 |
| 16 | **队列模式没有 SSE，拿不到打字机效果** | 队列是「跑完给结果」，要实时反馈只能用 `/workflow/run/stream`。二者不能兼得 |
| 17 | **`Document.status` 失败后不会自动重试到成功** | `attempts: 3` 是队列级重试；三次都挂就是 FAILED，需要用户删了重传 |
| 18 | **★ `storagePath` 有两种语义** | 本地存储 = 磁盘绝对路径；七牛云 = 对象 key。切了 `STORAGE_TYPE=qiniu` 后，私有空间下载要签名；删知识库 / 删文档都已通过 `StorageService.delete()` 统一清理对象（见 **附录 09** 坑⑦，已修复） |
| 19 | **★ `migrate dev` 曾把 `embedding` 列/索引 DROP 了**（已修） | schema 没声明时 Prisma 视向量列为「多余列」。现在 `DocumentChunk.embedding` 用 `Unsupported("vector(768)")?` 占位 + 手写恢复迁移 `20261010110000_restore_pgvector_embedding`；但 `DROP INDEX "dc_embedding_ivf"` 仍可能混进新迁移，跑完 `migrate dev` 要检查 |
| 20 | **★ Prisma 7 的 `datasource` 不写 `url`** | `schema.prisma:5-7` 只有 `provider = "postgresql"`。连接串两处提供：运行时由 `PrismaService` 传给 `new PrismaPg({ connectionString })`，CLI 由 `prisma.config.ts` 的 `env("DATABASE_URL")` 提供。**按 Prisma 6 的习惯去 schema 里找 url 会找不到** |
| 21 | **★ Prisma 7 不再自动加载 `.env`** | 靠两处显式 `import 'dotenv/config'`：`main.ts:1`（运行时）和 `prisma.config.ts:1`（CLI）。**漏了 `prisma.config.ts` 里那行，`prisma migrate` 会报连不上库** |
| 22 | **★ 后端没有开 CORS** | `main.ts` 里**没有 `enableCors()`**。浏览器直连 `:3000` 会被同源策略拦掉，开发时必须走 Vite 的 `/api` 代理（见第 1 篇）。用 Postman/curl 直连没事 |
| 23 | **★ 删知识库时文件删不干净（已修复）** | `knowledge.service.ts` 原先 `fs.rm(uploads/<kbId>)` 删目录，而文档实际存在 `uploads/documents/<uuid>.ext`（local）或 `documents/<date>/<uuid>.<ext>`（qiniu），路径对不上且七牛对象也删不掉。**现已改为**：删库前先按 `Document.storagePath` 逐个调 `StorageService.delete()`（local→unlink、qiniu→删对象），再级联删 DB 记录 |
| 24 | **★ JWT 校验每次都查库** | `jwt.strategy.ts:31-37` 的 `validate()` 会 `findUnique` 用户，查不到就抛「用户不存在，请重新登录」。好处是**删号后旧 token 立即失效**；代价是每次请求多一次 DB 查询 |
| 25 | **★ 模型引用是「软引用」，没有外键** | `Agent.llmModelId` / `KnowledgeBase.embeddingLlmModelId` 指向 `LlmModel.id` 但**没有 `@relation`**。删掉模型不会清空引用，指向它的 Agent / 知识库要到运行时才报错。**删模型前先确认没人引用**（第 10 篇 §9） |
| 26 | **★ API Key 加密密钥不能随便改** | `LLM_CONFIG_ENCRYPTION_KEY`（回退 `JWT_SECRET`）是全局一把。**改了它，之前存的 `encryptedApiKey` 全部解不开**（`decrypt` 抛错）。生产环境务必固定住（第 10 篇 §3、§9） |
| 27 | **★ 没配自建模型不会报错（这是设计）** | `llmModelId` 为空时，Agent / LLM 节点 / 知识库都**回退本地 Ollama**。所以「模型下拉选了 Ollama 本地」和「完全没配模型」行为一样，属于向后兼容，不是 bug |
| 28 | **★ `GET /llm-configs/models` 的路由顺序** | 必须写在 `GET /llm-configs/:id` **之前**，否则 Nest 把 `models` 当成 `:id` 参数匹配，`ParseUUIDPipe` 直接报 400（第 10 篇 §5.1） |
| 29 | **★ 人格不要往 `Agent` 表里塞** | `AgentService.update()` 对系统 Agent 只放开 `llmModelId / model / temperature` 三个字段（`SYSTEM_AGENT_EDITABLE_FIELDS`），多带任何一个字段整个请求 400。所以人格存独立表 `AgentPersona`，走自己的 `PersonaService`（第 12 篇） |
| 30 | **★ 记忆列表接口不返回 `content`** | `GET /memories` 的 `select` 里刻意排除了正文，只有 `summary`；要看全文得单独 `GET /memories/:id`。3D 图一次要 500 个节点，带上正文会把响应撑到几 MB |
