# AI WorkFlow Studio 学习指南
## 第 6 篇：前端业务与端到端链路 —— 从「用户点按钮」到「后端返回结果」

> **本篇核心**：把你已经学到的所有部分串成**完整的闭环**。
> 走 4 条真实链路：**登录 → 对话 → 工作流保存 → 工作流运行**。
> 每一条都按「前端发什么 → 后端收什么处理什么 → 返回到前端」来讲，并且讲清 **保存 vs 运行** 这对最容易踩坑的数据差异。

## 1. 链路一：登录

### 1.1 完整时序

```
用户点「Sign In」
  ↓
① 前端表单校验（TDesign form rules：邮箱格式、密码≥6位）
  ↓ 通过
② submitForm() 调 api：POST /api/auth/login
    body: { "email": "...", "password": "..." }
  ↓
③ 后端 AuthController @Body() LoginDto → ValidationPipe 校验
  ↓ 通过
④ AuthService.login()
    prisma.user.findUnique({ where: { email } })   // 查不存在 → 401
    bcrypt.compare(密码, user.passwordHash)        // 不对 → 401
    jwtService.signAsync({ sub: user.id, email, username })
  ↓
⑤ 返回 { user, accessToken }
  ↓
⑥ 前端收到：
    userStore.setToken(response.accessToken)   → ref + localStorage
    userStore.setUserInfo(response.user)       → 内存
  ↓
⑦ router.push(redirect || "/chat")
```

### 1.2 前端处理 400/401 报错的小细节

```typescript
} catch (error) {
  if (axios.isAxiosError(error)) {
    const message = error.response?.data?.message;
    errorMessage.value = Array.isArray(message)
      ? message.join("；")                    // ← 后端校验错误的 message 是数组！
      : message || "请求失败，请稍后重试";
  }
}
```

**为什么 message 可能是数组？** 因为后端 `ValidationPipe` 对一请求的多个字段错误会一次性返回：

```json
{ "message": ["username 不能为空", "password must be longer than or equal to 6 characters"] }
```

页面用 `；` 拼起来显示给用户。

**⚠️ 404？** 如果后端没启动（代理打不到 3000），`error.response` 是 undefined → 走最后一行 else："请求失败，请检查网络连接"。

### 1.3 一个「表单校验 vs 后端校验」的双保险模型

| 层 | 谁负责 | 规则 | 目的 |
|----|--------|------|------|
| 前端 | TDesign `formRules` | 必填、长度、格式 | **体验**：打字时就提示，不浪费时间 |
| 后端 | DTO 装饰器 | 必填、长度、格式 | **安全**：绕过前端也能挡（curl 直接打接口也一样校验） |

记住：**前端的校验是为了体验，后端的校验才是真正的安全线。**

## 2. 链路二：Chat 对话（含 RAG 预告）

### 2.3 后端怎么处理

`ai.controller.ts` 的 `chat`：

```typescript
@Post('chat')
async chat(@Body() body: { model; messages; temperature?; maxTokens?; knowledgeBaseIds? }) {
  if (!body.model) throw new HttpException('model 不能为空', 400);
  if (!body.messages?.length) throw new HttpException('messages 不能为空', 400);

  // TODO: 如果传了 knowledgeBaseIds，先调 KnowledgeRetrievalService 检索
  //       然后把检索结果注入 System Prompt 再调用 chat        ← ★ 见下

  return this.aiService.chat(body.messages, {
    model: body.model,
    temperature: body.temperature ?? 0.7,
    maxTokens: body.maxTokens,
  });
}
```

**⚠️ 重要事实**：`knowledgeBaseIds` **目前被无视**！注释写着 TODO。聊天页传了也白传。
真正的 RAG 只在**工作流的 RAG 节点**里跑（第 7 篇）。这就是 chat 页面「选了知识库但回答不带资料」的原因——不是 bug，是功能还没接。

## 3. 链路三：工作流保存（★ 必看：保存 vs 运行的数据差异）

### 3.1 编辑器整体结构（`views/workspace/workflow.vue`）

```
┌──────────────────────────────────────────────────────┐
│ PageHeader: [标题] [保存工作流] [运行]                  │
├──────────┬──────────────────────────┬────────────────┤
│ 左：节点面板 │  中：VueFlow 画布          │ 右：t-drawer 属性   │
│ Start    │  ○──→○──→○（节点+边）      │ 面板（改配置）     │
│ Input    │                           │                  │
│ LLM      │ 拖拽生成、连线、点击选中     │ (show-in-attached) │
│ Prompt   │                           │                  │
│ RAG/HTTP │                           │                  │
│ Condition│                           │                  │
│ Output   │                           │                  │
└──────────┴──────────────────────────┴────────────────┘
```

**组件结构分层：**

| 层 | 文件 | 职责 |
|----|------|------|
| 页面 | `views/workspace/workflow.vue` | 画布、对话框、属性面板模板 |
| 业务逻辑 | `composables/useWorkflow.ts` | 节点增删、连线、补默认值、**保存/运行数据转换**、变量列表 |
| 自定义节点渲染 | `components/workflow/CustomNode.vue` | 画布上每个节点的样式（圆角卡片、图标、label） |

### 3.2 编辑器里的「两种节点状态」（★ 最重要的概念）

Vue Flow 的节点对象长这样：

```typescript
{
  id: "llm-1",
  type: "custom",                 // ← 画布上用自定义组件渲染（不是业务类型！）
  position: { x: 250, y: 180 },   // ← 画布坐标
  data: {                         // ← 业务配置全在 data 里
    label: "LLM",
    nodeType: "llm",              // ← ★ 真正的业务类型存在这
    model: "qwen2.5:7b",
    prompt: "请分析：\n{{input}}",
    temperature: 0.7,
  },
}
```

**注意两个 type：**
- `type: "custom"` —— Vue Flow 渲染用，告诉画布「用 `<template #node-custom>` 渲染我」
- `data.nodeType: "llm"` —— 业务类型，后端 8 种执行器的关键字

**这张图帮助你记住：**

```
保存到后端时：{ id, type: "custom", data: { nodeType: "llm", ...配置 } }
                    ↑ 保持原样（Vue Flow 画布格式）

运行到后端时：{ id, type: "llm",     config: { ...data } }
                    ↑ 换成业务类型      ↑ 配置搬到 config
```

### 3.3 保存 = 存「画布原样」

`useWorkflow.ts` 的 `saveWorkflow`：

```typescript
const saveWorkflow = async () => {
  const definition = getCurrentDefinition();
  await updateWorkflow(workflowId, { definition });
};

const getCurrentDefinition = (): WorkflowDefinition => ({
  nodes: getNodes.value.map(sanitizeNodeForSave),   // ← 只做轻微清洗
  edges: getEdges.value,
});
```

`sanitizeNodeForSave` 做的「清洗」只有两件事：
1. HTTP 节点：编辑态的 `_headers` 数组（`[{ key, value }]`）→ 持久化 `headers` Record（`{ key: value }`）；`_query` 同理
2. Condition 节点：编辑态 `_conditions` → 持久化 `conditions`

**发到后端的 PUT 请求：**

```http
PUT /api/workflows/:id
Authorization: Bearer eyJ...
Content-Type: application/json

{
  "name": "客服助手",
  "description": "基于知识库的客服工作流",
  "definition": {
    "nodes": [
      { "id": "start-1", "type": "custom", "position": { "x": 250, "y": 50 }, "data": { "label": "Start", "nodeType": "start" } },
      { "id": "llm-1",   "type": "custom", "position": { "x": 250, "y": 180 }, "data": { "label": "LLM", "nodeType": "llm", "model": "qwen2.5:7b", "prompt": "请分析：{{input}}", "temperature": 0.7 } }
    ],
    "edges": [ { "source": "start-1", "target": "llm-1", "sourceHandle": null, "targetHandle": null } ]
  }
}
```

**后端 `update()` 做了什么（第 2 篇讲过，这里串起来）：**
1. 校验我是该工作流的 member（404）
2. 查当前最大 `version`
3. `$transaction`：`INSERT WorkflowVersion (version+1, definition)` + `UPDATE Workflow.currentVersionId`

### 3.4 运行 = 转换成引擎格式（★ 核心差异）

`handleRunWorkflow` 里的关键几行（`views/workspace/workflow.vue`）：

```typescript
const definition = getCurrentDefinition();
const workflow: WorkflowDefinition = {
  nodes: definition.nodes.map((node) => ({
    ...node,
    type: String(node.data?.nodeType ?? node.type),   // ← custom → llm/prompt/...
    config: { ...node.data },                          // ← 配置搬到 config
  })),
  edges: definition.edges,
};
```

**转换前（保存格式）：**

```json
{
  "id": "llm-1",
  "type": "custom",
  "data": { "label": "LLM", "nodeType": "llm", "model": "qwen2.5:7b" }
}
```

**转换后（运行格式）：**

```json
{
  "id": "llm-1",
  "type": "llm",
  "data": { ... },
  "config": { "label": "LLM", "nodeType": "llm", "model": "qwen2.5:7b" }
}
```

**为什么运行前必须转换？** 因为后端引擎：

```typescript
const executor = this.registry.get(currentNode.type);   // 需要 type='llm'
this.createParams(context, node) {
  node.config?.prompt, node.config?.userPrompt, node.config?.model   // 需要 config.xxx
}
```

| | 保存格式 | 运行格式 | 后端需要 |
|---|---------|---------|---------|
| `type` | `custom` | LLM 等 8 个业务类型 | ✅ Registry 关键字 |
| 配置位置 | `data` | `config` | ✅ 读 `config.xxx` |
| `data` | 留着（Vue Flow 需要） | 一并带着（无害） | 忽略（除了条件判断） |

> **⚠️ 最容易踩的坑**：直接把「保存格式」丢给 `/workflow/run`。
> 后端 Registry 找不到 `type='custom'` → 报「没有找到 Node Executor: custom」。
> 反过来，把「运行格式」存进数据库也可以（后端定义只存 JSON），但下次打开编辑器时 Vue Flow 因 `type='llm'` 找不到 `#node-llm` 渲染组件，画布会空白。**保存用画布格式，运行用引擎格式。**

### 3.5 属性面板：改配置 → 保存

点击节点 → `onNodeClick` → 打开右侧 t-drawer → 编辑 `tempNodeData`（**深拷贝**，防直接污染节点）→ 点「保存配置」→ 回写 `selectedNode.data` → `saveWorkflow()`。

```typescript
const handlePropertyConfirm = async () => {
  // 先清空旧字段再 Object.assign（保持响应式引用）
  Object.keys(selectedNode.value.data).forEach((k) => delete selectedNode.value!.data[k]);
  Object.assign(selectedNode.value.data, tempNodeData.value);
  await saveWorkflow();
  closePropertyDrawer();
};
```

**为什么用深拷贝 + 回写而不是直接 v-model 绑 `node.data`？**
因为编辑器里代码复杂、节点被选来选去，直接绑定容易出现「改 A 却改了 B」的引用混乱。先拷贝成 `tempNodeData`，确认后再统一回写 —— 这是常见的「编辑缓冲」模式。

### 3.6 变量选择器：`availableVariables`

`useWorkflow.ts` 里有个 `computed`，自动从画布所有节点提取「可用的变量」：

```
全局
  {{input}}          工作流初始输入
  {{previous}}       上一个节点输出
llm 节点
  {{llm_1.output}}
  {{llm_1}}          整体输出
http 节点
  {{http_1.status}}  {{http_1.headers}}  {{http_1.body}}
condition 节点
  {{cond_1.result}}  {{cond_1.branch}}
```

**它怎么知道每个节点有哪些字段？** `knownOutputFieldsFor(nodeType)` —— 设计期已知的字段（HTTP 的 `body` 内部字段运行时才知道，不硬编码）。

在 Condition 的 left 选择器、HTTP 的变量弹窗里都能看到它。这层设计 = **「前端帮用户生成 `{{nodeId.field}}` 模板字符串」**，后端 VariableService 负责解析。

## 4. 链路四：工作流运行（SSE 流式）

### 4.1 从点到链路

用户点「运行」→ 弹出对话框 → 填 input → 点确认 → `handleRunWorkflow()`：

```typescript
const handleRunWorkflow = async () => {
  const definition = getCurrentDefinition();
  const workflow = { nodes: definition.nodes.map(nodeToEngineFormat), edges: definition.edges };

  chatMessages.value.push({ role: "user", content: runInput.value });
  chatMessages.value.push({ role: "assistant", content: "" });

  await runWorkflowStream(
    { workflow, input: runInput.value },      // body
    (event) => {                              // 事件回调
      if (event.type === "node:start") {
        currentNodeStatus.value = `正在运行：${event.nodeType}`;
      } else if (event.type === "token") {
        // 追加到最后一个 assistant 消息里（打字机效果）
        chatMessages.value.at(-1).content += event.content;
      } else if (event.type === "complete") {
        runResult.value = { input: runInput.value, data: event.data };
      }
    },
  );
};
```

### 4.2 SSE 客户端 `runWorkflowStream`（`api/workflow.ts`）

```typescript
const response = await fetch("/api/workflow/run/stream", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    ...(userStore.token ? { Authorization: `Bearer ${userStore.token}` } : {}),
  },
  body: JSON.stringify(data),
});

const reader = response.body.getReader();     // ★ 拿到可流式读取的数据流
const decoder = new TextDecoder();
let buffer = "";

while (true) {
  const { done, value } = await reader.read();
  buffer += decoder.decode(value, { stream: !done });

  const events = buffer.split("\n\n");        // ★ SSE 以空行分隔
  buffer = events.pop() ?? "";                // ★ 最后一块可能不完整，留到下一轮

  for (const eventText of events) {
    const dataLine = eventText.split("\n").find((line) => line.startsWith("data: "));
    if (!dataLine) continue;
    const event = JSON.parse(dataLine.slice(6));   // 去掉 "data: " 前缀
    onEvent(event);                                 // 回调页面
    if (event.type === "error") throw new Error(event.message);
  }

  if (done) break;
}
```

**这段代码的原理：**

| 步骤 | 为什么 |
|------|--------|
| `reader.read()` | 浏览器原生流式读取。数据是「一块一块」来的，不是一下子全到 |
| `buffer += chunk` | 断块拼接：SSE 的完整事件可能被 TCP 切成两半 |
| `split("\n\n")` | SSE 事件之间用**空行**分隔 |
| `events.pop()` 留 buffer | 最后一段可能没有空行结尾（不完整），留到下轮 |
| `.find(line => startsWith("data: "))` | SSE 里有 `data:` 开头的内容（别的行类型忽略） |
| `dataLine.slice(6)` | `"data: "` 正好 6 个字符 |

**⚠️ 为什么不用 axios？** axios 基于 XHR，XHR 没有流式读取能力（一次返回全部）。要用 `fetch` + `getReader`。所以这个函数绕开了 `utils/request.ts`，token 得手写。

### 4.3 SSE 事件 → 界面状态（对照第 4 篇第 7 节）

| SSE 事件 | 页面动作 |
|----------|---------|
| `node:start` | 顶部状态条「正在运行：LLM」 |
| `token` | 追加到正在生成的 assistant 气泡 |
| `node:complete` | 状态条「已完成：xxx」 |
| `complete` | 保存 `runResult = { input, data }`，渲染 JSON 面板 |
| `error` | 弹错误提示 + 关闭 loading |

### 4.4 普通运行怎么办？——也有

`api/workflow.ts` 里还留着 `runWorkflow`（走 axios POST `/workflow/run`），一次等全部结果。编辑器 UI 只用流式版本，普通版本适合测试/脚本。

### 5.2 详情页 `detail.vue`（文件管理 + 上传）

const formData = new FormData();

const response = await fetch(`/api/knowledge-bases/${kbId}/documents`, {

### 5.3 ★ 上传是异步的：接口毫秒级返回 + 2 秒轮询

**后端现在只做 5 件事就返回**（第 7 篇 §4.2 详解）：
落盘 → 建记录（`status=UPLOADED`）→ `queue.add('process-document')` → 返回 `{ documentId, jobId, status, message }`。

所以上传**不会**卡在「解析中」——它几乎立刻就返回了。真正的解析 + 向量化在 Redis 队列里跑。

**前端靠轮询跟进状态**（`detail.vue`）：

```typescript
/** 启动状态轮询：有 UPLOADED/PROCESSING 状态的文档时每 2s 刷新 */
(d) => d.status === "UPLOADED" || d.status === "PROCESSING",
```

你会看到状态这样走：

```
上传点了 → 接口秒回 → 列表出现「已上传」
                ↓ 2s 轮询
           「处理中」+ 假进度条 60%
                ↓ 2s 轮询（可能反复几十秒，取决于 Ollama 速度）
           「已完成」  或  「失败」+ 错误提示
```

| 后端 `status` | 页面文案 | 主题 | 进度条 |
|---------------|---------|------|--------|
| `UPLOADED` | 已上传 | default | 无 |
| `PROCESSING` | 处理中 | primary | `t-progress :percentage="60"` |
| `COMPLETED` | 已完成 | success | 无 |
| `FAILED` | 失败 | danger | 无（显示 `errorMessage`） |

> **⚠️ 两个要注意的点**：
> 1. **失败不再 HTTP 报错**。以前传 `.docx` 上传请求直接 500；现在返回 201，
>    失败信息只在文档列表的 `errorMessage` 里。**必须靠轮询 + 展示错误**才能让用户知道。
> 2. **返回类型已改对（★ 本次修）**：`api/knowledge.ts` 现在有独立的 `UploadDocumentResult` 接口，
>    `uploadDocument` 的返回类型不再是 `DocumentItem`：
>
>    ```typescript
>    /** uploadDocument 返回 —— 后端入队后立即返回（异步处理中） */
>    export interface UploadDocumentResult {
>      documentId: string;
>      jobId: string;
>      status: "UPLOADED";
>      message: string;
>    }
>
>    export const uploadDocument = async (kbId: string, file: File): Promise<UploadDocumentResult> => { ... }
>    ```
>
>    同时补了 `getDocument(id)` → `GET /documents/:id`（页面目前还是用列表接口整体轮询，
>    文档多的时候不如按 id 查省流量）。

## 6. 五条链路串起来的「共同骨架」

不管哪条链路，都长这样：

```
① 用户交互（点按钮 / 输入）
      ↓
② 前端校验（可选，体验层）
      ↓
③ api/*.ts 组装请求
      ↓
④ axios 拦截器 or 手写 fetch 加 token
      ↓
⑤ Vite 代理 → 后端 :3000
      ↓
⑥ Guard 验权 → ValidationPipe 校验 → Controller 接参
      ↓
⑦ Service 业务逻辑（权限校验 + DB / 引擎 / Ollama）
      ↓
⑧ 返回 JSON（或 SSE）
      ↓
⑨ 前端状态更新 → 界面刷新
```

| 链路 | ④ 走哪个 | ⑧ 是什么 |
|------|---------|---------|
| 登录 | axios 拦截器 | JSON |
| 对话 | axios 拦截器 | JSON |
| 保存工作流 | axios 拦截器 | JSON（含版本定义） |
| 运行工作流 | 手写 fetch | SSE 流 |
| 知识库上传 | 手写 fetch | JSON（★ 只回 `{ documentId, jobId, status }`，结果靠轮询） |

### 6.1 ★ 「同步」和「异步」两种骨架

上面这个骨架假设「⑧ 就是最终结果」。**接了 BullMQ 之后，多了一种骨架**：

```
【同步骨架（上表那种）】
⑧ 返回 JSON → ⑨ 前端直接用

【异步骨架（走队列的）】

⑥ Controller：建记录(QUEUED) → queue.add() → ⑧ 立刻返回 runId/jobId → HTTP 结束
⑨ 前端拿到 id → 每 2s 轮询状态接口 → 看到 QUEUED → RUNNING → COMPLETED/FAILED
⑩ 终态了才渲染结果
```

| | 同步骨架 | 异步骨架 |
|---|---------|---------|
| 后端哪一环变重 | 全在 Controller 里跑完 | Controller 只入队，逻辑搬到 `queues/*/xxx.processor.ts` |
| 前端第 ⑧ 步拿到什么 | 最终结果 | **一个 id** |
| 前端第 ⑨ 步 | 直接渲染 | **轮询**直到终态 |
| 失败了怎么看 | HTTP 4xx/5xx | 查状态的 `errorMessage` |
| 本项目谁在用 | 工作流 SSE（**页面上已无入口**）、Chat | **文档上传 + 工作流运行**（前端都已接轮询） |
| 本项目谁还没用 | —— | ——（两条异步路线都接上了） |

## 8. 本篇小结（端到端一句话速记）

| 链路 | 一句话 |
|------|--------|
| **登录** | 表单 → DTO 校验 → bcrypt 验密 → 发 JWT → 存 localStorage → 跳转 |
| **Chat** | 最近 10 条历史 + 模型 + 知识库 ID → `/ai/chat` → 一次性返回 content |
| **保存工作流** | 画布原样（`type:'custom'` + `data`）→ `PUT` → 新版本号 + 定义 JSON |
| **运行工作流（同步 SSE）** | 转引擎格式（`type` 换业务值 + 配置搬 `config`）→ SSE 逐字渲染。**⚠️ 页面上已无按钮，只能 curl** |
| **运行工作流（★ 异步队列，页面在用）** | `POST /workflows/:id/run` 建记录 + 入队 → **秒回 runId** → 每 2s 轮询 `GET /workflow-runs/:runId` 直到终态 → 显示 `output`。**⚠️ 运行前要先保存** |
| **上传文档** | FormData → multipart → 落盘 + 建记录(`UPLOADED`) + **入队** → **秒回 `{documentId, jobId}`** → 每 2s 轮询文档列表看状态 |
| **两套节点格式** | 保存用 `custom/data`；运行用 `业务type/config` |
| **三类 token 携带** | axios 拦截器自动带 / fetch 手写带 / FormData 手写带 |
| **★ 两种链路骨架** | 同步（⑧ 就是结果）和异步（⑧ 只是个 id，⑨ 轮询到终态） |
