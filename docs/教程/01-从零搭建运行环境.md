# AI WorkFlow Studio 学习指南
## 第 1 篇：从零搭建运行环境（把项目跑起来）

> 目标：一步步在你电脑上把「数据库 + 后端 + AI 模型 + 前端」全部启动。
> 每个命令都解释**为什么**，你不需要懂代码也能跑通。
> 跑通之后去 [`08-前后端数据对照总表.md`](./08-前后端数据对照总表.md) 用 curl 亲手打几个接口，看看「前端发的数据」长什么样。

## 1. 四个必须先装好的东西

| 软件 | 版本 | 干什么用 | 怎么检查装没装 |
|------|------|---------|---------------|
| **Node.js** | **≥ 20.19（推荐 22 LTS）** | 跑前后端代码 | `node -v` |
| **pnpm** | 9+ | 装依赖的「小推车」 | `pnpm -v` |
| **Docker Desktop** | 最新 | 一键开 PostgreSQL + Redis | `docker -v` |
| **Ollama** | 最新 | 本地跑大模型 | `ollama -v` |

> **⚠️ Node 版本别只看「20+」**：`vite@8` 要求 `^20.19.0 || >=22.12.0`，`prisma@7.10` 要求 `^20.19 || ^22.12 || >=24.0`。
> **Node 20.0 ～ 20.18 会装不上依赖**（`EBADENGINE` 甚至直接报错）。最稳妥是装 **Node 22 LTS**。

> **小知识：为什么要 Docker？**
> PostgreSQL 是个「服务程序」，正常要下载安装包、设密码、开防火墙。
> Docker 把它装进一个「隔离盒子」里，一条命令就能跑起来，删盒子也不影响你电脑。
> 这套教程用的数据库镜像叫 `pgvector/pgvector:pg17` —— 它是**装了向量扩展的 PostgreSQL**，
> 这样我们才能做 RAG 知识库检索（第 7 篇详解）。

## 2. 第一步：启动数据库和 Redis（★ 两个都必需）

项目根目录已经写好了 `docker-compose.yml`：

```yaml
services:
  postgres:
    image: pgvector/pgvector:pg17      # ← 关键：这是带向量扩展的 PG17
    container_name: ai-workflow-postgres
    restart: unless-stopped
    environment:
      POSTGRES_USER: workflow          # 数据库用户名
      POSTGRES_PASSWORD: workflow      # 数据库密码
      POSTGRES_DB: ai_workflow         # 数据库名
    ports:
      - "5432:5432"                    # 宿主机 5432 → 容器 5432
    volumes:
      - postgres_data:/var/lib/postgresql/data
  redis:
    image: redis:7-alpine              # ★ BullMQ 队列要用
    container_name: ai-workflow-redis
    restart: unless-stopped
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data               # ★ 数据落盘，重启不丢待办任务
volumes:
  postgres_data:                       # 数据存到磁盘，容器删了数据还在
  redis_data:
```

> ### ⚠️ Redis 现在是**硬依赖**，不是可选的
>
> 后端 `app.module.ts` 里有：
>
> ```typescript
> BullModule.forRoot({
>   connection: {
>     host: process.env.REDIS_HOST || 'localhost',        // ← 有默认值
>     port: Number(process.env.REDIS_PORT || 6379),       // ← 有默认值
>   },
> })
> ```
>
> NestJS 在**启动引导（bootstrap）阶段**就要建立 Redis 连接，连不上直接抛 `ECONNREFUSED` 退出。
> **只拉起 postgres 不起 redis，后端是起不来的。**

在**项目根目录**（不是 backend 目录）执行：

```bash
docker compose up -d
```

| 参数 | 意思 |
|------|------|
| `compose` | 读 `docker-compose.yml` 这个文件 |
| `up` | 把里面声明的服务启动 |
| `-d` | **d**etach，后台跑，不占着终端 |

检查是否成功：

```bash
docker compose ps
```

看到 `ai-workflow-postgres` 和 `ai-workflow-redis` 都是 `running` 就 OK。

> **顺手验一下 Redis 能读写**（BullMQ 会用普通 Redis 命令）：
> ```bash
> docker exec -it ai-workflow-redis redis-cli ping     # 期望输出 PONG
> ```

> **确认向量扩展装上了**（做 RAG 必须要，做不到会报 `type "vector" does not exist`）：
> ```bash
> docker exec -it ai-workflow-postgres psql -U workflow -d ai_workflow -c "SELECT extname FROM pg_extension;"
> ```
> 输出里应该有一行 `vector`。

> **小知识**：PostgreSQL 默认端口 5432，Redis 默认 6379。后端要连数据库就必须用这些端口。

## 3. 第二步：配置后端环境变量

后端通过环境变量读配置。文件是 `backend/.env`（已被 `.gitignore` 忽略，不会上传仓库，里面是每个开发者的私有配置）：

```env
DATABASE_URL="postgresql://workflow:workflow@localhost:5432/ai_workflow?schema=public"

REDIS_HOST=localhost
REDIS_PORT=6379

JWT_SECRET=（一串随机字符，必须保密）
JWT_EXPIRES_IN=7d

# ★ 模型管理：API Key 加密主密钥（第 10 篇）。不配会回退到 JWT_SECRET，生产环境强烈建议单独配
LLM_CONFIG_ENCRYPTION_KEY=（一串随机字符，32 字节）

# 存储：local（本地磁盘） | qiniu（七牛云对象存储，完整配置见附录 09）
# ⚠️ 当前仓库里的 backend/.env 实际配的是 qiniu
STORAGE_TYPE=qiniu
LOCAL_UPLOAD_DIR=uploads

# —— 七牛云（STORAGE_TYPE=qiniu 时必需，5 个变量缺一不可）——
QINIU_ACCESS_KEY=你的 AccessKey
QINIU_SECRET_KEY=你的 SecretKey
QINIU_BUCKET=你的空间名
QINIU_REGION=z2                 # z0=华东 / z1=华北 / z2=华南 / na0=北美
QINIU_DOMAIN=https://你的域名.com
```

逐行解释：

| 变量 | 谁在读 | 含义 |
|------|--------|------|
| `DATABASE_URL` | **`prisma.config.ts`（CLI）+ `prisma.service.ts`（运行时）** | 连数据库的「地址+账号+密码」。格式固定：`postgresql://用户名:密码@主机:端口/数据库名`。**Prisma 7 里 schema.prisma 的 datasource 不写 url，连接串由这两个地方提供** |
| `JWT_SECRET` | `auth.module.ts` + `jwt.strategy.ts` | 给 JWT 通行证签名的「私章」。**必须保密**，泄露了任何人都能伪造通行证 |
| `JWT_EXPIRES_IN` | `auth.module.ts` | 通行证有效期，`7d` = 7 天 |
| **`LLM_CONFIG_ENCRYPTION_KEY`** | ★ **`common/crypto/encryption.service.ts`** | ★ 加密用户自建模型 API Key 的**主密钥**（AES-256-GCM）。不配会回退 `JWT_SECRET`（启动打 warning）。**生产环境务必单独配且固定住**，改了它旧 Key 全部解不开（第 10 篇 §3、§9） |
| `REDIS_HOST` / `REDIS_PORT` | ★ **`app.module.ts` 的 `BullModule.forRoot`** | ★ BullMQ 连 Redis 用的地址。**不配会用默认值 `localhost:6379`**；**Redis 没起来后端就起不来** |
| `STORAGE_TYPE` / `LOCAL_UPLOAD_DIR` | `storage.service.ts` | 上传文件存哪。`local` 存到 `uploads/documents/<知识库Id>/`；切 `qiniu` 需要下面一整套 `QINIU_*` 配置，详见 **附录 09** |
| `QINIU_ACCESS_KEY` / `QINIU_SECRET_KEY` | `storage.service.ts` | 七牛云密钥对，用来生成上传 token 和下载签名 |
| `QINIU_BUCKET` | `storage.service.ts` | 对象存储空间名，`PutPolicy` 的 scope 会拼成 `bucket:key` |
| `QINIU_REGION` | `storage.service.ts` | 存储区域，决定上传走哪台机房。**注意代码里默认是 `z0`（华东），华南空间要显式写 `z2`** |
| `QINIU_DOMAIN` | `storage.service.ts` | 访问域名，拼下载 URL 用。代码会自动去掉结尾的 `/` |

> **⚠️ 这两个变量现在真的在用了**（旧文档写「预留」已过时）。
> 如果你 Redis 装在别的机器/端口，就改这两个。

> **⚠️ 想省事就先改回 `STORAGE_TYPE=local`**：不配七牛也能完整跑通上传→解析→向量化链路，
> 只是文件落在本地 `backend/uploads/` 而不是云端。等要上线再切七牛（见附录 09）。

> **自查**：如果你 Docker 里改了数据库密码/端口，就改这个文件。
> **`JWT_SECRET` 怎么生成？** 随便跑一句：`node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"`

## 4. 第三步：安装依赖

前端和后端是**两个独立项目**，要分别装：

```bash
# 后端
cd backend
pnpm install

# 前端
cd ../fronted
pnpm install
```

`pnpm install` 会读三样东西：

1. `package.json` —— **依赖清单**（要装什么）
2. `pnpm-lock.yaml` —— **版本锁**（装哪个精确版本，保证大家环境一致）
3. 装到 `node_modules/` 目录

> **⚠️ 装后端依赖时会多出一段陌生输出，别慌**：`backend/package.json` 里有
> `"postinstall": "prisma generate && prisma skills sync || exit 0"` —— 这是 Prisma 7 新增的钩子，`pnpm install` 结束后会自动跑一次（先生成客户端再同步 skills，`|| exit 0` 保证 skills 同步失败不阻塞安装）。
> 它失败也不影响安装（末尾的 `|| exit 0` 会兜住），看到相关日志属于正常现象。
>
> **为什么 `prisma generate` 不用手动跑了？** 同上，`postinstall` 之后 Prisma 7 的客户端会随 `@prisma/client` 一起就绪；
> 但如果你改过 `schema.prisma`，还是建议手动补一次 `pnpm prisma generate`（见第 5 步）。

## 5. 第四步：把「表结构」建到数据库里（Prisma 迁移）

`backend/prisma/schema.prisma` 是一份「设计图纸」，用 Prisma 自己的语法描述了 31 张表。但**图纸不等于真实数据库**，要把图纸变成 reality，这一步叫**迁移（Migration）**。

```bash
cd backend
pnpm prisma migrate deploy    # ① 执行 migrations/ 里已有的 SQL，把表建出来
pnpm prisma generate          # ② 生成类型安全的查询代码到 node_modules/@prisma/client
```

### 5.0 ★ 前置：`prisma.config.ts`（Prisma 7 必需，旧版教程没有这一步）

本项目用的是 **Prisma 7**，它有一个**破坏性变更**：`schema.prisma` 的 `datasource` 块**不再写 `url`**。

打开 `backend/prisma/schema.prisma` 第 5～7 行，你会看到只有：

```prisma
datasource db {
  provider = "postgresql"
}
```

**没有 url！** 那连接串从哪来？两个地方各管一段：

| 场景 | 谁提供连接串 | 文件 |
|------|------------|------|
| **CLI**（`migrate` / `generate` / `studio`） | `prisma.config.ts` | `backend/prisma.config.ts` |
| **运行时**（NestJS 启动后查库） | `PrismaService` 里的 driver adapter | `backend/src/prisma/prisma.service.ts` |

`backend/prisma.config.ts` 全文只有 12 行：

```typescript
import "dotenv/config";                    // ① ★ 关键：Prisma 7 不再自动读 .env，必须显式引入
import { defineConfig, env } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",          // 图纸在哪
  migrations: { path: "prisma/migrations" }, // 迁移 SQL 放哪
  datasource: {
    url: env("DATABASE_URL"),              // ② 连接串从这里来
  },
});
```

运行时那一段（第 2 篇会细讲）长这样：

```typescript
// backend/src/prisma/prisma.service.ts
super({
  adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }),
});
```

> **踩坑提醒**：这两处**都必须能读到 `DATABASE_URL`**。
> `main.ts:1` 有 `import 'dotenv/config'`（管运行时），`prisma.config.ts:1` 也有（管 CLI）。
> **少了哪一行，对应场景就会报「连不上数据库」**，而且报错信息不会告诉你是 .env 没加载。

### 5.1 两个命令在干什么

| 命令 | 干什么 | 类比 |
|------|--------|------|
| `migrate deploy` | 读 `prisma/migrations/*/migration.sql`，在数据库里真正建表 | 按图纸施工 |
| `generate` | 根据 schema 生成 TypeScript 代码，让你写 `prisma.user.create()` 有类型提示、字段名写错会报错 | 给你一份「图例字典」 |

> **补充**：改了 `schema.prisma` 之后，开发期用 `pnpm prisma migrate dev`（会**自动生成一条新迁移**并顺带 generate）；
> 首次接手项目 / 上线部署用 `migrate deploy`（只执行已有迁移，不改 migration 文件）。
> ⚠️ 跑完 `migrate dev` 记得**检查新生成的 SQL 有没有 `DROP COLUMN "embedding"`**（见第 0 篇坑 #19）。

**「向量列」那条（`20260923130000_add_pgvector_embedding`）的内容是：**

```sql
CREATE EXTENSION IF NOT EXISTS vector;                            -- 装 pgvector 扩展
ALTER TABLE "DocumentChunk"
  ADD COLUMN IF NOT EXISTS "embedding" vector(768);               -- 加一列存 768 维向量
CREATE INDEX IF NOT EXISTS "dc_embedding_ivf"
  ON "DocumentChunk" USING ivfflat ("embedding" vector_cosine_ops) WITH (lists = 100);
```

第三条建的是 `WorkflowRun` 表（**走队列跑工作流的运行记录**，第 4 篇详解）：

```sql
CREATE TABLE "WorkflowRun" (
    "id" TEXT NOT NULL,
    "workflowId" TEXT NOT NULL,
    "input" JSONB,
    "output" JSONB,
    "status" TEXT NOT NULL DEFAULT 'QUEUED',    -- QUEUED / RUNNING / COMPLETED / FAILED
    "errorMessage" TEXT,
    "startedAt" TIMESTAMP(3),
    "completedAt" TIMESTAMP(3),
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT "WorkflowRun_pkey" PRIMARY KEY ("id")

-- 外键指向 Workflow，级联删除
-- 索引：(workflowId) 和 (status)

ALTER TABLE "Agent" ADD COLUMN "llmModelId" TEXT;                       -- Agent 用哪个自建模型
ALTER TABLE "KnowledgeBase" ADD COLUMN "embeddingLlmModelId" TEXT;      -- 知识库用哪个自建向量模型
```

**⚠️ 一个真实踩过的坑：向量列被 Prisma 误删**

`20261009073241_add_multi_agent_and_chat_session` 是 `prisma migrate dev` **自动生成**的。
生成时 Prisma 拿「数据库现状」对照「schema 声明」，发现数据库里有个 `DocumentChunk.embedding` 列、
而当时的 `schema.prisma` 里**没有**声明它 → Prisma 认为它是「多余的列」，于是把下面两句写进了迁移：

```sql
DROP INDEX "dc_embedding_ivf";
ALTER TABLE "DocumentChunk" DROP COLUMN "embedding";
```

一执行向量列就没了，RAG 检索直接报
`column "embedding" of relation "DocumentChunk" does not exist`。

**修复做了两件事：**

1. 新增手写迁移 `20261010110000_restore_pgvector_embedding`，用 `IF NOT EXISTS` 把列和索引加回来
   （重复执行也不会报错）；对**已经丢列**的数据库则手动执行了这段 SQL 恢复。
2. 在 `schema.prisma` 的 `DocumentChunk` 里**显式声明**这一列，告诉 Prisma「它合法，别删」：

   ```prisma
   embedding   Unsupported("vector(768)")?
   ```

   `Unsupported(...)` 是 Prisma 的「逃生舱」：它承认这列存在（`migrate dev` 不再生成 DROP），
   但**生成的 TypeScript 客户端里没有这个字段的类型**，所以读写向量仍然只能靠裸 SQL。

**为什么向量列非得手写？** 因为 Prisma 原生没有 `vector` 类型，`Unsupported` 只能「保命」不能「读写」。
另外 IVFFlat 索引 Prisma 也无法在 schema 里声明，**每次 `migrate dev` 仍可能生成 `DROP INDEX "dc_embedding_ivf"`**——
所以跑完 `migrate dev` 记得瞄一眼生成的 SQL；索引真没了，重跑恢复迁移里的那两句 `CREATE ... IF NOT EXISTS` 即可。

> `vector(768)` 里的 768 就是**向量维度**，必须和知识库里配置的 `embeddingDimension` 一致。
> 768 是 `nomic-embed-text` 这个模型输出的长度。

### 8.1 ★ 关键：前端怎么找到后端？—— 代理

浏览器有「同源策略」：页面只能请求**同域名**的接口。
前端在 `localhost:5173`，后端在 `localhost:3000`，**不同源，直接请求会被浏览器拦截**。

解决办法是 **开发代理**。`fronted/vite.config.ts`：

```typescript
server: {
  proxy: {
    "/api": {
      target: loadEnv(mode, process.cwd()).VITE_API_BASE_URL,  // = "http://localhost:3000"
      changeOrigin: true,
    },
  },
},
```

`fronted/.env.development` 里：

```
VITE_API_BASE_URL=http://localhost:3000
```

**代理干了什么**（重要，理解它你就懂前后端通信的全部）：

```
浏览器以为：  页面在 5173，请求 /api/auth/login
              ↓
       Vite 开发服务器收到（同一端口 5173，同源，不被拦）
              ↓
       Vite 悄悄转发到 http://localhost:3000/api/auth/login
              ↓
       后端返回 200 + JSON
              ↓
       Vite 把 JSON 原样转回浏览器
```

对浏览器来说，**它一直只跟 5173 说话**，跨域问题天然不存在。

> **这有两个重要推论**：
> 1. 前端代码里 `request` 的 `baseURL` 写的是 `"/api"`（**相对路径，不带域名**），
>    换句话说前端完全不知道自己连的是 3000 还是别的。
> 2. 因为后端**没有开 CORS**，所以必须走代理。生产环境要用 Nginx 做同样的转发，
>    或者给后端加 `app.enableCors()`。

| 10 | 进知识库详情 → 上传一个 `.txt` 文件 | **立刻**返回「已上传」→ 状态 `已上传` → `处理中` → `已完成`（页面每 2s 自动轮询） |

**这 10 步全过 = 你的环境和代码完全正常。** 后面的教程就是逐个拆解这 10 步背后发生了什么。

> ⚠️ **第 7 步的顺序已经不用操心了（v1.5+）**：画布上的「运行（异步）」按钮会**先自动保存当前画布**（`handleRunWorkflow` 里先 `saveWorkflow()` 再 `enqueueRun`），所以它跑的就是你眼前的内容。只有你用 curl 直接调 `/workflows/:id/run` 时，才要自己保证已保存——因为队列 Worker 读的是数据库里 `currentVersion` 那份 definition，不读画布内存。

> 后端 Worker 读的是数据库里 `currentVersion` 那份 definition，




> **第 7 步现在是异步的**：`enqueueRun` 立刻返回 `runId`，前端每 2 秒 `getRun` 查一次状态，
> 拿到 `COMPLETED` 才把 `output` 显示出来。所以看不到逐字打字机效果——那是 SSE 独有的。
> 想看打字机效果，用 curl 打 `POST /api/workflow/run/stream`（第 4 篇第 8.1 节）。

> **第 10 步也是异步的**：上传接口只负责「落盘 + 建记录 + 入队」，通常几十毫秒就返回了；
> 真正的解析和向量化在 Redis 队列里跑（可能几秒到几十秒）。所以你会看到状态**先变成「已上传」再变「处理中」**，
> 这是正常的——`detail.vue` 里有 2 秒轮询，会自动跟着变化。
> 想手动确认队列里在跑什么，看第 4 篇的「调试队列」。

## 10. 小白急救箱：出错了怎么办

| 症状 | 大概率原因 | 怎么查 |
|------|-----------|--------|
| `docker compose ps` 显示 exited | 端口被占（比如你本机装了 PostgreSQL / Redis） | `docker compose logs postgres` 看报错 |
| ★ **后端起不来，报 `ECONNREFUSED 127.0.0.1:6379`** | **Redis 没起**（BullMQ 在 bootstrap 阶段就连 Redis，连不上直接退出） | `docker compose up -d redis`，再 `docker exec -it ai-workflow-redis redis-cli ping` |
| ★ 后端起不来，日志有 `BullMQ` / `WRONGTYPE` | Redis 里有脏数据（上一版本用别的 key 格式） | `docker exec -it ai-workflow-redis redis-cli FLUSHALL` |
| ★ 上传文档永远停在「已上传」 | 后端 `DocumentProcessor` 没跑起来 / 后端进程重启了 | 看后端终端有没有启动日志；重启后端会让未完成任务**重新执行** |
| ★ 上传接口返回了，但 `Document` 没变化 | 队列任务失败了（看 `Document.errorMessage`） | 看后端终端 `[DocumentProcessor] Job ... failed` 里的具体报错 |
| 后端起不来，报 `PrismaClientInitializationError` | 数据库没起，或 `.env` 密码不对 | 查 `docker compose ps` + 核对 `.env` |
| `pnpm prisma migrate deploy` 报 `vector` 不存在 | 用的不是 pgvector 镜像 | 换镜像重建：`docker compose down -v && docker compose up -d` |
| `pnpm prisma migrate deploy` 报表已存在 | 上次没清干净 | `docker compose down -v`（**会删数据**）再来一遍 |
| 401（message 显示「登录已过期，请重新登录」） | token 没带或过期 | 重新登录；看第 3 篇 |
| 登录时 401（显示「邮箱或密码不正确」） | 邮箱或密码真的不对；登录接口的错误文案不区分「邮箱不存在」和「密码错误」，是刻意的安全设计 | 检查邮箱/密码；看第 3 篇 |
| 前端 404 / 空白 | 后端没起，或代理 target 写错 | 看终端 C 有没有报错 |
| `没有找到 Node Executor: xxx` | v1.5+ 引擎会自动把保存格式里的 `type: "custom"` 归一化成 `data.nodeType`（见第 4 篇 5 节）；**只有当 `data.nodeType` 也缺失/写错**、归一化后仍不认识这个类型才会报 | 检查节点 `data.nodeType` 是否拼错 |
| 运行工作流报连不上 Ollama | Ollama 没开，或模型没下载 | `ollama list` 看模型在不在 |
| ★ 运行工作流报 `Workflow xxx 或其当前版本不存在` | 该工作流一条版本都没建（`currentVersion` 为空） | 先 `PUT /api/workflows/:id` 保存一次 |
| 上传 PDF 后文档 `FAILED` | `pdf-parse` 对扫描件无效（扫描件是图片不是文字） | 换成 `.txt` / `.md` 试 |
| ★ 切七牛云后文档 `FAILED`，`errorMessage` 含 `Invalid URL` / `401` | 私有空间未签名 / 签名 URL 缺协议前缀 | 见 **附录 09** 踩坑②① |
| 上传 `.docx` 后文档 `FAILED` | **这是真的没实现**，见 `docx.parser.ts`。现在是后台任务挂的，所以 HTTP 请求**不会报错**，要去文档列表看 `errorMessage` | 换 `.txt` / `.pdf` / `.md` |
| RAG 节点没查到东西 | ① 没选知识库 ② 没上传文档 ③ embedding 模型和知识库配置不一致 | 第 7 篇第 8 节 |
| 前端 5173 端口被占 | 上一个进程没退 | `pnpm dev -- --port 5174` |

## 11. 现在你可以做的事

跑通之后，建议先花 10 分钟做这几件事，**建立「前后端数据流动」的第一印象**：

1. **打开浏览器 F12 → Network 面板**，登录一次，看 `POST /api/auth/login` 的 **Request Payload** 和 **Response**。
   你会看到前端发 `{"email":...,"password":...}`，后端回 `{"user":{...},"accessToken":"eyJ..."}`。

2. **在画布上点「调试运行（SSE）」**（右上角第二个运行按钮），看 `POST /api/workflow/run/stream` 的 **Request Payload**；再点「运行（异步）」，看 `POST /api/workflows/:id/run`（入队后轮询）。
   这个 JSON 有几百行 —— **这就是本教程要讲透的核心数据**。

3. **在终端看后端日志**，能看到引擎一行行打印的节点流转和 Ollama 请求详情。

4. **用 curl 亲手打一次接口**（Windows 用 PowerShell 也可以）：

```bash
# 注册
curl -X POST http://localhost:3000/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"test","email":"test@example.com","password":"123456"}'

# 登录，拿到 token
curl -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"123456"}'
# 复制返回的 accessToken，粘到下面

# 带 token 建工作空间
curl -X POST http://localhost:3000/api/workspaces \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer 粘贴你的token" \
  -d '{"name":"我的第一个空间"}'
```

5. **★ 亲手感受一次「队列式异步」**——这是本次新增的核心机制，值得专门试一次：

```bash
# ① 先建个工作流（definition 可以是空图，引擎会报「缺少 Start Node」，正好看到 FAILED）
#    假设工作流 id 是 <WF_ID>，跑一次「入队」
curl -X POST http://localhost:3000/api/workflows/<WF_ID>/run \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer 粘贴你的token" \
  -d '{"input":"你好"}'
# → 立刻返回一条 WorkflowRun，status = "QUEUED"（注意：不是结果！）

# ② 拿到返回里的 id（runId），隔 1 秒查一次
curl http://localhost:3000/api/workflow-runs/<RUN_ID> \
  -H "Authorization: Bearer 粘贴你的token"
# → status 在 QUEUED → RUNNING → COMPLETED / FAILED 之间跳

# ③ 看运行历史
curl http://localhost:3000/api/workflows/<WF_ID>/runs \
  -H "Authorization: Bearer 粘贴你的token"
```

**你会体验到三件事**：
1. 第 ① 步**几乎瞬间返回**（不用等引擎跑完）——这就是队列的价值。
2. 后端终端会打出 `[WorkflowProcessor] Job xxx completed for run xxx`（或 `failed`）。
3. 第 ② 步的 `status` 是**轮询**出来的，不是推送的。

> ⚠️ 注意：这个接口跑的是**数据库里 `currentVersion` 存的图**，不是你 POST 过来的。
> 所以拿它「试跑未保存的画布」是不行的——想试跑当前画布，请点页面上的「调试运行（SSE）」按钮，或直接打 `POST /api/workflow/run`（同步）/ `POST /api/workflow/run/stream`（流式）——这俩是无状态的直接运行接口。
