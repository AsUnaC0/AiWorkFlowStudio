## 1. 两个层次先分清楚

```
工作流项目里有两套"流程"：

① 管理流程（CRUD）:  前端点新建/保存/删除 → 读写数据库（WorkflowsService）
② 执行流程（Engine）: 用户点"运行" → 按 JSON 逐节点执行（WorkflowEngine）

①解决"怎么存"，②解决"怎么跑"。
```

模块结构：

```
backend/src/workflows/
├── workflows.module.ts         # 模块组装（注册两个控制器 + 一整套执行器）
├── workflows.controller.ts     # ①CRUD 接口 + ②执行接口（run / run/stream）都在这里
├── workflows.service.ts        # ① 数据库读写 + 版本管理
├── dto/                        # create/update 参数校验
└── engine/                     # ② 执行引擎，全部家当
    ├── node-executor.interface.ts   # 节点执行器"统一接口"
    ├── node-executor.registry.ts    # 执行器"查号台"
    ├── workflow.engine.ts           # 引擎主逻辑
    └── executors/
        ├── start.executor.ts    # 开始节点
        ├── input.executor.ts    # 输入节点
        ├── llm.executor.ts      # 大模型节点（调 Ollama，支持流式）
        └── output.executor.ts   # 输出节点
```

## 2. 工作流 CRUD 与版本管理（workflows.service.ts）

第 2 篇已经拆解过 `create`。这里补上 `update`（保存新版本）：`workflows.service.ts:79`

```typescript
async update(userId: string, id: string, dto: UpdateWorkflowDto) {
  const workflow = await this.prisma.workflow.findFirst({
    where: { id, workspace: { members: { some: { userId } } } },  // 权限：是该空间成员
    select: { id: true, workspaceId: true },
  });
  if (!workflow) throw new NotFoundException('Workflow not found');

  // 查当前最高版本号
  const latestVersion = await this.prisma.workflowVersion.findFirst({
    where: { workflowId: id },
    orderBy: { version: 'desc' },
    select: { version: true },
  });

  return this.prisma.$transaction(async (transaction) => {
    // ① 新建一条版本记录，version 递增
    const version = await transaction.workflowVersion.create({
      data: {
        workflowId: id,
        version: (latestVersion?.version ?? 0) + 1,
        definition: dto.definition as Prisma.InputJsonValue,
      },
    });

    // ② 把 currentVersionId 指到新版本，同时更新名称/描述（若传了）
    return transaction.workflow.update({
      where: { id },
      data: {
        ...(dto.name !== undefined ? { name: dto.name } : {}),
        ...(dto.description !== undefined ? { description: dto.description } : {}),
        currentVersionId: version.id,
      },
      select: workflowSelection,
    });
  });
}
```

**版本管理设计决策**（回答"为什么这样写"）：

| 方案 | 缺点 | 本项目的方案 |
|------|------|------------|
| 直接覆盖 `definition` | 老版本全丢、无法回滚 | 每个版本一条记录 |
| 每次保存重建整个工作流对象 | 外键复杂、历史丢失 | 只 +1 一条 WorkflowVersion |

`@@unique([workflowId, version])` 保证同一工作流里版本号不重复。

## 3. 执行引擎自顶向下看

### 3.1 执行器的"统一接口"：node-executor.interface.ts

```typescript
export interface NodeExecutionContext {
  input: unknown;                        // 工作流的初始输入（用户输入）
  data: Record<string, unknown>;         // 每个节点 id → 它的输出，便于后续引用
  previousOutput?: unknown;              // 上一个节点的输出（当前节点的"入参"）
}

export interface NodeExecutionResult {
  output: unknown;                       // 该节点执行完的输出
}

export interface NodeExecutor {
  execute(context: NodeExecutionContext, node: any): Promise<NodeExecutionResult>;
}
```

**接口（interface）是约定**：所有节点执行器都必须实现 `execute()`。引擎不用关心"你是 LLM 还是 Output"，只要调这个统一入口。这叫**面向接口编程**。

### 3.2 注册表：node-executor.registry.ts（"查号台"）

```typescript
@Injectable()
export class NodeExecutorRegistry {
  private readonly executors = new Map<string, NodeExecutor>();  // 类型名 → 执行器

  constructor(
    private readonly startExecutor: StartNodeExecutor,
    private readonly inputExecutor: InputNodeExecutor,
    private readonly llmExecutor: LLMNodeExecutor,
    private readonly outputExecutor: OutputNodeExecutor,
  ) {
    this.executors.set('start',  startExecutor);
    this.executors.set('input',  inputExecutor);
    this.executors.set('llm',    llmExecutor);
    this.executors.set('output', outputExecutor);
  }

  get(type: string): NodeExecutor {
    const executor = this.executors.get(type);
    if (!executor) throw new Error(`未知的节点类型: ${type}`);
    return executor;
  }
}
```

理解：工作流 JSON 里每个节点有 `type`（字符串，如 `"llm"`）。引擎执行时问注册表："node type 是 `llm`，给我对应的执行器。"注册表用 `Map`（加速版字典）返回 `LLMNodeExecutor`。

### 3.3 4 个执行器

| 执行器 | 做的什么事 |
|--------|-----------|
| **Start** | `output = context.input`：把入口输入透传下去（工作流起点） |
| **Input** | 同样透传 `context.input`（预留多输入场景） |
| **LLM** | 调 `AIService`：`prompt` 当 system 消息、`previousOutput` 当 user 消息，返回 AI 回复 |
| **Output** | `output = previousOutput ?? input`：把结果送出去（工作流终点） |

看 `llm.executor.ts` 的关键：

```typescript
async execute(context, node) {
  const prompt = node.config?.prompt ?? '...';
  const model  = node.config?.model  ?? 'qwen2.5:7b';
  return { output: await this.aiService.chat({
    model,
    messages: [
      { role: 'system', content: prompt },            // 系统指令（提示词模板）
      { role: 'user',   content: String(context.previousOutput) },  // 用户输入=上个节点的输出
    ],
  }) };
}

// 流式版本：逐 token 生成
async *executeStream(context, node) {
  yield* this.aiService.chatStream({ model, messages });
}
```

`node.config.prompt` 来自前端画布上节点配置的 Prompt 文本。`LLM` 节点因此能根据上游内容回答用户。

### 3.4 引擎主循环：workflow.engine.ts

先看**同步版 `run()`**（`workflow.engine.ts:16`）：

```typescript
async run(workflow: any, input: unknown) {
  const context = { input, data: {}, previousOutput: input };   // ① 初始化“状态包”

  let currentNode = workflow.nodes.find(n => n.type === 'start'); // ② 找起点
  if (!currentNode) throw new Error('Workflow 缺少 Start Node');

  const visitedNodeIds = new Set<string>();    // ③ 防循环“记账本”

  while (currentNode) {                        // ④ 主循环
    if (visitedNodeIds.has(currentNode.id)) throw new Error(`存在循环: ${currentNode.id}`);
    visitedNodeIds.add(currentNode.id);

    const executor = this.registry.get(currentNode.type);   // ⑤ 查号台：取执行器
    const result = await executor.execute(context, currentNode);  // ⑥ 执行

    context.data[currentNode.id] = result.output;            // ⑦ 记录本节点输出
    context.previousOutput = result.output;                  // ⑧ 更新“上一个输出”

    const outgoingEdges = workflow.edges.filter(e => e.source === currentNode.id); // ⑨ 找后继
    if (outgoingEdges.length === 0) break;                                    // 到头了
    if (outgoingEdges.length > 1) throw new Error('存在多个后继节点');          // 拒绝分叉

    currentNode = workflow.nodes.find(n => n.id === outgoingEdges[0].target); // ⑩ 跳到下一节点
    if (!currentNode) throw new Error('找不到目标 Node');
  }

  return context;    // ⑪ 返回所有节点输出
}
```

**每一步都在干什么（小白视角）**：
- ① `context` 是一个"随身书包"，里面装着：输入、每个节点的输出、上一个节点的输出。执行器们通过它互相传数据。
- ② 必须先有 `start` 节点，否则不知道从哪开始。
- ③ `Set` 是"去重集合"。防止图里有环（比如 A→B→A）死循环。访问过的节点如果再次出现直接抛错。
- ⑤ 引擎**不认识**任何具体执行器，只通过注册表查类型。这就是解耦。
- ⑦⑧ 数据在两代之间流动：节点输出的值存起来，同时更新 `previousOutput` 供下游使用。
- ⑨ 边（edge）里 `source` 是节点 id。引擎用"当前节点是谁的 source"找出下一跳。
- ⑩ 单线串行：**每个节点最多一条出边**。这是当前引擎的能力边界（还不支持条件分叉，第 6 篇讲扩展）。

### 3.5 流式版 `runStream()`（SSE 的核心）

`runStream` 结构几乎与 `run` 相同，但有三个关键改动（`workflow.engine.ts:70`）：

```typescript
async *runStream(workflow, input): AsyncGenerator<WorkflowStreamEvent> {
  ...
  yield { type: 'node:start', nodeId, nodeType, label };          // ① 节点开始时向外“广播”

  if (executor instanceof LLMNodeExecutor) {
    let streamedOutput = '';
    for await (const chunk of executor.executeStream(context, currentNode)) {
      streamedOutput += chunk;
      yield { type: 'token', nodeId, content: chunk };            // ② 每来一个 token 立刻广播
    }
    output = streamedOutput;
  } else {
    const result = await executor.execute(context, currentNode);
    output = result.output;
  }

  context.data[currentNode.id] = output;
  context.previousOutput = output;
  yield { type: 'node:complete', nodeId, nodeType, output };      // ③ 节点完成广播
  ...
  yield { type: 'complete', data: context.data };                 // ④ 全部完成广播
}
```

**理解 `AsyncGenerator` / `yield`**：普通函数一口气算完返回。生成器函数可以"算一段、吐一段、歇着，下次要再接着算"。`yield` 就是"吐"这个动作。配合 `async*`，我们可以边等 Ollama 边吐 token。

**事件清单**（前端就是靠这些事件渲染的）：

| 事件 type | 含义 | 前端反应 |
|-----------|------|---------|
| `node:start` | 某节点开始跑 | 显示"正在执行 LLM..." |
| `token` | LLM 吐出一小段字 | 追加到聊天气泡（打字机效果） |
| `node:complete` | 某节点完成 | 更新执行状态 |
| `complete` | 整个工作流完成 | 保留最终结果 |
| `error` | 出错 | 红色报错提示 |

## 4. SSE：怎么把"字一个个蹦出来"推给浏览器

SSE = Server-Sent Events（服务器推送事件），是基于 HTTP 的一根"实时管道"。

**普通的请求**：浏览器等全部结果 → 一次性返回 → 页面"转圈"直到全部完成。
**SSE 请求**：连接不关闭，后端口子小包一次次吐，比如每次吐几个字 AI 回复。

后端怎么开这条管道？看 `workflows.controller.ts` 里 `runStream`：

```typescript
@Post('run/stream')
async runStream(@Body() body, @Res() response) {
  response.setHeader('Content-Type', 'text/event-stream');   // 声明"流式事件"
  response.setHeader('Cache-Control', 'no-cache');           // 不许缓存
  response.setHeader('Connection', 'keep-alive');            // 长连接不关

  for await (const event of this.engine.runStream(workflow, body.input)) {
    response.write(`data: ${JSON.stringify(event)}\n\n`);    // 每条事件一帧，双换行隔开
  }
  response.end();
}
```

`text/event-stream` 是 SSE 的 MIME 类型。帧格式每条是 `data: JSON\n\n`。前端（第 5 篇讲）用 fetch 流式读取这段文本并逐步解析。

## 5. AI 模块：封装本地 Ollama（门面模式）

```
backend/src/ai/
├── ai.module.ts                  # @Global 全局模块
├── ai.service.ts                 # AIService（门面：把请求转给具体 provider）
├── ai-provider.interface.ts      # AiProvider 统一接口（未来接 OpenAI 等）
└── providers/
    └── ollama.provider.ts        # OllamaProvider（真干活的人）
```

`ai.service.ts`（门面 Facade）：

```typescript
@Injectable()
export class AIService {
  constructor(private readonly ollamaProvider: OllamaProvider) {}

  async chat(params)      { return this.ollamaProvider.chat(params); }
  chatStream(params)      { return this.ollamaProvider.chatStream(params); }
}
```

- **门面模式**：对外只暴露 `AIService` 一个口，内部具体用哪家 AI 不由调用方关心。
- 未来要支持 OpenAI：新写一个 `OpenAiProvider`，改一行注入就行，全项目无感切换。
- 引擎里的 `LLMNodeExecutor` 只依赖 `AIService`，衍生出"与具体 AI 厂商解耦"。

`ollama.provider.ts` 的 `chatStream` 思路：

```
向 http://localhost:11434/api/chat 发 stream:true 请求
  → 用 fetch 的 response.body.getReader() 读字节流
  → TextDecoder 解码成文本行
  → 每行是一个 JSON（Ollama 流式输出），抽出 message.content
  → yield 给上层
```

## 6. 运行接口的"漏洞"提醒（重要！）

`workflows.controller.ts` 里：

```typescript
@Post('run')          // ← 没有 @UseGuards(JwtAuthGuard)
@Post('run/stream')   // ← 没有 @UseGuards(JwtAuthGuard)
```

**执行工作流的两个接口当前没有登录保护**，任何人都可以提交一个任意 JSON 去消耗你的 Ollama 算力。这可能是有意（本地单机用），也可能是疏漏。**真实生产环境必须加鉴权 + 配额控制**。读完本文你可以试着给它加上 `@UseGuards(JwtAuthGuard)`。

## 7. 本篇小结（设计模式提炼）

| 术语 | 项目中的体现 | 好处 |
|------|-------------|------|
| **面向接口编程** | `NodeExecutor` interface | 引擎与具体节点解耦，加新节点不改引擎 |
| **策略模式** | 每种节点一个执行器类 | 每个节点逻辑独立，可单独测试 |
| **注册表模式** | `NodeExecutorRegistry` | 用节点类型字符串快速找到策略 |
| **门面模式** | `AIService` | 统一入口，底层 AI 厂商可替换 |
| **生成器/流式** | `async* ... yield` | 边算边吐，实现打字机效果 |
| **版本管理** | WorkflowVersion 表 | 可回溯，可发布回滚 |
| **事务** | `$transaction` | 多步写库要么全成要么全不成 |

**如果你要新增一种节点**（比如 `http` 节点），步骤是：
1. 新建 `http.executor.ts` 实现 `NodeExecutor`；
2. 在注册表构造器里 `this.executors.set('http', httpExecutor)`；
3. 前端节点面板加一项。**引擎一行不改** —— 这就是这套扩展设计的价值。
