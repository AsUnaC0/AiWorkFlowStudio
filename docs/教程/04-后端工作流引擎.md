# AI WorkFlow Studio 学习指南
## 第 4 篇：后端工作流引擎 —— 画布上的节点怎么真正跑起来

> **本篇核心**：前端把一张工作流图（nodes + edges）发给后端，后端怎么决定**先跑哪个、后跑哪个、条件怎么分流、结果怎么拼接**。
>
> 这是整个项目最核心、也是理解起来最过瘾的一章。
> 建议先通读，再回头对照 `backend/src/workflows/engine/` 里的源码逐行看。

---

## 1. 心智模型：一个逐节点走路的小人

把引擎想象成一个**在流程图上走路的小人**：

```
context（他的背包）
├── input           ← 项目开始时，他带入的初始输入（你的问题）
├── data {}         ← 一个空便签本：跑过每个节点就把它的输出记一笔
└── previousOutput  ← 他口袋里装着的「上个节点的输出」

小人从 Start 节点出发……
  1. 找当前节点对应的执行器（查号台 Registry）
  2. 执行器干活 → 得到 output
  3. 把 output 记进 data[节点id]，塞进口袋（previousOutput）
  4. 找出从这个节点「射出去」的边 edges[source==当前节点]
  5. 选一条边走过去 → 到达下一个节点
  6. 回到第 1 步

走到没有出边的节点 → 带着背包回家（返回 context）
```

**核心数据结构（记住这三姐妹）：**

| 变量 | 类型 | 含义 |
|------|------|------|
| `context.input` | 任意 | 前端传进来的初始输入 |
| `context.data` | `{节点id: 该节点输出}` | **每个节点跑完的输出都记在这**，供后续节点用 `{{节点id}}` 引用 |
| `context.previousOutput` | 任意 | 「上一个紧挨着跑的节点」的输出 |

**关键词**：`data` 按「节点 id」记，`previousOutput` 只记「上一个」。两者不要混淆：

- `{{llm_1.output}}` 永远能取到 llm_1 节点的输出（**无论隔了几个节点**）
- `{{previous}}` 只能取到「紧挨着的前一个」节点的输出

## 2. `run()` 的逐行解剖

文件：`backend/src/workflows/engine/workflow.engine.ts`（`run` 方法）

```typescript
async run(workflow: any, input: unknown) {
  const context = {
    input,
    data: {},
    previousOutput: input,
  };

  // ① 找到 Start 节点（必须是 type === 'start'）
  let currentNode = workflow.nodes.find((node: any) => node.type === 'start');
  if (!currentNode) {
    throw new Error('Workflow 缺少 Start Node');
  }

  // ② 防循环的「脚印」集合
  const visitedNodeIds = new Set<string>();

  // ③ ★ 主循环：小人开始走路
  while (currentNode) {
    if (visitedNodeIds.has(currentNode.id)) {
      throw new Error(`Workflow 存在循环: ${currentNode.id}`);
    }
    visitedNodeIds.add(currentNode.id);

    // 3.1 查号台：type → 具体执行器
    const executor = this.registry.get(currentNode.type);

    // 3.2 执行！得到 { output, branch?, metadata? }
    const result: NodeExecutionResult = await executor.execute(context, currentNode);

    // 3.3 Condition 节点存完整调试信息；其它节点仅存输出
    context.data[currentNode.id] = result.branch
      ? { result: result.output, branch: result.branch, metadata: result.metadata }
      : result.output;

    // 3.4 把输出塞进「口袋」
    context.previousOutput = result.output;

    // 3.5 找出从当前节点射出去的所有边
    const outgoingEdges = workflow.edges.filter(
      (edge: any) => edge.source === currentNode.id,
    );

    // 3.6 没有出边 → 走到头，结束
    if (outgoingEdges.length === 0) break;

    // 3.7 ★ 核心决策：选哪条边走
    const targetEdge = this.pickNextEdge(outgoingEdges, result);

    if (!targetEdge) {
      throw new Error(`Node ${currentNode.id} 无法选择后继边 ...`);
    }

    // 3.8 走到边的 target 节点
    const nextNode = workflow.nodes.find((node: any) => node.id === targetEdge.target);
    if (!nextNode) {
      throw new Error(`找不到目标 Node: ${targetEdge.target}`);
    }

    currentNode = nextNode;
  }

  return context;   // ★ 返回值就是「整个 context」
}
```

### 2.1 为什么返回 `context` 而不是最后一个节点的输出？

因为 `context.data` 记了**所有节点**的输出。前端拿到后可以随意取用任意节点结果。
普通运行接口（`/workflow/run`）返回的完整 JSON 就是：

```json
{
  "input": "今天是星期几？",
  "data": {
    "start_1": "今天是星期几？",
    "rag_1": "【问题】\n今天是星期几？\n\n【知识库参考】\n[1] ……",
    "llm_1": "用户在询问今天的日期与星期……",
    "output_1": "今天是 2026-09-30，星期三。"
  },
  "previousOutput": "今天是 2026-09-30，星期三。"
}
```

### 2.2 `visitedNodeIds` 是什么？—— 本引擎**不支持循环**！

```typescript
if (visitedNodeIds.has(currentNode.id)) {
  throw new Error(`Workflow 存在循环: ${currentNode.id}`);
}
```

**单调线性执行**：每条路径上的节点不能重复走。所以：
- 你想让节点 A 回头看节点 B（for 循环、while 循环）→ **不行，直接报错**
- 条件节点只能做**分支合并**，不能做**回路**

> 这是本引擎和「真正的编排引擎」（airflow、Temporal）的最大区别。
> 好处：实现简单、天然保证终止。代价：不能写循环工作流。

### 2.3 `pm`（一个走过程的完整例子）

前端传进来的 workflow 长这样（React Flow 格式的 nodes + edges）：

```json
{
  "nodes": [
    { "id": "start_1", "type": "start", "position": { "x": 0, "y": 0 }, "config": {} },
    { "id": "rag_1",   "type": "rag",   "position": { "x": 0, "y": 120 }, "config": {
        "knowledgeBaseIds": ["kb-uuid-1"],
        "topK": 5,
        "searchMode": "hybrid",
        "embeddingModel": "nomic-embed-text",
        "queryTemplate": "请查找：{{input}}"
    }},
    { "id": "llm_1",   "type": "llm",   "position": { "x": 0, "y": 240 }, "config": {
        "model": "qwen2.5:7b",
        "prompt": "你是智能客服，请根据资料回答：",
        "userPrompt": "{{rag_1.output}}"
    }},
    { "id": "output_1", "type": "output", "position": { "x": 0, "y": 360 }, "config": {} }
  ],
  "edges": [
    { "source": "start_1", "target": "rag_1", "sourceHandle": null, "targetHandle": "in" },
    { "source": "rag_1",   "target": "llm_1", "sourceHandle": null, "targetHandle": "in" },
    { "source": "llm_1",   "target": "output_1", "sourceHandle": null, "targetHandle": "in" }
  ]
}
```

**小人的踪迹：**

| 步 | 当前节点 | 执行器 | 入袋 `data[]` | `previousOutput` |
|----|---------|--------|--------------|------------------|
| ① | `start_1` | StartNodeExecutor | `output = context.input`（即"今天是星期几？"） | 初始就是 input |
| ② | `rag_1` | RAGNodeExecutor | 检索结果文本 | 检索结果 |
| ③ | `llm_1` | LLMNodeExecutor | 模型回答 | 模型回答 |
| ④ | `output_1` | OutputNodeExecutor | `output = previousOutput` | 不变 |
| 终点 | 无出边 → break | — | 返回整个 context | — |

## 3. 执行器查号台：`NodeExecutorRegistry`

文件：`backend/src/workflows/engine/node-executor.registry.ts`

```typescript
const executors = new Map<string, NodeExecutor>();
this.executors.set('start', startExecutor);
this.executors.set('input', inputExecutor);
this.executors.set('llm', llmExecutor);
this.executors.set('output', outputExecutor);
this.executors.set('prompt', promptExecutor);
this.executors.set('rag', ragExecutor);
this.executors.set('http', httpExecutor);
this.executors.set('condition', conditionExecutor);

get(type: string): NodeExecutor {
  const executor = this.executors.get(type);
  if (!executor) throw new Error(`没有找到 Node Executor: ${type}`);
  return executor;
}
```

**注册表模式（Registry）的价值：**

1. **type 字符串 ↔ 执行器类**一一对应，`workflow.nodes[i].type` 就是查号台的关键字
2. 加新节点类型 = 写一个 executor + `registry.set()` 一行，**不用改引擎本体**
3. 未知 type → 抛 `没有找到 Node Executor: ${type}`（所以前端节点 type 不能乱写）

**执行器接口**（每个执行器都要遵守）：

```typescript
interface NodeExecutionResult {
  output: unknown;              // ★ 必填：节点的输出（存进 context.data）
  branch?: string;              // Condition 用：'true' | 'false'
  metadata?: Record<string, unknown>;  // 调试信息（Condition 的诊断明细）
}
```

### 4.1 Start 节点 —— 起点制造者

```typescript

  return { output: context.input };   // 把初始输入原样输出
```

> #2 让「工作流入口」成为图的一部分，前端画得出来。

### 4.2 Input 节点 —— 输入中继

```typescript

  return { output: context.input };  // ★ 和 Start 一样！都是把输入透传

```

| 配置字段 | 用途 |
|---------|------|
| 无 | 就是「传送输入」的中继节点 |

### 4.3 LLM 节点 —— 调大模型（★ 唯一支持流式输出）

文件：`executors/llm.executor.ts`

```typescript
private createParams(context, node) {
  // system prompt 支持 {{变量}}
  const rawSystemPrompt = String(node.config?.prompt ?? '');
  const systemPrompt = String(this.variableService.resolve(rawSystemPrompt, context) ?? '');

  // user prompt：默认取上一个节点的输出
  const rawUserInput = String(
    node.config?.userPrompt ?? context.previousOutput ?? context.input ?? '',
  );
  const userInput = String(this.variableService.resolve(rawUserInput, context) ?? '');

  const messages = [];
  if (systemPrompt) messages.push({ role: 'system', content: systemPrompt });
  messages.push({ role: 'user', content: userInput });

  return {
    messages,
    options: {
      model: node.config?.model ?? 'qwen2.5:7b',
      temperature: node.config?.temperature,
      maxTokens: node.config?.maxTokens,
    },
  };
}
```

| 配置字段 | 默认值 | 说明 |
|---------|--------|------|
| `model` | `qwen2.5:7b` | 必须是 Ollama 里真实存在的模型 |
| `prompt` | `''` | **system** 提示词，支持 `{{变量}}` |
| `userPrompt` | `previousOutput` | **user** 内容，默认自动取上一个节点输出，也可写 `{{rag_1.output}}` |
| `temperature` | 模型默认 | 温度（0~2，越高越随机） |
| `maxTokens` | 模型默认 | 最大生成 token 数 |

**执行动作：**

```typescript
async execute(context, node) {
  const { messages, options } = this.createParams(context, node);
  const result = await this.aiService.chat(messages, options);   // 一次性等完
  return { output: result.content };
}

async *executeStream(context, node) {
  const { messages, options } = this.createParams(context, node);
  for await (const chunk of this.aiService.streamChat(messages, options)) {
    yield chunk;                        // ★ 一个字一个字往外吐
  }
}
```

> `aiService` → `provider`（Ollama）的链路在第 5 篇细讲。这里记住：
> `chat` = 憋一会儿一口气给；`streamChat` = 一个字一个字给。

### 4.4 Prompt 节点 —— 纯文本组装器（不调 AI）

文件：`executors/prompt.executor.ts`

```typescript
const template = String(node.config?.prompt ?? '');
const rawInput = context.previousOutput ?? context.input ?? '';
const previousOutput = stringify(rawInput);            // 对象会被 JSON.stringify

const hasVariables = HAS_VARIABLE_REGEX.test(template); // 模板里有没有 {{变量}}

const resolved = String(this.variableService.resolve(template, context) ?? '');

if (hasVariables) {
  output = resolved;                    // 有 {{变量}} → 完全由变量解析决定
} else {
  // 没变量 → 历史兼容行为：追加 previousOutput
  output = resolved ? `${resolved}\n${previousOutput}` : previousOutput;
}
```

| 场景 | 行为 |
|------|------|
| 模板含 `{{input}}` 等变量 | **完全按变量解析结果**，不追加任何东西 |
| 模板无变量（如"请分析以下内容"） | 自动换行追加 `previousOutput` |
| `previousOutput` 是对象（HTTP 输出） | 自动 `JSON.stringify` 成可读文本 |

> **⚠️ 为什么有「追加 previousOutput」这个行为？** 兼容旧工作流。
> 以前的人拖一个 prompt 节点、写死一句话，如果不追加输入，下游就会拿到一句干巴巴的话。
> **你在写工作流时最好主动用 `{{变量}}`**，别依赖这个隐式追加。

### 4.5 RAG 节点 —— 检索知识库（★ 第 7 篇详细讲）

### 4.6 HTTP 节点 —— 发一个外部请求

文件：`executors/http.executor.ts`

| 配置字段 | 默认值 | 说明 |
|---------|--------|------|
| `method` | `'GET'` | GET / POST / PUT / PATCH / DELETE |
| `url` | 必填 | 支持 `{{变量}}` |
| `headers` | `{}` | key/value 都支持 `{{变量}}`，空项被过滤 |
| `query` | `{}` | 查询参数，支持 `{{变量}}` |
| `bodyType` | `'json'` | body 的编码方式 |
| `body` | — | 支持 `{{变量}}`，保留原始类型 |
| `timeout` | `30000` | 1000~120000 ms |

**流程（5 步）：**

```typescript
// ① 校验
this.validateConfig(rawConfig);              // URL 必填、method 白名单、timeout 范围

// ② 变量解析（★ url/headers/query 强制字符串序；body 保留原始类型）
const resolved = this.resolveAll(rawConfig, context);

// ③ SSRF 安全检查（★ 防「拿后端当跳板」）
this.ssrfCheckService.validate(resolved.url!);

// ④ 构建 axios 配置（validateStatus: () => true —— 4xx/5xx 不 throw）
const axiosConfig = this.buildAxiosConfig(resolved);

// ⑤ 发请求，4xx/5xx 也当作「正常响应」捕获
let response;
try {
  response = await axios(axiosConfig);
} catch (error) {
  if (error.response) response = error.response;   // 有响应体 → 当结果
  else throw new Error(`HTTP 请求失败: ${error.message}`);  // 真·网络错误 → 抛
}
```

**标准化输出格式（★ 结构固定，前端好引用）：**

```json
{
  "status": 200,
  "headers": {},
  "body": { ... }
}
```

> 所以后续节点能这样引用：
> - `{{http_1.status}}` → 200
> - `{{http_1.body.userId}}` → body 里的 userId
> - `{{http_1.headers.content-type}}` → 响应头

**⭐ SSRF 防护（安全亮点）**：`ssrf-check.service.ts`

后端替你访问外部 URL，这就是把服务器变成「代理」。不能让用户用它去打内网/自己：
- 只允许 `http:`/`https:`
- 禁止 `localhost`、`127.0.0.1`、`::1`、`0.0.0.0`
- 禁止内网段：`10.x`、`172.16-31.x`、`192.168.x`、`fc00::`/`fd00::`
- 禁止链路本地 `169.254.x`、`fe80::`、保留/组播段

### 4.7 Condition 节点 —— 分支判断（★ 最复杂）

文件：`executors/condition.executor.ts`

| 配置字段 | 说明 |
|---------|------|
| `conditions` | 规则数组，每条 `{ id, left, operator, right }` |
| `logicalOperator` | `'AND'`（全对才 true）或 `'OR'`（一个对就 true） |

**10 种运算符：**

| operator | 含义 | 是否要 right |
|----------|------|------------|
| `eq` | 等于 | 要 |
| `neq` | 不等于 | 要 |
| `gt` / `gte` / `lt` / `lte` | 大于 / ≥ / 小于 / ≤ | 要 |
| `contains` / `not_contains` | 包含（子串 / 数组元素） | 要 |
| `is_empty` / `is_not_empty` | 为空 / 不为空 | **不要** |

**核心判断器（截取）：**

```typescript
private evaluate(left, operator, right) {
  switch (operator) {
    case 'eq':  return this.strictEquals(left, right);
    case 'gt':  return this.compareNumbers(left, right, (a, b) => a > b);
    case 'contains': return this.doContains(left, right);
    case 'is_empty': return this.isEmpty(left);
    ...
  }
}

private strictEquals(left, right) {
  if (typeof left === 'number' && typeof right === 'number') return left === right;
  // ★ 数字 vs 字符串数字 → 自动转成数字再比
  if (typeof left === 'number' && typeof right === 'string' && !isNaN(Number(right)))
    return left === Number(right);
  if (typeof right === 'number' && typeof left === 'string' && !isNaN(Number(left)))
    return Number(left) === right;
  if (typeof left === 'boolean' && typeof right === 'boolean') return left === right;
  if (typeof left === 'string' && typeof right === 'string') return left === right;
  if (left === null || left === undefined) return right === null || right === undefined;
  return false;
}
```

**返回值（★ 带 `branch` 和调试 `metadata`）：**

```typescript
return {
  output: matched,          // true / false
  branch: matched ? 'true' : 'false',    // ★ 决定走哪条边
  metadata: { conditions: debugInfo, logicalOperator: 'AND' },  // 每条规则的最小比较细节
};
```

**`branch` 怎么决定走哪条边？** 看第 6 节 `pickNextEdge` ——
引擎在 edges 里找 `sourceHandle === 'true'` 的边就是「真分支」，`sourceHandle === 'false'` 就是「假分支」。

**= 注意 =** Condition 的 `output` 是**布尔值**（true/false），不是分支的文本。
如果你想显示分支名，要读 `metadata.branch`，或干脆在 `left`/`right` 里放可读文本。

## 5. 变量服务 VariableService —— `{{变量}}` 是怎么解析的

文件：`backend/src/workflows/engine/variable.service.ts`

**支持的变量语法（支持嵌套路径）：**

| 写法 | 指向 |
|------|------|
| `{{input}}` | 工作流初始输入 |
| `{{previous}}` / `{{output}}` | **上一个节点**的输出（alias） |
| `{{节点id}}` | 指定节点的输出（从 `context.data` 取） |
| `{{节点id.field}}` | 指定节点输出的某个字段（支持嵌套 `a.b.c`） |
| `{{http_1.body.userId}}` | HTTP 节点 body 里的 userId |
| `{{http_1.status}}` | HTTP 节点的状态码 |

### 5.1 两种解析器：`resolve` vs `resolveAsString`

| 方法 | 行为 | 用在哪 |
|------|------|--------|
| `resolve(template, context)` | **保持原始类型**：整个模板若是单个 `{{xxx}}`，返回原始值（number/boolean/object/array）；否则字符串拼接 | HTTP body、Condition 的 left/right、Prompt 模板 |
| `resolveAsString(template, context)` | 强转字符串：null/undefined→`''`，对象→`JSON.stringify` | **URL / headers / query**（这些只能是字符串） |

**例：`{{input}}` 且 input 是数字 `42`**

```
resolve → 42（Number，不是 "42"）     ★ 类型保持
resolveAsString → "42"
```

### 5.2 一个模板里多个变量

```typescript
const resolved = template.replace(/\{\{\s*([^{}]+?)\s*\}\}/g, (_m, path) => {
  const v = lookupVariable(path.trim(), context);
  if (v === undefined || v === null) return '';          // 取不到 → 空字符串
  if (typeof v === 'object') return JSON.stringify(v);    // 对象 → JSON
  return String(v);
});
```

模板 `"用户 {{user.name}} ，分数 {{score}}"` + `user={name:"小明"}` + `score=88` →

```
"用户 小明 ，分数 88"
```

**取不到值的规则**：
- `resolveAsString`：null/undefined → `''`
- `resolve`（含单个变量）：返回 `undefined`（保持 undefined，不做替换）

### 5.3 递归解析（deep resolve）

`resolve` 遇到 `object` 会**递归**处理每个 key 的 value：

```typescript
if (typeof template === 'object') {
  const result = {};
  for (const [key, value] of Object.entries(template)) {
    result[key] = this.resolve(value, context);   // value 是字符串 → 再走字符串解析
  }
  return result;
}
```

所以 HTTP 节点的 `body: { "query": "{{llm_1.output}}" }` 会变成 `{ "query": "实际答案" }`。

## 6. 选边算法 `pickNextEdge` —— 分叉路口怎么走

文件：`backend/src/workflows/engine/workflow.engine.ts`（`pickNextEdge`）

```typescript
private pickNextEdge(outgoingEdges, result) {
  // ① 有 branch（Condition）→ 按 sourceHandle 匹配
  if (result.branch) {
    const matched = outgoingEdges.find((e) => e.sourceHandle === result.branch);
    if (matched) return matched;

    // ② 防御历史数据：-true / -false 或 source-true 后缀
    const fallback = outgoingEdges.find(
      (e) => e.sourceHandle === `${result.branch}` ||
                 e.sourceHandle === `source-${result.branch}`,
    );
    return fallback ?? null;
  }

  // ③ 无 branch（普通节点）
  if (outgoingEdges.length === 1) {
    return outgoingEdges[0];            // 只有一条边 → 没得选
  }

  // ④ 多条边：只能有一条不带 sourceHandle
  const noHandle = outgoingEdges.find((e) => !e.sourceHandle || e.sourceHandle === '');
  if (noHandle && outgoingEdges.filter((e) => !e.sourceHandle).length === 1) {
    return noHandle;
  }

  throw new Error('普通节点不能有多个带 sourceHandle 的后继边；请确认是否应该使用 Condition 节点');
}
```

**记住 4 条规则：**

| 情况 | 走法 |
|------|------|
| Condition 且 `branch='true'` | 找 `sourceHandle === 'true'` 的边 |
| Condition 且 `branch='false'` | 找 `sourceHandle === 'false'` 的边 |
| 普通节点且只有 1 条出边 | 没得选，直接走 |
| 普通节点且多条出边 | 只能有 **1 条**不带 sourceHandle 的，走它；否则报错 |

> **这解释了一个前端引号要小心的坑**：React Flow 里连接 Condition 时，
> 连接源的手柄（sourceHandle）必须精确等于 `'true'` / `'false'`，
> 否则引擎 fallback 找不到边会抛「无法选择后继边」。

### 6.1 一个带分支的全流程例子

```
    ┌──── start_1 ────┐
  （唯一入口）          │
    ┌──────────────────┘
    ▼
┌────┐  left: "{{http_1.status}}"   operator: eq   right: "200"
│cond_1│  logicalOperator: AND
└─┬─┬─┘
  │ │
 true... └──── false...
  │              │
  ▼              ▼
llm_1        prompt_1
  │              │
  └──────┬───────┘
         ▼
      output_1
```

`http_1` 返回 200 → `cond_1` 走 `true` 分支 → `llm_1` → `output_1`。
返回 503 → `cond_1` 走 `false` 分支 → `prompt_1` → `output_1`。

**汇合没问题**：两条分支能在 `output_1` 汇合，只要 `output_1` 是唯一目标。

### 6.2 一个常见的「图阴影陷阱」：为什么引出的边不要乱连

```
注意 cond_1 → llm_1 必须用 sourceHandle='true'，程序才不会报错
如果前端默认画出一条不带 handle 的边（sourceHandle=null），
引擎 fallback 也找不到 'true' -> 抛「无法选择后继边」
```

## 7. 流式运行 `runStream` —— 边执行边往浏览器吐

文件：`workflow.engine.ts`（`runStream`）

它与 `run` 的区别就三条：**① 每步先 yield 一个 `node:start`；② LLM 节点用 `executeStream` 逐字吐 token；③ 最后 yield 一个 `complete`**。

```typescript
async *runStream(workflow, input): AsyncGenerator<WorkflowStreamEvent> {
  ...
  while (currentNode) {
    // ★ 提前报"要跑这个节点了"
    yield { type: 'node:start', nodeId, nodeType, label: node.data?.label };

    const executor = this.registry.get(nodeType);

    if (executor instanceof LLMNodeExecutor) {
      // ★ LLM：用 executeStream 逐字 yield
      let streamedOutput = '';
      for await (const chunk of executor.executeStream(context, currentNode)) {
        streamedOutput += chunk;
        yield { type: 'token', nodeId: currentNode.id, content: chunk };
      }
      result = { output: streamedOutput };
    } else {
      result = await executor.execute(context, currentNode);   // 其他节点：一次性
    }

    // 记 data + previousOutput（与 run 相同）
    context.data[currentNode.id] = ...;
    context.previousOutput = result.output;

    // 报"跑完了"
    yield { type: 'node:complete', nodeId, nodeType, output: result.output, branch, metadata };
    ...选边、走人...
  }

  yield { type: 'complete', data: context.data };
}
```

### 7.1 SSE 事件的完整协议（前端 `api/workflow.ts` 就是按这个解析的）

| 事件 | 触发点 | 主要内容 |
|------|--------|---------|
| `node:start` | 每个节点开始 | `{ nodeId, nodeType, label }` |
| `token` | LLM 节点流式输出中 | `{ nodeId, content }`（一轮一个帖子） |
| `node:complete` | 每个节点结束 | `{ nodeId, nodeType, output, branch?, metadata? }` |
| `complete` | 整个工作流结束 | `{ data: context.data }` |
| `error` | 出异常 | `{ message }` |

### 7.2 Controller 怎么把它转成 SSE 响应

文件：`workflows.controller.ts`（`runStream`）

```typescript
@Post('run/stream')
async runStream(@Body() body: any, @Res() response: Response) {
  response.status(200);
  response.setHeader('Content-Type', 'text/event-stream');
  response.setHeader('Cache-Control', 'no-cache, no-transform');
  response.setHeader('Connection', 'keep-alive');
  response.flushHeaders();

  const send = (event) => response.write(`data: ${JSON.stringify(event)}\n\n`);

  try {
    for await (const event of this.engine.runStream(body.workflow, body.input)) {
      send(event);
    }
  } catch (error) {
    send({ type: 'error', message: ... });
  } finally {
    response.end();
  }
}
```

**前端看到的原始响应长这样：**

```
data: {"type":"node:start","nodeId":"llm_1","nodeType":"llm","label":"LLM"}

data: {"type":"token","nodeId":"llm_1","content":"你"}

data: {"type":"token","nodeId":"llm_1","content":"好"}

data: {"type":"token","nodeId":"llm_1","content":"，今"}

...
data: {"type":"node:complete","nodeId":"llm_1","nodeType":"llm","output":"你好，今天是..."}

data: {"type":"complete","data":{"start_1":...,"llm_1":"你好，今天是..."}}
```

**前端处理它（第 6 篇细讲）：**

```typescript
const reader = response.body.getReader();
const decoder = new TextDecoder();
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const text = decoder.decode(value, { stream: true });
  // 按 "\n\n" 切开每一行 data: {...}
  // 结尾没有 "data: " 的残缺块要存到 buffer 等下一段
}
```

### 7.3 ⚠️ 为什么用 `@Res()`？

NestJS 的 Controller 一般直接 `return` 对象，框架自动序列化。
但 SSE 要**持续不断吐字节**，等框架帮你处理就全堵住了。
所以用 `@Res()` 拿到**原生 express response**，自己控制一切：
`response.write()`、`response.end()`、`flushHeaders()`。
代价：不能再用 NestJS 的拦截器/守卫返回值了（Guard 还能用，是框架层；但 `@Res()` 之后类似「响应拦截器」可能会受影响）。

**请求 body 结构：**

**日志（后端 stdout）：**

```bash
执行 Start Node
执行 Input Node

[HTTP] 响应输出: {...}
```

**常见报错对照表：**

| 报错 | 原因 |
|------|------|
| `Workflow 缺少 Start Node` | 没有 `type === 'start'` 节点 |
| `Workflow 存在循环: xxx` | 图有回路（自环 / 成环），**本引擎不支持循环** |
| `没有找到 Node Executor: xx` | node.type 不在 8 个类型里 |
| `无法选择后继边（outgoing=2, branch=none）` | 普通节点连了多条带 sourceHandle 的边 |
| `普通节点不能有多个带 sourceHandle 的后继边...` | 同上 |
| `找不到目标 Node: xxx` | 某条 edge 的 target 没有对应 node |
| `Condition 节点配置缺少 conditions 数组` | condition 节点 config 没填 |
| `HTTP 节点配置缺少 URL` | http 节点 URL 空 |
| `禁止访问 localhost` | SSRF 拦截了 http://localhost:8080 这类地址 |

## 11. 本篇小结

| 概念 | 一句话 |
|------|--------|
| **引擎本质** | 「走格子小人」：context 背包 + 逐节点 `while` 循环 |
| **context** | `{ input, data, previousOutput }` |
| **data 与 previousOutput** | data 按节点 id 永久记录；previousOutput 只记上一个 |
| **Registry（查号台）** | `type` → 执行器类 一一对应 |
| **8 个执行器** | Start/Input（透传输入）、LLM（调模型）、Prompt（拼文本）、RAG（检索）、HTTP（发请求）、Condition（分支）、Output（透传结果） |
| **LLM 流式** | `runStream` 用 `executeStream` 逐字 yield `token` 事件 |
| **Condition 分支** | 返回 `branch: 'true'|'false'`，引擎按 `sourceHandle` 选边 |
| **变量语法** | `{{input}}` / `{{previous}}` / `{{节点id}}` / `{{节点id.a.b}}` |
| **两种解析** | `resolve` 保原始类型；`resolveAsString` 强转字符串（URL 用） |
| **SSE 协议** | 5 种事件：node:start / token / node:complete / complete / error |
| **不支持循环** | 跑过同一节点第二次 → 直接报错 |
| **运行接口** | `body: any` + **无鉴权**（安全隐患） |
