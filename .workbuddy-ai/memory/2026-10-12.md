## 功能 17：Agent 多类型输出（文件生成）— 验证与修复

完成了「需求 17」的收尾验证（前端编译 + 后端冒烟测试），并在过程中发现并修复了两个真实缺陷：

### 修复 1：Markdown 生成丢失行内标记（链接/粗体等）
- 根因：`parseMarkdownToBlocks` 用 `stripInline()` 把所有行内 Markdown 剥成纯文本，而 `md` 生成器又经 blocks 往返再序列化，导致 `[百度](url)` 变成 `百度`、丢失链接。
- 修复：`generateMarkdown(content, rawMarkdown?)` 新增可选 raw 参数；当提供原始 markdown 时直接输出原文（完整保留行内语法），标题用 `applyTitleToRaw` 智能处理（正文已以 H1 开头则保留原文，否则文首前置 H1）。`FileGeneratorService.generate` 的 md 分支传入 `input.markdown`。
- docx/pdf 生成器渲染的是已 strip 的纯文本 `TextRun`，无破损语法，保持原行为（已知限制：docx/pdf 暂无行内富文本）。

### 修复 2：表格表头对字符串列名不兼容
- 根因：`resolveHeaders` 假设 `SheetSpec.columns` 为 `{header}` 对象数组；LLM 常直接给 `["a","b"]` 字符串数组，导致表头变为 `undefined`。
- 修复：`resolveHeaders` 同时兼容 `string` 与 `{header}` 两种写法（excel.generator.ts）。

- 环境注意：backend/.npmrc 使用 `node-linker=hoisted` 解决沙箱中 pnpm 符号链接缺失问题（影响 docx/exceljs/pdfkit/mammoth/marked/sanitize-html 解析）。

### 后端构建修复（解决用户「后端启动报错」）
用户报告 `nest start`/`nest build` 报错：TS2688 `Cannot find type definition file for 'jest'/'node'`，且 CLI 崩溃 `chalk.blue is not a function`。

根因与修复：
1. **TS2688（类型找不到）**：沙箱里 pnpm 符号链接未生成，顶层 `@types`、`@nestjs`、`@prisma` 等作用域目录为空（真实环境 `pnpm install` 正常，因为 `@types/node@^24`、`@types/jest@^30` 均已在 package.json 声明并会被安装）。沙箱用 `flatten-deps.cjs` 把 `.pnpm` 仓库里的包直接 copy 到顶层 node_modules，绕开坏符号链接。
2. **`chalk.blue is not a function`（CLI 崩溃）**：flatten 时把顶层 `ansi-styles@6`/`supports-color@8`/`string-width@5`/`strip-ansi@7`/`ansi-regex@6`/`emoji-regex@9`（均为 ESM-only）覆盖到了 chalk@4.1.2 / cli-table3 等 CJS 消费者需要的 CJS 版本之上，导致颜色方法与 `stringWidth` 为 undefined。修复：从 `.pnpm` 仓库把对应 CJS 版本 copy 回顶层（ansi-styles@4.3.0、supports-color@7.2.0、string-width@4.2.3、strip-ansi@6.0.1、ansi-regex@5.0.1、emoji-regex@8.0.0）。is-fullwidth-code-point@3.0.0 顶层本就正确。ESM 消费者保留各自 `.pnpm` 嵌套副本，不受降级影响。

验证结果：
- `node node_modules/@nestjs/cli/bin/nest.js build` → EXIT 0。
- `nest start` → 编译、定位入口（dist/src/main.js，因 tsconfig 无 rootDir 且根目录有 prisma.config.ts，故产物在 dist/src/ 下）、启动至 `app.listen(3000)`，日志 `Nest application successfully started`，全部路由（含新增 dashboard 运行监控 3 个端点）映射正常。
- 注意：`start:prod` 脚本为 `node dist/main`，而实际入口是 `dist/src/main.js`；若要在生产直接跑 dist，需改用 `node dist/src/main.js` 或给 tsconfig 设 `rootDir: "src"`（但会排除根目录 prisma.config.ts，需相应调整 include）。开发用 `nest start` 不受影响。

## 修复：生成的 .docx 预览正常但 Microsoft Word 打不开

用户报告 `generate_file` 生成的 `人工智能发展概述.docx` 前端预览正确，但用 MS Word 打开报「无法读取内容」。

**定位**：用 `jszip` 解包生成器产出的 buffer——所有 XML part 均格式良好、`[Content_Types].xml` content-type 覆盖完整、`word/document.xml` 的 `<w:pPr>` 子元素顺序合规、rels 均有效。唯一异常：**`[Content_Types].xml` 是 zip 内最后一个条目（docx@9.10 的 Patcher 默认追加在末尾）**。OPC 规范要求它必须是第一个条目；docx-preview 用 jszip 按名读取、顺序无关所以能渲染，而 Word 的 OPC 读取器较严，于是判定「内容有问题」。存储链路（Qiniu 上传走 Buffer、下载走 arraybuffer→Buffer→file→Buffer）已核对为二进制安全，非传输损坏。

**修复**（`backend/src/files/generators/word.generator.ts`）：
1. `ensureCanonicalOpcPackage(buffer)`：用 `jszip` 重打包，强制把 `[Content_Types].xml` 放到第一个条目（顺带重算 CRC）。纯打包顺序修正，不动内容。
2. 给 `numbers` 段落补 `numbering.config` 注册 `reference: 'default-numbering'`：原来 numbers 块引用了从未在 Document 注册的 numbering，命中即触发 Word「unreadable content」（本单是纯段落没触发，但属同类隐患，一并修）。
- `package.json` 新增 `jszip@^3` 直接依赖（本来经 docx 传递引入，`node-linker=hoisted` 下已可用，故本沙箱无需重装）。

**验证**：重新 `nest build` 后，正文文档与编号文档 `[Content_Types].xml` 均落在 zip 首位（index 0）；编号文档 numId 均能在 numbering.xml 找到定义；两文档经 `mammoth`（更严格的解析器）转换正常；重打包后全部文本 run 无丢失（part 集合不变，仅顺序/CRC 变化）。

**注意**：修复只对**新生成**的文件生效；用户此前已生成/已存 Qiniu 的 docx 仍是旧（坏）文件，需**重启后端 + 重新生成/再下载**一次才能在 Word 打开。已按 `jszip` 直接依赖同步 memory，需用户侧 `pnpm install` 一次对齐 lockfile（hoisted 布局下已可运行）。

## 复现与二次修复：老 docx 仍打不开（读取时修复）

用户再次反馈「点击下载 Word 后打不开」。用 Qiniu 凭证把用户**实际生成的文件**拉下来（`generated/2026-10-12/c899be59-....docx`，10188B，生成于 16:28，早于 16:44 的修复）逐条解剖，确认它同时带**两个** Word 致命缺陷：

1. `[Content_Types].xml` 位于 zip 第 21 位（末位）——16:44 那次修复只对新文件生效，老文件未变。
2. **`word/document.xml` 里 `<w:numId w:val="{default-numbering-0}"/>`**（3 处）。`w:numId` 按 OOXML 必须为正整数，占位符字符串会让 Word 直接判「无法读取内容」。成因就是当时顺带修的那个未注册 numbering reference——老文件正是命中例子。
   → 教训：`docx` 库对未注册的 `numbering.reference` **不报错**，只是把占位符原样留在 XML 里，务必自查 `document.xml` 是否有 `{...}` 残留。

**修复（本次）**：新增读取时修复，老文件无需重新生成即可下载打开。
- 新增 `backend/src/files/generators/opc.util.ts`：`canonicalizeOpcPackage()`（`[Content_Types].xml` 置顶重打包）+ `repackWithContentTypesFirst()`。原 `word.generator.ts` 里的私有 `ensureCanonicalOpcPackage` 删除，改为复用。
- 新增 `backend/src/files/generators/word.repair.ts`：`repairDocx(buffer) -> {buffer, changed, notes}`。为非法 `w:numId` 分配真实存在的 numId（必要时新建 decimal abstractNum / 整个 numbering.xml，并补齐 Content_Types override 与 document.xml.rels 关系），而不是删 `w:numPr`（保住序号）。只读修复、失败降级返回原 buffer、幂等。
- `FilesService.readRaw()`：`file.format === 'docx'` 时先 `repairDocx()` 再返回，日志打印修复项。下载(`/download`)与预览(`/raw`)同时受益。

**验证**：`nest build` 通过。对真实坏文件跑修复 → 首位变 `[Content_Types].xml`、3 处 numId → 2、numbering.xml 新增 numId 2、二次修复 `changed=false`（幂等）；新生成文件 `changed=false`（无额外重打包开销）。全部 part 用 saxes 严格解析 + 关系目标解析 + Content_Types 覆盖检查均通过；mammoth 转换正常。产物示例 `Word打开验证-示例文档.docx`（工作区根目录，可删）。

**待用户操作**：后端进程在 3000 端口跑的是旧 dist，需**重启后端**后重新下载（前端无需改动）。

**排障套路**：本项目 STORAGE_TYPE=qiniu，可直接用 `.env` 里的 AK/SK + `qiniu` SDK 的 `listPrefix`/`privateDownloadUrl` 把线上真实文件拉到本地做二进制级分析——比本地造样例快得多。sandbox 内 `Add-Type`（.NET）被安全策略拦截，改用 Node 侧 `saxes`/`jszip` 做严格校验。
