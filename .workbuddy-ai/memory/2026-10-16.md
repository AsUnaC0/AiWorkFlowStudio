## 修复：图像生成导致 `chatMessage.create` content 落库报错

**现象**：Agent 聊天调用图像生成模型后，`persistAssistantMessage` 落库抛
`Argument content: Invalid value provided. Expected String, provided (Object)`，
content 实际是 `[{ url: "https://.../xxx.png?Signature=..." }]`。

**根因**：OpenAI 规范里 `message.content` 既可能是字符串，也可能是「多模态内容块数组」。
Provider 之前用 `content?: string` 直接透传（`msg?.content ?? ''`），
模型返回数组时把数组原样给了上层，最终写进 String 列。

**修复**：
- 新增 `backend/src/ai/content.util.ts` → `normalizeContentToString(content: unknown): string`。
  统一处理：字符串原样；数组逐块提取；文本块取 `text`；图片块取
  `url` / `image_url(string|{url})` / `image|source.url`；`b64_json` 转 data URI；
  嵌套 `content` 递归。图片统一输出为纯 URL 文本（聊天页直接展示）。
- 在 **Provider 边界**统一归一化（这是关键，Agent 与工作流 LLM 节点同时受益）：
  - `openai-compatible.provider.ts`：`chat` / `chatWithTools` 的 content 类型改 `unknown` 并归一化；
    `streamChat` 的 `delta.content` 也归一化（否则数组 token 拼接会变 `[object Object]`）。
  - `ollama.provider.ts`：同样三处。
- **落库兜底**：`agent.service.ts` 的 `persistAssistantMessage` 与 tool_calls 分支
  `chatMessage.create` 都用 `normalizeContentToString` 再写库（防御任何 Provider 漏网）。

**约定沉淀**：Provider 返回给上层的 `content` 必须是字符串 ——
`ChatResult.content` / `ToolChatResult.content` 声明为 string 就必须在 Provider 内保证，
不要让「可能是数组」的原始响应穿透到业务层与数据库边界。

**验证**：`npx tsc --noEmit -p tsconfig.json` 通过。

## 修复：keep-alive 的聊天页切回后 Agent 列表陈旧

**现象**：`/chat` 开了组件缓存，去「Agent 管理」页新建 Agent 后切回来，
侧边栏 Agent 列表仍是旧的，没有重新拉取。

**根因**：缓存页不会重新挂载，`onMounted` 只跑一次；
原 `onActivated` 只校准了会话列表（`loadSessions`），漏了 Agent 列表。

**修复**（`fronted/src/views/chat/index.vue`）：
- 新增 `refreshAfterActivate()`：`onActivated` 里先 `loadAgents()` 重新拉取 Agent 列表，
  再按结果校准 —— 选中 Agent 被删（`currentAgentId` 变化）则清空 `currentSessionId/messages`
  并重载会话；否则维持原「轻量校准会话列表」逻辑。流式进行中（`sending`）不打断。
- `loadAgents()` 选中逻辑改为三态：URL `?agent=` 优先 → 当前选中仍存在则保持
  → 否则（未选中 / 被删除）回退到 `isDefault` Agent。避免刷新列表把选中项重置。

**约定沉淀**：keep-alive 页面「切回时要刷新的数据」必须写在 `onActivated` 里，
并且要和 `onMounted` 的首次初始化区分开（用 `activatedOnce` 跳过第一次）。

**验证**：`vue-tsc --noEmit` 在 chat/index.vue 无报错
（仓库另有 3 处与本次无关的既有类型错误：knowledge/detail.vue、providers/index.vue）。

## 修复：chat 页 agent-sidebar 样式错乱

**现象**：`fronted/src/views/chat/index.vue` 侧边栏改成 `t-menu + t-menu-group` 后样式错乱。

**根因**：`:deep()` 里写的 TDesign 类名**全是错的**，规则静默失效，
TDesign 默认样式和自定义样式叠加（双倍 padding / 40px 固定高度 / hover 底色 / active 底色 + 左侧指示条）。

**TDesign Menu 真实类名（务必记牢）**：
| 用途 | 正确类名 | 之前写错的 |
|---|---|---|
| 根节点 | `.t-default-menu` | `.t-menu`（`.t-menu` 是内部那个 `ul`） |
| 菜单项 | `.t-menu__item` | `.t-menu-item` |
| 内容槽 | `.t-menu__content` | `.t-menu-item__content` |
| 图标槽 | `.t-menu__item-link` / `.t-icon` | `.t-menu-item__icon` |
| 激活态 | `.t-is-active` | `.is-active` |
| 折叠态 | `.t-default-menu.t-is-collapsed` | `.t-menu--collapsed` |
| 分组 | `.t-menu-group` / `.t-menu-group__title` | — |

DOM 结构：`.t-default-menu > .t-default-menu__inner > (.t-menu__logo, ul.t-menu.t-menu--scroll, .t-menu__operations)`；
`t-menu-group` 渲染为 `div.t-menu-group > (div.t-menu-group__title, ...default slot)`；
`t-menu-item` 渲染为 `li.t-menu__item > span.t-menu__content`。
`t-menu-group` 的 `#title` 插槽有效（`renderTNodeJSX("title")` 优先插槽、回退 prop）。

**其他连带修复**：
- `.agent-sidebar` 的 `overflow: hidden` 会把 `right: -14px` 的折叠按钮裁掉一半 → 改 `overflow: visible`
  （菜单自身滚动由 `.t-menu--scroll` 负责，需给 `ul.t-menu` 加 `min-height: 0` 否则 flex 子项撑破高度）。
- **折叠态 TDesign 会 `display:none` 掉 `.t-menu__item > .t-menu__content`**，
  而头像正好在内容槽里 → 折叠后头像整片消失。必须显式 `display: block !important` 恢复。
- 折叠态头像居中要靠 `.agent-item` 自己的 `justify-content`（`.t-menu__item` 的居中管不到它，因为它是 `width:100%`）。
- `.agent-name` 是 flex 容器，`text-overflow` 对它里面的文本节点不生效 →
  名称文本要用 `<span class="agent-name-text">` 包一层才能正确省略号。
- `.session-main` 原来 `width: 100%` 会把右侧删除按钮挤出容器 → 改 `flex: 1; min-width: 0`。
- 删除按钮隐藏时要带 `pointer-events: none`，否则会点到「看不见的删除」。

**约定沉淀**：`:deep()` 覆盖第三方组件样式前，**先去 node_modules 里确认真实类名**
（`grep -o '\.t-menu[a-z0-9_-]*' node_modules/<pkg>/es/<comp>/style/index.css | sort -u`）。
类名写错不会报错，只会静默失效 → 表现成「样式错乱」，极难排查。

**验证手段（可复用）**：不启动应用、不需要登录，用「真实组件 CSS + 组件 scoped CSS + 手写 DOM 快照」
渲染成静态 HTML，再用本机 Chrome 无头模式截图 / `--dump-dom` 读计算样式。
脚本见 `.workbuddy-ai/tmp/sidebar-check/render-check.cjs`（Chrome 路径 `C:\Program Files\Google\Chrome\Application\chrome.exe`，
注意截图输出必须落在工作区内，写系统 temp 会被沙箱拒绝）。
实测指标：menu=260/64、logoH=48、toggleRight=274/338（正好骑在右边框）、itemH=48、itemPad=0/0、
itemBg=transparent、contentDisplay=block（折叠态）、activeBg=rgb(237,233,254)。

## 核查：Agent 输出文件能力（已实现）

**结论**：后端已完整实现「Agent 真实产出可下载文件」，支持 **docx / xlsx / pdf / md / csv** 五种格式。

**链路**：
1. `src/files/` —— 生成能力内核。`types/generated-file.types.ts`（统一内容模型
   `DocumentContent` / `SpreadsheetContent` + `FORMAT_META`）；`generators/` 下
   `word.generator.ts`(docx) / `pdf.generator.ts`(pdfkit + 系统 CJK 字体) /
   `excel.generator.ts`(exceljs) / `markdown.generator.ts` / `markdown.util.ts`(md→DocBlock)；
   `file-generator.service.ts` 统一调度 + 格式/内容校验；`file-storage.service.ts` 上传+落库；
   `file-preview.service.ts` 预览；`files.controller.ts` REST（formats/generate/list/:id/preview/content/raw/download/DELETE）。
2. Agent 工具：`agent/tools/generate-file.tool.ts`（`generate_file`）→ 注册在
   `tool-registry.service.ts`，由 `Agent.enableFileGeneration`（schema 默认 true）控制；
   执行成功后 `context.files.push(file)` 回传。
3. `agent.service.ts`：工具执行时把 `runFiles` 传进 `ToolContext` → `flushFileEvents()`
   推 SSE `{type:'file'}` → 落库 assistant 消息后 `filesService.attachToMessage()` 回填 `messageId`。
4. 平台助理创建时 `enableFileGeneration: true`，同样具备该能力。

**设计红线**：模型只产出结构化内容（markdown / blocks / sheets），二进制一律后端生成，
不允许模型编造文件路径或下载链接。

**缺口**：
- **工作流引擎（`src/workflows/`）未接入文件生成** —— 没有节点能产出文件；
  `GeneratedFileSource` 里虽定义了 `'workflow'`，但全仓无调用点（只有 files.controller 与 generate-file.tool 两处调用 generate）。
- `platform-tools/tools/` 里没有独立的文件工具，平台助理复用 ToolRegistry 的 `generate_file`。
- 图片不在生成格式内（图片走 Provider 多模态返回，见当日上方记录）。
- PDF 依赖系统 CJK 字体（`simhei/msyh/simsun` 或 `PDF_CJK_FONT_PATH`），Linux 容器缺字体中文会异常。
- 已有对应文档 `docs/后端代码逻辑/09-文件生成模块.md`。
