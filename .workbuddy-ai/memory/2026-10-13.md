## 修复：migrate dev 报 P3006/P3018（shadow database 重放失败）

- 现象：`pnpm prisma migrate dev --name init` → 迁移 `20261010060846_shadow_replay_check` 无法干净重放到
  shadow DB，DB error 42704 `index "dc_embedding_ivf" does not exist`。
- 根因：`20261009073241_add_multi_agent_and_chat_session` 已执行 `ALTER TABLE "DocumentChunk" DROP COLUMN "embedding"`，
  **删列会级联删除建立其上的 dc_embedding_ivf 索引**；而排在后面的 `20261010060846` 又无条件 `DROP INDEX`。
  全新重放时索引早已不存在 → 报错。（同类 `20261010050605_add_llm_config` 写的是 `DROP INDEX IF EXISTS` 所以没事。）
- 修复：把 `20261010060846_shadow_replay_check/migration.sql` 改成 `DROP INDEX IF EXISTS "dc_embedding_ivf";`
  并加注释说明原因。
- 连带处理（踩坑记录）：
  - 真实库缺该索引（曾被 `prisma db push` 删掉）→ drift；新增迁移 `20261013104000_restore_dc_embedding_ivf` 补回。
  - Prisma 对「已应用后被修改」的迁移会强制要求 reset。绕过办法（不丢数据）：直接
    `DELETE FROM _prisma_migrations WHERE migration_name='<x>'` 再 `prisma migrate deploy` 重新应用，
    即可刷新校验和；官方 `migrate resolve --rolled-back` 只对 failed 状态有效（否则报 P3012）。
  - 若重放失败留下了 finished_at IS NULL 的孤儿记录，deploy 会卡在 P3009，需先 `migrate resolve --rolled-back`
    或手动删除该行。
- 最终按用户要求清库重初始化：`prisma migrate reset --force`（备份在 `backend/.backup-ai_workflow-20261013-1038.dump`）。
  重置后 20 条迁移全部重放成功、索引存在、status = up to date。

## 已知设计约束（pgvector + Prisma 7）

- schema.prisma 无法声明向量索引（Prisma 7 不支持，官方 pgvector 扩展要 Prisma 8），
  `dc_embedding_ivf` 只存在于手写迁移里 ⇒ **每次 `prisma migrate dev` 都会生成 `DROP INDEX "dc_embedding_ivf"`**。
- 流程约定：`npx prisma migrate dev --create-only` → 打开生成的 SQL → 删掉该 DROP（必要时末尾补
  `CREATE INDEX IF NOT EXISTS`）→ 再 `npx prisma migrate dev` 应用。已在 schema.prisma 的 DocumentChunk 注释里写明。
- 另：IVFFlat 在数据量少时召回率低（PostgreSQL 会提示 low recall），数据上来后应重建或换 HNSW。

## 评估：是否升级 Prisma 8（结论：暂不升级，停留在 7.10.0）

- 版本现状（2026-10-13 实测 npm）：`prisma` latest = **8.0.0-rc.22（仍是 RC）**；
  `@prisma/client` / `@prisma/adapter-pg` latest 仍是 **7.10.0**，8.x 只有 dev 通道的 8.1.0-dev.x。
- Prisma 8 是「ground-up rethink」重写，非平滑升级：schema.prisma → `contract.prisma`、
  `@prisma/orm-postgres` 运行时、`definePrismaConfig`、客户端改成
  `postgres<Contract>({ contractJson, url, extensions })` + `db.sql` 类型化查询构建器
  ⇒ 现有 PrismaService 及所有 service 的数据访问代码都要改。
- pgvector 扩展（`@prisma/orm-extension-pgvector`）状态也是 Release candidate，且必须配 Prisma 8。
- 并存方案（已核实 7.10.0 release notes）：`@prisma/prisma7` 兼容包可让 prisma@8 与 prisma7 CLI
  同项目共存（`npx prisma7 generate/migrate dev`），但仍需 prisma8 侧是全新 ORM 运行时才算真正用上 8。
- **实测 Prisma 7 无法声明向量索引**：`@@index([embedding(ops: raw("vector_cosine_ops"))])` 生成的是
  `CREATE INDEX ... ("embedding" vector_cosine_ops)`（无 USING，默认 btree），PostgreSQL 直接报
  `operator class "vector_cosine_ops" does not exist for access method "btree"`；
  `type: Ivfflat / Hnsw` 被 schema 解析器拒绝（Unknown index type）。
  ⇒ 只能继续用「手写迁移 + 每次 migrate dev 后删掉自动生成的 DROP INDEX」的流程。
- 影响面有限：`migrate deploy`（生产）不会重新生成 DROP，该问题只在 develop 阶段出现。
