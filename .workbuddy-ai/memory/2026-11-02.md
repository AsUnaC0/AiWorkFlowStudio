## 小蝶 · UI Control（AI 操作页面）落地 P1+P2+P3(网页)

### 架构决策
- **UI Control 与 Platform Tools 分离**：UI 工具只改界面、不写业务数据（`meta.audit=false`，不落 PlatformOperationLog）。
- **前端执行 + 后端等结果（反向 RPC over SSE）**：后端发 `ui_action` 事件后 `await` 一个 Promise；前端执行完 `POST /platform/ui-result` 回传，后端才把真实结果喂回模型。这样满足「不能假设成功」。超时 15s 按失败处理。
- **页面操作不写进静态 actions 文件，而是页面 `onMounted` 动态注册 handler**（而非 Pinia 弹窗状态）。原因：弹窗是组件内 `ref`，动态注册无需重构 5 个页面，且仍然「语义化调用、不碰 DOM」。
- **`uiControl` 开关**：网页聊天传 true（等待回传）；桌宠等不支持回传的客户端不传 → 后端按「已发出指令」处理，不挂起。避免桌宠每步卡 15s。

## P4：桌宠接入 UI Control（同一日期续做）

### 核心矛盾
桌宠是独立 Electron 进程（`file://`），网页是浏览器标签页，后端没开 CORS，两者无法直接 IPC。
**解法：后端做中转的「指令通道」，网页版长轮询取指令。**

### 通道设计（刻意不用 WebSocket）
- `POST /api/platform/ui-command/poll`（body: `{timeout, uiContext}`）：无指令时**挂起** 20s（上限 25s），有指令立刻返回。
- `UIActionBridgeService` 新增按 userId 的 `channels`：`queue` + `waiters` + `lastPollAt` + `lastContext/contextAt`。
- `publish()` 有挂起的 waiter 就直接唤醒（亚秒级），否则入队（上限 10 条，溢出丢最旧）。
- `isBrowserOnline(userId)` = `waiters.length>0 || now-lastPollAt<45s`。

### 谁执行、谁等待（关键分流）
`agent.service.ts` 的 ui_action 块：
```
const browserOnline = isBrowserOnline(userId)
if (!options.uiControl) publish(...)          // 桌宠发起 → 下发队列
const canWait = !!options.uiControl || browserOnline
if (canWait) wait(...) else 直接回失败
```

## P4.1：UI Action Bridge 可靠化（同日续做）

用户评审 P4 后给出 7 点改进 + P4.1/P4.2/P4.3 优先级，明确「先解决 Browser Session ID 与 Command 生命周期，不要重写通信模块、不引入 WebSocket」。

### 一、修掉一个既有真 bug（最关键）
`agent.controller.ts` 的 `chat/stream` 端点**没有把 `uiContext/uiControl` 透传到 `runStream`**。
网页聊天走的正是这个端点，于是 `uiControl` 恒为 undefined → 走「桌宠 dispatch 分支」，
网页 chat 自己执行 SSE 一次 + browser-bridge 轮询再执行一次 → **同一 UI Action 执行两次**。
已补 `uiContext/uiControl/taskId` 三个字段（非流式端点也补了 taskId）。

### 二、后端：会话化 + 生命周期（`ui-action-bridge.service.ts` 重写）
- `Map<userId, Map<sessionId, BrowserSession>>`，一标签页一会话。
- `UICommand`：commandId / taskId / status / createdAt / expiresAt / retryCount。
  状态 `pending→delivered→success/failed`，另有 `expired/cancelled`；**`executing` 只在枚举里，前端未上报中间态**。
- `createCommand` 只登记不投递；`dispatch` 才入队/交给 waiter —— 网页 chat（uiControl=true）只 create 不 dispatch，天然避免重复执行。
- `StoredCommand.dispatched: boolean`：入队后 status 仍是 pending，只靠 status 挡不住重复 dispatch（单测抓到过，会入队两次）。**新增该标记**。
- 原子 poll：先同步取队列，再同步注册 waiter；全程无 await，publish/dispatch 不会插进来。
- **早到结果缓存 `earlyResults`**：`yield ui_action` 后前端可能先于 `wait()` 回传结果，旧实现会丢结果干等 15s 误判失败。
- `cancelTask(taskId)`：清队列 + 唤醒 pending wait（返回 cancelled）+ 记 `cancelledTasks`；`isTaskCancelled` 供 Agent 每轮检查。
- `sweep()` 15s：过期队列指令→expired、空闲会话回收、终态指令 5min 后删除。**未进终态但已过期的指令也要标 expired**，否则永不回收（已修）。
- 目标会话选择：优先 `lastUserActivityAt`（可见性/聚焦心跳），退回 `lastActivityAt`。
  只比 lastActivityAt 会被后台 tab 的轮询污染 —— 后台 tab 每 20s 也在轮询，时间戳一样新。
