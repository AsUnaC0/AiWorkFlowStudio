## 修复 baseUrl 重复拼接导致测试连接 404（智谱 BigModel 案例）
用户报错：在 baseUrl 填了完整聊天接口 `https://open.bigmodel.cn/api/paas/v4/chat/completions`，后端又在其后拼 `/models`，变成 `…/chat/completions/models` → 智谱返回 404。

### 根因
`OpenAICompatibleProvider` 把所有 endpoint 拼成 `${baseUrl}/chat/completions`、`${baseUrl}/models`、`${baseUrl}/embeddings`；若 baseUrl 本身已是叶子接口地址，就会重复拼接路径。

### 修复
- `backend/src/ai/providers/openai-compatible.provider.ts`：新增 `static normalizeBaseUrl()`，构造时先归一化——去首尾空白/末尾 `/`，再剥离已知的叶子接口后缀 `/chat/completions`、`/embeddings`、`/models`（仅剥最后一级，保留 `/v1`/`/v4` 等版本段）。DeepSeekProvider 继承此类、factory 也走这里，故 openai/deepseek/openai-compatible 全部受益。
- 前端 `views/providers/index.vue`：给「API Base URL」与「模型 ID」两项加了 `tips` 说明——明确区分 API Base URL（填到版本号为止的根地址，如 `https://open.bigmodel.cn/api/paas/v4`）vs 聊天接口 `/chat/completions` vs 模型列表 `/models` vs 模型 ID（标识符，可手动填），并提示后端会自动处理误填的接口后缀。

## 修复：Agent 配置页保存不生效（根因：UpdateAgentDto 缺校验装饰器）
用户反馈 detail.vue 编辑后保存无效。根因：`main.ts` 的 `ValidationPipe({ whitelist: true, transform: true })` 会**剥离所有没有校验装饰器的属性**；而 `src/agent/dto/update-agent.dto.ts` 只有属性声明、**一个装饰器都没有** → 请求体被整体剥成 `{}` → `prisma.agent.update({ data: {} })` 变空操作，所以永远保持原值。
- 验证（关键证据）：用项目自身的 `ValidationPipe` 对 `UpdateAgentDto` 跑 `pipe.transform({name,temperature,llmModelId,...})`：
  - 修复前 → `keys: []  values: {}`（全被剥离）；
  - 修复后 → 保留 `name/llmModelId/systemPrompt/temperature`，未知字段 `bogus` 仍被正确剥离。
- 修复：给 `UpdateAgentDto` 补齐装饰器（`@IsString/@IsIn/@IsArray/@IsNumber/@Min/@Max` + 全字段 `@IsOptional()`），与 `CreateAgentDto` 对齐。项目未装 `@nestjs/mapped-types`，故不用 `PartialType`，手写装饰器。
- 排查范围：全项目仅 `UpdateAgentDto` 有此问题，其余 update DTO（chat-session/workflow/skill/mcp/workspace/knowledge）都有装饰器。
- 提醒用户：需**重启后端**（3000 端口上的旧实例仍是旧代码）后保存才生效；若为 `nest start --watch` 则会自动重载。

## 修复：Agent 调工作流返回空（3 个叠加 bug）
用户反馈：Agent 调工作流后 `[WorkflowTool] 请问 输出长度: 0`，且大模型反复重试。

### 根因链（逐层挖出，均有实证）
1. **`tool_call.function.arguments` 是「对象」而非「字符串」**（根因）
   - 数据库持久化的原始 toolCalls 实测：`"arguments": {"input":"..."}`，`typeof = object`。DeepSeek（经 SiliconFlow）违反 OpenAI 规范，直接返回对象。
   - `agent.service.ts` 旧代码 `JSON.parse(tc.function.arguments)` 对对象抛 `SyntaxError` → 走 `catch` 兜底成 `{ raw: {...} }` → `WorkflowTool` 读 `args.input` 得 `undefined` → `String(undefined ?? '')` = `''` → **工作流输入为空** → 输出长度 0 → 大模型拿不到结果就反复重试。
2. **`WorkflowEngine.run()` 从不更新 `context.previousOutput`**（`runStream()` 有，`run()` 漏了）
   - 导致 Output 节点拿到的是初始 `input` 而非上游 LLM 产物。修 1 后现象变成"输出 = 原始输入"，即此 bug。
3. **Ollama 要求 `arguments` 是对象，OpenAI 要求是字符串**
   - 修 1 把 arguments 统一成字符串后，Ollama 的 `chat`/`streamChat` 又报 `400 {"error":"Value looks like object, but can't find closing '}' symbol"}`。
   - curl 实测：同一 payload，`arguments` 为对象 → 正常；为字符串 → 必现该 400。
   - 且 `chat`/`streamChat` 当时直接把原始 `messages` 发出去，**没走 `toOllamaMessages`**（只有 `chatWithTools` 走了），所以带 tool_calls 的历史消息没被转换。

### 修复
- 新增 `src/ai/tool-args.util.ts`：
  - `parseToolArguments(raw)`：null→{}；对象→原样；JSON 字符串→parse；非 JSON 字符串→`{input: raw}`；标量→`{input: raw}`。
  - `stringifyToolArguments(raw)`：统一输出为 JSON 字符串。
- `providers/openai-compatible.provider.ts`：`chatWithTools` 用 `stringifyToolArguments` 归一化 arguments（类型改 `unknown`）。
- `providers/ollama.provider.ts`：读入用 `stringifyToolArguments`；**发送时 `toOllamaMessages` 用 `parseToolArguments` 把 arguments 转回对象**；并让 `chat`/`streamChat` 也走 `toOllamaMessages`（此前漏了）。
- `agent/agent.service.ts`：`JSON.parse` 兜底替换为 `parseToolArguments`。
- `agent/chat-session.service.ts`：`getHistoryForLLM` 回放历史时把 tool_calls 的 arguments 归一化为字符串（清历史脏数据影响）。
- `agent/tools/workflow.tool.ts`：新增 `extractInput()`，兼容 `{input}`、`{raw:{input}}`、`{raw:"..."}`、未知字段（整体 JSON 化）。
- `workflows/engine/executors/llm.executor.ts`：`executeWithTools` 用 `parseToolArguments`。
- `workflows/engine/workflow.engine.ts`：`run()` 补上 `context.data[nodeId] = ...` 与 `context.previousOutput = result.output`，与 `runStream()` 对齐。

## 审查 docs/后端代码逻辑（README + 01~08）准确性

逐篇对照 `backend/src/**` + `prisma/schema.prisma` 核验，产出 `docs/后端代码逻辑审查报告.md`（未改文档正文，仅出报告）。结论：**框架/链路/设计意图基本正确**，但有 8 处硬性事实错误、6 处不完整、3 个未揭示缺口。

### P0 硬性错误（照文档写代码会直接出错）
1. **StorageService 接口全错**：文档写 `save(...): Promise<string>` + "DI 按 env 注入 Local/Qiniu 两个实现类"；实际是 `upload(buffer, originalName, subDir='documents'): Promise<{key,size}>`，且**只有单一 StorageService 类**内部按 `this.type` 分支（storage.module 只有 `providers:[StorageService]`）。另漏 `getDownloadUrl()`、`LOCAL_UPLOAD_DIR`/`QINIU_REGION`/`QINIU_DOMAIN`、七牛「签名http→签名https→公开http→公开https」多候选下载。
2. **WorkspaceMember 无 role 字段**：schema 只有 id/workspaceId/userId/createdAt；role 是 `listMembers()` 里 `user.id === workspace.ownerId ? 'OWNER':'MEMBER'` 算出来的。另漏 inviteMember 必须 ACCEPTED 好友、removeMember 限 owner。
3. **加密密钥变量名错**：不是 `ENCRYPTION_KEY`，是 `LLM_CONFIG_ENCRYPTION_KEY` → `JWT_SECRET` → dev 常量，再 sha256 压 32B；算法 AES-256-GCM，密文 `base64(iv):base64(tag):base64(ct)`；maskApiKey 实为「前4+****+后4」。
4. **ToolDefinition 参数错**：WorkflowTool 实有必填 `input` 参数（非 `properties:{}`）；KnowledgeTool 有 query/knowledgeBaseIds/topK 三个（非只有 query），且 description 注入了 KB 清单（支持前 8 位缩写匹配 UUID）。
5. **ChunkService 描述错**：写入字段是 chunkIndex（非 metadata），无 skipDuplicates，且在 `$transaction` 里 increment chunkCount；chunkSize 100/overlap 50 是**硬编码**（LangChain RecursiveCharacterTextSplitter），不可配置。
6. **"只有 COMPLETED 文档才被检索" 未落地**：vectorSearch/keywordSearch 只过滤 kbId + `embedding IS NOT NULL`，**无 `d.status` 条件**。
7. **MCP 多处错**：transport 默认 `STREAMABLE_HTTP` 且 SSE 在 callTool 直接抛错；credentials 是**明文 JSON**（非加密）；authType 是 NONE/API_KEY/BEARER_TOKEN；status 还有 ERROR。漏三步 JSON-RPC（initialize 2024-11-05 → notifications/initialized → tools/call）、SSE 响应解析、X-API-Key/Bearer 头、isError 处理、testConnection 缓存 availableTools。
8. **Skill 注入时机错**：文档写"AgentService 启动时"——**AgentService 根本没注入 SkillService/McpService**，Agent 的 `skillIds`/`mcpServerIds` 是死配置（存了不读）。Skill.instructions 是 `String?` 非必填。

- **ReAct 最终答案会生成两次**：`toolCalls.length===0` 时先 yield 非流式的 `result.content`，**再调 streamChat 重新生成一遍**逐 token yield（前端会看到回退重播）。文档完全没写。
- 工具执行异常被 catch 成字符串继续喂 LLM；超轮次会落库一条 `⚠️ Agent 达到最大工具调用次数限制`；executeTool context 还带 knowledgeBaseIds；ChatMessage 有 `trail` 字段。
- 引擎缺 start 节点/无后继/找不到目标节点三种抛错；pickNextEdge 有 `${branch}`/`source-${branch}` 历史兜底；版本状态机守卫未写（ARCHIVED 不可直接发布等）；publish 的 version 取该 workflow 最大 version+1（防撞 v1 unique）。
- runStream **从不 yield `error` 事件**（类型有、实现无），异常直接 throw。
- Ollama 流式结束信号**不是 `done:true` 字段**（靠 reader.done）；Ollama embedding 逐条发请求（BATCH_SIZE=100 只是外层分批）；Ollama 用 `{model,prompt}`、OpenAI 用 `{model,input}`。
- `fetchModels()` upsert 时 capabilities 写死 `['CHAT','STREAM']`——**不自动识别 EMBEDDING**，云端 embedding 模型需手工改。
- Dashboard：概览实返回 successRate/avgDurationMs/skills/mcpServers/tokenUsage(恒0)；节点排行是按 nodeType 聚合均耗时（非 Top10 单条）；最近运行默认 limit=10（非20）；队列监控是查 WorkflowRun.status 计数（**没调 BullMQ API**）。
